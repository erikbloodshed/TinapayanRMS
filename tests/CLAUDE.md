# Tests

Loaded when working under `tests/`. The root `CLAUDE.md` has the commands that run them.

Tests (TUnit, AwesomeAssertions) use a real database.

- There is one test project per src project: `ApplicationCore.Tests` (Rules and Validators, with no database), `Infrastructure.Tests`, `Pricing.Tests`, `Presentation.Tests` (the screen states), `Components.Tests` (the DI wiring, the page's list of Syncfusion scripts, the Vim keys' C#, the components rendered with bUnit, and the architecture's rules in `Architecture/`, with no database and no MAUI), `Mcp.Tests`, `RecipeApi.Tests` and `UseCases.Tests` (the use cases on real repositories). A moved screen's draft is tested in `Presentation.Tests` with no database, by CsCheck's random sequences (`SubAssemblyDraftTests`, `RawMaterialDraftTests`, `ProductPackagingDraftTests`, `ProductComponentsDraftTests`, `ProductCostingTests`, `ProductRecipeDraftTests`, `ProductDraftTests`), each step only what the screen lets the user do: such a class needs neither attribute below. The database-backed ones share their fixtures through `tests/TinapayanRMS.Tests.Common`, a plain library. `tests/TinapayanRMS.Benchmarks` is no test project either (its name doesn't end in `.Tests`): an exe of measured scenarios, which `Benchmarks.Tests` holds to their budgets.
- Each database-backed project runs against its own database on the PostgreSQL server, `tinapayanrms_test_infrastructure`, `tinapayanrms_test_pricing`, `tinapayanrms_test_presentation`, `tinapayanrms_test_mcp`, `tinapayanrms_test_recipeapi` or `tinapayanrms_test_usecases`, never the dev `tinapayanrms` database. Presentation.Tests and Infrastructure.Tests also have `_2` to `_4` of theirs, one for each of their four database collections, which run side by side. The backup tests also make and drop `tinapayanrms_test_backup_*` databases of their own, and the benchmarks and their budgets `tinapayanrms_bench_*` ones, restored from the golden master's fixture. `dotnet test --solution` runs the projects side by side, so they can't share one. Respawn resets it before each test. Nothing is mocked.
- Database test classes inherit `PersistenceTestBase` from `Tests.Common`. **Each concrete class must also carry `[NotInParallel(DatabaseCollection.Name)]` and `[ClassDataSource<DatabaseFixture>(Shared = SharedType.Keyed, Key = DatabaseCollection.Name)]`**, or in Presentation.Tests and Infrastructure.Tests one of `DatabaseCollection.A` to `D` in both (the one with least in it; each has its own database). Without the first, its tests run side by side against one database; without the second, TUnit can't construct it. `DatabaseFixture` and `DatabaseCollection` are defined in each project's own `Fixtures/`.
- **TUnit runs every test in parallel, a class's own tests included**, unless a `[NotInParallel]` key holds them apart: one that shares state with another test needs one. Each test gets a new instance of its class, made on one thread and often run on another: set a thread's state (a synchronization context) in the test, not the constructor.
- **In Components.Tests a command run nothing awaited that fails is reported as the app reports it**, set up once for the whole run by a `[Before(TestDiscovery)]` hook (`CommandFailuresSetup`): a test or fixture never sets it up itself.
- **A test that drives a screen's state runs in `UiThread.RunAsync`**, a thread that runs one thing at a time as the app's UI thread does, and waits for the screen's work with `Settle.UntilAsync`, never a fixed delay.
- **`CostingGoldenMasterTests` (Mcp.Tests) fails when a costing figure moves.** A change meant to move one approves the new figures on the developer's PC (`$env:TINAPAYANRMS_APPROVE_COSTING = '1'`, then run that test), and the diff of `Golden/costing.approved.txt` shows what moved. Read it before keeping it.
- **`BudgetTests` (Benchmarks.Tests) fails when a benchmark scenario sends another SQL command, or allocates over 10% more** (or 20% less, so its budget follows it down). A change meant to move one approves the new figures on the developer's PC (`$env:TINAPAYANRMS_APPROVE_BUDGETS = '1'`, then run Benchmarks.Tests), and the diff of `Budgets/budgets.approved.txt` shows what moved: never approve a higher one just to make the test pass, and say why in the commit. A scenario is added to `ScenarioCatalog` (Benchmarks' `Scenarios/`), which gives it a budget and a benchmark alike.
- **A component test** builds its context with `AppServices.NewContext()` (the app's registrations, an in-memory view state and print settings, and a `FakeAppWindow`), and calls `RenderingAsTheWebView()` when it draws a Syncfusion dialog. bUnit's own `TestContext` is aliased away: `TestContext` is TUnit's. It awaits bUnit's waits (`WaitForAssertionAsync`, never the blocking `WaitForAssertion`, which starves the renderer when tests run side by side); `WaitsSetup` gives each one 30 seconds.
