# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**`PLAN.md` is the project guide and the source of truth** for the tech stack, domain model, application architecture and conventions. This file only covers what you need before you open it, and it doesn't repeat PLAN.md. PLAN.md opens with an overview ("At a glance"), then long bullets, so read it by section: list its sections with `grep -n "^#" PLAN.md`, then read the ones the task touches. It describes the app as it is now; the history (when a thing changed, who asked, what it replaced) is in the build plan's dated log. Its largest parts live in `docs/plan/` and are still part of it: the app's design notes (`maui-app.md`: the window, and how the Blazor screens are built), each main screen's design notes (`products-screen.md`, `raw-materials-screen.md`, `sub-assemblies-screen.md`), and the build plan with its dated change log and open items (`build-plan.md`). Keep PLAN.md and those files up to date when a decision changes: rewrite what they say, and log the change in the build plan.

TinapayanRMS is a desktop app for a bakeshop: a .NET MAUI Blazor Hybrid window on Windows, its screens Blazor components with Syncfusion Blazor, drawn in WebView2. It tracks raw material prices and cascades cost changes up through made ingredients and sub-assemblies to each finished product's cost and selling price.

## Commands

Run everything from the repo root. The .NET 11 SDK (11.0.100) is pinned in `global.json`, which also sets `test.runner` to Microsoft.Testing.Platform. VSTest-style flags such as `--filter` and `--collect` don't work here.

```sh
dotnet build TinapayanRMS.slnx
dotnet test --solution TinapayanRMS.slnx                                          # all tests
dotnet test --project tests/TinapayanRMS.ApplicationCore.Tests --treenode-filter "/*/*/UnitConversionRulesTests/*"   # /assembly/namespace/class/test
dotnet test --project tests/TinapayanRMS.Presentation.Tests --treenode-filter "/*/*/*/*SomeTestName*"
powershell -ExecutionPolicy Bypass -File scripts/Test-Changed.ps1               # only the test projects your changes reach (-List, -Class, -Since)
powershell -ExecutionPolicy Bypass -File scripts/Watch-Tests.ps1 Presentation -Class "*X*"   # rerun a class on each save, by hot reload
dotnet run --project src/TinapayanRMS.Maui                                        # the app's window
dotnet run --project src/TinapayanRMS.RecipeApi                                   # the Recipe API, http://localhost:5290/api/v1
powershell -ExecutionPolicy Bypass -File scripts/Install-TinapayanRMS.ps1         # install or update the app for this Windows user

dotnet ef migrations add <Name> --project src/TinapayanRMS.Infrastructure
dotnet ef database update --project src/TinapayanRMS.Infrastructure
dotnet ef migrations has-pending-model-changes --project src/TinapayanRMS.Infrastructure
dotnet ef dbcontext optimize --project src/TinapayanRMS.Infrastructure --output-dir CompiledModels --namespace TinapayanRMS.Infrastructure.CompiledModels
```

- **While developing, run what a change reaches:** `scripts/Test-Changed.ps1` picks the test projects from the project references (a change to the screens runs `Components.Tests` alone). The full suite still decides when work is done. Neither script runs while that project's tests already are, as both would reset its test databases: stop any `Watch-Tests.ps1` first.
- **A costing figure that moves fails `CostingGoldenMasterTests`** (Mcp.Tests), which prices an anonymized copy of the shop's data. `tests/CLAUDE.md` says how a change meant to move one approves it.
- **Migrations come only from `dotnet ef migrations add`.** Never write or edit one by hand. `TinapayanRMSDbContextFactory` provides the design-time DbContext. **The app applies pending migrations itself as it opens**, after a `before-update` backup (`DatabaseUpdater`, through `DatabaseReadiness`), so an install is the whole update on any PC; a launched build therefore migrates the database it opens, the dev one included, as `dotnet ef database update` would. A check against a scratch database leaves that database's backups in the shared `%ProgramData%\TinapayanRMS\Backups`: delete them after.
- **The app runs on a compiled EF Core model** (`Infrastructure/CompiledModels/`, found by EF without a `UseModel` call). Regenerate it with `dotnet ef dbcontext optimize` (above) after any model change, and never edit it by hand. `CompiledModelTests` fail while it's stale.
- **Work counts as done** when the solution builds, all tests pass, and any new migration applies cleanly to the local database. GitHub checks the build, the migration check and the whole suite on each push to `main` that changes code (`.github/workflows/build.yml`; `gh run list`, `gh run view <id> --log-failed`). A change users can see (a screen, button, field, rule or cost formula) also updates the user manual, `docs/user-manual.md`, in the same change. A change to anything the developer manual, `docs/developer-manual.md`, describes (the setup, commands, solution layout, architecture, a pattern or convention, or a type or file it names) also updates it in the same change.
- **Building the app needs the .NET MAUI workload**, `maui-windows` (11.0.0, `MauiPackagesVersion` in `Directory.Packages.props`; `dotnet workload list`), installed from an administrator terminal: `dotnet workload install maui-windows --skip-manifest-update`. A running copy (`TinapayanRMS.Maui`) locks its build's DLLs: close it before building. It writes its view state and log under `%LocalAppData%\TinapayanRMS\Maui`.
- **The build compiles the Syncfusion licence key into the app from the `SYNCFUSION_LICENSE_KEY` user environment variable** (an `AssemblyMetadata` item in the Maui project), so an installed copy needs no variable. `MauiProgram` reads the compiled-in key, falls back to the variable, and with neither logs it and opens with Syncfusion's licence notice. `dotnet publish` fails without the variable.
- **The app, the tests and `dotnet ef` need the local PostgreSQL 18 server** (service `postgresql-x64-18`, `localhost:5432`), reached as the `tinapayanrms` role. Its password is in `%APPDATA%\postgresql\pgpass.conf`, which Npgsql, `psql` and `pg_dump` all read, so no connection string carries one. The dev database is `tinapayanrms`, named in `src/TinapayanRMS.Maui/appsettings.json` (the servers and the test fixtures link that file). Query it with `& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h localhost -U tinapayanrms -d tinapayanrms` (`psql` isn't on the PATH). Every table and column name is snake_case (`raw_materials.cost_per_base_unit`). SQL Server Express and LocalDB are still installed, holding the data from before the move (2026-10-21), but are unused.
- **Build settings are centralized.** `Directory.Build.props` sets the shared compiler settings, the .NET analyzers (`AnalysisLevel` `latest-recommended`, with per-folder exceptions in `.editorconfig`, where IDE0005 makes an unneeded using a warning every build reports) and the target frameworks (`net11.0` by default; the Maui project uses `$(WindowsTargetFramework)`). `tests/Directory.Build.props` adds TUnit, the assertion package, `tests/TestRunSettings.cs` and `tests/HotReloadReruns.cs` (a workaround for TUnit's hot reload reruns) to every `*.Tests` project. `Directory.Packages.props` turns on Central Package Management, so a `PackageReference` never carries a `Version`: add or bump versions there.
- **Docker isn't used anywhere in this project.**
- **`ilspycmd` (11.0, a global dotnet tool) is installed for decompiling and inspecting .NET assemblies.** Use it instead of writing reflection scripts. For example, `ilspycmd -l c <dll>` lists the classes in an assembly, `ilspycmd -t <Full.Type.Name> <dll>` decompiles one type, and `ilspycmd -m "M:Namespace.Type.Method(System.String)" <dll>` decompiles one member. The Syncfusion assemblies are in the NuGet cache under `~/.nuget/packages/syncfusion.blazor.*/<version>/lib/net10.0/` (the grid's is `Syncfusion.Blazor.Grids.dll`, plural), MAUI's under `~/.nuget/packages/microsoft.maui.*/<version>/lib/`.
- **The `tinapayanrms` MCP server (`src/TinapayanRMS.Mcp`, started from `.mcp.json`) prices products from the dev database with the app's own code.** A product's cost and price are computed on read, so SQL can't show them. Use `list_products`, `get_product_costing` and `simulate_price_changes` to check a costing change against real data, or to see what a price change reaches. It can't write. It builds as it starts, so restart it (`/mcp`) after changing the code it runs. `scripts/Start-McpServer.ps1` runs it from a copy of the build, so a running server never blocks a build.
- **The Recipe API (`src/TinapayanRMS.RecipeApi`) serves the recipes, read-only, to the shop's other apps over the LAN**: TinapayanBMS in `../TinapayanBMS` copies its recipes, ingredients, prices and costs through it, and plans production from them: the Production Plan moved there on 2026-10-31 and is gone from this app. Its records (`Contracts/RecipeContracts.cs`) are copied by those apps, so add to them rather than rename or remove. Like the MCP server it builds on `DatabaseHost` and `ReadOnlyConnection`, and prices with `TinapayanRMS.Pricing`, with no UI in it. The developer manual's "The Recipe API" has the rest.
- **`dotnet-stack`, `dotnet-dump` and `dotnet-trace` (global dotnet tools) are installed for diagnosing the running app.** Use them instead of guessing. `dotnet-stack report -p <pid>` shows where a frozen UI thread is blocked. `dotnet-dump collect -p <pid>` followed by `dotnet-dump analyze <file>` covers crashes, deadlocks and memory growth, but its `dumpasync` can't read .NET 11's runtime async, which the app's async methods (and .NET's own) use: to see what a hung app's async work is waiting on, use the debugger's Parallel Stacks window or `dotnet-trace`. `dotnet-trace collect -p <pid>` covers slowness. Find the PID with `dotnet-trace ps`.

## Architecture in brief

- **Architecture decisions are records in `docs/adr/`** (since 2026-11-20): read the ones a change touches before it, and write one before adding a project, a layer, a framework or a library the code is built around. The screens are moving, a screen at a time, to a `UseCases` project and a draft, a form and a view per record screen (ADR 0002, the build plan's open items); one structural change at a time, never mixed with features (ADR 0005).
- **The build and Components.Tests' `Architecture/` enforce the rules as ratchets** (ADR 0004): the layers, no data-access type held by a screen but as many as `DataAccessTests.StillReaching` lists, at most six things through a screen state's constructor but as `ConstructorDependencyTests.StillOver` lists, `BannedSymbols.txt` (RS0030), and CA1502/CA1506 with each place over them suppressed with why. **Never raise a listed number, add a type to a list or add a suppression to make the build or a test pass**: split the class, or go through a use case. When work lowers a number, lower it in the same commit (the test says to).
- **Layers:**
  - `Domain` holds the entities and has no dependencies.
  - `ApplicationCore` holds the business and costing rules (static `*Rules` classes), the repository interfaces and the FluentValidation validators.
  - `Infrastructure` holds EF Core (PostgreSQL through Npgsql, snake_case names), the repositories, and the cross-entity services (the cost propagators and `ProductCloner`). `DatabaseHost.AddTinapayanRMSDatabase` registers the database and every repository, the one way the app and both servers do.
  - `Pricing` holds `SavedProductReader` and what it builds: the one way a saved product is read and priced, shared by the screens, the Recipe API and the MCP server. Its `Versions/` holds the product versions' snapshot and the saves that record them (`VersionedSaves`). Keep Blazor, MAUI, Syncfusion and ReactiveUI out of it: the two servers are on plain `net11.0`.
  - `UseCases` holds what the screens do with the records (ADR 0002): each moved screen's queries and editor (`UseCases/SubAssemblies/`: `ISubAssemblyQueries`, `ISubAssemblyEditor`, `ISubAssemblyRoleEditor`), above ApplicationCore and Pricing, never referencing Infrastructure. Sub-Assemblies is moved; the other screens still hold repositories until their phase.
  - `Presentation` holds the screens' states (the app's own `ObservableState` and `ScreenCommand`, with Rx and DynamicData), tested without a window: a folder per screen (`Products/`, `Settings/`…), with what they share in `Shared/` and `Trees/` and what's around the screens in `App/`. Keep MAUI, Blazor and Syncfusion out of it.
  - `Components` is the screens, a Razor class library (Blazor, Syncfusion Blazor) on `net11.0`, with their styles and scripts in its `wwwroot` (served at `_content/TinapayanRMS.Components/`, its JS initializer loading Syncfusion's scripts); `ServiceRegistration.cs` registers the app's services (`AddTinapayanRMS`), and what only the window can do is an interface there (`IAppWindow`, `IFileDialogs`, `IPagePrinter`). `Maui` is the app, the screens' host: `MauiProgram`, `MainPage` (the `BlazorWebView`), `wwwroot/index.html` (the host page, which links the screens' styles and scripts) and `Platforms/Windows` (the window: `WindowsWindow`, `AppWindowChrome`), Windows only.
  - **Each folder is its own namespace, and files are grouped by kind, a screen's by screen** (Components' `Pages/Products/`, Presentation's `Products/`). Only app-startup plumbing, the DbContext pair and `Pricing`, one kind of thing throughout, sit at a project root.
- **A screen is a Blazor page over its state.** The page inherits `ScreenBase<TState>` (`Components/Shared`), which runs the state's load each time the page opens, shows its messages as toasts, answers its confirmations with a dialog, and redraws when it, its lists or its commands change (found by the type each property is declared as, so declare a list or command a screen should watch as one, not as an `IReadOnlyList<T>`). Record screens have an address per record (`/products/42`), so Back and Forward work. Each record view (Sub-Assemblies, Raw Materials, Products) opens each record in a tab of its own: its state (`RecordViewState`: `SubAssembliesState`, `RawMaterialsState`, `ProductsState`) keeps the list, the load and the tabs, each tab a form of its own (`SubAssemblyForm`, `RawMaterialForm`, `ProductForm`, each a `RecordScreenState`) drawn by a `FormBase`, and its page a `RecordViewBase` (the developer manual's "A record view opens each record in a tab of its own").
- **Some costs are stored, others are computed on read.**
  - Stored: `RawMaterial.CostPerBaseUnit` and `BufferedCostPerBaseUnit`, and nothing else. When a price, BOM or line changes, `IngredientCostPropagator` updates the made and linked ingredients in dependency order (using `IngredientCostGraph`), on the save's own context, before its transaction commits. A computed cost is stored at its column's scale (`RawMaterialRules.StoredCost`), or an unchanged one reads as changed.
  - Computed on read by `SubAssemblyRules`, `ProductRules` and `CostingRules`: a sub-assembly's batch weight and cost (from its lines), product usages, packaging lines, and product cost and price. A composite product's lines bring each held product's recipe cost, which `SavedProductReader` also works out on read.
  - Before changing any cost path, read PLAN.md's "Reactive Costing Cascade" section.
- **`TinapayanRMSDbContext` comes from `SharedTransactionDbContextFactory`**, registered as `IDbContextFactory` and as `IUnitOfWork`. Screen states are scoped, one set per page the web view loads (so a reload after a restore builds them afresh), and outlive any one operation, so each operation creates its own short-lived context. Inside `IUnitOfWork.RunAsync`, every context shares one transaction, so its reads must not run side by side, and a repository begins its transaction with `BeginOrJoinTransactionAsync`.
- **A failure never escapes a screen.** Rules throw `BusinessRuleException`. A screen state runs an action in `RunSafelyAsync`, a `LoadCommand`'s body in `LoadSafelyAsync`, and a load driven by a selection through `LoadLatest`, never a bare `Observable.Switch(...).Subscribe()`: an error reaching `Switch` ends the subscription for good. A task nothing awaits (`_ = ...`) deals with its own failure, through `RunSafelyAsync` on a screen: otherwise it only reaches a warning in the log, and the click that started it just does nothing.
- **A screen's state is a plain class, with no MVVM library** (ReactiveUI went on 2026-11-16; the classes were called ViewModels until 2026-11-17). A screen's state, a part of one and a row derive from `ObservableState` (through `ScreenState` or `ObservableRow`); a value worked out from others is a plain getter, and a figure worked out from a table or many fields (costs, a batch's totals) a getter over a `Derived<T>`, worked out when read and marked stale broadly, never pushed; what follows a change is called by the setter that made it, in the order it has to run, never a subscription to the state's own properties, and what only the user's edit sets off is a method the page calls (`Pick`, `ChangeType`, bound as `Value`/`ValueChanged`), so a load or an undo just writes the property; a command is a `ScreenCommand` (`ExecuteAsync`, and `CanExecute()` asked when it's wanted); and a question the screen answers (a dialog, a file picker) is the app's own `Interaction`. Rx (`System.Reactive`) and DynamicData stay for what they do: `LoadLatest`'s latest-pick-wins loads, the `Subject`s one screen follows on another, and the sorted and auto-refreshed lists. The developer manual's "Screen state" has the rules.
- **Tests (TUnit, AwesomeAssertions) use a real database, never the dev `tinapayanrms` one.** How to write them (the test databases, the two attributes every database test class needs, TUnit's parallelism, `UiThread`, component test contexts) is in `tests/CLAUDE.md`, which loads when you work under `tests/`.
- **Costs are `decimal` at full precision** (`numeric(18,4)` by convention in `ConfigureConventions`). Round only for display and for the final selling price. Never turn a `double` into a `decimal` with a cast or `Convert`: since .NET 11 that keeps the double's binary noise (28.35 becomes 28.3499…). Every typed number comes through `NumberField`, and test data with decimals goes in a `[MethodDataSource]` method as `m` literals (PLAN.md, Conventions, "Decimal precision").

## UI work

- **Prefer a Syncfusion Blazor component over a plain HTML control where one fits.** All Syncfusion packages share one version, the `SyncfusionVersion` property in `Directory.Packages.props`, so they upgrade together. The theme is Syncfusion Blazor's Fluent 2 (`fluent2-lite.css`), recoloured to the app's palette (Catppuccin Latte) in `Components/wwwroot/app.css`; icons are Syncfusion's own, drawn by `SfIcon`: a screen state or page names one by what it stands for (`AppIcon`, in Presentation) and `Shared/AppIcons.cs` picks Syncfusion's icon for it (`AppIconsTests` checks the theme draws each). The window's caption buttons are inline SVG, as Syncfusion has none. **The page loads the scripts of only the Syncfusion components named in `Components/wwwroot/syncfusion.js`**: a component new to the screens goes there too, or it fails in the window (`SyncfusionScriptsTests` checks the list).
- **To learn how a Syncfusion Blazor component is meant to be used**, ask the `syncfusion-blazor` MCP server (Syncfusion's Blazor documentation), which `.mcp.json` starts with the API key from the `SYNCFUSION_API_KEY` user environment variable, then read the type with `ilspycmd`.
- **Use the shared components for what the screens type into**, not Syncfusion's inputs: `TextField`, `NumberField`, `PickField`, `LineGrid` and `FolderTree`. `docs/plan/maui-app.md` ("How it's built") says why each exists. **Never write into a box that has the cursor** (a redraw for an earlier keystroke overwrites the ones typed since; when another record takes the form's place, `IUndoRecorder.FormVersion`, the box is replaced instead); **bind a picker by index**, as `PickField` does; **key a table's rows** (`@key`), and never draw one object as two rows in a pass; **make a repeated row's handlers once** (`FolderTree`'s and `LineGrid`'s `RowEvents`), not as a lambda over the row on every drawing.
- **A component that redraws on a screen state's events asks a `RedrawGate`** (`Request`), as `ScreenBase` and `FolderTree` do, and never calls `InvokeAsync(StateHasChanged)` from a handler that runs once per change: a load makes hundreds. A button bound to a command is a `CommandButton`; one for a command with a parameter or a screen's own action an `ActionButton`; one that drops a list of commands a `MenuButton`.
- **A component lets go of whatever it hooked into something that outlives it** (a screen state's events, lists or commands, the screen state's rows, a service), in its `Dispose`: the screen states last as long as the window, and each visit draws a screen afresh. A page hands its state nothing of its own to keep (a lambda over its grid) except through `AddSubscription`, which gives it back as the page goes, as the Price Simulator's table is lent (`ShowProductsFrom`). An `SfGrid`'s rows don't notify: Syncfusion never unhooks a row added after the grid bound. `Visits.ShowAndLeave` (Components.Tests) tests a component for it.
- **The window is chromeless**: the page draws the title bar (`Layout/TitleBar.razor`), and the window takes the gaps between its buttons as the caption (`AppWindowChrome`, from `app.js`'s `watchTitleBar`). MAUI's own title bar row is hidden by calling its internal `NavigationRootManager.SetTitleBarVisibility` after each style change: after a MAUI update, check the row is still gone. Anything clickable added to the title bar must be a `button`, `a` or `input`, or it's taken as caption. Closing the window ends the process there and then (`App`): left to itself it stayed 17 to 22 seconds after the window had gone.
- **Check a screen in the app's window before calling it done**: bUnit has no web view, so focus, typing, drag and drop, printing, the dialogs, the Vim keys (`Components/wwwroot/vim.js`) and the title bar only show there. Use the `run-tinapayanrms` skill (`.claude/skills/run-tinapayanrms/`): its `driver.ps1` starts the app with WebView2's debugging port and drives the page with `playwright-core`, so nothing touches the mouse or the screen, and captures the whole window with `PrintWindow`. Close any copy the user has open first. It works on the dev database: save nothing. It starts the Debug build signed in (`TINAPAYANRMS_SIGNED_IN=1`, which a Release build ignores), since a check can't know the user's password; check the sign-in panel itself with `TINAPAYANRMS_SIGN_IN=1` against a copy of the dev database (`ConnectionStrings__Default`), never by setting a password in the user's.
