- **Embedded management panel for an editable child lookup** (`SubAssembliesView`, Phase 7): `SubAssemblyRole` is editable but has no screen of its own — it gets a small self-contained grid + form + New/Save/Delete panel living directly inside `SubAssembliesView`, with its own independent `SourceCache`, selection, and commands in `SubAssembliesViewModel` (not a separate tab, and not folded into the sub-assembly form itself). Use this shape for a future lookup that's editable but too small/tightly-coupled to its owning screen to deserve a top-level tab. **Since Phase 16 it sits inside a collapsed native `Expander`** (`IsExpanded="False"`) at the bottom of the screen's right rail, rather than an always-visible side panel — it's used rarely enough (editing categories/roles is occasional, not part of the main workflow) that keeping it collapsed by default gives the main list more room without hiding the feature. The native `Expander` is used rather than a Syncfusion accordion (`SfAccordion` would need its own package just for this), and since `ApplyThemeAsDefaultStyle` is off (see the accent-customization note above), the native `Expander` renders with the plain OS chrome rather than the theme's — functional, just not accent-styled, the same trade-off as the other native fallbacks (`CheckBox`, `ProgressBar`) noted elsewhere in this document.

A derived type's class handlers run before `UIElement`'s, which call the `On…` overrides. The picker then closes and keeps the pick as for a full name. A name matching nothing still highlights nothing, so Category's add prompt is unchanged.

The handler writes the next name into the box and focuses its row, as the picker does. It also swallows that key's key-up, since `OnKeyUp` would otherwise refilter by the full name and leave only that row.

      - **Every such picker selects its whole text as the keyboard enters it, by a click or by Tab** (2026-10-16, at the user's request: "whenever i select or click inside a searchable combobox the text inside is highlighted"). A click used to select the text only for a moment: `ComboBoxAdv.Part_IsEdit_GotFocus` selects it (only with a pick, and by the length of `SelectedItem.ToString()`), then the `TextBox`'s own mouse-down puts the caret where the click landed. `Controls/PickerSelectOnEntry`, registered from `App`'s static constructor, adds class handlers on `TextBox`, limited to an editable `ComboBoxAdv`'s `PART_Editable`.
        - `PreviewMouseLeftButtonDown` on a box without the keyboard focuses it and marks the press handled, so the box never places the caret. A click on a box that already has the keyboard is left alone: it places the caret, and a double-click selects a word.
        - `GotKeyboardFocus` calls `SelectAll`, whether or not the text names a pick, but only when `OldFocus` is outside the picker. Old focus on the picker itself counts as outside, since `ComboBoxAdv_GotFocus` hands the keyboard on to the box. The keyboard also comes back to the box from a list row (an arrow key focuses the row, and typing brings it back), and selecting then would have the next letter replace the text. "Inside" walks up through `FrameworkElement.Parent`, then the visual parent: the list's pop-up is no visual child of the picker, but its child's logical parent is the `Popup`.

Otherwise the letter was lost, whether it replaced a selected name or was added to one: `Part_IsEdit_TextChanged` clears a pick its text no longer names, and `OnSelectionChanged` empties the box unless the key was Backspace or Delete (`isBackspaceOrDeleteKeyPressed`, private).

They cover the selection on a click or Tab, typed text that names no pick, the letter typed over a pick, and a focus change raised from a list row (an off-screen window's pop-up doesn't reliably take the keyboard).
      - **A picker emptied while bound to a value that can't be null shows that value again once the keyboard leaves it** (2026-10-16, at the user's request: Raw Materials' Type stayed empty after its text was deleted, through a switch to another material or the tab closing). Another material of the same type then sets the value it already holds, which raises no change, so the picker stayed empty. `Controls/PickerRestoresPick`, a class handler on `ComboBoxAdv`'s `LostKeyboardFocus`, calls `UpdateTarget` on a null `SelectedItem` or `SelectedValue` whose binding `HasError`, once `IsKeyboardFocusWithin` is false. It doesn't run while the box is typed in, or Backspace over a name and then typing another would bring the old name back after the first key. A picker bound to a nullable value took the null, so its binding has no error and it stays empty. I don't like the protection for that") **and asked for the conversion factor to live on the unit itself instead** — so `IsProtected`/`WellKnownUnitOfMeasureIds`/the `HasData` seed rows were removed altogether (a new migration deletes the six seeded rows), and `UnitOfMeasure` gained two real columns: `IsLengthUnit` (bool) and `MillimetersPerUnit` (decimal?, enforced by `UnitOfMeasureRules.EnsureLengthUnitFieldsAreConsistent` to be positive exactly when `IsLengthUnit` is true, null otherwise). `LengthConversion.Convert`/`ProductRules.EnsureValidEntryUnit`/`CalculatePackagingLineCostPerPiece` all now take full `UnitOfMeasure` entities instead of bare ids, reading `.IsLengthUnit`/`.MillimetersPerUnit` directly — nothing is special-cased by id anywhere anymore, so a shop owner's own custom length unit (say, a "foot") works identically to a built-in one the moment they tick the checkbox and enter its factor. `PackagingMaterialRules.IsValidStandardUnit`/`EnsureValidStandardUnit` ("must be Piece or a length unit") were dropped for the same reason — "Piece" was never a real concept once nothing was seeded, so there was no principled way left to restrict what a standard unit could be; a packaging material's standard unit is now trusted the same way an ingredient's purchase unit always was. `PackagingLineRepository.SetLinesAsync` was updated to load full `UnitOfMeasure` rows (for both the material's standard unit and each line's entry unit) instead of bare ids, which also meant adding an entry-unit-existence check it had never had before (mirroring the delete-before-validate fix from the Phase 14 audit) and a `.ThenInclude(m => m!.StandardUnit)` on the two `PackagingLineRepository` read queries so `PackagingLineEdit.CostPerPiece`/`ReportsViewModel`'s margin calculation have the material's standard unit entity already loaded, not just its id.

Gone: `IsLengthUnit`, `MillimetersPerUnit`, `LengthConversion`, `UnitOfMeasureRules.EnsureLengthUnitFieldsAreConsistent`, `ProductRules.EnsureValidEntryUnit`, `PackagingLine.EntryUnitId` and the Products screen's Entry Unit picker. `CalculatePackagingLineCostPerPiece` takes no units, and `IPackagingLineRepository.SetLinesAsync` tuples are `(PackagingMaterialId, AuthoredField, AuthoredValue)`.   - **`UnitOfMeasure` losing its seed data meant `DatabaseFixture` no longer needed a special case for it.** It previously excluded `UnitsOfMeasure` from Respawn's per-test reset specifically because the migration-seeded rows 1–6 were baseline data every other persistence test's FK depended on (Respawn can only "delete everything" or "touch nothing," no partial reset) — with no seed data left, that whole justification disappeared, so the exclusion (and the extra manual cleanup query it needed once `UnitOfMeasureRepository.AddAsync`/`DeleteAsync` existed) was simply removed, and `UnitsOfMeasure` now resets exactly like every other table. Every persistence test that referenced a `WellKnownUnitOfMeasureIds` constant as an FK value now seeds its own unit first via one of two new `PersistenceTestBase` helpers: `SeedUnitOfMeasureAsync` (always inserts a fresh row — for a test that specifically needs a distinct new unit) or `GetOrCreateUnitOfMeasureAsync` (looks up an existing row by name first — for a test's shared per-file seed helper that gets called multiple times in one test method with "any valid unit," where a second unconditional insert would violate the unique `Name` index).
  - **A `TabControlExt`'s inactive tab pages stay fully materialized in the UI Automation tree, not just the visible one** — confirmed the hard way while verifying this feature: a UI Automation query for "the first/last button named 'New'" (or "the first two Edit controls") across the *whole window*, run without scoping to the currently-visible tab's subtree, can silently match a control that belongs to a completely different, invisible tab page. Zero break-on-first-match logic combined with an index-based `.Item(0)`/`.Item(1)` guess landed on the wrong screen's controls one turn later even though the intended screen's own action had already appeared to work correctly moments earlier in the same session — the fix is to always scope a `FindFirst`/`FindAll` call to the specific View's own root automation element (e.g. found via its own distinctive, screen-unique control first), never to `AutomationElement.FromHandle(hwnd)` directly, when more than one tab's content could contain a same-named control.
  - **Syncfusion's number boxes take Ctrl+Z and Ctrl+Y for themselves, on the way down** (found 2026-09-20, building undo). `Syncfusion.Windows.Shared.DoubleTextBox.OnPreviewKeyDown` — and `CurrencyTextBox`'s — handles both keys for its own per-character undo and sets `e.Handled = true` on **every** branch, including when `IsUndoEnabled` is false. Because that's the tunnelling pass, the bubbling `KeyDown` never runs, so a `Window.InputBindings` Ctrl+Z is dead in every numeric grid cell and numeric field — most of the app. **The fix is a class handler on `typeof(Window)` for `PreviewKeyDown`** (`Controls/UndoShortcuts`, registered from `App`'s static constructor beside the three existing class handlers): tunnelling runs root to source, so the window sees the key before the focused box can claim it. The screen is found by walking up from `Keyboard.FocusedElement` to the first `DataContext` that is an `IUndoScreen`, which needs no registry and leaves Settings and the prompt window alone. Verified in the app: Ctrl+Z pressed with the cursor inside a `DoubleTextBox` took the change back rather than a character.
  - **A driving script must make its own thread per-monitor DPI aware, or its clicks miss** (found 2026-09-20 while verifying Products' Revert). UI Automation's `BoundingRectangle` is always in physical pixels, but `GetWindowRect`, `SetCursorPos` and `Graphics.CopyFromScreen` in a non-DPI-aware PowerShell host speak the *virtualized* coordinates Windows makes up for it — on this machine the primary is 125%, so the two spaces differ by 0.8 and a click computed from a screenshot landed hundreds of pixels away, silently selecting nothing. `SetProcessDpiAwarenessContext` is no use here: it only works before the process has done any DPI-dependent work, which a started PowerShell already has. **`SetThreadDpiAwarenessContext(-4)` (`PER_MONITOR_AWARE_V2`) works at any time** and brings all four into the same physical-pixel space; check it took by confirming `GetWindowRect` and the root element's `BoundingRectangle` agree before clicking anything.
  - **A `TabItemExt` can't be selected through UI Automation; the main strip's tab list can** (found 2026-09-27, verifying Reports). Its peer offers only `InvokePattern` (no `SelectionItemPattern`), and `Invoke` leaves the selection where it was. The main window's tabs can still be switched with no mouse or keys: `Invoke` the strip's ˅ button (AutomationId `PART_MenuButton`), then `Invoke` the `MenuItem` named after the tab (it's in a popup, so search from the desktop root, filtered by the app's process id). This works with the app behind other windows, and `PrintWindow` then captures it. The in-card tab controls hide that list (`ShowTabListContextMenu="False"`, no ˅ button), and their inactive pages aren't built until first shown, so reaching one takes a real click with the app in front.
