## Open items (for later phases)

- **Adopting a Syncfusion control the app doesn't use yet.** The theme package already styles every Syncfusion control, so a new control only needs its `PackageReference` in `TinapayanRMS.UI`, at the same version as the other Syncfusion packages. (Through Phase 15 this took a three-step procedure against the trimmed `TinapayanRMS.Theme` project — obsolete since the theme became a package.)
  - If the control is built around Syncfusion's newer "Sf*"/`Syncfusion.UI.Xaml.*` theming framework (as opposed to the older `Syncfusion.Windows.Tools.Controls`/`Syncfusion.Windows.Shared` control set), **check the locally installed Syncfusion Sample Browser source before assuming a property works the way its name suggests.** Essential Studio installs its full demo source to `C:\Users\Public\Documents\Syncfusion\WPF\<version>\SampleBrowser\` (grouped by area, e.g. `navigation\NavigationDrawer\Views\*.xaml`), and it is the authoritative answer to "which properties is this control actually meant to be set with, together" — a question neither the property list, the XML docs, nor the generated theme XAML answers. Demo filenames don't always contain the control's name (`DisplayMode.xaml`, `Hierarchical.xaml`), so grep contents rather than globbing filenames. These controls can have several control templates selected by a mode property, each honoring a genuinely different subset of properties, so the "does this control support X" question is really "does the template for the mode I'm in support X".
  - **`SfNavigationDrawer` is the worked example** (Phase 15, `MainWindow`'s navigation drawer): it has two control templates selected by `DisplayMode`. The `Compact`/`Expanded` template draws the drawer's **own built-in hamburger toggle** (a `ToggleButton` two-way bound to `IsOpen`, so no toggle button of your own is needed) and renders the `Items` collection through a `NavigationView`. The `Default` template has **neither** — no toggle at all, and it presents `DrawerContentView` instead, ignoring `Items` entirely. Setting `Items` under `DisplayMode="Default"` compiles fine and the drawer's own chrome still themes correctly, so it looks like a theming problem, but nothing from `Items` ever renders. **`MainWindow` moved to `DisplayMode="Default"` on 2026-09-22** (at the user's request: the menu should be hidden until summoned, with no permanent rail), so the Default template's two gaps are now the thing to work around rather than avoid — see the sub-bullets below.
    - **The menu marks nothing as current** (2026-09-22, at the user's request: "highlighting an item in the Navigation Drawer as the currently selected is redundant"). The tab strip right below the drawer already shows the page showing, so the amber row was saying it twice. Removing it took the selection out of the design altogether: **navigation is driven by the row's click, not by the `ListBox`'s `SelectedItem`**, because an invisible selection would be free to drift from the tab actually open, and a click on a row that happened to still be selected raises no `SelectionChanged` — it would have closed the menu without navigating. That also retired `SelectMenuItemFor` and its `_syncingMenu` re-entrancy guard, which existed only to keep the highlight in step with the tab strip. Regression test worth keeping by hand: pick the same destination twice in a row; the second pick must still navigate and close.
    - **The arrows have to walk the rows by hand; `MoveFocus` does not work here.** A `ListBox` sets `KeyboardNavigation.TabNavigation` to `Once`, so `FocusNavigationDirection.Next`/`Previous` leave the list altogether instead of visiting the sibling rows — Down jumped straight past the destinations and the menu could not be driven from the keyboard at all (reported by the user, 2026-09-22, after the first cut shipped with `MoveFocus`). `MoveMenuFocus` indexes `NavigationMenu.Items` and calls `Focus()` on the next row instead. The arrows are handled in `PreviewKeyDown` so the `ListBox` never sees them and can't move a selection this menu doesn't use.
    - **Opening the menu focuses the `ListBox`, not a row**, so nothing lights up on open; the first Down steps onto the top row (`MoveMenuFocus` treats "nothing focused" as start-at-the-end-you-came-from). Focus then shows as the *same* `#14000000` wash as hover — an outline of its own was read as the "current page" marker all over again, which is what had just been removed.
    - **It stays a `ListBox` even with no selection**, rather than becoming stacked `ButtonAdv`s like the Add Sub-Assembly drop-down, and the reason is hover: a flattened `ButtonAdv`'s themed hover is an opaque `#FFF9F9F9` that its template sets on its own border, which beats any `Background` set on the control and is a 3-level grey step against this panel (measured in a screen capture, 252,252,252 → 249,249,249). `DrawerItemStyle`'s rows own their hover outright (`#14000000`, the wash `ToastCloseButtonStyle` already uses), so it actually reads.
    - **The toggle and the menu are hand-rolled.** The toggle is a flat icon-only `ButtonAdv` in `MainWindow`'s header row — *outside* the drawer, which lives in row 1, so the scrim never covers it and a second click closes the menu. The menu is a `ListBox` in `DrawerContentView` whose `ListBoxItem`s are templated by the window's own `DrawerItemStyle`, with Settings a `ButtonAdv` below it. A `ListBox` rather than the stacked `ButtonAdv`s the Add Sub-Assembly drop-down uses, because this menu needs a persistent "you are here" state, which is exactly a `Selector`'s `SelectedItem`; templating a *framework* control is fine, since App.xaml's no-`Style` rule is about Syncfusion controls, whose templates must stay intact.
    - **Each row needs `AutomationProperties.Name`.** Its content is a glyph and a label in a `StackPanel`, not a string, so UI Automation reads the row out as `System.Windows.Controls.ListBoxItem` without it (seen in the running app before it was added). `NavigationItem.Header` used to supply this for free.
    - **The size property swaps with `Position`, and both apply only in `Default` mode.** `DrawerWidth` sizes a `Left`/`Right` drawer, `DrawerHeight` a `Top`/`Bottom` one; under `Compact` neither is read (the drawer expands to `ExpandedModeWidth`), which is why the `DrawerWidth="220"` this screen carried from Phase 15 until 2026-09-22 never did anything. Defaults worth knowing: `CompactModeWidth` 40, `ExpandedModeWidth` 250, `DrawerWidth` 400, `DrawerHeight` 636, `Transition` `SlideOnTop`, `AnimationDuration` 100 ms, `Position` `Left`.
    - **`Position="Top"` was tried and reverted** (2026-09-22, same day: asked for on "the menu drawer slides from top to bottom", then reverted on "I don't like that the items inside the navigation drawer is now horizontally positioned"). The lesson worth keeping: a top drawer is **not** a narrow panel entering from above — `UpdateDrawerAnimation`'s `Position.Top` branch zeroes the horizontal offset and translates the panel down by its own height, so the drawer always spans the window width. That forces the destinations into a row, which is what the user rejected. If a top drawer is ever wanted again, the menu has to be laid out horizontally (a horizontal `ItemsPanel`, an underline marker instead of the left bar, Settings at the right end, a bottom edge instead of a right one) — it is not a one-property change.
    - **`MenuAdv` was considered as a replacement for the whole drawer and not taken** (2026-09-22, the user asked "why not just use MenuAdv"). Recorded so it needn't be researched again: `MenuAdv`/`MenuItemAdv` are `Syncfusion.Windows.Shared` in **`Syncfusion.Shared.WPF`** (not `Syncfusion.Tools.WPF`), already present transitively and covered by the existing `http://schemas.syncfusion.com/wpf` xmlns, so no new `PackageReference`. Windows11Light themes them fully (`MenuAdv`, `MenuItemAdv`, `MenuItemSeparator`, plus `SyncfusionMenuCheckBoxStyle`/`SyncfusionMenuRadioButtonStyle`), so unlike a plain `ListBox` they'd need no hand-templating. `MenuItemAdv.Icon` is `typeof(object)`, so a glyph `TextBlock` drops in as `NavigationItem.Icon` did, and `IsCheckable` + `CheckIconType="RadioButton"` + `GroupName` would give the current-page mark. **The catch: the theme's item template puts `IconContent`, `CheckBoxPanel` and `RadioButtonPanel` in one overlapping `IconGrid`, so an item shows a glyph *or* a check mark, never both** — and `OnIsCheckablePropertyChanged` drives those visibilities, so it isn't something markup can dodge. Note also that every shipped Sample Browser demo drives `MenuAdv` through `ItemsSource` + `HierarchicalDataTemplate` + `ItemContainerStyle`; none declares `MenuItemAdv` elements inline.
    - **`HeaderHeight` and `FooterHeight` are registered but never bound by the Windows11Light template**, and the three drawer views are just the `Auto`/`*`/`Auto` rows of one grid, so they size to their content. Only `DrawerContentView` is used here, with one `Border` giving the panel its padding and its one edge. `DrawerHeight` is left unset too: `RefreshSlider` derives it from `ActualHeight` and re-runs on `SizeChanged` (verified by maximizing and resizing with the menu open — the panel tracked the window every time).
    - **Hosting `NavigationView`/`NavigationItem` by hand doesn't work**, so don't reach for it to get `IsSelected` and `ItemType="Button"` back. Both types are public, but every one of those behaviours hangs off the internal `NavigationItem.navigationDrawer` back-reference that only `SfNavigationDrawer.UpdateItems` sets from the `Items` collection: `Border_MouseUp` raises `ItemClicked` only `if (navigationDrawer != null)`, it flips `IsSelected` unconditionally so items toggle instead of behaving like radio buttons, and `NavigationView.UpdateNavigationItemFocus` dereferences `sfNavigationDrawer.FooterItems` before its own null check, so Tab throws `NullReferenceException`. The types also carry `<exclude/>` and `[EditorBrowsable(Never)]`.
    - **There is no dimmed backdrop and can't be one** without retemplating: the scrim grid is hardcoded `Background="Transparent"` and the only knob, `SfNavigationDrawer.Opacity`, is `internal`. The drawer reads as floating by its own `CardBorderBrush` right edge instead.
    - **Clicking away closes the menu through that scrim**, whose `PreviewMouseLeftButtonDown` sets `IsOpen = false` — but only inside `if (flag)`. `flag` is set by `ToggleDrawer()` **and** by `OnIsOpenChange`'s open path, so `IsOpen = true` would work too; the app calls `ToggleDrawer()` anyway because it's the documented way in, it's what Syncfusion's demos use, and it clears the secondary drawer's state. Closing uses `IsOpen = false` directly, since those are unconditional closes and toggling would *open* a shut drawer.
  - **A `NavigationItem`'s icon goes in `Icon` (a real element), not `IconTemplate`, and the element has to center itself** — `HorizontalAlignment="Center" VerticalAlignment="Center"`, as every icon in Syncfusion's own `DisplayMode.xaml` demo does. The item template drops the icon into a fixed-size `ContentPresenter` with a negative left margin, so an unaligned glyph renders visibly off-center. (Still true of `Compact`/`Expanded`, but **no longer applies to `MainWindow`** since 2026-09-22: its glyphs sit in the app's own menu rows, aligned by `DrawerIconStyle`.) In compact mode the icon is the *only* thing visible for each destination, so every item needs one.
  - **`TabControlExt.CloseMode="Hide"` (Phase 16), not the default `Delete`, is what actually makes "close a tab, reopen it from the drawer" work.** The first implementation (Phase 15) left `CloseMode` at its default and had the drawer's click handler re-add the closed `TabItemExt` instance to `MainTabControl.Items` if it was missing (`if (!Items.Contains(tab)) Items.Add(tab);`). That compiled, selected the right content, and even looked right in a quick check — but a real close-then-reopen cycle (caught only once the user actually did it) showed the tab's *content* switching in correctly while its *header* never reappeared in the strip at all: `TabControlExt`'s header strip doesn't regenerate a header for a `TabItemExt` instance that has ever actually left `Items` under `Delete` mode, even when the exact same instance is re-added later. `CloseMode="Hide"` (`Syncfusion.Windows.Tools.Controls.CloseMode`, confirmed against `Syncfusion.Tools.WPF.xml`'s member docs) sidesteps the whole problem: a closed tab is only `Visibility.Collapsed`, never removed from `Items`, so `ShowTab` just needs `tab.Visibility = Visibility.Visible;` before selecting it — the instance was never invalid to begin with. This also fixed a smaller side effect of the `Delete`-mode workaround: a reopened tab used to land at the *end* of the tab strip (`Items.Add` appends) instead of back in its original position, since `Hide` mode never reorders `Items` at all. (Syncfusion also ships a fully built alternative for exactly this scenario — `TabListContextMenuOptions` including `ShowHiddenItems` on the tab-list dropdown menu, which lists and restores hidden tabs on its own — but the app keeps the `SfNavigationDrawer` as the single reopen affordance rather than offering two different ones for the same action.)
  - **The app starts with only Raw Materials, Sub-Assemblies and Products open** (2026-10-04, at the user's request). Reports, Production Plan and Price Simulator are declared `Visibility="Collapsed"` in `MainWindow.xaml`, the state `CloseMode="Hide"` leaves a closed tab in, so the menu's `ShowTab` opens them the same way and `gt`/`gT` pass over them until then. Each loads when first shown, since `LoadSelectedTab` only runs the shown tab's `LoadCommand`.
