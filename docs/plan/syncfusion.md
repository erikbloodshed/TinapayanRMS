# Syncfusion UI Framework

Moved out of PLAN.md on 2026-10-28, unchanged, to keep PLAN.md short enough to read. PLAN.md is still the overview and the source of truth, and this file is part of it. "The Syncfusion section" means [syncfusion.md](syncfusion.md); a section named without a file (Domain Model, Application Architecture, Reactive Costing Cascade) is [PLAN.md](../../PLAN.md)'s.


The app is styled with **Syncfusion Essential Studio for WPF 35.1.39**, licensed with a key the build compiles in from the `SYNCFUSION_LICENSE_KEY` environment variable (see Tech Stack), and Syncfusion's **Windows11Light** theme.

- **The theme is Syncfusion's official `Syncfusion.Themes.Windows11Light.WPF` package (Phase 16).** It depends only on `Syncfusion.SfSkinManager.WPF` and `Syncfusion.Licensing`, and it styles every Syncfusion control, so adopting a new control never needs theme work. It replaced a trimmed in-repo theme project (see "Why the theme is no longer trimmed" below) — briefly via a locally packed Theme Studio export, then this package, which is the same theme.
  - **Every Syncfusion package is pinned to the same version, currently `35.1.42` (from 35.1.41 on 2026-10-28; 35.1.40 → 35.1.41 on 2026-10-21).** The theme package requires `SfSkinManager`/`Licensing` at its own version, NuGet rejects the mismatch as a downgrade (`NU1605`), and Syncfusion doesn't support mixing versions across its assemblies — so upgrading any Syncfusion package means upgrading all of them together: they share the `SyncfusionVersion` property in `Directory.Packages.props`. The `34.2.2` → `34.2.7` upgrade (a patch within the 34.2 release) kept the same license key: no license popup at startup. The move to `34.2.9` (2026-09-26) was another patch within 34.2. Notes elsewhere in this file that name `34.2.7` record what was read from that version's assemblies at the time. A move to a new feature release (e.g. 34.3) needs a new key from the Syncfusion account.
    - **35.1.42's ChromelessWindow fix changes nothing for the app** (checked 2026-10-28, at the user's request: "I believe there is a fix for Syncfusion chromeless window on 35.1.42"). The release notes' one entry, "#I882322 - Fixed an issue in ChromelessWindow where caption buttons were not clickable", is a single line of the Windows11Light theme's `SyncfusionChromelessWindowControlTemplate`, the template for `UseNativeChrome="False"`: its Minimize/Maximize/Close panel now takes `IsHitTestVisibleInChrome` from Syncfusion's own `shell:WindowChrome`, as the rest of that template does, rather than WPF's. The app's windows use native chrome (`AppWindow`), whose `SyncfusionChromelessWindowWindows11Template` didn't change. Decompiled against 35.1.41, `Syncfusion.Shared.WPF` is otherwise identical, and `ChromelessWindow` itself hasn't changed since 35.1.37, so the three bugs `AppWindow` works around are all still there: the hook that marks `WM_DPICHANGED` handled (`ChromelessWindowDpi`), the content mask (`ChromelessWindowMask`) and the square window region (`DropWindowRegion`).
  - **The move to `35.1.37` (2026-10-02, a new major release) needed a new key.** The 34.x key failed `SyncfusionLicenseProvider.ValidateLicense` against 35.1.37, so the user generated a v35 key first. The only breaking changes in 35.1 are to `GanttControl`, which the app doesn't use, and the upgrade needed no code change. The private members that `ChromelessWindowMask` and `ChromelessWindowDpi` reach by reflection, the template parts the app looks up by name, and the behaviours those two classes work around are all unchanged in 35.1.37. The local Sample Browser is still the 34.2.2 install.
  - **One theme gap is patched in the app**: the theme's `SfTextBoxExt` style — unlike its `ComboBoxAdv`, `DoubleTextBox` and `DateTimeEdit` styles — never sets `VerticalContentAlignment`, so the text sits against the top of any box taller than its text (every one, at the 32px `SizeMode="Touch"` height the app used until 2026-09-15). `App`'s static constructor calls `Control.VerticalContentAlignmentProperty.OverrideMetadata(typeof(SfTextBoxExt), new FrameworkPropertyMetadata(VerticalAlignment.Center))`, changing the type's default so every instance (including future ones) is centred without a `Style` on the control; it must run before any `SfTextBoxExt` exists. Verified at runtime: `VerticalContentAlignment=Center`, value source `Default`.
  - **A second `SfTextBoxExt` theme gap: its text sat about 5px further right than the other fields.**
    - The theme's `SfTextBoxExt` template puts a fixed `Margin="10,0,0,0"` on `PART_ContentHost`. `DoubleTextBox`'s template uses 3px of padding instead.
    - Measured in an off-screen replica with the same theme and Touch size, a Name box's text started 13px from its left edge. A `DoubleTextBox` started at 8px and a `ComboBoxAdv` at 7px.
    - The template passes `Padding` (the theme sets -1) to the text presenter inside that margin. `App`'s `AlignTextBoxText` class handler, on `SfTextBoxExt.Loaded`, sets a left padding of -6, which moves the text to 8px.
    - That padding has to be a local value. The theme sets `Padding` through the control's default style (value source `DefaultStyle`), which outranks an `OverrideMetadata` default. A `SetCurrentValue` at `Loaded` was tried first and didn't survive.
    - A `Padding` set in XAML still wins.
  - **A third `SfTextBoxExt` theme gap: its watermark sat at the top of the box, 4px right of typed text.** The template shows `Watermark` in a plain `ContentControl`, whose default template honors neither `VerticalContentAlignment` nor `Padding`, so neither fix above reaches it. `App.xaml`'s `AlignedWatermarkTemplate`, set as the box's `WatermarkTemplate`, centers the hint and moves it 4px left. Measured with the same text typed and as the watermark (a true-size capture with the blinking caret filtered out by keeping each pixel's brightest value across frames), both now start 8px in and cover the same rows. Give it to any `SfTextBoxExt` with a `Watermark`; today that's the Raw Materials search box.
- **Core control set**: the app adopts `SfDataGrid` (lists/grids), `Syncfusion.SfInput.WPF`'s edit controls (`ComboBoxAdv`, `AutoComplete`, `MaskedTextBox`, `DateTimeEdit`, `CurrencyTextBox`, and others), `ButtonAdv`, `TabControlExt`, `DockingManager`/`Ribbon` for the app shell, and `SfChart` for charts (none in use since 2026-09-27). `TinapayanRMS.UI` takes its own `PackageReference`s (pinned to the shared Syncfusion version above) for exactly these.
  - **`DateTimeEdit`'s bindable date property is `DateTime`, not `Value`** (`Syncfusion.Windows.Shared.DateTimeEdit`, in `Syncfusion.Shared.WPF`) — it doesn't follow the `Value`-property convention `DoubleTextBox`/`IntegerTextBox` use. Confirmed by reflecting over the built assembly (`[System.AppDomain]::CurrentDomain.GetAssemblies() | Where Name -eq Syncfusion.Shared.WPF`, then `.GetType(...).GetProperties()`) rather than guessing again after the compiler rejected `Value`.
  - **Every editable `DoubleTextBox` binds `Value` with `UpdateSourceTrigger=PropertyChanged`** (2026-09-13). Without it the typed value reaches the ViewModel only when the box loses focus: the Syncfusion DoubleTextBox skill says to bind this way "for live updates", and Syncfusion's unit-converter showcase does.
    - It showed up as a dead click: Add Line (the BOM and Sub-Assemblies line editors) stays disabled until the quantity is positive, and a disabled button doesn't take focus, so the first click after typing a quantity neither committed it nor added the line.
    - It also kept the Purchase Cost Setup's cost per base unit and Products' Price Summary from updating as a number is typed.
    - Verified in the app on a new made ingredient (quantity starting at 0): with the cursor still in Quantity, Add Line was already enabled, and one click added the line. Typing 1234.5 arrived intact, with no reformatting mid-typing.
    - `Value` is registered on `DoubleTextBox` itself, so unlike the `SfTextBoxExt` default in `App.xaml.cs`, `OverrideMetadata` can't change the default; set it on each new binding.
  - **`ButtonAdv` icons use `IconTemplate` (a `DataTemplate`), not `SmallIcon`/`LargeIcon`** — those two want an `ImageSource` (a bitmap/vector image file), not a font glyph. With no `IconTemplate` set, the Windows11Light theme falls back to a generic placeholder glyph on every button (reported as "always shows the letter A"). Icons are **Segoe Fluent Icons, falling back to Segoe MDL2 Assets** (`App.xaml`'s `IconFontFamily` resource) — Windows' own icon font, so no extra icon package, and it matches the theme natively. Four reusable `DataTemplate` resources in `App.xaml` (`AddIconTemplate` U+E710, `SaveIconTemplate` U+E74E, `DeleteIconTemplate` U+E74D, `RemoveIconTemplate` U+E738) cover every button so far — reuse them (`IconTemplate="{StaticResource AddIconTemplate}"`, etc.) on new screens' buttons rather than repeating the glyph markup, and add a new named template here if a future screen needs a verb these four don't cover.
  - **`ButtonAdv.Label` defaults to the literal string `"Button"` when left unset** (confirmed by reflecting on `ButtonAdv.LabelProperty`'s metadata the same way `DateTimeEdit`'s shape was confirmed) — an icon-only button (`MainWindow`'s hamburger nav toggle, Phase 15, which was one until 2026-09-26) needs `Label=""` set explicitly, or that placeholder text renders squeezed into the button's icon-sized box ("the button has text that doesn't fit"). Even with `Label=""`, the empty `AccessText` keeps its 2px margin on each side, so an icon-only ButtonAdv's glyph sits 2px left of centre. **An icon-only button that must look like a title-bar or tab-strip glyph button is now a plain `Button` in the theme's `WPFGlyphButtonStyle`** (see the Back/Forward passage); a ButtonAdv's opaque, rounded hover can't be flattened to match. Every other `ButtonAdv` in the app already sets a real `Label` ("New", "Save", …) so this never came up before.
  - **`DropDownButtonAdv` is Add Sub-Assembly's button** (Products' Recipe Structure, 2026-09-20): one item per way a sub-assembly comes in, so the way is picked in the click that opens the form. It lives in `Syncfusion.Shared.WPF`, in `Syncfusion.Windows.Tools.Controls` beside `ButtonAdv`, so it needs no new `PackageReference` and takes the same `Label`, `IconTemplate`, `SizeMode` and `ToolTip`; the Windows11Light package styles it. Three things about it, from decompiling it and from Syncfusion's own `editor\Buttons\ButtonView.xaml` demo (no `syncfusion-wpf-*` skill covers it):
    - **Its `Content` *is* the drop-down** — it's a `ContentControl`, and whatever is put inside the element is what the pop-up shows. There is no `Items` or `DropDownContent`.
    - **It doesn't close when something inside the pop-up is clicked.** It closes the drop-down from its own `OnMouseLeftButtonUp`, which only runs for a click on the button itself: the handler it puts on the pop-up (`_dropdown_MouseLeftButtonUp`) forwards to the base `ContentControl` implementation and closes nothing, and a `ButtonAdv` inside has handled the click before it anyway. Each item's `Click` sets `IsDropDownOpen = false` in `RecipeStructureCard.xaml.cs`; the command still runs from the item's own `Command` binding.
    - **The pop-up holds `ButtonAdv`s, not the `ListBox` Syncfusion's demos put there.** A plain `ListBox` keeps the OS default look in this app, since `ApplyThemeAsDefaultStyle` is deliberately off (above), and its blue selection would fight the app's accent; and a `SelectionChanged` command would want `Microsoft.Xaml.Behaviors`, which isn't referenced. Stacked `ButtonAdv`s theme with everything else, reuse the `Add`/`Link`/`Copy` icon templates, and honour `HorizontalContentAlignment="Left"` (checked in the app), so they read as menu items.
      - **Each item is flattened with `Background="Transparent"` and `BorderThickness="0"`** (2026-09-21, at the user's request: the items read as raised buttons, not menu rows). The Windows11Light `ButtonAdv` template `TemplateBinding`s both onto its `ItemBorder`, so setting the two properties is enough — no `Style` and no template override, keeping App.xaml's rule that Syncfusion controls are only ever recolored through `Windows11LightThemeSettings`. Verified in the app on the secondary monitor: the drop-down shows three glyph-and-label rows with no chrome, and the header's own Add/Delete Sub-Assembly buttons are untouched.
      - **The theme's hover survives the transparent background but is nearly invisible on a flat item.** Its `IsMouseOver` trigger sets `ItemBorder.Background` by `TargetName` to an opaque `#FFF9F9F9`, which beats the `TemplateBinding`, so hovering still repaints the row — but against the pop-up's `#FCFCFC` that is a 3-level grey step, measured pixel-by-pixel in a screen capture (252,252,252 → 249,249,249). It also rules out the obvious fix of wrapping each item in a highlighting `Border`: the opaque `#F9F9F9` paints straight over it. A stronger hover would need a template override, which the convention above forbids, so the faint one stands for now.
  - **`SfTreeGrid` is the Products screen's Scaling tab** (`Syncfusion.UI.Xaml.TreeGrid`, in the `Syncfusion.SfGrid.WPF` already referenced; 2026-09-30): read-only, nested rows (`ChildPropertyName="Children"`), every level open. `GridHeaderHeight` and `GridKeyboardFocus`'s focus-rectangle handler are registered on it as on `SfDataGrid`: its header cell is a `TreeGridHeaderCell`, not a `GridHeaderCellControl`, and both are `SfGridBase`s.
    - **It must be themed on its own, never through the window** (`SfSkinManager.Theme` and `SizeMode` set on the `SfTreeGrid` in `ScalingCard`; found by the user the day it shipped: "after starting the program all the datagrids are white, not until I start editing one of them"). The Windows11Light `SfTreeGrid` dictionary merges in SfGrid's **unthemed** `Control/Themes/Generic.xaml`, whose implicit `GridCell`, `GridHeaderCellControl`, row and add-row styles are the same keys the `SfDataGrid` dictionary themes. SfSkinManager adds each control's dictionary to one root dictionary in the order it meets the controls (`AddRootResourceDictionaty`, deduplicated by `Source`), and the Scaling tab comes after every data grid, so the generic styles were searched first and every data grid in the app lost the theme: black lines, a bold add-row +. With the theme set locally, SfSkinManager merges the tree grid's dictionaries into its own `Resources`. Pinned by `TreeGridThemeScopeTests`, which also expects the inherited case to break, so it fails once Syncfusion's dictionary stops carrying the generic styles. **Any future `SfTreeGrid` needs the same local theme.**
  - **`SfTreeView` is the Products list** (`Syncfusion.SfTreeView.WPF`, 2026-09-26; see the Products screen's list below), **and since 2026-09-27 the Raw Materials list** (`MaterialListCard` over `RawMaterialTree`, built the same way, so everything below holds for both; see the Raw Materials screen's list), **and since 2026-10-07 the Sub-Assemblies list** (`SubAssemblyListCard` over `SubAssemblyTree`, the same again; see the Sub-Assemblies screen). What it took, found in its decompiled source and checked in the app:
    - **A row gets an expander whenever its children are an observable collection, even an empty one.** A product row therefore has no child property at all. The folder type alone gets a `HierarchyPropertyDescriptor` (`ChildPropertyName="Children"`), and the tree's own `ChildPropertyName` is left unset, as Syncfusion's `SelectionDemo` does for its leaf type.
    - **`AutoExpandMode` did nothing here.** It's applied only if the tree's view is built before the control has loaded. Whether a folder is open is kept on the model instead (`ProductFolderNode.IsExpanded`, the descriptor's `IsExpandedPropertyName`), which the tree reads and writes both ways.
    - **The tree reads `IsExpanded` as it changes, but not for a folder added back to its parent** (it expands the parent instead). A folder a search hid would come back closed, so `ProductTree.Refresh` raises `IsExpanded` again for each folder it re-adds (`AnnounceExpanded`).
    - **Nor can it open a folder with nothing in it** (`TreeCollectionView.ExpandNode` sets the node's `IsExpanded` to `ChildNodes.Any()`), and it doesn't look again when rows arrive under a folder it holds closed. Found when the open folders were first remembered between runs (2026-09-26): they came back closed, because `LoadCommand` merges the categories before the products, so every folder is made empty and filled a moment later. `Refresh` therefore also re-announces every open folder that has just got its first rows; this also covers a product moved into an open, empty folder. **The same holds for the top-level folders on the screen showing at startup** (found 2026-09-27 on Raw Materials, the first tab): its tree binds to the type folders before the first load has filled them, so they came up closed however they were set. `Refresh` therefore also re-announces an open top-level folder that was empty when it began (`RawMaterialTree` and `ProductTree` both).
    - **Removing the selected item from its collection drops it from the selection**, and `SelectedItem` goes null. A product moved to another folder leaves one collection and joins another, so the Products screen puts the row back on the product afterwards (`SyncTreeSelection`). `ProductTree.Refresh` also makes every removal before any insertion, so a moved product is never in two folders at once.
    - **Drag and drop:** `ItemDragOver`'s `DropPosition` only drives the indicator and the cursor. `ItemDropping` works its position out again, and `Handled = true` there stops the tree moving any node itself. `DropAsChild` is offered only over a row whose type has children, so over a product the list shows a line under it instead. A drag starts only on a move past the system drag distance while the pointer is still over the row pressed: a script driving it has to nudge within the row before moving away.
    - **Folders stay selectable.** Cancelling `SelectionChanging` for folders would trap the arrow keys, which move by selecting the next row, so a folder row would stop them dead. A folder picked just leaves the product showing.
    - **Several rows can be picked (`SelectionMode="Extended"`), so the screen binds `SelectedItems`, not `SelectedItem`** (2026-09-26). The tree takes the ViewModel's `ObservableCollection<object>` (`SelectedTreeNodes`) as its own and changes it as rows are clicked; the ViewModel changes it too, and the tree follows, setting its `SelectedItem` to the collection's first item itself (`SelectionController.UpdateSelectionProperties`). Binding both would loop: in Extended mode a `SelectedItem` set from outside is *inserted* at the front of `SelectedItems` without clearing it (`ProcessSelectionPropertiesChanged`), and from inside a `CollectionChanged` handler that throws, since the tree is a second handler. `SelectedTreeNode` is therefore the collection's first item, raised by the ViewModel; setting it picks that row alone, as a click does.
      - **A plain click adds the new row before removing the old ones**, so the first item only changes on the removal; a Ctrl+click appends, leaving the first (and the product showing) as it was. When a product row becomes first, picking its product leads to `SyncTreeSelection`, which finds the row first already and leaves the collection alone, as it must mid-change.
      - **A moved row is dropped from the selection too**, and with several picked the next one would become first and its product picked. So `ProductTree.Refresh` runs flagged (`TreeSelection.Quietly`, which sets `IsSyncing`), and after a move the rows picked are put back (`TreeSelection.Restore`). `TreeSelection` (2026-10-28) holds this for all three trees: the rows picked (`Nodes`, which each screen exposes as `SelectedTreeNodes`), `Pick` (the `SelectedTreeNode` setter), `BringFirst` (each screen's `SyncTreeSelection`) and `Restore`. Each screen keeps its own `TreeSelectionChanged`, which knows its leaf type and what picking one means.
      - **A drag carries every row picked** when the row pressed is one of them (`GetDraggingNodes`), and only that row otherwise.
    - **A row's right-click menu is `ItemContextMenu`, swapped per row in `ItemContextMenuOpening`** (2026-09-26; the approach of Syncfusion's `treeview/Views/EditingDemo.xaml`). The tree opens a row's menu only while `ItemContextMenu` is non-null, so a stand-in empty `ContextMenu` is set in XAML and `e.ContextMenu` replaced with the one built for the row (`ProductsViewModel.TreeMenuFor`, turned into `MenuItem`s by `ProductListCard.BuildMenu`). The tree sets the menu's `DataContext` to a `TreeViewItemContextMenuInfo` and opens it itself, then marks `ContextMenuOpening` handled, so the tree's own `ContextMenu` (also a stand-in, swapped in the tree's `ContextMenuOpening`) only opens on the empty space below the rows. From the menu key or Shift+F10 (`ContextMenuEventArgs.CursorLeft` and `CursorTop` both −1) the event is handled and the picked row's menu opened by hand under its row: a menu the context-menu service opens from the keyboard is placed by the service, over the row, whatever `PlacementTarget` and `Placement` it was given. **A right-click doesn't select the row** (`TreeViewItem.OnTreeViewItemMouseRightButtonDown` only focuses the tree), so `ItemContextMenuOpening` picks it first unless it's already among the rows picked. **The menu is themed explicitly** (`SfSkinManager.SetTheme` with the window's theme), like a dialog: it opens in a popup of its own, outside the window's tree.
    - **A toolbar under the search box** (2026-10-08, at the user's request, on all three lists): the empty-space menu's commands (`EmptySpaceMenu`) as icon-only `ButtonAdv`s (`SizeMode="Small"`, named in `Label` and `ToolTip`, `Focusable="False"`), bound with no parameter as the menu binds them. Products: New Product, New Composite Product, New Category…, Print All Products, Expand All, Collapse All. Raw Materials: New Raw Material, New Category (a `DropDownButtonAdv` offering the ingredient or packaging kind, closed by `NewCategoryItem_Click` as Add Sub-Assembly's items close theirs), Expand All, Collapse All. Sub-Assemblies: New Sub-Assembly, New Role…, Expand All, Collapse All. The icons are the App.xaml templates, with `NewFolderIconTemplate` (E8F4, the menus' `NewFolderGlyph`), `ExpandAllIconTemplate` (E70D) and `CollapseAllIconTemplate` (E70E) added for it. The title row's 12 px gap went under the toolbar, with 8 between them.
      - **Centring the glyphs** (2026-10-08, the user noticed they sat off-centre). A Small `ButtonAdv` gets `Padding` 2,0,4,0, and its icon box is 16 × 16 with the 14 px glyph in the top-left corner (a layout probe of the themed control found both). So each button sets `IconWidth`/`IconHeight` 14 and `Padding` 3,1,3,0; the 1 DIP at the top makes up for rounding at 125%. Raw Materials' `DropDownButtonAdv` ignores `Padding`, so its icon box is 16 tall with the folder at its bottom (a `ContentPresenter` over `NewFolderIconTemplate`). Measured on screen, every glyph lands within half a pixel of its button's centre.
    - **F2, Del and Enter reach the tree's `KeyDown`**: its own keyboard handling takes F2 only with `AllowEditing`, Delete only with `AllowDeleting`, and Enter only to end an edit, none of which is on (`SelectionController.HandleKeyBoardInteraction`).
    - **The theme draws the tree transparent and never reads its `Background`** (its template's grid, border, scroll viewer and row panel are all fixed to Transparent), so it showed the Latte Base card through it while the grids beside it are white. At the user's request (2026-09-26: "why isn't it white?") `ProductListCard` puts a Border behind it filled with `ListBackgroundBrush`, rounded as the tree's own border (4px). The theme's own brush, `ContentBackground`, can't be used from XAML: `{skinManager:ThemeResource ThemeKey={skinManager:ThemeKey Key=ContentBackground}}`, which Syncfusion's demos use, resolves only with `SfSkinManager.ApplyThemeAsDefaultStyle` on (`Theme.Helper` is created only then), and it stays off here. Checked by rendering `ProductListCard` off-screen with the app's resources and the theme: `#FFFFFF` inside the tree, Base around it.
- **`PrintPreview` is the Products screen's print pane** (`Syncfusion.Windows.Shared.Printing`, in `Syncfusion.Shared.WPF`, already referenced; 2026-09-27, see Print under the Products screen). It's the print backstage SfDiagram uses. On its left are Print (straight to the printer picked there), Copies, the printer and its properties, the page range, collation, orientation, the printer's own paper sizes, and margins. On its right are the pages, with page navigation and zoom. No `syncfusion-wpf-*` skill covers it, and no Sample Browser demo drives it with content of its own (SfDiagram's `PrintingService` hosts it), so what follows comes from decompiling 34.2.9 and SfDiagram's `DiagramPrintManager`:
  - **It's driven by a `PrintManager` subclass** (`Printing/ProductPrintManager`).
    - `ComputePageCount` (protected virtual) lays the printout out and sets `PageCount`.
    - `CreatePage(int, PrintPageControl)` sets the page control's `Content`. It's `protected internal`, so it's overridden as `protected override` from outside the assembly.
    - The page control's template lays the page out with its margins (a Viewbox, then the page's Border with `Margin=PageMargin`, then header, content and footer rows), so the content only fills the printable area.
    - `InitializePrint` swaps `PageWidth` and `PageHeight` for the orientation before it calls `ComputePageCount`. The pane calls it again (`PrintPreviewPanel.InValidate`) on every change of paper, margins or orientation. `OnPrintPropertyChanged()` (protected internal) does the same for a change of the subclass's own.
  - **The pane shows one page at a time.** It reuses one page control as it scrolls (`CreatePage(i, sameControl)`), and printing asks again with new controls, so every call builds new visuals: an element can only have one parent. `InValidate` returns early when `PageCount` is 0 and leaves the old pages showing, so a layout always has a page.
  - **`ProductPrintManager` overrides `PrintDocument`** (`protected virtual`), so the job goes out on the printer's own ticket.
    - The base class prints on the ticket the pane builds (`GetCustomizedPrintTicket`), after swapping its named paper for a bare size. Microsoft Print to PDF can't take that ticket: its filter pipeline stops (event 824 in the PrintService log, "The print filter pipeline process was terminated", 0x80040004) and the PDF comes out empty, 0 bytes. The same pages printed on the printer's own default ticket, both through `PrintQueue.AddJob` and through a `PrintDialog`, which is how the ticket was found to be the cause.
    - `JobTicket` takes the printer's own ticket (`UserPrintTicket ?? DefaultPrintTicket`), puts the pane's orientation, copies and collation on it with the printer's own paper nearest the page (to 2 px either way), and has the printer validate the result (`MergeAndValidatePrintTicket`).
    - The base class also swallows every exception, so a failed print showed nothing. The override logs the failure and raises `PrintFailed`, which the Print tab (`ProductPrintView`) shows in a message box. A cancel where the printer asks something, such as Microsoft Print to PDF's file name, stays quiet.
    - Only Microsoft Print to PDF has printed it so far: the user's terms for the in-app check ruled out a real printer.
  - **It's themed like everything else, but the theme has to come first.** The Windows11Light package has its style (`printpreview/printpreview.baml`), applied with `SfSkinManager.SetTheme` on its window, as for any dialog. `Syncfusion.Shared.WPF`'s own generic template (`Print/themes/generic.baml`) covers the pages printed outside the window.
    - **The window is themed before the pane goes in.** A `PrintPreview` already in the window when `SetTheme` reaches it throws a `NullReferenceException` from `OnApplyTemplate` on its first layout, and the first Print in the app crashed that way. SfDiagram's own print window themes itself first too. The pane was in a window of its own then (`ProductPrintWindow`, whose constructor called `SetTheme` before creating it); it's on the main window's Print tab now, which the app themes at startup, before the pane is ever made.
    - `PrintPreviewThemeOrderTests` opens a pane both ways round and expects the wrong order to throw, so it fails once Syncfusion fixes the pane. SfSkinManager keeps the dictionaries it loads for a theme with the thread that loaded them, and a window themed on a second thread fails with "The calling thread cannot access this object because a different thread owns it" (a `XamlParseException`). So **every test that themes a window runs on one shared STA thread, `StaThread.RunThemed`**, which also registers the app's theme settings (`App.ThemeSettings`, the accent and the 14 px text), so a test measures what the app shows.
  - **It's fitted to the app's 14 px text** (`Printing/PrintPaneFit`, 2026-09-27, at the user's request: "we can increase the width of the left pane. we can also increase some of the controls to fit the font size"). The theme sizes the pane for its own 12 px, so at 14 px "Copies:" lost its colon, the Print caption lost its foot, the two-line dropdowns ran their second line into the edge ("Left: 2.5 cm Right: 2.5 c…") and the page box under the pages clipped its number.
    - The theme's resources can't be reached from the app's XAML (see "the Products tree's white" above), so a copy of its templates would lose their styles. Instead, once the pane is loaded (its templates applied, before its first frame), `PrintPaneFit` changes the parts it finds by name: the settings column 250 → 340 px (`OptionsWidth`), each dropdown 220 → 300 px and as tall as its item, the Copies, From and To boxes 60×24 → 76×30, the Copies label and the Print caption sized to their text, and the page box 24×16 → 40×26 with "/ n" beside it as wide as it needs. A part it can't find is logged and left alone, for a Syncfusion template that has changed. (The dialog it was in then grew by the same 90 px; it's a main tab now.)
    - The dropdowns get item templates of their own (`Printing/PrintPaneTemplates.xaml`, loaded as a class so tests can load it too): the theme's are 43 px rows for 12 px text. Each item is an icon and a name, with a second line where the theme has one (what the page range means, the collation order, the paper's size, the margins), at least 44 px tall and growing with its text.
