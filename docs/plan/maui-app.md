# The app: .NET MAUI Blazor Hybrid

Part of [PLAN.md](../../PLAN.md). The app's screens are Blazor components with Syncfusion Blazor, drawn in a .NET MAUI window's WebView2, over the WPF app's ViewModels, rules and database. Its projects are `TinapayanRMS.Components` (the screens, a Razor class library), `TinapayanRMS.Maui` (the window) and `TinapayanRMS.Presentation` (the ViewModels). It ran beside the WPF app for a day, and replaced it the same day (below). The branch it was built on, `maui-blazor-hybrid`, became `main` on 2026-11-08, and the tag `wpf-final` marks the last commit with the WPF app.

## Decisions kept from the web app

- **Blazor components with Syncfusion Blazor, drawn by .NET MAUI Blazor Hybrid.** The components run in the app's process, beside the ViewModels and the rules, with nothing listening on the network: the web view serves the app's own files to itself. The licence key covers Syncfusion Blazor.
- **The ViewModels were kept, not rewritten.** They referenced no WPF type, so the costing, undo, merge-on-refresh and tree behaviour the WPF app is verified with is what this app runs.
- **ViewModels are scoped, not singletons.** In Blazor Hybrid a scope is a page the web view loads, so the screens keep their state and edits while the app runs, and a reload (after a restore) builds them afresh, as the WPF app restarts.
- **What each WPF View did became a component's job**: dialogs for the confirmations, toasts for the messages, and Windows' own file dialogs for files (`IFileDialogs`).
- **What didn't port, and what replaced it**: printing became a print-styled page and the web view's print dialog; the grid behaviours became `LineGrid` and `SfGrid`; Back and Forward became an address per record; the Vim keys' input handling became `vim.js`, over the WPF app's key table, command line and hint labels, kept as C# (`Components/Vim`).

## The window

- **Chromeless, as the WPF window is** (the user's, 2026-11-07). Windows draws no title bar; the page draws it (`Layout/TitleBar.razor`), 32px in the card colour: the menu toggle and the heading on the left, and on the right the Vim keys' mode, Find, Back, Forward, then Minimize, Maximize (Restore Down while maximized) and Close, as 40×32 buttons (their glyphs drawn in 1px lines, inline SVG) with a faint wash on hover and Close red. The window keeps its border, so Windows still resizes it from every edge and corner and draws its rounded corners and shadow.
  - **How**: `WindowsWindow.Configure` calls `OverlappedPresenter.SetBorderAndTitleBar(true, false)` and collapses the title bar (`TitleBarHeightOption.Collapsed`). The Windows App SDK does "no title bar" by extending the content over a title bar it hides, its Minimize, Maximize and Close with it, and keeps the window's caption style (`WS_CAPTION`), for snapping and the taskbar.
  - **MAUI's own title bar row is hidden by reflection.** MAUI keeps a 32px row of its own, with the window's title in it, above the page of any window with a caption, and decides again at every change to the window's style (showing it, maximizing, restoring). Its switch, `NavigationRootManager.SetTitleBarVisibility(bool)`, is internal; `AppWindowChrome.AfterStyleChanged` calls it with `false` after each `WM_STYLECHANGED`, once MAUI has dealt with it (MAUI's `OnPlatformMessage` lifecycle event). If a MAUI update renames it, the log says so and the row shows above the page's title bar. Tried first and not enough: turning the content's extension off (`SetBorderAndTitleBar` turns it back on) and the collapsed height alone (MAUI sizes its row to its title template).
  - **The bar is the window's caption to Windows.** `app.js` (`watchTitleBar`) sends the bar's and its buttons' places, in device pixels, whenever any of them moves or changes size; `AppWindowChrome` gives Windows the gaps between the buttons as the caption (`InputNonClientPointerSource`, `NonClientRegionKind.Caption`; `DeviceRect.Caption` works the gaps out). So dragging the bar moves the window and snaps it to an edge, a double-click maximizes or restores it, and a right-click opens the system menu, all done by Windows as on any title bar. Only caption rectangles are set, not the whole bar with its buttons passed through: MAUI clears the passed-through rectangles whenever its row changes size.
  - **The buttons are the page's.** Minimize and Maximize call the window's presenter; Close posts `SC_CLOSE`, as Windows' own Close button does, so the window's closing asks about a form's unsaved changes first. Back and Forward call the web view's history, and are enabled from its Navigation API (`navigation.canGoBack`), which follows every move between addresses.
  - **Checked** by asking the window's hit test (`WM_NCHITTEST`) at points on the bar: the gaps answer `HTCAPTION`, the buttons and the page `HTCLIENT`, the top edge `HTTOP`; after a maximize and a restore too.
- **Closing the window ends the process there and then** (`App`: `Environment.Exit` once `BackgroundWork.Stop` has stopped the backups and flushed the log). Left to end by itself, the process stayed 17 to 22 seconds after the window had gone, in native teardown once the app's own code was done (its `ProcessExit` never ran), and a start in that time found it running (`SingleInstance`) and exited with nothing to bring forward. Found while dropping the WPF app; the web repo's app likely does the same.
- **It opens at 1400×800, in the middle of the work area of the monitor the mouse is on**, no larger than it, as the WPF window does (`StartupCentering`). It's moved onto that monitor first, so it has that monitor's scale before it's sized. The web app opened maximized.
- **The title Windows shows** (the taskbar, Alt+Tab) is the WPF window's, `MainWindowViewModel.Title`; the icon is the WPF app's `.ico`, the `.exe`'s icon.
- **Closing the window asks about unsaved changes** (Save, Don't Save or Cancel): the window's `Closing` holds it open and asks the screen's own question through `UnsavedChangesGuard`.
- **One copy per folder**: started again, it brings its window forward (`SingleInstance`). The WPF app (run from `wpf-final`, or installed) keeps to one copy of its own, so the two can be open at once.
- **Startup**: the window opens at once, with no wait screen: a database that can't be reached shows on each screen's load, as the WPF app's screens show it. `StartupTasks` (started by `BackgroundWork`, stopped with the window) warns in a banner when the database lacks this version's migrations, and takes the day's automatic backup, checked hourly.
- **A restore loads the window's page afresh**, which builds every ViewModel anew, as the WPF app restarts.
- **Syncfusion's telemetry is off** (`MauiProgram`, first thing: `Syncfusion.Telemetry.Telemetry.Disable()`), as the WPF app had it since 2026-11-06 at the user's request. Syncfusion Blazor's grid and charts report their use through the same `Syncfusion.Telemetry` package (`GridTelemetryHelper`), and the port had left the call out: found while dropping the WPF app. The web repo's app still reports.

## View state and backups

- **The app keeps its own view state**: `%LocalAppData%\TinapayanRMS\Maui\view-state.json`, beside the WPF app's `view-state.json`, which an installed WPF copy, or one run from `wpf-final`, still writes. Each app reads its file once and writes it whole (`JsonViewStateStore`), so two sharing one would write over each other's changes. The first time it runs for a Windows user it starts as a copy of the WPF app's (`ViewStateSeed`), so it opens with the lists' folders as they were left, the Vim keys as they were set, and the backups' second folder; from then on each keeps its own.
- **The backups are the WPF app's folder** (`DatabaseBackups.DefaultFolder`, in ProgramData), since it's the same database, so either app lists, restores and takes the same backups. Each takes the day's automatic backup only when the folder has none for the day, so with both open the day still gets one.
- **Settings → Database's Open Folder is the WPF tab's**, which the web app, whose folder was the user's own, had left out: File Explorer on the backups folder (`IFileDialogs.ShowFolder`, `explorer.exe` as the WPF app started it). The folder is made first if no backup has made it yet, as a backup makes it (`IDatabaseBackups.EnsureFolder`), so it has the entry that lets every Windows user in.
- **Its log** is `%LocalAppData%\TinapayanRMS\Maui\logs\tinapayanrms-<date>.log`. It holds warnings and errors, and nothing at Information on a start that goes well.

## How it's built

Most of this was found and measured in the web app, where a "circuit" was a browser tab's connection; in the MAUI app the page the web view loads takes its place, and its dispatcher is the window's UI thread.

- **A screen is a page with an address**, and a record screen also takes a record (`/products/42`), so Back and Forward work. `/` goes to Raw Materials.
  - **A page acts on an address once, when it arrives.** As the screen opens, the record is given to the load, which opens it at its end (`OpenProductOnLoad` and its like); a changed address opens its record there and then. New drops a record still waiting: otherwise New clicked during the load had the record load over the new form, and a name typed into it was saved as the old record's.
  - **A screen reloads each time it's opened**, and its ViewModel lives as long as the page, so unsaved edits survive a visit to another screen.
  - **Nothing that outlives a screen keeps hold of it.** Each visit draws the screen afresh, while its ViewModel and the services last as long as the window. So whatever a screen or one of its parts hooks into them, or into the ViewModel's rows, it lets go of in its `Dispose`. `ScreenBase` disposes its own subscriptions and the page's (`AddSubscription`); `FolderTree` and `LineGrid` unhook their rows; the title bar, Find, the Vim keys and the undo keys dispose their `DotNetObjectReference`, and their JavaScript registrations remove their listeners. What a page lends its ViewModel goes back the same way: the Price Simulator's table (`ShowProductsFrom`). The ViewModel used to keep that as a lambda, holding the last page, its grid and its 70 rows' 1,065 cells (about 245 KB) while any other screen was showing.
    - **An `SfGrid`'s rows don't notify.** Syncfusion lets go of a grid's `DataSource` when the grid goes, but it hooks the `PropertyChanged` of a row added to that list after the grid bound without keeping the handler, so it can't unhook it, and each such row the ViewModel keeps would hold the grid. No grid's rows here notify.
    - **Blazor keeps the page shown before until the next move**: a component keeps the frames of its last drawing until it draws again (`ComponentState`'s next render tree), so the layout holds one page past its time.
    - **Measured** after Syncfusion's memory management guide, at the user's request (2026-11-08): heap dumps of the window after 1, 11 and 21 rounds of the same 20 addresses (every screen, a record of each, Print and every Settings page), ending on Settings → Keyboard. Every screen, grid and ViewModel was at the same live count after 220 visits as after 20, the Price Simulator's page and grid being the only ones left over, and they went with the fix. The live heap grew 1.7 MB between the first round and the eleventh, all of it one-off caches (System.Text.Json's metadata for JS interop, reflection's emitted invokers, DI's call sites), and not at all over the ten after: 51.3 MB at 11 rounds and at 21.
- **The screens have the WPF window's tabs, a strip under the title bar.** Raw Materials, Sub-Assemblies and Products are open from the start; Reports, Price Simulator and Print open when their screen is first shown; any tab closes with its ✕ but the last. A tab is a link, and the address decides which is marked (`ScreenTabs`). Closing a tab only takes it off the strip: the screen keeps its record and its edits. **Settings has a tab** (the web app's choice, at its user's request), where the WPF app has a Settings dialog; one tab stands for all its pages. `/print/preview` has no tab, as it's a window of its own in the WPF app.
- **`ScreenBase<TViewModel>`** is what every screen inherits. It answers confirmations with a dialog, shows the messages as toasts, runs the load, and redraws when the ViewModel, any of its lists, any command's `CanExecute`, or any of its parts (`ProductsViewModel.Costing`, `Packaging` and the rest) changes, subscribing to every collection and command property by reflection, once.
- **A form with unsaved changes is never left with them.** `ScreenBase`'s location-changing handler asks before any move to another address, Back and Forward included, and stays on Cancel; the window's closing asks the same through `UnsavedChangesGuard`; and the web view's own leave warning covers a reload while the form holds changes. The WPF app's `ScreenNavigator` is in Presentation, but nothing here uses it: it's built round the WPF tabs and history.
- **A screen is drawn once for changes that come together.** A load sets hundreds of properties in a row, and a redraw asked for on the dispatcher is drawn and sent to the web view there and then: picking a product drew its whole screen 445 times and sent 7.2 MB, in 1.4 seconds. **`RedrawGate`** queues one redraw behind the work in hand, and every request until it's drawn finds it queued, so a redraw follows a change by one turn of the dispatcher, not by a timer. Measured in the web app: a product's pick went to 87 ms, 14 redraws and 138 KB. `ShouldRender` leaves a redraw to the one queued. What has to follow the drawing asks for it at once (`RedrawNowAsync`): New's cursor going to the name, and undo putting the cursor back.
- **The `Interaction`s' handlers** sit in `MainLayout`, one set per page: `ConfirmationHost` (an `SfDialog`) and `PromptHost` for a name asked for. The file dialogs are Windows' own (`IFileDialogs`). `ScreenLinks` turns one screen's request to open another into navigation.
- **Typing: nothing ever writes into a box that has the cursor.** A redraw for an earlier keystroke overwrote the ones typed since ("zz web test material" arrived as "zt material"), so `TextField` and `NumberField` keep their own text while focused and take the ViewModel's value again once left. Syncfusion's text boxes are only used where nothing follows the typing (Settings' forms).
  - **A number box's or picker's text is selected as it takes the cursor**, in the page (`app.js`), so the first key replaces it. When the cursor comes in by a click, it's selected again as the click ends, since the click puts the caret where it lands; only then (the pointer was down on the box as it took the cursor), so a click in a box the cursor came into by Tab or the Vim keys puts the caret where it's clicked.
  - **Numbers show with a point before the decimals and commas between thousands, whatever the Windows region** (`NumberCulture`, applied first thing in `MauiProgram`): the region's culture with those number symbols, its dates and names as they are. `NumberField` and `VimExpression` read numbers that way, and in a region with a comma before the decimals a box had shown `12,50` and read `12,5` as 125.
  - **`NumberField` passes a number on as it's typed** once it reads back the same (`2.5`, not `2.` or `2.50`), and on leaving otherwise, and takes no number beyond 999,999,999.9999 either side of zero (`Largest`): 21 digits in a recipe line's grams overflowed a `decimal` in an Rx subscription, which nothing can catch without detaching it.
  - **A box is given up when another record takes the form's place under the cursor** (`IUndoRecorder.FormVersion`): the box is replaced by a fresh one with the record's own value, so a name typed into it isn't saved as the other record's. Not for the same record loaded again, as a Save does. A list's search box isn't one of the form's.
  - **A number box left holding text it didn't take is drawn twice**, as typed and then as its number, so the box doesn't go on showing "abc" over a value that's still the old one.
- **`PickField` is bound by index**, since `SfComboBox` reads an enum's first value as empty.
  - **It filters on every key** (`DebounceDelay` 0). Syncfusion's default held each filter back 300 ms after the key, so a recipe line's ingredient picker took 330 to 470 ms a letter to show its list and fill-in, when it had one (measured in the window, 2026-11-08, at the user's word that it wasn't responsive); with none, 22 to 89 ms. The window was busy for only about 20 ms a key either way: the rest was the wait.
  - **It lists the best match first and highlights it, and writes nothing into the box.** Each item's `Rank` (`RecordNameMatch.Rank`: the name itself, then starting with the text, then a word starting with it, then holding it) is set in the `Filtering` event, before the combo box filters, and `PickComboBox`, the app's own `SfComboBox`, sorts by it in `GetQuery` and puts the highlight (`e-item-focus`) on the first item after each filter: Syncfusion's goes to the item the box held, where that's still listed. Enter takes the highlighted item; Tab, or a click elsewhere, takes it when the combo box settles typed text that names no item (`CustomValueAsync`, which `PickComboBox` reports as `LeftWithTypedText`); after Escape it doesn't, so the pick stays. The arrow keys move the highlight, the first press taking the highlighted item into the box (Syncfusion's rule). The theme's highlight, `#f5f5f5` on the list's white, couldn't be seen: `app.css` draws every highlight alike, in the pale Sky (`--accent-soft`) the screens mark a selected row with, in the list's own ink and weight, and the item Enter takes (`e-item-focus`, or `e-active`: the item held as the list opens, or the one the arrow keys moved to; one item at a time) also with a deep Sky bar. The item under the mouse (`e-hover`) has the tint alone. As the list opens on an empty box the first item has the bar: Enter takes it, but Tab only closes the list.
  - **It keeps its own pick while it has the cursor.** Text rubbed out, where a pick is needed (a line's ingredient), is a pick refused, and the box used to be drawn again at once with the old pick, which wrote it back under the cursor: Backspace after the fill-in it then had brought back the line's ingredient and nothing more would delete. Now the old pick shows again once the box is left.
  - **On a table's lines it's a look-alike until its cell has the cursor** (`Deferred`, every `LineGrid` picker): a box with the item's name and the arrow, wearing the combo box's own classes, so it's drawn the same to the pixel. As it takes the cursor (a click, Tab, Insert Line, the Vim keys' moves and labels) or its arrow is pressed, the combo box is made beside it, unseen and taking no clicks, and once it's set up (`Created`) the cursor is handed to it in the page (`tinapayan.handOverPick`): what was typed into the look-alike meanwhile goes with it and is filtered on (the box's `input`, then a `keyup`; no `keydown`, which the Vim keys would read as a command), and the Vim keys' mode stays as it was (`focusKeepingMode`), but for a press on the arrow, which starts typing as a press on the combo box's own did. A look-alike that lost the cursor before then stays. Leaving puts the look-alike back, from the combo box's `Blur`: what the combo box still does after it, a float label's size in its script, finds nothing to do. One combo box a line, each setting up its whole list and its script as it was drawn, was most of the window's time opening or picking a record: measured on 2026-11-12 (Release builds, off-screen, the UI-thread probe, medians of 11), opening Sub-Assemblies on a 13-line recipe held the window 92 ms before and 24 after, picking another 56 and 7, opening Products 122 and 51, picking another product 57 and 12, the longest single hold 26 to 32 ms before and 4 to 21 after. The record shows as soon as before: what's gone is the setting up after it showed.
- **`LineGrid` is every table typed straight into**: a plain table of fields, one keyed row per line, every cell live at once, which `SfGrid`'s cell-or-row editing isn't. The add row is a draft from the ViewModel's factory that joins the lines on its first change; lines and draft are one keyed loop; `IsBlank` keeps a draft the screen itself changes out of the lines. **Insert Line** is `LineGrid`'s too. **`PickGrid`** is a list to pick one record from (an `SfGrid`); the reports use `SfGrid` directly and keep each Windows user's sort, filters and columns in the view state.
- **An `SfGrid` draws all its rows again for each change to the list it's given.** An `ObservableCollection`'s `Clear` and each `Add` are a change apiece, and DynamicData's `AddRange` adds a row at a time, so Reports, filling its five tables that way, drew growing tables some 330 times a visit: about 9 seconds a visit, the window held for 7 of them, 4 without a break (2026-11-07, measured in the window with a probe timing how long the UI thread kept a posted no-op waiting, and a trace: the time was Syncfusion's `GridRow` drawing). **A table an `SfGrid` draws is a `TableRows<T>`** (Presentation), whose `ReplaceWith` replaces every row in one change, a single Reset, as Syncfusion's own docs advise ("Add a range of items into ObservableCollection"). **Reports' tabs build their tables when first shown** (`ContentLoad.Demand`), so the page opens with one table to draw, not five drawn twice (the last visit's rows, then the new). Following Syncfusion's performance guide, at the user's request: **rows that show the same as before are no change** (`ReplaceWith` keeps its own), so a visit that finds nothing new draws its table once, and **each grid is in a `SelfDrawn`**, which keeps the page's own redraws (a button's state, a toast, any grid's event) from taking every grid through its drawing; the guide's per-event `PreventRender` spares only the grid that raised the event. Its row virtualization was tried and left out: with `Height="100%"` it drew Syncfusion's default 12 rows and left the rest of the view empty until a scroll, and for these hundred-odd rows it would only move the drawing into scrolling, which costs the window nothing now. A visit now settles in about 0.75 s, the window held for about 0.45 of it; a filter, a pick or a first tab of up to 11 rows holds it for nothing measurable, and a first tab of 107 to 129 rows for about 0.1 s.
- **`FolderTree` is the app's own, not `SfTreeView`**, because the ViewModel already owns the nodes, which folders are open and the rows picked, all kept through a refresh.
  - **A row's name is typed in place, as in a file explorer, by a `TreeNameBox`** the screen's row template draws in place of the title (all three lists, since 2026-11-09). It wraps a `TextField` outside the form's undo (a null `IUndoRecorder`), keeps what's typed and gives it back only on Enter, or on leaving with it changed (`OnCommit`), or gives up on Esc, or on leaving with the text it started with (`OnCancel`, the cursor staying where it went); the first of them counts, as leaving follows Enter. **Leaving it unchanged gives up** (since 2026-11-10): a new row starts with what a new one is called, and given back on a click on the form or another row, it had saved a product called "New product" there and then; for a rename the screen took the name it had for an Esc anyway. Enter still names a new row by its starting text. It takes the cursor with its text selected. **A cursor taken away before the box is used (typed or clicked in), in its first second (`SettleTime`), with no mouse press anywhere in the page since the box showed, is taken back** (`tinapayan.showNameBox` notes when it showed, `takeFocusBack` compares the page's last press) rather than counted as leaving: whatever started the naming can take it as it closes, pressing nothing, New's drop-down putting it back on its arrow, or the dialog asking about unsaved changes putting it back on New. Counted as leaving, it had named the new row by the text it started with ("New ingredient", in the window; on Products it would have saved "New product"), and now it would take the new row away. A press since it showed is the user moving on (another row picked, a field clicked), and the box closes at once: taken back then too, at first, it stayed open on the old row while the new one was picked, which the user saw as the rename not ending. Its keys, clicks and right-clicks stop at it, so the tree doesn't move, pick or open a menu as it's typed into, and the web view's own menu (cut, copy, paste) opens in it. After Enter or Esc the cursor goes back to the tree (`tinapayan.focusClosest`). `FolderTree`'s **`IsEditing`** says which row has the box: that row isn't dragged (a draggable row keeps the mouse from selecting text in it), and a click, F2 or Del on it does nothing. A refused name comes back as a new `TreeNameEdit`, which keys a new box.
  - **A slow second click on the row picked does what F2 does**, as in File Explorer, on the rows a screen names (`RenamesOnSecondClick`; the three lists' records): a plain click anywhere on the row picked alone already, not a double-click's second (`Detail` 2), renames after a wait (`SecondClickWait`, half a second) that another click, a key, a drag, a menu, the cursor leaving the tree (`focusout`, since 2026-11-10) or the tree going calls off. Left running, a field clicked straight after lost the cursor to the name box, and what was typed there renamed the record. A double-click renames nothing (the user's choice). It counted only on the name text at first (the row's template in a span whose click noted it), which is short beside the row: the rename came and went with where the click landed, so the whole row counts.
- **`MenuButton`** closes its list once a command is clicked, which `SfDropDownButton` with custom content doesn't do. **A button bound to a command is a `CommandButton`**; one for a command with a parameter or a screen's own action is an `ActionButton`.
- **An `SfTab` is given no `Height`**; the `details-tabs` CSS sizes the tabs. With a `Height`, its script read a strip not yet drawn and threw, which ended the page.
- **The page loads the scripts of only the Syncfusion components the screens use** (`wwwroot/syncfusion.js`), following Syncfusion's best-practices page, at the user's request (2026-11-08). Syncfusion's all-components script, `syncfusion-blazor.min.js`, is 6.95 MB, every component Syncfusion makes, and the page ran all of it before Blazor started; the screens' 14 components need 26 of its files, 1.64 MB. They're loaded as Syncfusion's per-component scripts load theirs, through the loader in Syncfusion's base script (`sfBlazor.loadDependencies`), which fetches each component's scripts and those they need. **Blazor's start waits for them** (the app's JS initializer, `TinapayanRMS.Maui.lib.module.js`, whose `beforeStart` Blazor awaits): nothing in Syncfusion waits for its scripts (its service counts them as in from the start), and the window starts Blazor once the page is parsed (`WinUIWebViewManager`, at `DOMContentLoaded`), so a component whose script wasn't in yet would throw as it started, which ends the page, or quietly do without. `index.html` starts the loads in its head, and they're in by the time Blazor starts. `SyncfusionScriptsTests` keeps the list to the components the Components assembly names, and to the loader in the package at `SyncfusionVersion`. **Measured in the window** against the all-components script and the full theme, 8 alternating Release starts of each and 40 reloads: the web view's JS heap went from 21.2 MB to 9.2 MB at every start; its main thread's work to the first screen from about 369 ms a load to 265 (lower in all 8 pairs), with Syncfusion's scripts 48 → 26 ms, the theme's parsing 60 → 29 ms and style recalculation 58 → 35 ms; `DOMContentLoaded` 783 → 478 ms at a start (lower in 7 of 8 pairs); and the publish is 8 MB smaller. The time to the first screen at a start moved by less than the laptop's own noise (2.2 to 12 s for the same build), so the start isn't noticeably faster. Every screen and every component's popup, shot in both, came out the same to the pixel.
- **Theme**: Syncfusion Blazor's Fluent 2, its lite file (`fluent2-lite.css`; the build leaves the package's other themes out): `fluent2.css` without the rules for Syncfusion's bigger, touch size (`e-bigger`, 3,542 of its 22,353 rules; the others are the same, rule for rule), which nothing here uses, 4.31 MB rather than 5.48. Over it, `app.css` sets Syncfusion's colours to the WPF app's palette (Catppuccin Latte, accent `#04a5e5`). Glyphs are Segoe Fluent Icons, at the WPF app's code points (`Shared/Glyphs.cs`). **Controls are 24px tall**, as the WPF app's are (`--control-height`); an `SfGrid`'s `RowHeight` says 24 itself, and a grid whose headings wrap keeps 20px a line for them.
- **A record header's title keeps 200px for the name**: where the buttons would leave it less (Products, at the window's 1400 wide), they go under it, still on the right, rather than the name shrinking to its first letter.
- **Printing**: `PrintDocument` renders a printout as HTML, `print.css` lays it out for paper and hides the app around it, and WebView2's own print dialog prints it (`IPagePrinter`). The preview draws a sheet for each part that starts a page.
- **The Vim keys** are read in the page (`vim.js`), in the capture phase, before any control sees them, from the key table the components send as the keys are turned on (`VimKeymap`), so the keys and the cheat sheet can't drift apart. Everything is done as a hand would: a key moves the cursor, clicks, or presses the arrow it stands for. `gt` and `gT` click the next and previous tab; `H` and `L` are Back and Forward; Ctrl+J and Ctrl+K move through a list (Ctrl+N is the web view's); Ctrl+R is taken from the web view for redo while the keys are on. While a dialog is open the keys are for it. A box typed into inside a tree (`TreeNameBox`) is a field, not the tree: its keys are text.
- **Undo's keys** leave the field with the cursor first, so what's half-typed lands, then put the cursor back once the screen has redrawn.

## Checking it in the window

bUnit has no web view, so focus, typing, drag and drop, printing, the dialogs, the Vim keys and the title bar only show in the app's window.

- **The `run-tinapayanrms` skill** (`.claude/skills/run-tinapayanrms/`) does it: `driver.ps1 launch` starts the built app with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`, and `driver.js` attaches Node's `playwright-core` (installed on first use into `%LOCALAPPDATA%\TinapayanRMS\dev\playwright`) with `chromium.connectOverCDP`, so its clicks, keys and screenshots go to the page, not the mouse or the screen. The window opens on the monitor the mouse is on, which may be the one the user is working on: keep a check short.
- **The window itself** (the frame, MAUI's row) isn't in the page's screenshot: `driver.ps1 window` captures it with `PrintWindow` (flag 2, for WebView2's content), and `driver.ps1 hit` asks its hit test (`WM_NCHITTEST`) for the caption. Both read the window only, whatever is in front of it.
- **Windows PowerShell's web requests look for a proxy first**, which can take longer than a short timeout: the driver tests the debugging port with a TCP connect, not an HTTP request.
- **It works on the dev database**, the user's data. Never click Save, Delete, Move or Restore in a check; whatever a check creates, delete afterwards. The first start also copies the WPF view state and may take the day's backup, as the WPF app's start does.
- **The first visit to a screen is slower in a Debug build**, the code's first run. Reports took 10.5 seconds the first time after a start, but most of that was its grids drawing their rows again for each row added ("How it's built"): since 2026-11-07 its first visit shows its rows in under a second and settles in one to two.
- **A minimized window doesn't draw**, so the driver's clicks and shots wait and time out (`waiting for element to be visible, enabled and stable`), while the page's script and the screens still run. `IsIconic` on the window says so; the window can still be closed with `WM_CLOSE` (`Process.CloseMainWindow`).
