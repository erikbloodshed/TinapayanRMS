# TinapayanRMS — Project Guide & Build Plan

Product recipe management & costing app for Tinapayan Festival Bakeshoppe. Tracks ingredient expenses, recipe/product margins, and cascades ingredient and packaging price changes up through sub-assemblies and finished products automatically.

## At a glance

- **What it is**: a Windows desktop app over PostgreSQL 18 through EF Core, for one bakeshop: a .NET MAUI Blazor Hybrid window (.NET 11), its screens Blazor components with Syncfusion Blazor over state classes of the app's own, drawn in WebView2. Its screens were ported from the `../TinapayanRMS_Web` repo on 2026-11-07 ([docs/plan/maui-app.md](docs/plan/maui-app.md)).
- **Layers**: `Domain` (the entities), `ApplicationCore` (the `*Rules` classes, repository interfaces, validators), `Infrastructure` (EF Core and Dapper, the repositories, the cost propagators, `ProductCloner`, the unit of work), `Pricing` (how a saved product is read and priced, and the saves that record product versions), `Presentation` (the screens' states), `Components` (the screens: Blazor components, printing, export, the Vim keys) and `Maui` (the window). Two servers share the lower layers: the MCP server and the Recipe API.
- **Costs**: a raw material's cost per base unit is stored, and the cascade keeps a made or linked one's current (Reactive Costing Cascade). A sub-assembly's batch and a product's cost and selling price are worked out on read.
- **Screens**: Raw Materials, Sub-Assemblies and Products (with its Recipe, Costing, Clone and History tabs), then Reports, Price Simulator and Print, and Settings. Production planning is TinapayanBMS's, which reads the recipes through the Recipe API.
- **Saves**: a screen's Save writes its whole form in one transaction, and a save that records product versions writes them in that same transaction (`VersionedSaves`, `IUnitOfWork`).

## Tech Stack

- **Language / Runtime**: C# 15, .NET 11 (`net11.0`; `net11.0-windows10.0.19041.0` for the Maui project: MAUI's Windows target needs at least that Windows SDK version, and the bare `net11.0-windows` moniker resolves to `windows7.0`). The SDK is pinned in `global.json` to 11.0.100, the release, and the runtime is 11.0.0. The change in .NET 11 that matters to this code: a `double` converts to a `decimal` at its exact binary value (Conventions, "Decimal precision"). Runtime async is on (Build settings, below).
- **UI**: Blazor components (`Microsoft.AspNetCore.Components.Web`, the runtime's release) with **Syncfusion Blazor 35.2.12** and its Fluent 2 theme recoloured to the app's palette, in a **.NET MAUI Blazor Hybrid** window (`Microsoft.Maui.Controls` and `Microsoft.AspNetCore.Components.WebView.Maui`, 11.0.10, `MauiPackagesVersion`, on the `maui-windows` 11.0.0 workload: MAUI ships as these packages, so they can be ahead of the workload), drawn by WebView2. Each screen draws itself again as its state says it changed (`ScreenBase`). See [docs/plan/maui-app.md](docs/plan/maui-app.md).
- **Screen state**: plain classes of the app's own, with no MVVM library (ReactiveUI until 2026-11-16, and called ViewModels until 2026-11-17, the build plan's log): `ObservableState` (an `INotifyPropertyChanged`) under every screen's state, part and row, `ScreenCommand` for commands, and `Interaction<TInput, TOutput>` for what a screen asks of whoever shows it (a dialog, a file picker). A command run nothing awaited (a menu's item, a key) that fails goes to `UnhandledFailures.Report`, logged and shown as an error toast. **Rx** (`System.Reactive` 7) stays where it does real work: the loads where the latest pick wins (`LoadLatest`, a `Switch`), and the `Subject`s one screen follows on another (a product asked to be opened).
- **Reactive collections**: DynamicData.
- **Persistence**: EF Core 11 (11.0.0-rc.3, on the 11.0.0 runtime: it moves to 11.0.0 when Npgsql's provider and `EFCore.NamingConventions` have 11.0.0 releases, since the provider asks for exactly rc.3 and NamingConventions 10.0.1 for anything under 11.0.0) on PostgreSQL 18 (`localhost:5432`, role `tinapayanrms`, database `tinapayanrms`) through Npgsql (`Npgsql.EntityFrameworkCore.PostgreSQL` 11.0.0-rc.3, with `EFCore.NamingConventions` making every table and column snake_case), for writes, the schema and migrations; **Dapper** (2.1.x) for reads (Conventions, "Reads through Dapper, writes through EF Core").
- **DI / Hosting**: `Microsoft.Extensions.Hosting` and `Microsoft.Extensions.DependencyInjection`. Infrastructure's `DatabaseHost` is the host both servers start from, and `DatabaseHost.AddTinapayanRMSDatabase` registers the database and repositories, the one way the app and both servers do; the app adds its services in `src/TinapayanRMS.Components/ServiceRegistration.cs` (its screen states scoped, one set per page the web view loads), called from `MauiProgram`.
- **Validation**: FluentValidation.
- **Logging**: Serilog (rolling file sink).
- **Charts**: Syncfusion Blazor Charts (`Syncfusion.Blazor.Charts`), for the Products History tab's Cost Over Time. Reports shows summary grids, not charts.
- **Excel export**: the Syncfusion Blazor grid's own export (`SfGrid.ExportToExcelAsync`), on XlsIO (`Syncfusion.XlsIO.Net.Core`), at `$(SyncfusionVersion)` like every Syncfusion package. The licence key covers Excel as well as Blazor, so a workbook carries no trial notice.
- **Testing**: TUnit, AwesomeAssertions, Respawn, and bUnit (2.15) for the components. TUnit finds the tests by a source generator at build time and runs them on Microsoft.Testing.Platform, every test in parallel unless a `[NotInParallel]` key holds it apart; its own assertions aren't used. Integration tests run against the local PostgreSQL server, and Respawn (`DbAdapter.Postgres`) resets each test project's database between tests. Nothing is mocked. AwesomeAssertions rather than FluentAssertions: FluentAssertions 8+ needs a paid licence for a for-profit product, and AwesomeAssertions is a same-API, MIT-licensed fork of the last free release.
- **MCP server for AI assistants**: `src/TinapayanRMS.Mcp`, a Model Context Protocol server over stdio on the official C# SDK (`ModelContextProtocol` 2.4.0). It gives an AI coding assistant what SQL can't, a product's cost and price, which are worked out on read: `list_products`, `get_product_costing` and `simulate_price_changes` (`Tools/CostingTools`). It builds its host with `DatabaseHost` and prices with `TinapayanRMS.Pricing`, so the tools can't price differently from the screens. **It can't write**: `ReadOnlyConnection` sets `default_transaction_read_only` on its connection to the dev database, so PostgreSQL refuses a write whatever runs it. Claude Code starts it from `.mcp.json` through `scripts/Start-McpServer.ps1`, which builds Release and runs a copy of the build from `bin/Release/runs/<hash>`, so a running server holds only its copy and never blocks a build. One start builds at a time (a named mutex), a copy no server runs from goes at the next start, and the server ends with the script. It builds as it starts, so Claude Code waits 2 minutes for it (`MCP_TIMEOUT` in `.claude/settings.json`). Its JSON rounds decimals to 6 places (`ToolJson`), where full precision ran to 28 digits. Tested by `TinapayanRMS.Mcp.Tests`, on its own database and on the read-only connection. See the developer manual's "Checking costs from an AI assistant".
- **Recipe API for the shop's other apps**: `src/TinapayanRMS.RecipeApi`, a read-only HTTP API (ASP.NET Core minimal APIs on Kestrel, JSON under `/api/v1`) on port 5290 of every address, so TinapayanBMS (`../TinapayanBMS`, the app that weighs ingredients out ahead of mixing and plans production) can read the recipes on this PC or across the LAN. **An API in this repo**, rather than TinapayanBMS reading this database directly, which would tie it to this schema and have it work batches out again; TinapayanBMS is a repo of its own. Like the MCP server, it builds its host with `DatabaseHost` (`RecipeApiHost.AddRecipeApi` puts the web server on top), prices with `TinapayanRMS.Pricing`, and reads through `ReadOnlyConnection`; installed, it also connects as `tinapayanrms_reader`, a role that can't write (`Database:ReadOnlyUser`, made by `scripts/New-DatabaseReader.ps1`). Endpoints: `status`, `ingredients`, `boms`, `categories`, `products`, `products/recipes`, `mixes`, `mixes/details`, `mixes/{id}` and `materials`. The records it sends are `Contracts/RecipeContracts.cs`, which the other apps copy, so a change adds rather than renames or removes. Every request has to carry the key (`RecipeApi:Key` in `recipeapi.json`, sent as `X-Api-Key`); with none set, only this PC is answered. What fails comes back as `{ error }`: a 503 in `Failure`'s fixed sentence for a database that can't be used, and a 500 with a fixed sentence for anything else. `status` reads the database, so its answer means that's there too. Installed by `scripts/Install-RecipeApi.ps1`, which starts it hidden at sign-in as the signed-in user, so it reads that user's `pgpass.conf`, and, run as an administrator, opens port 5290 to the local subnet on private networks. A connection it leaves idle closes after 10 seconds (`ReadOnlyConnection`), since a restore can't end another role's connections and waits only 30 seconds for them. Tested by `TinapayanRMS.RecipeApi.Tests` (`tinapayanrms_test_recipeapi`), in memory through ASP.NET Core's `TestServer`, where `RecipeApiContractTests` pins the JSON field names the other apps read. See the developer manual's "The Recipe API".
- **The pricing has a project of its own, so the servers have no UI in them.** `src/TinapayanRMS.Pricing` (`net11.0`, on ApplicationCore) holds `SavedProductReader` and what it builds: a saved product is read as immutable `PricedSection`s and `PricedPackagingLine`s, whose figures come from the same `SectionFigures.Of` and `PricedPackagingLine.Price` the screens' editable rows use, along with `ProductCostSummary`, `PackagingLinkTarget`, `PurchaseUnit`, `BaseUnitText`, `TriedPriceChange` and `PriceSimulatorProductRow`. Its `Versions/` holds the product versions' snapshot and the saves that record them (`VersionedSaves`). The editable rows (`ProductUsageEdit`, `PackagingLineRow`, `SimulatedPriceChange`, `ObservableRow`), printing and comparing stay in Presentation. A project rather than a folder in ApplicationCore, since these rows carry display text that doesn't belong beside the rules. The servers are on plain `net11.0`, and the pricing references no UI, so MAUI, Blazor, Syncfusion and the screens' states can't creep into them: the API builds at about 10 MB and the MCP server at 14 MB.
- **Solution format**: `.slnx`.
- **Build settings**: `Directory.Build.props` at the repo root sets `TargetFramework` (`net11.0`), `ImplicitUsings` and `Nullable` for every project, plus a `WindowsTargetFramework` property that the Maui project uses as its `TargetFramework`.
  - **Runtime async** is on for every project (`<Features>$(Features);runtime-async=on</Features>`): .NET 11 runs `async` methods itself, so the compiler no longer turns them into state machines. It's still a preview, opt-in compiler feature in the release SDK (11.0.100): without the line, the compiler writes state machines again (checked 2026-11-13). **Kept on as the direction .NET is taking** (the user's decision, 2026-11-13, after it was measured, and after reading Gérald Barré's "the runtime takes over await" and its benchmarks): .NET 11's own libraries (`System.Private.CoreLib`, `System.Net.Http`) already ship compiled this way, so every await into them runs on it whatever the app does. **Measured** on the screens' reads, 12 alternating processes with it on and off: no difference a user could notice (a few ms either way: product picks slightly faster, Reports' costing slightly slower), and the same allocations to within 0.2%. The app's awaits wait on PostgreSQL one or two frames deep, where runtime async gains least; its big gains are deep chains of awaits that don't wait. **What it costs**: `dotnet-dump`'s `dumpasync` (10.0.745401) can't read its continuations, so a hang's async work is followed with the debugger's Parallel Stacks window or `dotnet-trace` instead; exception stack traces, breakpoints and stepping are unchanged. The unit of work's `AsyncLocal` behaviour is pinned under it by `SharedTransactionDbContextFactoryTests`, which, like every test, compiles as the app does. To turn it off, delete that one line.
  - **Satori GC is an experiment, off unless asked for** (2026-11-08). The Maui project takes the `PublishWithSatoriGC` MSBuild SDK (nuget.org, an `11.0.*-satori.*` version, built from .NET's `release/11.0`: 11.0.1 now), which swaps the runtime's own files (`coreclr.dll`, `clrjit.dll`, `System.Private.CoreLib.dll`) for [Satori](https://github.com/VSadov/Satori)'s, a low-pause garbage collector that isn't .NET's. That only works for a self-contained app, and the app is framework-dependent, so the project keeps `UseSatoriGC` `false`. `-p:UseSatoriGC=true` on a build, run or publish turns it on: the app is then built self-contained for `win-x64`, into `bin\Satori\` so it never mixes with the everyday build. The app logs which collector it started with. The tests, the servers and the installed app don't use it.
  - **The commit stays out of everyday builds**: with it in, each commit's hash went into every assembly's version and its Source Link file, so the first build after any commit recompiled every project, and the MCP server, which builds as it starts, missed Claude Code's wait. `EnableSourceControlManagerQueries` and `EnableSourceLink` are off unless `_IsPublishing`, which `dotnet publish` sets, so a published copy still carries its commit (`1.0+<hash>`, its Product version, which Settings → Database shows as **App Version**).
  - **`tests/Directory.Build.props`** imports it and adds what every test project shares: `IsPackable=false`, the `TUnit.Engine`, AwesomeAssertions, coverage and hot reload packages, `tests/HotReloadReruns.cs` (under hot reload only, reopens TUnit's per-session dynamic test queue before a rerun, which TUnit (1.81.16 to 1.86.6 so far) would fail on, since the platform reruns in the same session) and `tests/TestRunSettings.cs` (a `[Before(TestDiscovery)]` hook that caps the tests running at once at the processor count, where TUnit would run twice that and slow the suite's one-at-a-time chains by about a minute and a half, and turns off TUnit's HTML and JSON report, which it would otherwise write to `TestResults/` on every run while recording every traced call, each Npgsql command included), only to projects whose name ends in `.Tests`, so `TinapayanRMS.Tests.Common` stays a plain library (it takes `TUnit.Core`, since `TUnit.Engine` would make it a test executable).
  - **`Directory.Packages.props`** enables Central Package Management: every package version is a `PackageVersion` there (EF Core, Microsoft.Extensions and Syncfusion through the `EFCoreVersion`/`MicrosoftExtensionsVersion`/`SyncfusionVersion` properties), and a project's `PackageReference` has no `Version`. `CentralPackageTransitivePinningEnabled` is on, so a `PackageVersion` also overrides a transitive dependency: the "Transitive pins" group lifts `Microsoft.EntityFrameworkCore.Relational` to `EFCoreVersion`, because `EFCore.NamingConventions` asks for EF Core 10 and every project should run the one EF Core Npgsql's provider takes. Drop a pin once the package that brings it no longer needs it. A `.csproj` holds only what's unique to it.
  - **Code analysis**: `AnalysisLevel` is `latest-recommended`, the SDK's built-in .NET analyzers at their Recommended rule set (the Default set reported nothing, and All about 1,700 warnings, mostly style). The root `.editorconfig` marks `Migrations/` as generated code, and turns off CA1707 in `tests/`, whose method names use underscores, and CA1716 everywhere (it flags `IPriceHistoryEntry.Date` for being a Visual Basic keyword). It also makes IDE0005, a using nothing needs, a warning, which the build reports since it runs the code-style rules and reads the doc comments (`EnforceCodeStyleInBuild`, `GenerateDocumentationFile`, with the missing-comment warnings CS1591 and CS1573 off). Warnings aren't errors, but the build has none; keep it that way (CI builds with `-warnaserror`).
- **`dotnet test`**: the .NET SDK's `dotnet test` has no VSTest support; `global.json`'s `test.runner` setting runs it on Microsoft.Testing.Platform. Run the tests with `dotnet test --solution TinapayanRMS.slnx`.
- **Syncfusion license key**: compiled into the app at build time from the `SYNCFUSION_LICENSE_KEY` Windows user environment variable, so an installed copy runs without the variable. The Maui project adds it as an `AssemblyMetadata` item named `SyncfusionLicenseKey` when the variable is set, and its `RequireSyncfusionLicenseKey` target fails `dotnet publish` when it isn't. `MauiProgram` reads that attribute, falls back to the variable, and registers the key before anything touches a Syncfusion type; with neither it logs the fact and the window opens with Syncfusion's licence notice, since a MAUI app that throws as it starts just disappears. The key is readable from the published assembly, as it would be with Syncfusion's own advice of a string literal in code; the build-time step only keeps it out of git.

**Folder = namespace, grouped by kind, and a screen's code by screen.** Every folder inside a project is a sub-namespace of it (`src/TinapayanRMS.Presentation/Products/` → `TinapayanRMS.Presentation.Products`). A new file goes in the folder for its kind, never at the project root. The screens' code, one kind throughout, is grouped by screen instead: Components' pages (`Pages/Products/`) and Presentation's state classes with their parts and rows (`Products/`), what several screens share in Presentation's `Shared/`, and the record lists' trees in its `Trees/`. Only app-startup plumbing (the MAUI app's `MauiProgram`, `App` and `MainPage`, Components' `ServiceRegistration`, `StartupTasks`, `UnhandledFailures` and `OneCopyPerPc`, Infrastructure's `DatabaseHost` and `ReadOnlyConnection`, and the servers' `Program` and `RecipeApiHost`), the DbContext pair, and `TinapayanRMS.Pricing`, one kind of thing throughout, live at a project root. Code in a sub-namespace sees its parent namespaces without a `using`: a repository uses `TinapayanRMSDbContext` from `TinapayanRMS.Infrastructure`. Sibling folders need a `using`. Table names come from the DbContext, not from entity namespaces, so moving an entity between namespaces leaves the EF model unchanged.


## Domain Model

- **UnitOfMeasure**: `Id`, `Name`, `Abbreviation`, nothing else. **No unit is seeded or protected by a fixed id**: the table starts empty on a fresh database, and the shop owner adds every unit they need (gram, piece, mm, or a sack or roll) in Settings → Units of Measure, as any other user-managed lookup. **A unit carries no conversion factor of its own.** Conversions live on each raw material instead (Multi-unit materials, below): every material has a **base unit** its quantities and costs are tracked in (always the gram for an ingredient; chosen per packaging material), plus any number of **alternative units**, each a multiple of that base unit.
  - **Standard units have a fixed multiplier.** `ApplicationCore/Rules/StandardUnitRules` recognises a unit by its name or abbreviation, whatever the case, across mass (mg, g, kg/kilo, oz, lb), length (mm, cm, m, in, ft) and volume (ml, l). When the unit and the material's base unit are the same kind, the multiplier is fixed: a kilogram of an ingredient is 1,000 g, an inch of ribbon in centimetres is 2.54. Anything else is typed: a bag, a litre of an ingredient (only its density says how many grams), a kilogram of wrappers counted in pieces. The fixed multiplier is rounded to the 4 places the column keeps (an ounce is 28.3495 g), so a saved one reads back equal, and one that rounds to 0 (a milligram of a kilogram) is left to type.
  - `RawMaterialUnitRepository.AddAsync`/`UpdateAsync` save a standard unit at its fixed multiplier whatever was sent (`MultiplierToSaveAsync`). On the screen a row takes it as the unit is picked, renamed into one in Settings, or the base unit or type changes under it (`RawMaterialUnitRow.ApplyStandardMultiplier`), and neither the Alternative Units grid's Multiplier cell (`CanTypeMultiplier`) nor Purchase Cost Setup's Qty per Purchase Unit (`CanTypeQuantity`, via `IBrandPriceRowHost.IsMultiplierFixed`) can be typed into for one (each is a read-only `NumberField` there).
- **RawMaterial: ingredients and packaging share one table, told apart by `Type` (`Ingredient` or `Packaging`).** The differences that are real are rules on the type:
  - **Base unit**: an ingredient's is always the gram, so its `BaseUnitId` is null, and recipes, BOMs and sub-assembly weights all add up grams. A packaging material picks its own (`BaseUnitId` required).
  - **Source**: only an ingredient can be `Made` (made from a sub-assembly, with add-ins and a weight loss) or `Linked` (a share of another ingredient's cost); packaging is always `Purchased`.
  - **Where it can be used**: sub-assembly lines and a made ingredient's add-ins take ingredients only; a product's packaging lines take packaging only.
  - `RawMaterialRules.EnsureFieldsMatchType`/`EnsureFieldsMatchSource` run in `RawMaterialRepository` before every save, backed by two check constraints (`CK_RawMaterials_BaseUnitMatchesType`, `CK_RawMaterials_OnlyIngredientsAreMade`). Type and source are fixed once created (`EnsureTypeUnchanged`/`EnsureSourceUnchanged`). Each line repository checks every line's type (`EnsureUsableInRecipes`/`EnsureUsableAsPackaging`, through Infrastructure's `LineChecks`) before it replaces anything, with a message naming the material, and the pickers only offer the right type. A name is unique across both types.
  - The line entities keep their role names: `SubAssemblyLine.Ingredient`, `IngredientBomLine.Ingredient`/`ComponentIngredient` and `PackagingLine.PackagingMaterial` are all `RawMaterial`s. A packaging line's unit is `UnitId` (a `RawMaterialUnit`); recipe lines have no unit, since they're in grams (Ingredients, below). `IngredientCostPropagator` is named for ingredients because it only ever deals with them.
  - **`CostPerBaseUnit`** (stored, derived): the true cost of one base unit (one gram, for an ingredient).
  - **Buffered cost**: a per-material **`CostBufferPercent`** (0–100; a new one starts at Settings' default, see Costing defaults; `RawMaterialRules.EnsureValidCostBuffer`, the validator, and `CK_RawMaterials_CostBufferPercent`) is a cushion for price swings, waste and yield variation. **`BufferedCostPerBaseUnit`** (stored, derived) is the cost with it on top (`RawMaterialRules.BufferedCost`, the only buffer formula). **It's the value every sub-assembly line, BOM rollup and packaging line uses**, so products are costed and priced with it; `CostPerBaseUnit` stays the true cost, shown beside it on the Raw Materials screen and in Price History.
    - Purchased: **a fixed amount**. Brand prices don't move it. `ApplyBrandPrices` only works it out, as `CostPerBaseUnit × (1 + buffer / 100)`, the first time the material is priced (while it's still 0), and sets it back to 0 when the last price goes. Otherwise it changes only when the screen sends a new one: typed, or from typing the Cost Buffer % (the dearest brand as typed with the % on top). `RawMaterialRepository.UpdateAsync` writes the form's amount (0 sent means "work it out from the cost and the %", and `SaveAsync` does that from the new prices when it has them) and cascades an ingredient whose buffered cost changed. `EnsureValidBufferedCost` (and the validator) rejects a negative amount; one below the cost is allowed, and the screen warns about it. So a price change alone reaches product costs only through the true cost, and the buffered cost everything is costed with waits for the screen to send a new one. `CostBufferPercent` is kept as the % that puts the buffer back on top, and `TargetCostBufferPercent` as the one last typed (Raw Materials' Re-apply Target).
    - Made: the BOM rollup of the components' *buffered* costs, and nothing more. **A made ingredient adds no buffer of its own**, so a buffer is counted once however deep the tree. `RawMaterialRules.StoredCostBufferPercent` is the one place that says so: `RawMaterialRepository`'s Add and Update store a made ingredient's `CostBufferPercent` as 0 whatever the form sends (refusing it instead would leave a row that has one unsaveable, since the screen has no buffer box for a made ingredient), and `IngredientCostPropagator` sets it to 0 on every recompute, which cleans a *dependent* made row the propagator reaches without a save. A linked part of a made ingredient inherits 0%, which is right: it takes a share of an already-buffered cost.
    - Linked: the same share of the linked-to ingredient's buffered cost as its true cost is of the true cost (`LinkedCost(linkedTo.BufferedCostPerBaseUnit, …)`), so a part follows the linked-to ingredient's fixed amount.
    - It's stored, not computed on read, because a made ingredient's buffered cost isn't a multiple of its own true cost once its components have buffers.
- **Multi-unit materials**:
  - **`RawMaterialUnit`** (`RawMaterialId` Cascade, `UnitOfMeasureId` Restrict, `BaseUnitsPerUnit` > 0, `Description`; unique per material + unit; never a packaging material's own base unit). The base unit never has a row: **an empty unit means the base unit** everywhere a unit is optional (price entries, packaging lines), so nothing depends on a "gram" row existing in Units of Measure. Recipe lines take no unit at all: an ingredient's alternative units price it and work in the Usage Example, but a recipe is always written in grams.
  - `UnitConversionRules.ToBaseQuantity(quantity, multiplier?)` / `CostPerBaseUnit(price, multiplier?)` / `EnsureValidMultiplier` are the only conversion formulas.
  - **Any number of alternative units per material.** Nothing in the schema or the rules limits them.
  - **Every price records the unit it was priced in** (`UnitId?`), both a brand price and a price history entry, so switching from buying bags to buying packs leaves the old per-bag prices correct. The stored cost is per base unit only: `CostPerBaseUnit` = the dearest brand price ÷ its unit's multiplier. The material stores no purchase unit or current price: a price is meaningless without its unit, and storing the unit on the material would make a material ↔ unit FK cycle.
  - **Correcting a multiplier reprices.** `RawMaterialUnitRepository.UpdateAsync` (and the screen's Save, through the same shared write method) reprices the material from its brand prices when one is in that unit (`RawMaterialBrandPriceRepository.RepriceAsync`, which also logs a new cost in price history); for an ingredient whose cost moved that way it then calls `IngredientCostPropagator.RecomputeAndPropagateAsync`, which reaches every dependent made ingredient. Recipe lines are in grams, so nothing else moves. A packaging material needs nothing more: packaging lines are costed on read.
  - **A unit in use can't be deleted**: the repository counts price entries, and for a packaging material's unit its packaging lines and its packaging sets' lines, first and says which (Restrict FKs back that up). An ingredient's unit is never on a line.
  - **A packaging material's base unit is fixed once it has alternative units, prices or packaging lines** (`RawMaterialRules.EnsureBaseUnitCanChange`, checked in `RawMaterialRepository.UpdateAsync`), since all of them are measured in it.
- **RawMaterialCategory** (Flour, Dairy, Boxes, Ribbons, …): one user-editable list for both material types, **each category typed** (`Type`, a `RawMaterialCategoryType` stored by name): `Ingredient`, `Made` (made ingredients only) or `Packaging`. Managed in Settings → Material Categories, which has a Type column and a Type picker on its form (Application Architecture, below).
  - **A material goes only in a category of its kind**: `RawMaterialRules.CategoryTypeFor(type, source)` says which (a made ingredient a Made one, any other ingredient an Ingredient one, packaging a Packaging one) and `MaterialTypeOf` which material type a category holds. `EnsureCategoryMatchesType` takes the source too ("Flour is an ingredient category. Put this made ingredient in a Made category."), in `RawMaterialRepository`'s add, update and `MoveAsync`, after the type and source checks.
  - **A category's type can change while everything in it fits the new one** (`EnsureCategoryTypeCanChange(name, newType, materialsThatDontFit)`, in `RawMaterialCategoryRepository.UpdateAsync`), so an ingredient category of made ingredients alone can become Made in Settings. A made ingredient left in an ingredient category still loads, but its Save is refused with the message above until it's moved.
  - **Raw Materials screen**: the Category picker offers the categories of `CategoryTypeFor(EditingType, EditingSource)`, and a new material's type or source changed under one of another type empties it (only while `CanChangeTypeAndSource`: loading a saved one sets its category before its source). A Made category's folder (`RawMaterialFolderNode.CategoryType`; its `Type` is Ingredient, so it sits in Ingredients) offers **New Made Ingredient Here**; the Ingredients folder, the empty space and the toolbar's New Folder drop-down offer **New Made Folder**, a row named in place. Move To, drags (`RawMaterialTree.MoveTo`/`MovesTo`) and a category typed into the picker all follow `CategoryTypeFor`, so made ingredients and the others never move together. Covered by `RawMaterialRulesTests`, `CategoryPersistenceTests`, `RawMaterialMovePersistenceTests` and `RawMaterialsStateTreeTests.A_Made_categorys_folder_starts_made_ingredients_and_takes_only_them`.
- **ProductCategory** (Breads, Cakes, Pastries, …): a user-editable list **of its own**, not shared with `RawMaterialCategory`, so a Category picker never mixes Flour and Boxes with Cakes. `Product.CategoryId` is **optional**, and a product without one is Uncategorized. **A category isn't a folder of the Products list** (since 2026-11-12; ProductFolder, below): it's what kind of product it is, for the list's category filter (`ProductCategoryFilter`), the Wastage % and the printouts, wherever the product is filed, and a move never changes it. Its FK is **Set Null**, not Restrict like a raw material's, so deleting a category leaves its products uncategorized (the delete confirmation says so). A category can set the Wastage % its products are priced with (Costing defaults, below). Managed in Settings → Product Categories, or added from the Products header's Category picker. `ProductRepository` reads it with the product and writes it in add, update and `SaveAsync`; `ProductCloner` gives a clone its source's category.
- **ProductFolder** (`Id`, `Name`, `Stage`, `ParentId`): the Products list's folders, the user's own, as in a file explorer. A folder is in a stage and holds products (`Product.FolderId`, nullable: null is loose at the top of the stage) and other folders (`ParentId`, null at the top), as deep as wanted; they sort by name, a folder's folders before its products. Managed only from the list (`IProductFolderRepository`, `ProductFolderRepository`: Dapper reads, EF writes).
  - **Rules** (`ProductFolderRules`, checked by the repositories before the database would refuse, so the message can say where): a name is trimmed, 1 to 100 characters, and unique among the folders beside it whatever its case (the unique index on stage, parent and name, `AreNullsDistinct(false)`, with the `case_insensitive` collation: "Production › Breads already has a folder named Holiday."); a folder is in its parent's stage, and a product in its folder's (the repositories keep this, as no database constraint can without hand-written SQL); a folder never goes inside itself or a folder of its own (`EnsureNotInsideItself`, and `CK_ProductFolders_NotOwnParent`). Every walk of the tree stops where a folder comes round again, so a loop left by an edit outside the app can't hang it (the list shows such folders at the top of their stage, and a printout lists them there, `ProductFolderRules.IsInLoop`).
  - **Moving a folder** (`MoveAsync(ProductFolderMove)`) takes everything in it; to the other stage, every folder in it and every product in those, deleted ones too, changes stage, and the products' `UpdatedAt` is stamped. **Deleting one** (`DeleteAsync`) deletes no product: what it holds, deleted products included, goes up into the folder it was in, or to the top of the stage, and the delete is refused if a folder in it has a name taken there. The parent FK is Restrict and the product's Set Null, for what's deleted outside the app.
  - **Promote, Send Back, Clone and Create Variant mirror the path** (`IProductRepository.MoveToStageAsync`, `ProductCloner`, both through `ProductFolderRepository.EnsurePathAsync`): the product goes in the other stage (a clone or variant in Innovation) in the folder at the same path as its own (Innovation › Breads › Holiday to Production › Breads › Holiday), each folder on the way found by its name or made. `MoveToStageAsync` returns the folders it made (`StageMove`), which the list's Undo takes away again while they're empty (`DeleteIfEmptyAsync`). It finds each folder's path in the other stage once, however many of the products moved are in it (all 84 of the dev database's: 90 round trips, now 14). Chosen over "the top of the stage" because on the folders the 2026-11-12 upgrade made, it does exactly what Promote did when folders were categories.
  - **The first layout** came from the data upgrade "2026-11-12 product folders" (`ProductFoldersUpgrade`, after the migration `ProductFolders`): a folder at the top of each stage for each category with an undeleted product there, holding those products, and a deleted product in its category's folder in its stage when one was made. Uncategorized products stayed at the top of their stage.
- **Product stage** (`Product.Stage`, a `ProductStage` stored by name): `Innovation` or `Production`, the Products list's two top-level folders (`ProductRules.StageTitle`). Innovation was `ResearchAndDevelopment` until 2026-11-09: the data upgrade "2026-11-09 innovation stage" renamed what was stored, and `ProductStageConverter` (EF) and `ProductStageTypeHandler` (Dapper) still read the old name, which a copy built before then writes until it's updated. Such a copy can't read the new name, so it fails to load the products once one is in Innovation: every copy on a database is updated together. Innovation's folder kept closed under the old name reads as Innovation's (`ProductFolderNode.CurrentFolderKey`). The Recipe API sends the new name. A clone and a variant start in Innovation, set by `ProductCloner`, in the folder at the path of their source's (ProductFolder, above); a product started by New goes in the stage Settings gives a new product, Production unless it says otherwise (`CostingDefaults.NewProductStage`). The column's database default is Production, and `HasSentinel((ProductStage)(-1))` makes EF always write the product's own stage. Only moving a product in the list changes a saved product's stage and folder (dragging it to another folder, or its right-click menu's Move to: `IProductRepository.MoveAsync`, which sets the stage and the folder together, never the category, for any number of products in one save, refuses a folder gone or in the other stage, and stamps `UpdatedAt`; Promote and Send Back: `MoveToStageAsync`; or moving the folder it's in to the other stage); the form's Save never writes either (`UpdateAsync`, `SaveAsync`), so a move rewrites none of the form's undo steps. **A new product's are Save's to write**: `SaveAsync` copies `Stage` and `FolderId` for a product it adds (the folder's stage wins, and a folder gone files it at the top of the stage), so New Product Here on a folder files the product there, and the header says where until it's saved ("Goes in Innovation › Breads").
- **Deleted products** (`Product.DeletedAt`, nullable): a **soft delete**, in two steps. A deleted product waits in the Products list's **Deleted folder**, and **keeps holding what it uses**, so a restore never finds a hole.
  - `IProductRepository.DeleteAsync` stamps `DeletedAt` and changes nothing else: stage, folder, category, recipe, packaging, links, costing and `UpdatedAt` all stay. `RestoreAsync` clears it. A category deleted in the meantime has already left the product uncategorized (`SetNull`). `DeletePermanentlyAsync` is the hard delete with its cascades. Both deletes are refused while another product, deleted or not, links its packaging or holds it in a composite (`EnsureNothingLeansOnAsync`), so a restore never needs a check.
  - **Reads**: `GetAllAsync` returns only the products in use, and `GetDeletedAsync` the deleted ones. `GetByIdAsync` and `GetByIdsAsync` return either. Every screen but Products reads `GetAllAsync`, so Reports, Print, the Price Simulator, the Recipe API and every picker leave deleted products out. There's no EF global query filter, because it would also hide them from the "in use" checks.
  - **Named as deleted where it's in the way**: `ProductRules.ListedName` gives "Cheese Roll (deleted)" in the Sub-Assemblies Dependents and its refusals (`SubAssemblyRepository`'s `LinkRow`), Raw Materials' Dependents (`GetDependentsAsync`), the delete refusals, and a composite's role refusals. A Dependents tile for one opens its row in the Deleted folder.
  - **Its name stays taken** (the unique index covers it): Add, Update, Rename and a clone refuse it first with "A deleted product is named Mamon. Restore it from the Deleted folder, or delete it permanently there first." (`ProductRules.EnsureNameNotHeldByDeleted`). A deleted product can't be newly linked for packaging or put in a composite; each refuses by name.
  - Covered by `DeletedProductPersistenceTests`, and on the screen by `ProductTreeTests` and `ProductsStateTreeTests`.
- **Ingredients** (`Type = Ingredient`):
  - **The base unit for every ingredient is the gram.** Every weight total is in grams: sub-assembly lines' and BOM lines' `Grams`, a sub-assembly's batch weight, and weight per piece. **Recipe lines are entered in grams only**: sub-assembly lines and add-ins have no unit picker.
  - **`Source`**: `Purchased`, `Made` or `Linked`. It's set when the ingredient is created and can't change afterwards, so an ingredient's cost always comes from exactly one place.
  - **`Units`**: its alternative units (a 25 kg bag is `BaseUnitsPerUnit = 25000`, an egg piece `50`). Any source can have them; only a purchased one is priced in them.
  - **Purchased** ingredients are priced through their brand prices (`RawMaterialBrandPrice`), each in one of the ingredient's units (or per gram). `CostPerBaseUnit` = the costed brand's price ÷ grams in its unit (the dearest, unless `PreferredBrand` names one; see RawMaterialBrandPrice).
  - **Made** ingredients are produced in-house **from a sub-assembly, with add-ins of their own**, so a recipe is written once, on the Sub-Assemblies screen, and both a made ingredient and products can use it.
    - **`RawMaterial.SubAssemblyId`** (FK Restrict, indexed): the recipe it's made from. Required for a made ingredient and null for any other (`RawMaterialRules.EnsureFieldsMatchSource`, the validator, `CK_RawMaterials_SubAssemblyMatchesSource`). Only a recipe kept on the Sub-Assemblies screen: not a packaging set, not a product's own (`SubAssemblyRules.EnsureLinkableByMadeIngredient`). Several made ingredients can be made from one sub-assembly, each with its own add-ins and weight loss, and products can link the same one.
    - **Add-ins: `IngredientAddInLine`** (`IngredientId` Cascade, `AddInIngredientId` Restrict, `Grams`, `SortOrder`; unique per made ingredient and add-in), the made ingredient's own extras on top of the recipe, as a product's linked usage has `UsageAddInLine`. None is fine; each needs positive grams, comes once, and isn't already in the recipe (`IngredientBomRules.EnsureValidAddIns`, sharing `AddInRules` with `ProductRules.EnsureValidAddIns`). They belong to the made ingredient: the sub-assembly's lines and totals never include them.
    - **Its bill of materials is read, never stored**: the sub-assembly's lines, then the add-ins (`IngredientBomLine`, below).
    - They have no brand prices or price history.
    - **`WeightLossPercent`**: weight lost while making the ingredient (e.g. water boiled off syrup). At least 0 and less than 100 (`RawMaterialRules.EnsureFieldsMatchSource`). **The screen starts a new made ingredient at 3%**, the usual shrink in the shop (`??=` on the source change, so a saved material keeps what it was saved with), and the box caps at 0–99.99 to match the rule. A cleared box saves 0, a legitimate value.
    - Output grams = `Σ BOM line grams × (1 − WeightLossPercent / 100)`.
    - Cost per gram = `Σ (BOM line grams × component cost per gram) / output grams`. The buffered cost per gram is the same formula over the components' buffered costs, with nothing of its own on top. The formula is `IngredientBomRules.CalculateCost`; a component's cost is whatever's currently stored on it, which the cascade keeps current (Reactive Costing Cascade), so it's read directly rather than by walking the tree.
    - Example: simple syrup from 1000 g sugar (₱0.09/g, so ₱90) and 500 g water (unpriced: a literal ₱0 brand price is refused, so "free" means unpriced), with 20% weight loss, makes 1500 × 0.8 = 1200 g, at ₱90 / 1200 = ₱0.075/g.
  - **Linked** ingredients are parts of another ingredient, costed as a share of its cost. An egg is bought by the 1,500 g tray at ₱135 (₱0.09/g); egg white is 70% of its weight and carries 30% of its cost, egg yolk 30% of the weight and 70% of the cost. A made ingredient can't do this: a BOM spreads cost by weight only.
    - **`LinkedToId`** (self-referencing FK, Restrict, so an egg can't be deleted while a part links to it), **`WeightSharePercent`** and **`CostSharePercent`** (each above 0, at most 100). Only a linked ingredient has them, and it has no price history, no BOM and no weight loss (`RawMaterialRules.EnsureFieldsMatchSource`, the validator, `CK_RawMaterials_LinkMatchesSource`). The link and shares can be edited after creation; the source can't.
    - **Cost per gram = linked-to cost per gram × cost share ÷ weight share** (`RawMaterialRules.LinkedCost`, the only place the formula is). White: 0.09 × 30/70 = ₱0.038571; yolk: 0.09 × 70/30 = ₱0.21. 1,050 g of white and 450 g of yolk cost ₱40.50 + ₱94.50 = ₱135, the whole tray. It doesn't depend on the unit the egg was priced in.
    - **The cost share is of the linked-to ingredient's unbuffered cost, and the buffered cost is the same share of its buffered cost**, so a part follows the linked-to ingredient's fixed amount, and a buffer is never counted twice.
      - **The part shows the linked-to ingredient's `CostBufferPercent`, stored on it and kept in step**: `RawMaterialRepository` sets it from the linked-to ingredient's on add and update, whatever the form sent (`EnsureValidLinkAsync` returns it), and `IngredientCostPropagator` copies it again every time the part is recomputed. A buffer edit already cascades, so it reaches every part, down a chain of links; relinking takes the new ingredient's. Storing it keeps everything that reads `CostBufferPercent` (the Usage Example, the list) right without knowing about links.
      - The Linked Cost card shows the inherited percent read-only (bound to `EditingLinkedTo.CostBufferPercent`); it's changed on the linked-to ingredient.
    - **The parts of one ingredient take at most 100% of its weight and at most 100% of its cost** (`RawMaterialRules.EnsureLinkSharesFit`, checked by `RawMaterialRepository` on add and update against the *other* parts, so a part never counts against itself). Less is fine: the shell is neither white nor yolk. The message names the other parts: "Egg Yolk (30%) already takes 30% of Egg's weight, so Egg White can take at most 70%."
    - **Ingredients only**: the target must be another ingredient (`EnsureValidLinkTarget`, which also refuses a link to itself), purchased, made or itself linked. Packaging stays purchased-only; `CK_RawMaterials_OnlyIngredientsAreMade` already covers it.
    - **A link is one more edge in the cost graph** (Reactive Costing Cascade), so a cycle can't close through a mix of recipes and links: linking egg white to a meringue base made from egg white is refused, and so is a made ingredient whose recipe uses a part linked to it. `IngredientDependencies.LoadAsync` builds the combined graph for both checks (`IngredientBomRules.EnsureNoCycle`) from `IngredientCostRules.Dependencies`, the edges the cascade orders by, so the two can't disagree about what depends on what; a refusal names both ingredients ("Egg White can't be costed from Meringue Base: Meringue Base is already costed from Egg White, …").
- **IngredientBomLine**: one component of a made ingredient, **a read model, not a table**: a line of the sub-assembly it's made from, or one of its add-ins (`IsAddIn`). `Infrastructure/Queries/IngredientBoms` is the one definition, which the cascade, the cycle check, `IngredientBomLineRepository` and the Recipe API's `/boms` all read, so everything that reads a BOM (the Price Simulator, Reports) sees the recipe and the add-ins together.
  - BOMs nest to any depth: caramel can be made from syrup, and syrup from sugar. `IngredientBomRules.EnsureNoCycle` keeps an ingredient out of its own BOM tree, checked at save time against the *other* made ingredients' current graph.
  - BOM lines are ingredients only, never packaging (`RawMaterialRules.EnsureUsableInRecipes`).
- **Packaging materials** (`Type = Packaging`):
  - `BaseUnitId` (FK to UnitOfMeasure) is its base unit, set per material: typically a count unit (piece) for boxes and wrappers, a length unit (cm) for ribbon. No rule restricts which unit that can be, but it's fixed once anything is measured in it (Multi-unit materials).
  - `Units` are its alternative units (a pack of 100 boxes is `BaseUnitsPerUnit = 100`, a 1000 cm ribbon roll `1000`), and `CostPerBaseUnit` its stored cost.
  - Always purchased, and priced through brand prices like a purchased ingredient.
  - Packaging lines can be entered in the base unit or any alternative unit (PackagingLine).
- **RawMaterialBrandPrice**: what each brand of a purchased material costs now. `Brand` is optional free text (trimmed, max 100, `null` when blank); `UnitId` is one of the material's units or `null` for per base unit; `Price` is per unit and positive (`CK_RawMaterialBrandPrices_Price`). **The material is costed at the dearest brand per base unit** (`RawMaterialRules.ApplyBrandPrices`/`FindDearestBrandPrice`), so costing stays conservative, **unless its Basis names a brand** (`RawMaterial.PreferredBrand`), when it's that brand's dearest price. A brand is priced once per unit, whatever its case (`EnsureDistinctBrandPrices`); the same brand in two units is fine. `RawMaterialBrandPriceRepository.SetAsync` (and the screen's Save) replaces them all, reprices and cascades.
- **RawMaterialPriceHistory**: **a log of the prices a purchased material has been costed at.** `RawMaterialBrandPriceRepository.RepriceAsync` adds an entry, dated today, with the costed brand's price, unit and `Brand`, whenever brand prices move the cost; a Save that leaves the cost as it was logs nothing, and one that leaves no prices logs nothing either. **Deleting an entry only tidies the log** and never reprices. Made and linked ingredients have none.
  - **An unchanged cost has to compare equal.** A cost that doesn't come out even (170 ÷ 240 = 0.708333…) is worked out to 28 places and stored to 20, so every stored cost per base unit is set through `RawMaterialRules.StoredCost` (20 places, rounded half away from zero); otherwise a Save that changed nothing would read the cost as changed, log the same price again, and the cascade would re-date a made ingredient's cost (`StoredCostPrecisionPersistenceTests`).
- **SubAssemblyRole**: an editable lookup table (`Id`, `Name`, `SortOrder`, `IsPackaging`, `IsProductOwned`), seeded with Dough, Filling, Topping, Inclusion and Finishing. More roles can be added in Settings → Roles. `SortOrder` sets the order of a recipe's sections. A role can't be deleted while any sub-assembly uses it.
  - **The Packaging role**: seeded at **Id 6** with `IsPackaging = true`, the only role with the flag. A standalone sub-assembly in it is a **packaging set** (Packaging sets, below). The code checks the flag, never the name, so the role can be renamed; `SubAssemblyRoleRepository.DeleteAsync` refuses to delete it, and nothing in Settings can clear the flag (`UpdateAsync` writes only `Name` and `IsProductOwned`).
  - **Product-owned roles (`IsProductOwned`)**: a checkbox on Settings → Roles (and a read-only Product-owned column in its grid) for the roles a product can own a sub-assembly in, such as Filling, Topping or Pan Greasing; never the Packaging role (`SubAssemblyRoleValidator`, `SubAssemblyRules.EnsureProductOwnedAllowed`, in `AddAsync`/`UpdateAsync`, and the checkbox is disabled for it). See "Product-owned sub-assemblies" under SubAssembly. Not seeded.
- **SubAssembly** + **SubAssemblyLine**: a sub-assembly is an in-house recipe that products use directly, such as a dough, a filling or a topping. Its lines are the ingredients that make it up. **`UpdatedAt`** (`DateTime?`, local time) is when it was last saved, null until a save stamps it: what its form's Save is checked against.
  - **Kept on the Sub-Assemblies screen, or a product's own.** A sub-assembly with no owner (`OwnerProductId` null) is made and edited on the Sub-Assemblies screen, and every product using it links it. One with an owner (`OwnerProductId`, Cascade from `Product`) is that product's own: its lines are edited in the product (`ProductUsageEdit.IsOwned`), it isn't on the Sub-Assemblies screen (`GetStandaloneAsync` leaves it out, and `SaveStandaloneAsync`/`DeleteStandaloneAsync` refuse it), and taking it out of the recipe or deleting the product deletes it. `SaveStandaloneAsync` writes the name, role, then the lines through `SubAssemblyLineRepository.SetLinesAsync`, in one transaction.
  - **A new section becomes a sub-assembly on Save.** A section typed in the Products screen's Recipe Structure (New, Copy an existing one, or Make a Copy of a linked one) goes to `SetRecipeAsync` as a `NewSubAssemblyDraft(RoleId, Lines, AuthoredField, AuthoredValue, SectionName)` with an `Id` (0 for new, else the product's own saved one, rewritten in place) and a `Placement` (`SectionPlacement`, one case for each thing the form can ask): `ByRole` (the product's own in a product-owned role, otherwise kept on the Sub-Assemblies screen and linked), `ProductsOwn` (its own whatever its role: an unlinked section, or a clone's copy of its source's own), `MoveToSubAssemblies` and `MoveToInHouse(MadeIngredientDraft)` (below). A saved one of the product's own is released only when it moves **out of a product-owned role** into one that isn't (the stored role's flag is read before `RoleId` changes); one unlinked in a plain role stays its own wherever it moves. `RecipeDraft` carries `(New, Linked, Components)`.
  - **Its name is the product's and the role's** (`SubAssemblyRules.StandaloneNameFor`): "Cheese Roll Dough", and with the section's own name after them when it has one that isn't just the role's, "Cheese Roll Filling: Cheese". The product's name is read inside the save's transaction, so a new or renamed product saves under its new name. **A name already taken gets the next number**, "Cheese Roll Dough 2" (`UniqueStandaloneName`, case- and space-insensitively, against every sub-assembly and the ones the same save just made), cut short to fit 100 characters with its number. Renaming a product later leaves the names of the sub-assemblies it saved to the Sub-Assemblies screen alone; **its own are renamed with it**, and with their role (`ProductRepository.UpdateAsync`, which `SaveAsync` runs even without a recipe, and `SubAssemblyRoleRepository.UpdateAsync`, whether or not the role is product-owned), when they're named after them (`SubAssemblyRules.IsNamedAfter`, numbered or cut to fit or not: one named otherwise keeps its name). Renames go through `SubAssemblyRepository.RenameAsync`: a throwaway name first, then the new ones, so two can swap.
  - **How a section goes by its name in a recipe** (`SubAssemblyRules.LabelIn`): a product's own by its **stored** label (`SubAssembly.SectionName`), never parsed back out of its name, since a name numbered when the plain one was taken ("Cheese Roll Filling 2") would read as a section called all of that; a linked one by `SectionLabel(name, productName, roleName)`, less the "Cheese Roll Filling: " it was saved under from that product (the tab reads "Filling: Cheese"), nothing at all when it's exactly "Cheese Roll Filling" (it goes by its role alone), and another product's by its whole name ("Filling: Ube Bun Filling"). Save, Clone and a role made product-owned write `SectionName`, and a role made not product-owned clears it. A version snapshot keeps each section's label (`VersionSection.Label`). `SetRecipeAsync`, `EnsureDistinctWhereLinkedAsync` and the Products form all read labels the same way.
  - **A product can have several sub-assemblies in one role, its own and linked together, as long as they can be told apart** (`SubAssemblyRules.EnsureSectionsDistinct`, in `SetRecipeAsync` and on the Products form's Apply): within a role no two go by the same label (case- and space-insensitively), and at most one goes without. A section's own name is optional, trimmed, at most 100 characters (`EnsureValidSectionName`). **A new role or name can't leave a linking product unable to tell its sections apart**: a rename or a new role on the Sub-Assemblies screen is refused when a product linking it would then have two in a role by one label, naming that product (`SubAssemblyRepository.EnsureDistinctWhereLinkedAsync`).
  - **Removing a section, or deleting the product, keeps a linked sub-assembly**: `SetRecipeAsync` only replaces the usages, a product's usages cascade, and the usage's sub-assembly FK is Restrict. What's left unused stays on the Sub-Assemblies screen until it's deleted there. **It can't be deleted from under a product that links it**: its Delete there is refused while any product uses it, naming them (`EnsureNoneLinkedElsewhereAsync`, `SubAssemblyRules.EnsureNotLinkedElsewhere`: "Cream Loaf Mini links Sweet Dough. Make a copy of it there, or remove it there, first.").
  - **Product-owned sub-assemblies**, in a role whose `IsProductOwned` is set, or unlinked into a product:
    - **Copy only**: another product can copy one (the Copy picker lists it as "Cheese Roll Filling: Cheese — Cheese Roll (Filling)", `GetLinkableAsync` bringing each one's owner) but never link it (`SubAssemblyRules.EnsureLinkable` in `SetRecipeAsync`; the Link picker leaves it out), so nothing but its product uses it, and it can be changed or removed freely. **Its product's variants link it** (Create Variant, below), the one exception.
    - **Turning a role product-owned** (`SubAssemblyRoleRepository.UpdateAsync`, one transaction, after a confirmation saying how many move, `CountOwnershipChangesAsync`): each of its sub-assemblies on the Sub-Assemblies screen that exactly one product's recipe uses becomes that product's own, keeping its name (`AdoptSingleUseAsync`), and that product's add-ins on it are merged into its lines, after its own. Used by several, or none, it stays. **Turning it off** releases every one products own in it to the Sub-Assemblies screen, still linked by the same product (`ReleaseOwnedAsync`); merged add-ins stay merged, which the confirmation says, and unlinked ones go too, since nothing tells them apart without a column. The Products screen picks either up on its next refresh: with nothing typed it reads the product again, so what Save compares against is how it's saved now.
    - **Clone and Create Variant give the new product its own copy of each owned section** (named after the new product; lines, piece size and what it went by), drafted `ProductsOwn`, and link what the source links (`ProductCloner.DerivedRecipe`).
  - **What a linked section's form offers** (Products):
    - **Make a Copy** and **Unlink** (`UnlinkCommand`), which both build the copy in `CopyOfLinked`, its add-ins merged into its lines. Make a Copy follows the role (the product's own in a product-owned role, otherwise kept on the Sub-Assemblies screen and linked). Unlink makes the copy **the product's own whatever its role**: its Role and Name show at once in place of the linked badge (`ProductUsageEdit` takes `isOwn`; `IsOwned` is `LinkedName is null && (SubAssemblyId > 0 || isOwn)`), and Save sends it as `ProductsOwn`. The one it was linked to stays on the Sub-Assemblies screen as it was.
    - **Undo puts the form back clean.** `UndoHistory` keeps, beside each step, the settled snapshot as it stood when the step was taken (`TryUndo`/`TryRedo(out restore, out settled)`), and `ProductsState.RestoreSnapshot` ends by rebasing that snapshot's form and tabs (`WithFormOf`) onto it. So undoing an Unlink or a Make a Copy stops offering Save, while typing put back that wasn't yet in the recipe still counts. The recipe, costing and header stay as settled now, so a costing-defaults rebase in between isn't lost. Raw Materials and Sub-Assemblies don't rebase their forms.
    - **Change the link in place**: an Edit glyph beside the badge (`ProductUsageForm.StartChangingLinkCommand`) swaps it for a searchable picker (`ChangeLinkOptions`: the Sub-Assemblies screen's recipes the recipe doesn't use yet, any role, never packaging or a product's own) and a cancel glyph (`ProductUsageForm.CancelChangingLinkCommand`). Picking one (`ChangeLinkTarget`) runs `ChangeLinkAsync`, which reads the new one's lines and replaces the section in place (`ReplaceUsage`, one undo step), so it keeps its tab, which takes the new one's role and name. The piece size (the typed figure) and add-ins carry over, less any add-in the new recipe already has, which a toast names. Lines edited in the old link's form but not saved go with it. Save writes the new link; the old sub-assembly stays on the Sub-Assemblies screen.
    - **Its lines are edited in the product**, and written with the product's Save, so Undo and Revert cover the change; Save asks first, naming the other products using it. The lines grid is typed into like an own one's (`ProductUsageForm.IsFormLinesEditable`; only a link being picked shows its lines read-only), and its role and name stay the Sub-Assemblies screen's. `ProductUsageEdit` keeps the lines as last read, and only when `AreLinkedLinesEdited` (ingredients, grams and base ticks, not costs) does `ProductRecipe.CurrentDraft` send them, as `LinkedUsageDraft.Lines` (null otherwise), so a product's Save never puts back lines the Sub-Assemblies screen changed since. `SetRecipeAsync` checks them with `EnsureValidLines` up front, checks this product's add-ins against them rather than the stored ones, and relines the sub-assembly before writing the add-ins, all in the product's transaction. A refresh keeps lines changed here (`WithLinked`). Save reads `GetStandaloneLinkedByAsync` and asks through `ConfirmDelete`: "Save changes the lines of Cream Loaf Dough, also used by Cream Loaf. Their recipes and costs change with it. Save anyway?"; declined, nothing is written and the change stays in the form. Not checked, as on the Sub-Assemblies screen: a new line that *another* product has as an add-in on the same sub-assembly.
  - **What a section of the product's own offers**:
    - **Move to Sub-Assemblies**, Unlink's reverse, in any role (`MoveToSubAssembliesCommand`, shown by `IsEditingOwnedUsage`). It applies whatever is typed into the form first (`ApplyUsageForm`; a refused one stays, with the message), so what moves is what shows, then marks the section (`ProductUsageEdit.IsReleasing`, via `Released()`), in one undo step. Until Save the section is still edited here, with a "Moves to Sub-Assemblies on Save" badge. Save sends it as `MoveToSubAssemblies`, which `SetRecipeAsync` puts ahead of the role: a saved one keeps its id, name and the lines just written, loses its owner, and the product links it at the same piece size; a new one is kept on the Sub-Assemblies screen, named after the product. In a product-owned role it stays there; only turning the role's flag off and on again would adopt it back. The Packaging tab has the same for the product's own packaging lines (Derived products, below).
    - **Move to In-House** (`MoveToInHouseCommand`, shown by `CanMoveEditingUsageToInHouse`): Save moves the section to the Sub-Assemblies screen as Move to Sub-Assemblies does (`SectionPlacement.MoveToInHouse` is a move there too: `MovesToSubAssemblies`), keeping its lines and baker's percentages, links the product to it at the same piece size, and adds a made ingredient made from it (`RawMaterialRepository.AddMadeAsync(dbContext, made, subAssemblyId)`, 0% loss, no add-ins, so it costs per gram what the recipe does; the real loss is set on the Raw Materials screen afterwards). The prompt (`PromptForMadeIngredient`, built by `MadeIngredientPrompt.RequestFor`) asks for the name, starting with the section's saved name, and a Made category, read fresh on each click and starting on In-House when one has that name; with no Made category it says to add one; a taken name is refused (`SubAssemblyRules.EnsureValidMadeIngredientName`). Its badge reads "Moves to Sub-Assemblies and In-House on Save, as …", and the snapshot compares `ToMadeIngredient`, so Undo stops offering Save. **On the Sub-Assemblies screen** the list's **Make In-House Ingredient…** (`MakeInHouseIngredientCommand`, `ISubAssemblyRepository.AddMadeIngredientAsync`) adds a made ingredient made from a recipe there, and leaves the recipe, its products and their versions alone.
    - **Why made ingredients and sub-assemblies both exist**: a `SubAssemblyLine` only references an ingredient, so a made ingredient is the only way one recipe goes inside another (Butter Icing is a line in many toppings), and only a made ingredient has a weight loss. Nesting sub-assemblies instead was rejected: the cascade's two fixed steps would become one mixed ordering.
  - `RoleId` (FK to `SubAssemblyRole`, required): each sub-assembly has exactly one role, so custard is always a Filling. It can change at any time; every recipe using the sub-assembly then shows it in the new role's place.
  - Each line has an FK to an ingredient (a `RawMaterial` of the Ingredient type, refused otherwise) and `Grams`. Line cost = grams × the ingredient's `BufferedCostPerBaseUnit`. `SubAssemblyRules.EnsureValidLines` refuses no lines, non-positive grams or an ingredient twice, so a sub-assembly always has a batch.
  - **A sub-assembly's batch weight and cost are worked out on read** from its lines (`SubAssemblyRules.CalculateTotals`), never stored, so there's nothing to keep in step when a line or an ingredient's cost changes.
  - **Baker's percentage: `SubAssemblyLine.IsFormulaBase`.** Each line reads as a percentage of the ticked lines' total weight, the formula's 100% base, usually the flour. `SubAssemblyRules.FormulaBaseWeight` sums the ticked lines and `CalculateBakersPercent(grams, baseWeight)` gives the figure, **null when nothing is ticked**. The sum of every line's percentage ("whole formula 201.5%" under the table) is the number a batch is scaled by (`flour = target ÷ (total% ÷ 100)`).
    - **Per line, not per ingredient**, rather than an `IsFlour` flag on the raw material: sugar is the base of a syrup and an extra in a dough, two flours tick together and make 100% between them, and it never depends on a user-editable category. Named `IsFormulaBase` because "base" already means a *unit of measure* in this codebase (`BaseUnitId`, `CostPerBaseUnit`); the column header is "Base".
    - **Nothing about cost changes.** Grams are the source of truth; the tick is a reading of the batch, never stored as a figure.
    - **Lines travel as `RecipeLine`** (`ApplicationCore/Interfaces/RecipeLine.cs`), a `readonly record struct (IngredientId, Grams, IsFormulaBase = false, AuthoredBakersPercent = null)` with an **implicit conversion from the `(IngredientId, Grams)` tuple**, so tests write `[(flourId, 1000m)]`. The same conversion makes a *lossy* projection compile silently (`.Select(l => (l.IngredientId, l.Grams))` drops the tick and the typed percentage without an error), so the places that rebuild lines from existing data name them explicitly: `ProductRecipe.CurrentDraft()` (miss it and ticks never save, and `IsSameRecipe` never sees the change), `SubAssembliesState`'s save, and `ProductCloner`'s own-copy branch. Anything that carries sub-assembly lines from one place to another has to do the same.
    - **Add-ins have no tick** and stay on the plain tuple (`LinkedUsageDraft.AddIns`, `UsageAddInLineRepository`): an add-in is never part of the base. Each still gets a percentage, **read against the linked recipe's base**: 100 g of buttermilk on a dough's 1,000 g of flour reads 10.0, and the whole-formula figure includes it.
    - **Typed either way, and whichever was typed stays put.** A line's grams or its baker's percentage can be typed; the other is worked out. **`SubAssemblyLine.AuthoredBakersPercent`** (nullable) records a typed percentage, null when the grams were typed, the same idea as a usage's `AuthoredField`/`AuthoredValue`. When the base weight changes, a line typed as a percentage has its grams worked out again (`SubAssemblyRules.GramsFromBakersPercent`), and a line typed in grams keeps them while its percentage moves: on 1,000 g of flour, water typed as 65% and eggs typed as 100 g; double the flour and the water is 1,300 g, still 65%, while the eggs stay 100 g at 5%.
      - **Grams are still stored for every line** and still all that's costed. A typed percentage is worked back into grams the moment the base changes, in the form, and saved that way, so the stored grams are never stale. `GramsFromBakersPercent` rounds to the 4 decimals grams are stored in, so reopening a saved line reproduces exactly what was worked out; unrounded, a line could come back a ten-thousandth off and make a recipe nobody touched look changed.
      - **Any change to the base weight counts**: a base line's grams, a tick, or a base line added or removed. Ticking a line into the base makes it a grams line (the base is 100% between its lines by definition), and `EnsureValidLines` refuses a base line carrying a percentage. With nothing ticked, a typed percentage keeps its last grams and waits: tick the flour again and the line follows it.
      - **Where it can't be typed, it won't open**: on a base line, and while nothing is ticked (`IngredientLineRow.CanTypeBakersPercent`). The recipe table's box is read-only on the rows that say no (`IngredientLinesGrid`, `NumberField`'s `ReadOnly`). The row's setter ignores such a value too, as a backstop.
      - **Carried everywhere lines are**: `RecipeLine.AuthoredBakersPercent`, `SectionLine`, `ProductUsageEdit.ShowsSameAs`, the three line-copying projections above, `Repriced`, and both add rows' item factories, which hand a new line the current base so a percentage can be typed into it straight away.
      - **Add-ins can be typed either way, but only grams are kept.** An add-in's base is the linked recipe's, which can change on another screen; remembering a typed percentage would mean working its grams out on every read, in Products and Reports alike, from a base those screens don't load.
    - **With nothing ticked, the column shows absolute percentage**: `SubAssemblyRules.CalculateAbsolutePercent(grams, batchWeight)`, a line's share of the whole batch, so the lines come to 100 between them. `IngredientLineRow.Percent` reads baker's percentage while `BaseWeight > 0` and absolute percentage against `BatchWeight` otherwise; `ApplyFormulaBase` hands every row both weights, and the batch counts the rows with an ingredient picked (`IngredientLineRow.BatchWeightOf`).
      - **The header follows** (`SubAssemblyBatch.PercentHeader`, `ProductUsageForm.UsageFormPercentHeader`, both from `IngredientLineRow.PercentHeader`): `IngredientLinesGrid` draws it in its own header cell (its `PercentHeader` parameter), so it changes with the table. The caption under the table says "Absolute %: each line's share of the batch. Tick the base — usually the flour — for baker's %."
      - **Read-only.** `CanTypeBakersPercent` is false without a base; the row's setter checks it before a cleared value, so a line whose typed baker's percentage is waiting for a base to come back doesn't lose it.
      - **On a linked recipe with add-ins, both tables divide by the whole batch**: the recipe's lines and the add-ins together come to 100%. With a base, add-ins are read against the recipe's base.
    - Not modelled: a preferment (a sponge made as a made ingredient) ticked as the base counts its whole weight, not the flour inside it; and true hydration, counting the water in milk and eggs.
- **Packaging sets: SubAssembly in the Packaging role + SubAssemblyPackagingLine.** A standalone sub-assembly whose role has `IsPackaging` holds packaging materials **per set** instead of ingredients in grams: a gift box with its ribbon and tag, or the 8 bags and the box that make up an "Ensaymada Box of 8".
  - **`SubAssemblyPackagingLine`** (`SubAssemblyId` Cascade, `PackagingMaterialId` Restrict to a `RawMaterial` of the Packaging type, `UnitId?` Restrict to a `RawMaterialUnit`, `QtyPerSet` > 0 in that unit; unique per set + material; `CK_SubAssemblyPackagingLines_QtyPerSet`). A table of its own, not `SubAssemblyLine`, which is ingredients in grams and feeds the cost cascade.
    - **`UnitId?`**: the unit the quantity is entered in, one of the material's own alternative units, or its base unit when empty, as `PackagingLine.UnitId` has it. The quantity is stored as typed and converted at cost time, so 1 roll stays 1 roll rather than the 1,000 cm it comes to, and correcting the roll's multiplier reprices the line without rewriting it. `SubAssemblyRepository.SaveStandalonePackagingAsync` refuses a unit that isn't that material's own, with the message `PackagingLineRepository.SetLinesAsync` uses, and `RawMaterialUnitRepository.DeleteAsync` counts set lines beside packaging lines before it lets a unit go.
  - **Costed on read**, like a product's packaging lines. A set has no ingredient lines, so the cost propagator never meets one.
  - **Standalone only.** A recipe section never takes the Packaging role (`SubAssemblyRules.EnsureRecipeRole`, in `SetRecipeAsync`; the Products form's role picker leaves it out), and `GetLinkableAsync` leaves sets out of the recipe link/copy picker.
  - **The kind is fixed once saved**, as a raw material's type is: `SubAssemblyRules.EnsureKindUnchanged` refuses moving a saved recipe to the Packaging role or a saved set to a recipe role. `SaveStandaloneAsync` refuses the Packaging role; `SaveStandalonePackagingAsync` requires it (one transaction: name and role through the shared `StageStandaloneAsync`, then `SubAssemblyRules.EnsureValidPackagingLines` (at least one line, positive quantities, no material twice) and `RawMaterialRules.EnsureUsableAsPackaging` per material, then the lines replaced).
  - **Used by a product's packaging, one whole set per sellable unit**, linked or copied from the Products screen's Add Sub-Assembly ("Link the packaging" under Derived products). A packaging material's base unit is fixed once a set uses it too (`RawMaterialRepository.UpdateAsync`'s `hasLines`).
  - **Deleting a linked set is refused**, naming the products (`DeleteStandaloneAsync`, the wording of `EnsureNotLinkedElsewhere`), and `GetStandaloneLinkedByAsync` counts packaging links, so the screen's Dependents names them.
- **Product** + **ProductSubAssemblyUsage**: a finished product is built from distinct sub-assemblies, its own and linked ones. It can use several in one role, e.g. an ube filling and a cheese filling, told apart by their labels (SubAssembly, above), and each sub-assembly only once.
  - **`Description`** (optional, at most 500 characters: `ProductValidator.MaxDescriptionLength`, which `ProductConfiguration`'s `HasMaxLength` also uses) and **`UpdatedAt`** (`DateTime?`, local time) for the Products screen's header. `UpdatedAt` is stamped by `ProductRepository`'s add and update, so by the screen's Save and by a clone when it's made; null shows as "—". It's also what the form's Save is checked against.
  - **`CurrentPrice`** (`decimal?`, per sellable unit, VAT included): what the shop charges now, entered in the Products header beside the computed Selling Price and saved with the product (null until entered; `ProductValidator` refuses a negative one). A clone copies it. It prices nothing: the header shows the **Markup %** it earns, `CostingRules.CalculateMarkupPercentFromPrice` (VAT taken out first, then the markup on the base cost, `(CurrentPrice ÷ (1 + VAT%) − BaseCost) ÷ BaseCost`), the same definition as the costing's Margin, so the computed Selling Price gives back exactly the Margin %.
  - **Each usage has its own piece size, as total weight, yield and weight per piece.** The user types either the **weight per piece** (grams) or the **yield** (pieces per batch), and the other is worked out from the batch's total weight. A usage stores only what was typed: **`AuthoredField`** (`UsageAuthoredField.WeightPerPiece` or `Yield`) and **`AuthoredValue`** (≥ 0, `CK_ProductSubAssemblyUsages_AuthoredValue`).
    - **Neither figure is required**: a section goes into the recipe, and saves, before how much of it a piece takes is known, stored as `AuthoredValue` 0. `ProductRules.EnsureValidUsages` and the check constraint refuse only a negative; an unsized section has a batch but costs the product nothing per piece, and the form's caption says so.
    - **The pieces share out the whole batch: no shrinkage.** What's lost making a product is a cost on it, the Wastage % (Costing defaults, below), not a smaller batch, so `ResolvePieceSize` and `CalculateUsageCostPerPiece` divide the effective batch's total weight. A saved version's sections may still hold a `ShrinkagePercent` in their JSON, which `ProductVersionContent.FromJson` ignores.
    - **A section added in a product-owned role starts at a yield of 1.** Such a section is written for the one piece it goes into, so the add form opens with `AuthoredField` `Yield` and `AuthoredValue` 1 where any other role opens unsized (`ProductsState.StartingPieceSize`), New and Copy alike; a Link stays unsized, its batch being shared. With the yield stored, the weight per piece is the Grams column's total and goes on following the lines after Save. It's the role's start, not an entry: while neither figure has been typed it follows the role picked (`IsPieceSizeAsStarted`), and a form still at it counts as untouched (`IsUsageFormUntouched`); both are worked out from the form rather than remembered, so they hold for a form an undo put back. Saved sections are left as they are.
  - **`ProductRules.ResolvePieceSize(authoredField, authoredValue, totalWeight)`** is the one formula: weight typed → `Yield = TotalWeight / WeightPerPiece`; yield typed → `WeightPerPiece = TotalWeight / Yield`. It's worked out on every read, never stored, which is what makes **the typed figure stay put when the batch changes**: a 60 g piece stays 60 g and the yield moves; a 24-piece yield stays 24 and each piece gets heavier or lighter. Being computed on read, a line edit in one recipe never has to update other products' rows. A batch that weighs nothing has no other figure (0). Every caller passes the effective batch's weight (`SectionFigures.Of`, for `ProductUsageEdit` and saved products, and `ProductUsageForm`'s `Recompute` and `FollowPieceSize`), so the rule stays one line.
  - Usage cost per piece = `TotalCost × WeightPerPiece / TotalWeight` (the effective batch's, worked out from its lines and add-ins), the same as `TotalCost ÷ Yield`. For example, 100 g / ₱24 of filling used at 10 g a piece gives ₱2.40 a piece, yield 10. A per-line share of a piece, should one be wanted, must divide by the usage's *effective* batch (`ProductRules.CalculateEffectiveBatch`), not the sub-assembly's own, or a linked usage's add-ins would be left out of every line's share.
  - **UsageAddInLine: a product's own extras on top of a sub-assembly it links.** The same dough goes into several products, but one wants ube flavouring and another pandan colour; without add-ins the only way would be Make a Copy, which breaks the link, so the dough would stop being shared.
    - `UsageAddInLine` (`UsageId` Cascade, `IngredientId` Restrict, `Grams`; unique per usage + ingredient) hangs off the **usage**, not the sub-assembly: two products linking the same dough each keep their own set, and neither moves the dough's own lines.
    - **Add-ins go into the batch**: the usage's **effective batch** is the sub-assembly's plus its add-ins (`ProductRules.CalculateEffectiveBatch`, over `SubAssemblyRules.CalculateTotals`), so 1,700 g of dough with 20 g of flavouring is a 1,720 g batch and a piece takes its weight-per-piece share of the whole thing. The typed figure still stays put, so adding a flavouring moves the other one.
    - **Linked usages only.** A section of the product's own has no add-ins: its extras just go in its lines, and a second table there would be two ways to do one thing.
    - **An ingredient the linked recipe already has is refused** (`ProductRules.EnsureValidAddIns`, rather than merging the grams): "Water is already in Variety Bread Dough. Add-ins are only for what its recipe doesn't have — change how much it uses where Variety Bread Dough is kept, or make this product a copy of it." Checked in the form as Apply is pressed, and again in `SetRecipeAsync`'s pre-flight and `UsageAddInLineRepository.SetLinesAsync` as it writes. An empty set is valid: most linked usages take the recipe as it is.
      - That guard is load-bearing: since an add-in can never duplicate a base ingredient, **Make a Copy and Unlink concatenate the base lines and the add-ins** into the new sub-assembly's lines without a merge step, and the result always passes `EnsureValidLines`. The batch it was showing is the batch it keeps.
    - **Written with the rest of the recipe**: `LinkedUsageDraft.AddIns` (an `init` property). `SetRecipeAsync` adds the linked usages together, saves once so every one has the id its add-ins need, then writes each one's lines. `ProductSubAssemblyUsageRepository.GetAddInsForProductAsync` reads them back. Everything that prices a product goes through `SavedProductReader` or `ProductUsageEdit`, both on `CalculateEffectiveBatch`, so no figure leaves add-ins out.
  - A product has **no yield of its own**. Each usage has its own yield, and those usually differ between a product's sub-assemblies. That's expected, not an error.
  - Product material cost per piece = the sum of all its usages' cost per piece; its packaging lines are per sellable unit (Quantity Required, below).
  - Sub-assembly and product weights are raw input weights; baking and moisture loss aren't modelled for them. Made ingredients are the only place weight loss is (`WeightLossPercent`), and Wastage % is the product's allowance for what's lost making it.
- **PackagingLine**: one packaging material used by one whole sellable unit of a product: its wrapper, its box, its label, its ribbon. "Unit" throughout this bullet means that sellable unit, which is one finished piece unless the product's `QuantityRequired` says otherwise.
  - FK to a `RawMaterial` of the Packaging type (`PackagingLineRepository` refuses an ingredient).
  - **`UnitId?`**: the unit the line's quantities are entered in, one of the material's own units, or its base unit when empty. Quantities are stored as entered, in that unit.
  - **`QtyPerUnit`**: amount of the packaging material used by one sellable unit, in the line's unit (12.7 for 12.7 cm of ribbon, `0.1667` for a 6-piece box, 1 for a label). **Typed, and never rescaled**: changing a product's `QuantityRequired` from 8 to 12 doesn't touch it, so the packaging is revisited by hand. The Packaging tab's caption says which unit the figures are for (`ProductCosting.CostUnitCaption`).
  - **`UnitsPerPackagingUnit`**: sellable units served by one of the line's unit of the packaging material (6 for that box).
  - **`AuthoredField`**: which of the two the user typed; the other is recalculated as its reciprocal on every edit. Ribbon is naturally entered as `QtyPerUnit`, a box as `UnitsPerPackagingUnit`. Its members are stored as ints, so they may be renamed but **never reordered**.
  - **`IsBulk`** (2026-11-10): a line of the product's **bulk packaging**, what one bulk pack takes (a box several units share, its tape), its `QtyPerUnit` per **pack**, not per unit. Kept apart from the lines for each unit: the unique index is `{ProductId, PackagingMaterialId, IsBulk}`, so tape can be both. **`Product.BulkPackagingQuantity`** (`int?`, `CK_Products_BulkPackagingQuantity` ≥ 1) is how many sellable units one pack holds, set while it has bulk lines and null otherwise (`ProductRules.EnsureValidBulkPackaging`). What it costs a unit is the pack's lines' cost over that (`ProductRules.CalculateBulkPackagingCost`, `PricedBulkPackaging.CostPerUnit`), one more entry in `ProductCostInputs.PackagingCosts`. See Derived products, "Bulk packaging".
  - The unique index is **`{ProductId, PackagingMaterialId, IsBulk}`**: one line per material for each unit, and one in the bulk pack; a material a unit takes twice belongs on one line at the combined quantity.
  - Cost per unit = `BufferedCostPerBaseUnit × QtyPerUnit` converted to base units (`ProductRules.CalculatePackagingLineCost(costPerBaseUnit, qtyPerUnit, baseUnitsPerEntryUnit?)`), computed on read. It's a cost per *sellable unit*, so `CalculateMaterialCost` adds it once however many pieces that unit holds.
  - Example: a ribbon costs ₱45.00 per roll. Its base unit is cm and a roll holds 1000 cm, so it costs ₱0.045 per cm. One product uses 12.7 cm per piece (₱0.5715); another is entered as 0.08 m per piece (8 cm → ₱0.36).
  - Storing both directions differs from `ProductSubAssemblyUsage` on purpose: people describe packaging quantities both ways, but recipe weights only one way.
- **Quantity Required** (`Product.QuantityRequired`): how many finished pieces make one sellable unit. 1 for a product sold by the piece, which is nearly all of them; 8 for "Ensaymada Box of 8". `int`, defaulting to 1 in the CLR and in the database, `CK_Products_QuantityRequired` keeping it positive, and `ProductValidator` refusing anything below 1 on the screen.
  - **The recipe is authored per piece, costing and pricing are per sellable unit, and this is the bridge.** `ProductRules.CalculateMaterialCost(usageCostsPerPiece, quantityRequired, packagingCosts)` = `usageCostsPerPiece.Sum() × quantityRequired + packagingCosts.Sum()`: only the usages are multiplied, since a packaging line is already for one whole unit.
  - **`ProductConfiguration` sets `HasDefaultValue(1).HasSentinel(-1)`.** The sentinel moves "leave it to the database" off 0, which EF would otherwise take it to be: without it a product explicitly saved as 0 pieces would be quietly stored as 1 on an insert while being refused on an update.
  - **A pack is a product**: a variant of the single, with a Quantity Required and packaging of its own, so it has a price, a markup, a category and a row in the list like any product.
  - **The worked example**, which `ProductQuantityRequiredPersistenceTests` pins: Ensaymada takes 10 g of a 1,000 g / ₱50 dough, so ₱0.50 of recipe a piece. "Ensaymada Box of 8" is **Create Variant** of it (the recipe linked, so still 10 g a piece) with Quantity Required 8 and its packaging linked to a standalone **packaging set** holding the 8 bags (`QtyPerSet` 8) and the one box (`QtyPerSet` 1). Its material cost is `8 × ₱0.50 + 8 × ₱0.25 + ₱12 = ₱18`.
  - **The per-piece wrapper is written down twice**, rather than giving a product a second packaging slot. A product's packaging is its own lines **or** one `PackagingLink`, never both (`CK_PackagingLinks_OneTarget`), so a boxed variant can't read the single's wrapper *and* link a box set; the set carries both instead. (A box several units share, on top of either, is bulk packaging.) Prices still follow on their own, since both point at the same `RawMaterial`; only the composition is duplicated.
  - **Pricing is linear in the sub-assembly cost** (labor, overhead and administrative are percentages of it, packaging passes straight through, margin and VAT are multiplicative), so **a unit of 8 with no packaging of its own prices at exactly 8 times the single's price**: its own packaging is the whole of the difference. Pinned by a test in `CostingRulesTests`.
  - **Every figure on the Products screen is per sellable unit**: the header's Material Cost, Base Cost, Current Price and Markup % (`ProductHeader`), and the whole of the Costing tab's breakdown (`Costing`). `ProductCosting.CostUnitCaption` ("Per piece", or "Per unit of 8 pieces") is bound into their tooltips, the breakdown's column header and the Packaging tab's caption. The recipe tabs stay per piece: a usage's weight per piece, yield and cost per piece.
  - **Typed in on the header's row of fields** (`ProductHeader`), beside Current Price (a `NumberField` of `int`, at least 1). Undo covers it (`ProductFormSnapshot.QuantityRequired`), a clone and a variant both copy it, and Reports' Product Cost Summary is per unit too, with a Pieces column saying how many.
- **Composite products** (`Product.IsComposite`): a product made of other products and its own packaging, such as a Pasalubong Box of 6 Ensaymada and 4 Cheese Rolls.
  - **A kind of product holding products and packaging, fixed once saved**, rather than letting any product take in whole products beside its own sub-assemblies.
    - It's picked with New ▸ New composite product, or New Composite Product (Here) in the list.
    - `CompositeProductRules.EnsureKindUnchanged`, in `ProductRepository.UpdateAsync`, refuses a change, as `RawMaterialRules.EnsureTypeUnchanged` does for a raw material.
    - `ProductComponentRepository.SetComponentsAsync` refuses products for a product of sub-assemblies.
    - **Its own sections are only in product-owned roles** (`SubAssemblyRole.IsProductOwned`, reused rather than a second per-role flag), such as a topping or a filling.
      - `CompositeProductRules.EnsureSectionRoles`, run by `SaveAsync` through `ProductComponentRepository.EnsureSectionRolesAsync`, refuses a section, new or linked, in any other role, naming it.
      - `SubAssemblyRoleRepository.UpdateAsync` refuses unticking Product-owned while a composite has a section in the role, and `SubAssemblyRepository`'s standalone save refuses moving a sub-assembly a composite links into a role that isn't product-owned. Both name the composites (`CompositesUsingRoleAsync`).
      - A composite is one unit, so a section's piece size is per whole composite, and its cost per piece joins the products' lines in the recipe cost. A composite held in another brings that whole recipe cost, sections included.
      - Clone and Create Variant copy or link its sections as any product's (`DerivedRecipe`). Raw Materials' Dependents takes any product's sections (`SectionUsers`), and `RecipeUsers` climbs from there.
    - It's always **one sellable unit**, `QuantityRequired` 1. `CompositeProductRules.EnsureOneUnit` (in the static Add and Update), `ProductValidator` and `CK_Products_CompositeIsOneUnit` all enforce it.
  - **Each product brings its recipe cost, as a Box of 8 does**, rather than its recipe and its packaging, or its full base cost with only the composite's markup and VAT on top.
    - A line brings the product's Sub-assemblies (ingredients) figure for one sellable unit, × the line's quantity (`CompositeProductRules.CalculateComponentCost`).
    - Its packaging stays out, so the composite's packaging covers the box and anything wrapping the pieces, the same choice as the per-piece wrapper written into a Box of 8's set.
    - The composite's own labor, overhead, admin, wastage, markup and VAT apply to that recipe cost as for any product. So `ProductCostSummary` takes the lines, then its sections, as its `ProductCostInputs.Parts` at a quantity of 1, and every formula is unchanged; `IsComposite` and `HasOwnSections` only rename the rows (`PartsTitle` "Products (ingredients)", or "Products and sub-assemblies (ingredients)" with sections).
    - Pricing stays linear: products at the same percentages and a composite with no packaging price at exactly the sum of their prices. `SavedProductReaderCompositeTests` pins it: 2.50 → 5.096 and 5.00 → 10.192 make 12.50 → 25.48.
  - **Include each product's packaging** (`Product.IncludesComponentPackaging`), off by default, for pieces that go into the box already wrapped.
    - **It joins the composite's packaging, not its recipe cost**: labor, overhead and administrative, percentages of the recipe alone, don't go on it, as for any packaging. So products at the same percentages still price at exactly the sum of their prices with their packaging in, which `SavedProductReaderCompositeTests` pins.
    - A line brings its product's Packaging figure for one sellable unit × its quantity (`CompositeProductRules.CalculateComponentPackagingCost`). A composite held in another brings all of its Packaging figure, its own products' included when it has the box ticked, so it nests the way the recipe cost does.
    - `SavedProductReader.ReadComponentCostsAsync` returns `ComponentCosts`: recipe and packaging, buffered and unbuffered, from the one read. `ProductCostSummary` takes it as `ProductCostInputs.ComponentPackaging` (null when not ticked), keeps `OwnPackaging` (its own lines and bulk share) apart from its products', and names the row `PackagingTitle`, "Packaging (own and products')" when ticked, on screen and in print.
    - Only a composite can have it: `CompositeProductRules.EnsureComponentPackagingOnComposite` in the static Add and Update, and `CK_Products_ComponentPackagingOnComposite`. Clone and Create Variant copy it.
    - Raw Materials' Dependents climbs for it: `PackagingCosts` in `DependentsSql` goes from every product whose packaging cost the material is in to each composite with the box ticked holding it, and on up. It's a CTE of its own because a packaging link takes only the linked product's lines, so `PackagingUsers` mustn't climb through composites.
  - **Composites nest, with a loop check.**
    - `CompositeProductRules.EnsureNoCycle`/`Contains` check every other composite's lines, in `SetComponentsAsync`. The message names both: "Party Package can't go into Pasalubong Box: it already contains Pasalubong Box, so …".
    - The picker leaves out the composite and every composite holding it.
    - A composite holding itself, as only an edit outside the app can leave one, is read with the loop cut where it closes (the product that comes round again brings nothing there, `ComponentCosts.None`) and flagged (`ProductDetail.HoldsItself`), which the Products screen says when it opens it (`CompositeProductRules.HoldsItselfText`); Save goes on refusing the loop. Refusing the read instead would fail every product's read in a batch: the list, Reports, Print and both servers.
  - **At least two different products** (`CompositeProductRules.MinimumProducts`): six of one product is a Box of 6. A new composite saved with a null recipe (the form's unchanged-recipe shortcut sends none) counts as holding none, so the rule can't be skipped. The public `AddAsync` refuses a composite: only `SaveAsync` writes one with its products.
  - **Quantity**: a whole number, 1 or more, counting the component's sellable units. 1 of "Ensaymada Box of 8" is the whole box and brings 8 pieces' recipe. Every variant is a product of its own, so each is a line of its own.
  - **Storage**: `ProductComponent`. `ProductId` cascades. `ComponentProductId` is Restrict: a product in a composite can't be deleted, and `ProductRepository.DeleteAsync` names the composites before the key would refuse ("Pasalubong Box holds this product. Take it out there first."). `Quantity` is an int above 0, and `SortOrder` records the dragged order. It's unique per composite and product, with `CK_ProductComponents_Quantity` and `CK_ProductComponents_NotItself`.
  - **Written as the recipe**: `RecipeDraft.Components` is an init property. `ProductComponentRepository` is static, like `UsageAddInLineRepository`; its reads are `IProductRepository.GetComponentsAsync` and `GetAllComponentsAsync`.
  - **Worked out on read, nothing stored**: `SavedProductReader.ReadDetailAsync` reads a composite's lines and prices each product through itself, recursively (`ProductDetail.Components`, `SavedComponent`). So a composite's line always matches its product's own Costing tab, in Reports and Print as on the screen. `ReadComponentCostsAsync(ids)` serves the screen.
  - **Clone and Create Variant** give the copy the same products at the same quantities (`SetComponentsAsync`). Create Variant still links the packaging.
  - **Raw Materials' Dependents** climbs `ProductComponents` for an ingredient, however deep. For packaging it climbs only into composites that include their products' packaging (above).

- **Line order: every line table stores each line's position.** `SortOrder` (an `int`, from 0) is on `SubAssemblyLine`, `SubAssemblyPackagingLine`, `IngredientAddInLine`, `PackagingLine`, `UsageAddInLine` and `ProductComponent`, the tables whose lines the user types in and drags into order (Application Architecture: rows are dragged into order).
  - **Written from the list's order, read in it.** Every `SetLinesAsync` (and `SaveStandalonePackagingAsync`) deletes a set's lines and inserts them again, so each line's `SortOrder` is its index in the list it's handed. Every read that returns lines in order orders by `SortOrder, Id`.
  - **A column, not the Id order**: EF Core inserts several rows in one batch, and the database doesn't promise to hand out identities in that order, so Id order would only be the insert order by habit. A dragged order is the user's, and has to survive a save for certain. Pinned by `LineOrderPersistenceTests`.
- **CostingParameters**: a product's labor, overhead and administrative (office, permits, bookkeeping) percentages, at least 0, and its margin %. **Always independent per product**, even for derived and linked products. **Labor, overhead and administrative are percentages of the sub-assembly (ingredient) cost per piece alone, packaging left out** (`CostingRules.CalculateCostFromSubAssemblyPercent`): 25% labor on ₱20 of sub-assemblies is ₱5. Packaging still goes into the base cost, just not into these three: what they pay for is making the recipe, not wrapping it.
  - **The VAT is the shop's**: `CostingDefaults.VatPercent` (`CK_CostingDefaults_VatPercent`), read live with every product as the wastage is (`ProductDetail.VatPercent`). The Costing tab shows it greyed; Settings changes it, repricing every product. A version snapshot keeps the shop's VAT it was priced with (`ProductVersionContent.VatPercent`; schema 2 and before kept the product's own in their costing, read through `VatThen`), and the History tab lists a change in it, or in the wastage, after the product's own changes (`ProductVersionRules.ShopChanges`), never counted as one.
  - **Apply Costing Defaults** on the Products list's menu, for the products picked, sets their labor, overhead, administrative and markup percentages to the defaults once it's confirmed, in one unit of work with a version of each one it changes, noted "Costing defaults applied" (`VersionedSaves.ApplyCostingAsync`); the product on the form has its unsaved changes saved or thrown away first, and shows its new costing after.
  - **Costing defaults** (`CostingDefaults`): a table of one row (`Id` 1, never an identity, `CK_CostingDefaults_SingleRow`), edited on Settings' **Costing Defaults** tab (`Pages/Settings/CostingDefaults` over `CostingDefaultsState`, checked by `CostingParametersValidator`, and `CostingRules.EnsureValidParameters` in `CostingDefaultsRepository.SetAsync`). It holds two kinds of setting:
    - **Starting values for something new**, which never reach what's saved:
      - **Labor, overhead, administrative and markup %**, a new product's costing. `ProductsState` reads them with every `LoadCommand` (Settings closing reloads the screen on show), and `StartNewProduct` puts them in the Costing fields while what Save compares against stays at none, so the product's first Save writes them as its own `CostingParameters` (all-zero defaults write nothing). A new product still showing the defaults it started with takes up changed ones on the next load; one whose costing was typed into keeps it. A saved product, a clone and a variant keep their own (a saved product without a row shows zeros).
      - **New Products In** (`NewProductStage`, a picker over `CostingDefaultsState.Stages`), the stage New files a product in, Production unless set (`DefaultNewProductStage`). Stored by name as `Product.Stage` is, with `HasSentinel((ProductStage)(-1))`, so EF always writes the stage picked, Innovation (the CLR default) included. It's only New's (and New Composite Product's, from the empty space): New Product Here keeps its folder's, and a clone or a variant starts in Innovation.
      - **Cost Buffer %** (`CostBufferPercent`), a new raw material's, 0 to 100 (`RawMaterialRules.EnsureValidCostBuffer` in `SetAsync`, `CK_CostingDefaults_CostBufferPercent`), 10% unless set (`DefaultCostBufferPercent`), with `HasSentinel(-1m)` so EF always writes it, 0 included. `RawMaterialsState` reads it with every `LoadCommand`, and `ClearForm` (New, New … Here, after Delete) starts `EditingCostBufferPercent` at it. A new material still showing the default takes a changed one on the next load, with `History.Rebase` so it stays clean (`RefreshDefaultCostBuffer`). Only a purchased material keeps it: a linked one inherits and a made one stores 0.
    - **Figures every product is priced with, saved ones included**, so a change reprices them all:
      - **VAT %** (above).
      - **Wastage %** (`WastagePercent`), 0 to 100 (`CostingRules.EnsureValidWastage`, `CK_CostingDefaults_WastagePercent`), 3% unless set (`DefaultWastagePercent`), with `HasSentinel(-1m)`. **A product category can set its own** (`ProductCategory.WastagePercent`, Settings → Product Categories; blank keeps the shop's), and a product is priced with its category's or the shop's (`IProductRepository.GetCategoryWastageForProductsAsync`). It's a **cost allowance** added on top (₱100 × 3% = ₱3), not a physical loss (₱100 ÷ 0.97), a percentage of the **sub-assembly (ingredient) cost per piece alone**, as labor, overhead and administrative are, with those three still on the ingredients before it: `BaseCost = SubAssemblies + Wastage + Packaging + Labor + Overhead + Administrative` (`CostingRules.CalculateSellingPrice`'s `wastagePercent`; `ProductCostSummary.Wastage`/`WastagePercent`/`WastageShare`). `SavedProductReader` stamps `ProductDetail.WastagePercent` on every detail it reads, so Reports, Print, the Price Simulator, composites and both servers have it; the Products screen keeps it from each `LoadCommand` for the live Costing tab (`RefreshCostingDefaults`, which reprices the open product when it changed).
        - **Added once, never at each level of a composite**: a composite's products bring their recipe cost before their wastage (`ComponentCosts` holds `SubAssemblies`), and the composite adds it on all of it, at its own category's figure, never its products', so a composite of products at their own percentages is still priced at exactly what they are together.
        - **Shown** as a **Wastage (3% of sub-assemblies)** row under the sub-assemblies on the Costing tab's breakdown (read-only: Settings owns it), the same line on a printout's costing and the Price Simulator report's, and a **Wastage Cost** column on Reports. The Price Simulator's Raw Material Cost (`ProductCostSummary.Material`) leaves it out, as it leaves labor out.
        - **A version keeps the wastage it was priced with** (`ProductVersionContent.WastagePercent`, null for one saved before there was a wastage, which prices with none), and its today figures take today's (`ProductVersionHistory.WastageNow`). It's the shop's, like a material's price, so it isn't part of a version's recipe (`IsSameRecipe`).
        - Tests whose figures are about something else call `PersistenceTestBase.WithoutWastageAsync()` (or `SetWastageAsync`) first.
      - **Price rounding** (`PriceRoundingStep`: none, 0.25, 0.50, 1, 5 or 10, `CostingRules.PriceRoundingSteps`): the selling price rounded up to the next multiple of it (`CostingRules.RoundPriceUp`; up, never down, so a rounded price still earns at least its markup), as `ProductCostSummary.RoundedSellingPrice`, a price the shop would charge.

- **AccessSettings: the app's password and auto-lock** (2026-11-15, the user's: "let's implement login, note that this app is single user only"; asked, they chose a password with no user name, kept in the database, asked at every start, by a Lock button and by an auto-lock, set on the first start and cleared by a script when forgotten). **Table `access_settings`**, one row (`Id` 1, never an identity, `CK_AccessSettings_SingleRow`): `PasswordHash` and `PasswordSalt` (`bytea`, both or neither, `CK_AccessSettings_PasswordWhole`), `PasswordIterations`, `PasswordChangedAt`, and `AutoLockMinutes` (0 to 240, 0 for never, 15 unless set, `HasSentinel(-1)`, `CK_AccessSettings_AutoLockMinutes`). No row, or no hash, is no password yet.

- **ProductVersion: a product's version history.** A version on **every save that changes a product's recipe or price**, each version's cost shown **as it was then and at today's prices**, and **view and compare, Restore and Notes**.
  - **Table `product_versions`**: `Id`, `ProductId` (Cascade: a product deleted for good takes its history; the Deleted folder keeps it), `Number` (1, 2, 3 … per product, unique with `ProductId`, `CK_ProductVersions_Number` ≥ 1), `SavedAt`, `Note` (optional, at most `ProductVersionRules.MaxNoteLength`, trimmed, blank stored as null), and `Content`, the snapshot as JSON text.
  - **A snapshot is self-contained** (`ApplicationCore/Interfaces/ProductVersionContent.cs`, written and read by source-generated JSON, `ToJson`/`FromJson`, with a `Schema` number so an old snapshot can still be read): the product's quantity required, current price, whether a composite includes its products' packaging, its costing percentages, each section (its sub-assembly's id and name, its label, whether it's the product's own, its role, piece size, lines and add-ins), the shop's VAT and wastage then, its packaging link and the lines it showed (resolved through the link, so a link changed later doesn't change the version), a composite's products with what each brought then, and **every material it uses with its costs then** (both bases, base unit and alternative units). It points at nothing, so a deleted material, sub-assembly or role leaves old versions readable. The name, description, category and stage are kept for display but aren't part of a version's recipe.
  - **Written with the save that makes it, in one transaction** (`Pricing/Versions/VersionedSaves`, over `IUnitOfWork`): `SaveProductAsync` calls `ProductRepository.SaveAsync`, reads the product's `ProductDetail` back inside the same transaction, turns it into the content (`ProductVersionSnapshot.From`) and writes it with `IProductVersionRepository.AddAsync`. A version that can't be written takes the save back with it, and the screen shows the error. `SaveSubAssemblyAsync` (the Sub-Assemblies screen's Save), `MakeProductFromAsync` (Clone and Create Variant) and `ApplyCostingAsync` (Apply Costing Defaults) work the same way.
  - **Only a change of recipe or price makes a version** (`ProductVersionRules.IsSameRecipe`, checked by `AddAsync` against the latest): its sections, lines, add-ins, piece sizes, packaging, products, costing percentages, quantity required and current price. Prices of materials don't count (that's what the today column is for), nor do the name, description or category, so a rename records nothing, nor the shop's VAT and wastage. "Changed" has one definition: `IsSameRecipe` is `ProductVersionRules.Changes` finding nothing to list, so a version never appears with an empty list of changes.
  - **The first version is the product as it was before**: a save of a product with no versions yet first records it as it stood (`Note` "Before version history began", `SavedAt` its `UpdatedAt`), priced at the costs of that moment, so there's something to go back to.
  - **A save elsewhere records the products it changes** (`ProductVersionRecorder`). Sub-Assemblies' Save, and a Products Save that edits shared lines or packaging others link, snapshot every product reading through what's saved (`CaptureAsync`, over `IProductRepository.GetProductsReadingAsync`: usages, packaging links to a set, and packaging links to a product followed recursively in one CTE) and, after the save, record a version of each one whose recipe changed (`RecordChangesAsync`, through `AddRangeAsync`: one transaction, every product's latest in one query), with a baseline first for one with no history. Notes: "{sub-assembly} changed on Sub-Assemblies", "Changed when {product} was saved". The success notice names them (`RecordedMessage`, three named, the rest counted). A Products Save captures only when it writes linked lines (`AreLinkedLinesEdited`) or packaging (`ProductPackaging.ChangedLines`, `ChangedLink`), since nothing else it writes is read by another product; a price-only Save would otherwise read every product sharing its dough, twice. Not recorded: a role change or rename (not part of a recipe), a material's cost (the Today columns), and a composite's held products' recipes (only their quantities are its recipe).
  - **A clone or a variant starts its history** with its first version, noted "Cloned from X, version N" / "Variant of X, version N" (`RecordMadeFromAsync`); the number only when the source as saved is its latest version. Its first Save then records no baseline.
  - **Figures, then and today, are worked out on read, by the code the screen prices with**: `ProductVersionSnapshot.ToDetail` rebuilds a `ProductDetail` from the content, and `SavedProductReader.Build` prices it. Then: its materials at their costs then, and its products at what they brought then. Today: the materials as they are now in their place (`Build`'s `materialsById`, the Price Simulator's way in), and each product at its recipe cost now (`ReadComponentCostsAsync`); a material deleted since keeps its cost then. Both at the screen's cost basis (buffered, or unbuffered when switched).
  - **The History tab** (the Products screen's details tab after Clone, `ProductsState.HistoryTab`; a saved product only): a table of versions, newest first (Version, Saved, Note, Base Cost and Suggested Price then and today, Current Price), the note typed into the table and saved as it's left (`IProductVersionRepository.SetNoteAsync`); under it the picked version's **changes** against the one picked in **Compare With** (the version before, the product as it's saved now, or any other version, always read older to newer; `VersionComparison`, equal by value so a re-read keeps the pick), as lines such as "Dough: Bread Flour 500 g → 450 g", "Packaging: Paper Bag added, 1 pc", "Margin %: 30 → 35"; beside them **Cost Over Time**, an `SfChart` of Base Cost, Suggested Price and Current Price then, from the second version on (`ProductVersionHistory.Trend`; no current price is `NaN`, a gap); and **Restore**. Read when the tab is shown, after every Save, and for a product picked while it shows; hidden, its versions are cleared, so showing it reads them. `ProductsState.LoadCommand` re-reads a showing tab, so a version recorded from Sub-Assemblies shows when Products is shown again.
  - **Restore loads a version into the form as unsaved edits**, in one undo step (`RestoreSnapshot`), so Save keeps it and Undo takes it back. The History tab works it out (`ProductVersionHistory.RestoreCommand`, a `RestoredVersion`) and the screen puts it in the form (`IProductVersionHistoryHost.ApplyVersion`). It puts back the sections, packaging, products, costing percentages, quantity required, current price and whether a composite includes its products' packaging; the name, description, category and stage stay as they are. Section by section:
    - **The product's own** keeps its sub-assembly's id when the product still owns it (rewritten in place by Save); otherwise it comes back as a new section of the product's own.
    - **A linked one is linked again as it is now**: Save never writes a version's lines into a sub-assembly other products may share. When its lines have changed since, the message says so.
    - **A sub-assembly deleted since** comes back as a new section with the version's lines, which Save treats as any new section in its role.
    - **Packaging**: the link, when what it linked still exists; otherwise the lines it showed, as the product's own. A line in an alternative unit deleted since is put in base units.
    - **Refused, naming them**, while a material, role or product it needs no longer exists: nothing is changed.
    - **The section tab showing opens its form afterwards**, as showing it would, and what Save measures against moves onto that form (`RebaseSettledForm`): only the recipe, packaging, costing and price put back count as changes.
  - **Print Version, and Print while the tab shows, prints the version picked.** `PreparePrintout` returns `ProductVersionHistory.PrintoutOf`: the version priced at its costs then and the screen's cost basis, titled "Almond Cheese Bread (Version 2)", dated with its save, its footer note `ProductPrintout.VersionNote`, its category and stage the product's now. The form isn't applied first, and isn't changed. With no version picked, Print says so and the Print tab doesn't open.
  - **Reports' Margin Erosion** reads each product's latest version as of a date (`IProductVersionRepository.GetLatestAsOfAsync`, one query) against its markup now.
  - Tests: `ProductVersionPersistenceTests`, `ProductVersionRulesTests`, `VersionedSavesTests`, `ProductVersionRecorderTests`, `SubAssembliesStateVersionTests` and `ProductsStateVersionTests` (shared lines, a version from another screen, comparing any two, the chart's points, clones and variants, and the commands a price-only Save takes, counted once its background work is done, `SqlCommandCounter.SettledAsync`). The `VersionRecorders` fixture (`Tests.Common`) builds the recorder for the screens' tests.
- **PriceScenario: the Price Simulator's saved scenarios.** Kept **in the database** (shared, and in every backup) rather than per Windows user; **a line keeps what was typed**, so a percentage goes on the price as it is when the scenario is opened and a typed new price stays as saved; and **save, open and delete**, one scenario on screen at a time.
  - **Tables `price_scenarios`** (`Id`, `Name` unique ignoring case, at most `PriceScenarioRules.NameMaxLength` 100, `SavedAt`) **and `price_scenario_lines`** (`PriceScenarioId` Cascade, `RawMaterialId` **Cascade**, `ChangePercent?`, `NewPrice?`, `SortOrder`; unique per scenario and material). Check constraints back up `PriceScenarioRules`: exactly one of `change_percent` and `new_price` (`CK_PriceScenarioLines_OneTyped`), a change above -100%, a price above 0. A material's lines go when it's deleted, rather than blocking the delete, since a scenario is only a trial; one no longer bought (its source changed) is left out when the scenario opens, and the screen says which.
  - **`IPriceScenarioRepository`**: `GetAllAsync` (newest first, then by name, each with its lines, two queries), `SaveAsync(name, lines, savedAt)` (an upsert by name, ignoring case: an existing scenario keeps its name and has its lines replaced, in one transaction; `PriceScenarioRules.EnsureValid` first), `DeleteAsync`.
  - **The screen** (`PriceSimulatorState`): a **Scenarios list at the left of the Price Changes table**, a table of Saved (`MMM d, yyyy  h:mm tt`) and Name, newest first, whose picked row is `SelectedScenario`, under a Scenarios heading with Save Scenario and Delete Scenario. The two sides share the card's rows, so headings, captions and the two 200-high tables line up. `SimulatedPriceChange.ToScenarioLine` gives the typed one of Change % and New Price, and `Open(line)` types it back. The table is compared with what was last opened or saved (`HasUnsavedChanges`, by value); picking a scenario over unsaved changes asks first, and keeping them picks the open scenario again in the list (`OpenScenarioAsync` goes on after a `Task.Yield`, so the list's own pick is over before it's undone). Save asks for a name (the open scenario's to start with, `PromptHost`) and asks again before replacing another scenario of that name. Delete leaves the changes in the table. Clear All closes the scenario too. The list letting go of its pick, as the grid can when its rows are replaced, closes nothing.
  - **Price to Keep Markup**: `PriceChangeRules.PriceToKeepMarkup(currentPrice, baseCost, newBaseCost)` = the current price × the base cost's own factor, since the markup is on the base cost and VAT goes on top, so VAT cancels out; null without a current price or a base cost. The Products table shows **Current Price** before Markup %, and **Price to Keep Markup** after Simulated Markup % (`PriceSimulatorProductRow`); the report prints it under a moved product's Current Price ("To keep markup 61.28", `PrintDocument.KeepMarkupNote`). Not rounded. With 14 columns, the Products table's headings take three lines (`GridHeaderHeight.Lines="3"`).
  - **Unbuffered**: a button on the Products card, before Print Report (`ToggleCostBasisCommand`, `CostBasisButtonLabel`/`Tooltip`, named for the costs it switches to), switches every figure, now and simulated, between the materials' buffered and true costs, with an **Unbuffered costs** badge beside the Products heading (`IsUnbuffered`). Session-only like Products' (`PriceSimulatorState.CostBasis`, buffered at every launch), not part of a scenario and not an unsaved change. A change moves both costs by the same factor (`PriceChangeRules.CostsAfter`), so its percent is the same at either basis. `ReadAsync` prices every product as saved at both bases, so a switch only reruns the recalculation at the other basis; the recalculation keeps the now figures it used beside the simulated ones, so the report matches the table. Print Report's pages say "Unbuffered costs" (`ProductPrintout.CostBasis`), and Export to Excel suggests **Price Simulator (Unbuffered)** with a **Products (Unbuffered)** sheet.
  - Tests: `PriceScenarioRulesTests`, `PriceChangeRulesTests`, `PriceScenarioPersistenceTests`, `PriceSimulatorStateTests` and `PrintDocumentCostingTests`.

### Derived products

Some products derive from others (e.g. Special Ensaymada Small from Special Ensaymada Big, differing only in weight; or products sharing a dough but differing in toppings). Recipes are shared through links to sub-assemblies, and copied through Copy, Make a Copy and Clone:

- **Link a sub-assembly** (Add Sub-Assembly ▸ **Link an existing one**): a product uses a sub-assembly kept on the Sub-Assemblies screen, as it is, through a `ProductSubAssemblyUsage` of it. Its lines follow every change made there, and can be changed in the product too (SubAssembly, "Its lines are edited in the product"); the **piece size is the linking product's own**, so Small and Big can share a dough at 30 g and 60 g a piece. Links don't chain (only a sub-assembly on the Sub-Assemblies screen, or for a variant its source's own, can be linked), so there's nothing to cycle. **Make a Copy** or **Unlink** splits a section off.
- **Copy a sub-assembly** (**Copy an existing one**): a new section starting from another sub-assembly's lines and role, not its name. If the recipe already has that role, the form starts on the first role it doesn't. Nothing connects it to its source afterward.
- **The three ways in** are Add Sub-Assembly's drop-down items, **New sub-assembly**, **Link an existing one** and **Copy an existing one**, and a link's or copy's form is titled with the one picked ("Link an existing sub-assembly"). A new one's form has no title: in its place the **Moves to Sub-Assemblies on Save** badge shows while its role is neither product-owned nor packaging (`IsFormNewMovingToSubAssemblies`). Its picker, **Existing Sub-Assembly**, lists the Sub-Assemblies screen's first (`GetLinkableAsync`), as "Butter Glaze — Sub-Assemblies (Finishing)". A linked section's badge reads "Cheese Roll Dough, from Sub-Assemblies" (`PricedSection.LinkedFromText`, the one place that names where a linked sub-assembly comes from), or for a variant's link to its source's own "Ensaymada Big Filling, from Ensaymada Big" (`LinkedOwner`, `LinkedFromToolTip`), and opens where it's kept (`OpenLinkedSourceCommand`: the Sub-Assemblies screen, or the source product). A new, unsaved product is offered them too: `RefreshLinkableOptions` matches `OwnerProductId is null` first, since a null owner compared with a new product's null id would otherwise count as its own.
- **Link the packaging** (`PackagingLink`, table `packaging_links`, one per product): a product's packaging reads through to a **packaging set** (`LinkedSubAssemblyId`, Restrict) or another product's packaging (`LinkedProductId`) instead of owning lines; `CK_PackagingLinks_OneTarget` requires exactly one. It resolves every line the target has.
  - **One set per sellable unit**: `PackagingLineRepository.ResolveEffectiveAsync` returns the set's lines as unsaved `PackagingLine`s of the product being resolved (`UnitId` and `QtyPerUnit` the set line's own, `AuthoredField = QtyPerUnit`, the material with its units), so the Products screen, the cost summary, Reports and an unlink's copy take them unchanged.
  - **Chains** (C's packaging linked to B's linked to A's) are resolved recursively at read time and end at a set, which links nothing; a cycle is refused when a link is made (`PackagingLinkRules.EnsureNoCycle`). One left by an edit outside the app is read as no packaging and flagged (`ProductDetail.PackagingLinkedRoundInALoop`, `PackagingLinkRules.LinkedRoundInALoopText`), which the Products screen says when it opens it; refusing the read instead would fail every product's pricing in a batch. A clone or an unlink, which copy the lines, still refuse it (`PackagingLinkRules.LoopText`). A product whose packaging another links can't be deleted until that link goes.
  - **Made on the Recipe Structure's Packaging tab, with its own Link and Copy, saved with Save**, so an unsaved product can link too. Its Link offers only what the Sub-Assemblies screen keeps, packaging sets, never another product's packaging, which its Copy still offers (`ProductPackaging.StartLinkingCommand`, `StartCopyingCommand`). Add Sub-Assembly never offers packaging. Nothing in the app makes a new link to another product's packaging; one that exists reads through as any link does.
  - **`IProductRepository.SaveAsync` takes a `PackagingLinkDraft?`** (a closed record: `Set(SubAssemblyId)`, `OtherProduct(ProductId)`, `None` or `NewSet`; null leaves the link alone), written in the same transaction just before the lines (`PackagingLinkRepository.SetAsync`, sharing the product and set checks with `SetLinkAsync`/`SetSubAssemblyLinkAsync`). `None` only drops the link; unlike `RemoveLinkAsync` it copies nothing, since the form sends the lines it holds.
  - **Bulk packaging** (`PackagingLine.IsBulk`, `Product.BulkPackagingQuantity`): packaging several sellable units share, such as a box of 6 and its tape, typed for one pack with how many products the pack holds; each unit carries the pack's cost over that. **Always the product's own, never read through a link**, whatever its packaging is, and open to every product, with packaging for each piece or none (the Packaging tab is always there): `PackagingLineRepository.ResolveEffectiveAsync` leaves bulk rows out (so linking, Make a Copy, `RemoveLinkAsync` and `LinkNewSetAsync` never touch them) and `ReadBulkAsync` reads them, in `EffectivePackaging.Bulk`. Written apart through `IProductRepository.SaveAsync`'s `BulkPackagingDraft` (its lines and quantity, `SetBulkLinesAsync`; null leaves both), refused with lines and no quantity, the quantity stored as null with no lines. `SavedProductReader` puts it in `ProductDetail.BulkLines` and prices it as `SavedProduct.BulkPackaging` (`PricedBulkPackaging`); the share joins the Packaging cost, so composites that include their products' packaging, Reports and the Price Simulator follow. The Recipe API's `PackagingPerUnit` adds each bulk line's base quantity over the pack's products (one entry a material); the MCP cost sheet has `BulkPackaging`; a printout has a Bulk Packaging table under the packaging. Clone copies it; Create Variant doesn't. A version keeps it (`VersionPackagingLine.IsBulk`, `ProductVersionContent.BulkPackagingQuantity`). It came in place of packaging add-ins with a Holds column, tried the same day: typing Holds rewrote Qty, and the user wanted the pack's products typed once, apart from the lines. Covered by `BulkPackagingPersistenceTests` and `ProductsStatePackagingTests`.
  - **Storage**: the product's packaging is its `PackagingLines` or its one `PackagingLink`, and its bulk `PackagingLines` beside either, never a `SubAssembly` row, so `EnsureRecipeRole` keeps the Packaging role off a product's own sub-assemblies.
  - **Unlinking never loses data.** On the Packaging tab it's **Make a Copy** (`ProductPackaging.MakeCopyCommand`): the lines showing become the product's own, and Save writes both the unlink and the lines (`ChangedLines` writes them whenever the product was linked when loaded, even if they match). `IPackagingLinkRepository.RemoveLinkAsync` likewise materializes the lines it shows before it removes the link.
  - The banner reads "Linked to Gift Box Set (Sub-Assemblies)". The Products `LoadCommand` refetches linked packaging's lines while the form still shows the link as saved, so a set edited on the Sub-Assemblies screen shows on return; own lines and an unsaved link choice aren't touched, since they may hold unsaved edits.
  - **Move to Sub-Assemblies on the Packaging tab**, Make a Copy's reverse. While the packaging is the product's own lines (`CanMovePackaging`), the tab's top row has **Move to Sub-Assemblies** at the far right, the same spot as a recipe section's form. `ProductPackaging.MoveToSubAssembliesCommand` checks the lines (`CurrentLines`: a half-filled line, or none, is refused with the message) and sets `IsPackagingMoving`, in one undo step (`PackagingSnapshot.IsMoving`); a "Moves to Sub-Assemblies on Save" badge takes the linked badge's place, and the lines are still typed into until Save. `ProductPackaging.ShowLink`, which every load, Link, Copy, Make a Copy and Remove Link go through, ends it; `RestoreSnapshot` puts it back after. Save sends `PackagingLinkDraft.NewSet` with the lines, and `ProductRepository.SaveAsync` runs `PackagingLinkRepository.LinkNewSetAsync` in place of the link-then-lines pair, after the recipe: the lines become a standalone set in the Packaging role (found by its flag), named `StandaloneNameFor(product, role, null)` made unique ("Ensaymada Packaging", "… 2"), each line's quantity per sellable unit its quantity per set in the same unit and order, through `SubAssemblyRepository.SavePackagingSetAsync`, so every set check applies; the product's lines are deleted and its packaging links the set. Costs don't change. The top row keeps the button's height (`MinHeight="34"`) with the badge in it, so the table doesn't jump. Covered by `PackagingSetPersistenceTests` and `ProductsStatePackagingTests`.
- **Clone** (`IProductCloner.CloneAsync`, one transaction): a one-time copy of a product as saved. It **links every sub-assembly the source links**, at the same piece sizes, with the source's add-ins as its own, and **gets its own copy of each of the source's own** (named after the clone; `ProductCloner.DerivedRecipe`, each drafted `ProductsOwn`). Its packaging is copied as it shows, resolved through any link, except **a packaging set the source links directly, which stays linked**, like a recipe's sub-assemblies, since it's kept apart to be shared. It copies the quantity required, description, category, current price, costing parameters, a composite's products and whether it includes their packaging. A source with two sections in one role that can't be told apart is refused.
- **Create Variant** (`IProductCloner.CreateVariantAsync`, one transaction): a product whose recipe is **linked instead of copied**, for Ensaymada Small from Ensaymada Big. It's the Clone tab's second button, beside Clone, sharing its New Product Name.
  - **A variant links every sub-assembly the source uses**, at the source's piece sizes, with the source's add-ins on each as its own: **the source's own** (product-owned roles, or unlinked into its own) and **the ones it links** from the Sub-Assemblies screen (a dough, sponge or batter). **It has no packaging**, neither linked nor copied: it's given its own afterward, a packaging set for a Box of 8, which is what makes a variant the way to add a pack. `ProductCloner.VariantRecipe` builds the recipe; Clone and Create Variant share one core (`CreateFromAsync`), and differ only in the recipe and the packaging. The quantity required, description, category, current price and costing parameters are copied, as for Clone.
  - **Only Create Variant links another product's own.** `ProductSubAssemblyUsageRepository.SetRecipeAsync`'s `linksOthersOwn` is passed by the cloner alone. Every other save runs `SubAssemblyRules.EnsureLinkable`, except on a sub-assembly the product already links, so a variant keeps its links through its own saves, and one it drops can't be linked again. The Link picker leaves products' own out.
  - **The source can't pull one out from under a variant.** `SetRecipeAsync` refuses to drop one of the product's own that another product links (`EnsureNoneLinkedElsewhereAsync`, the Sub-Assemblies screen's message), before anything is written, and `ProductRepository.EnsureNothingLeansOnAsync` refuses deleting the product, to the Deleted folder or for good, while one of its own is linked elsewhere. Moving one to the Sub-Assemblies screen, or a role losing product-owned, releases it, and the variant's link follows.
  - **The Products screen names where it's kept.** `SubAssemblyReads` brings every sub-assembly's owner, usages included, and `ProductUsageEdit.LinkedOwner` carries it (kept through `With`, `Released`, `WithLinked`, `WithLinkedForm` and a version restore). A variant can change the linked lines as for any link, and Save writes them to the source's own.
  - Covered by `ProductVariantPersistenceTests`, the composite and Quantity Required persistence tests, and `ProductsStateRefreshTests.Create_Variant_makes_a_product_that_links_the_sources_own_with_no_packaging_and_shows_it`.
- **`CostingParameters`** always stay independent per product: nothing links them.

## Application Architecture

- **The window opens locked, and draws no screen until the password is given** (AccessSettings, above). `AppLock` (Presentation, a singleton, so the page loading again after a restore stays signed in) holds whether it's locked, whether the password has been given since the start, the auto-lock's minutes, and the wait after five wrong passwords in a row (30 seconds). `MainLayout` is the gate: before the first sign-in it draws only the title bar and `SignInScreen` (over `SignInState`), so no screen is built or loads; locked after that (the title bar's Lock, or `CheckIdle` after the auto-lock's minutes without a key, pointer or wheel event in the window), the screens stay drawn with their unsaved edits but `inert`, under the panel, every move to another address is cancelled, and `app.js`'s `lockKeys` stops every key outside the panel and every Ctrl, Alt or Win combination before any of the page's own listeners. The title bar keeps only the window's buttons while locked. Settings → Security (`SecurityState`) changes the password and the minutes. A Debug build started with `TINAPAYANRMS_SIGNED_IN=1` starts signed in with no auto-lock, for checks driven by script; a Release build has no such path. The developer manual's "Signing in" has the rest; tests: `AppLockTests`, `SignInStateTests`, `SecurityStateTests`, `SignInTests`.
- **Repository interfaces live in `ApplicationCore`, implementations in `Infrastructure`** (`IRawMaterialRepository`/`RawMaterialRepository`, and so on), consumed by the screen states through DI. Every lookup table has a repository of its own, since each is edited in Settings: `IUnitOfMeasureRepository`, `IRawMaterialCategoryRepository`, `IProductCategoryRepository` and `ISubAssemblyRoleRepository` with full CRUD, `IProductFolderRepository` for the Products list's folders, and `ICostingDefaultsRepository` for its one row. Don't bring in a generic repository just because a table is small.
- **Each operation makes its own short-lived `TinapayanRMSDbContext`.** screen states outlive any one operation (scoped: one set per page the web view loads, which lasts as long as the window), so a context injected into them would be shared by two screens loading at once ("A second operation was started on this context instance…"). Every repository takes `IDbContextFactory<TinapayanRMSDbContext>` and creates and disposes a context per call (`await using var dbContext = await dbContextFactory.CreateDbContextAsync(cancellationToken);`), which is also safe for concurrent calls from different screens. Never inject `TinapayanRMSDbContext` directly into a repository or screen state.
  - **The factory is also the unit of work.** `SharedTransactionDbContextFactory` (`Infrastructure/Services`) is registered as both `IDbContextFactory<TinapayanRMSDbContext>` and `IUnitOfWork`. `RunAsync(work)` opens one connection with a Serializable transaction (`ProductVersionRepository` numbers versions under Serializable) and puts it in a static `AsyncLocal`. Every context made on that flow, by any factory instance for the same connection string, is built on that connection with `UseTransaction`, so tests' many factories join too. A repository's own transaction is begun with `BeginOrJoinTransactionAsync` (`Services/Transactions.cs`), which inside a run hands back a part whose commit and dispose do nothing. No repository rolls back by hand or catches a database error and carries on, which a shared PostgreSQL transaction couldn't survive (a failed statement aborts it). **A run PostgreSQL cancels for a transaction beside it** (a serialization failure, 40001, or a deadlock, 40P01, however wrapped: `IsCancelledForAnother`) is run again from the start on a new connection, up to three times (`Attempts`), a few random milliseconds apart; a run inside a run leaves that to the outer one. So a run's work is its repositories' calls and nothing else, which copy what they're given, as `VersionedSaves`' are.
    - **A read that must agree with itself is a snapshot**: `ReadSnapshotAsync(work)` shares one connection the same way, in a Repeatable Read transaction set read only, so its queries all read as of the first and a write in it is refused; inside a run it joins the run. `SavedProductReader` reads every detail in one (`ReadDetailsAsync`, and `ReadComponentCostsAsync` with its products), so a Save that replaces a product's sections can't commit between its add-ins and its sections and fail the read. Pinned by `SharedTransactionDbContextFactoryTests` and `SavedProductReaderBulkTests.A_recipe_saved_while_its_product_is_being_read_is_wholly_in_the_read_or_not_at_all`.
    - **Writes take turns: every write transaction takes one lock before it writes anything** (`Transactions.BeginOrJoinTransactionAsync`: `pg_advisory_xact_lock(Transactions.WritesLockKey)`, held until it commits or rolls back, a run's from its first write). Two PCs on one database, or Recalculate Costs beside a save, could otherwise cascade side by side at Read Committed, each working a made or linked ingredient out from the other's costs as they stood before it committed, and the one committing last would store a cost from stale inputs that nothing flags (`CostCascadeConcurrencyPersistenceTests`, which fails without the lock). Behind the first, the second reads what it committed. One lock, taken first by every writer, so two writers can't each hold what the other waits for; a run that read before it took its turn fails to serialize instead, and is run again. A write that isn't a cascade's input (a category, a unit of measure, the costing defaults) saves without it.
    - **Reads inside a run go one at a time**: they share one connection. `SavedProductReader.ReadDetailsAsync`/`ReadComponentCostsAsync` and `ProductVersionRecorder`'s snapshots read in sequence. The batching that keeps the number of queries fixed however many products there are is what matters for speed (68 products: every detail read in 31 ms).
    - **`VersionedSaves`** (`Pricing/Versions`) holds the saves that record versions, each in one run: the Products Save (baseline, `ProductRepository.SaveAsync`, the product read back and its version, then the sharing products' versions), Clone and Create Variant with their first version, the Sub-Assemblies Save with its products' versions, and Apply Costing Defaults. A version that can't be recorded takes the save back with it. Pinned by `SharedTransactionDbContextFactoryTests` and `VersionedSavesTests`.
- **Startup time.** The window opens at once, and its first screen fills in as its load comes back; a screen is built when it's first shown. What else could keep a start busy, EF Core building its model on the first query, is kept out by:
  - **A compiled EF Core model** in `Infrastructure/CompiledModels/`, made by `dotnet ef dbcontext optimize --project src/TinapayanRMS.Infrastructure --output-dir CompiledModels --namespace TinapayanRMS.Infrastructure.CompiledModels` and regenerated by the same command after every model change (rather than the `Microsoft.EntityFrameworkCore.Tasks` build step, which would regenerate it on every build). EF Core finds it through the generated `[assembly: DbContextModel]` attribute, so `Configure` has no `UseModel`, and the design-time commands still build the model from `OnModelCreating`. A stale one compiles and runs (it finds properties by name), so `CompiledModelTests` compare it with the configured model: its `ShortDefault` debug view (entities, properties, keys, relationships, indexes) and a listing of its tables, columns, store types, keys, foreign keys and indexes. They don't use the migrations differ, which needs design-time data the compiled model leaves out.
- **The screens' shape.** The three main screens (Raw Materials, Sub-Assemblies, Products) are a **list card** on the left (a search box, a toolbar, and the records in a folder tree, `FolderTree`) beside a **header card** (the record's title, New, Save, Delete and its figures, with the fields typed in under them) over a card of **details in tabs** (`SfTab`). Settings' lookup pages (Units of Measure, Material Categories, Product Categories, Roles) are the simple case: a list and a form. A screen is a page in `Components/Pages/` over its state (`ScreenBase<TState>`), a large one split into components in a folder named after it (`Pages/Products/`, …).
  - **Money shows as a bare number** (`930.00`, not `₱930.00`), with thousands grouped. Money columns use 2 decimals for totals and prices, and 4 for per-unit costs (`CostPerBaseUnit`, `CostPerPiece`). A packaging line's own total (`PackagingLineRow.CostPerUnit`) counts as a total, at 2; its Unit Cost stays at 4.
- **Tables.** A table typed straight into is a `LineGrid`: every cell live at once, a draft add row that joins the lines on its first change, rows dragged into order, and Insert Line, which puts a blank line in above the selected one. A read-only list is an `SfGrid`, sorted by a header click, its rows and heading 24px. [docs/plan/maui-app.md](docs/plan/maui-app.md) has why each is what it is. **The order of lines is the order of the screen state's collection**, which Save writes (Domain Model: Line order), and it needs nothing else to count as a change: every form snapshot compares its lines with `SequenceEqual`, so a move is an undo step, marks the form dirty, and an undo puts the order back. A line left blank costs nothing: `IngredientLineRow.CompleteLines` leaves it out at Save.
- **Classes are sealed unless they're a base class** (`ScreenState`, `RecordScreenState<TSnapshot>`, the record screens' form: undo, the dirty check, the unsaved-changes question and opening a record; `ScreenBase<TState>`), and hot lookups use `FrozenDictionary` (`BackupRules.Suffixes`, `StandardUnitRules.ByName`, looked up by span through `GetAlternateLookup` so a trimmed unit name isn't allocated). LINQ is left alone where it costs nothing measurable.
- **A purchased material can be costed at a brand picked instead of the dearest.** `RawMaterial.PreferredBrand` (nullable, 100 characters), kept trimmed for a purchased material and null for any other (`RawMaterialRepository.StoredPreferredBrand`), is **Basis** on the Purchase Cost Setup card (`EditingPreferredBrand`, `CostFrom`/`CostFromOptions`, `RawMaterials/CostFromOption`; in the form snapshot, so Undo takes it back). `RawMaterialRules.FindCostBrandPrice` picks the price the cost comes from: the dearest per base unit of that brand's prices (matched as brands are), else the dearest of all, which is also the fallback when the brand picked has no price left. It's the one rule `ApplyBrandPrices` (so the Save, `RawMaterialBrandPriceRepository.SetAsync` and a unit's new multiplier), the price history entry `RepriceAsync` logs, `PurchaseUnit.Of` (the Price Simulator's current price, the Recipe API's `/materials`) and the form's live figures (`CostBrandIndex`) all use, so nothing downstream of `CostPerBaseUnit` changes: the cascade starts from it. The Raw Materials Save always sends a purchased material's brand prices, so a change of Basis alone reprices it and cascades. **There's no average**: price history, the simulator's current price and the purchase unit each need the one brand price the cost comes from. Reports' Cost Buffers column is **Brand Cost**. `RestoreSnapshot` raises `TypedCostBufferPercent`, so an Undo puts the Cost Buffer % box back too.

- **A "replace-all" child collection editor** (every `SetLinesAsync`, `ProductSubAssemblyUsageRepository.SetRecipeAsync`): the UI builds up an in-memory list of lines and one Save sends the *whole* list, and the repository deletes the parent's rows and inserts the new set, then saves once. Simpler and less error-prone than diffing an edited collection against the database, and how a person edits a recipe (the whole line list at once). **Every check runs before anything is deleted** (the lines, and every record they refer to), so a refused set leaves the old one untouched. **Delete the old rows with `ExecuteDeleteAsync`**, not `ToListAsync` + `RemoveRange`: every row is discarded, never mutated first, so loading them buys nothing but a round trip. It runs at once, so call it before the `AddRange`/`SaveChangesAsync` that follows. **The set a method replaces must match what the UI edits as one unit**: a product's recipe is edited whole, so `SetRecipeAsync(dbContext, productId, RecipeDraft)` (called by `ProductRepository.SaveAsync` and `ProductCloner`, inside their transactions) replaces all of a product's usages, and adds, updates, relines or deletes its own sub-assemblies to match: the usages go, then the dropped sub-assemblies (their lines cascade), then kept ones are updated before new ones are added (so a new one can take a name a kept one gave up), each relined through `SubAssemblyLineRepository.SetLinesAsync`.
- **A query that needs only the latest row of a growing table asks for that row** (`OrderByDescending(…).FirstOrDefaultAsync()` over an index), never loads the table to pick it in C#.
- **What can be worked out on read isn't stored.** A usage stores only its typed figure; its yield, its cost per piece, a sub-assembly's batch weight and cost, a packaging line's cost and a product's cost and price are `SubAssemblyRules`/`ProductRules`/`CostingRules` functions called fresh, so nothing has to be kept in step. Only a raw material's costs are stored, because a made ingredient's buffered cost isn't a multiple of its true cost (Reactive Costing Cascade).
- **Cost-plus pricing, not gross margin on price** (`CostingRules.CalculateSellingPrice`): `BaseCost = SubAssemblyCost + Wastage + PackagingCost + Labor + Overhead + Administrative`, where wastage, labor, overhead and administrative are each their percentage of `SubAssemblyCost`, the sub-assemblies alone, not the packaging. That's why `CalculateSellingPrice` takes the sub-assembly cost and the packaging cost as **two parameters** rather than one material cost: only the first is the base for the percentages, and both go into the base cost. It takes the percentages and works the pesos out itself, so every caller prices the same way. `PreVatPrice = BaseCost × (1 + Margin%/100)`, `SellingPrice = PreVatPrice × (1 + VAT%/100)`: separate steps, never folded into one formula, so the shop owner can check each by hand. `PercentOf(part, whole)` (0 when the whole is 0) serves every "% of the price" on the Products screen and changes no price. Gross-margin pricing (margin as a % of the *final* price, `price = cost / (1 − margin%)`) would be a different, explicitly chosen mode: don't swap the maths in `CalculateSellingPrice`.
- **An in-memory reciprocal (`1m / 6m`) is rounded to 4 places on its round trip through a `numeric(18,4)` column**: `PackagingLine`'s two quantities are exact reciprocals in `ProductRules.ReconcileReciprocal`, but the column stores `0.1666666…` as `0.1667`. Harmless at money scale, but a test asserting a reciprocal that has been through the database must assert the rounded value.
- **A link that reads through to another record resolves recursively at read time, with a visited-set guard, rather than copying data on write** (`PackagingLineRepository.ResolveEffectiveAsync`): it follows a product's `PackagingLink` chain to whatever holds the lines, and returns those. The write path refuses a cycle (`PackagingLinkRules.EnsureNoCycle`), and the read carries its own `HashSet<int>` of visited ids, since an edit outside the app could still leave one. **Unlinking materializes what it shows into owned rows before removing the link** (`PackagingLinkRepository.RemoveLinkAsync`): read the effective lines while the link still resolves, delete the link, *then* write the rows, so a product never shows less than it did a moment before.

- **One Save writes the whole material.**
  - **The screen edits everything in memory.**
    - Alternative units are rows over the form's own copies of the units (Id 0 until saved). Save checks them first (`RawMaterialUnits.EnsureValid`): every row has a unit ("Pick a unit for every alternative unit, or remove the empty row.") and a positive multiplier (naming Quantity per Purchase Unit for a unit added there, else Alternative Units), then `RawMaterialUnitValidator`, not the base unit, not already listed. The list is rebuilt only when it actually changes, so an open unit cell keeps its items.

  - **What Save sends** to `IRawMaterialRepository.SaveAsync(material, units, brandPrices, addIns)`:
    - A field still being typed into passes its value on when it's left, which clicking Save does first, so Save includes it.
    - `units` is the complete list.
    - For a purchased material, every brand row (a row left entirely blank is skipped), each naming its unit by unit of measure, since a unit added in the same save has no id yet. A row missing its unit or price, in a unit the form doesn't have, or repeating a brand in the same unit is refused first. `null` for any other material, which leaves brand prices alone.
    - A made ingredient's add-ins only when they differ from the ones last loaded; untouched add-ins aren't replaced.
    - Afterwards `LoadCommand` runs, then a fresh copy of the material is picked, so the form reloads what was saved: units with ids, the brand prices, the price history and the BOM.
  - **How it saves: one context and one transaction.** Every step goes through the `internal static` write methods the single-purpose repository methods share: `RawMaterialRepository.AddAsync`/`UpdateAsync`, `RawMaterialUnitRepository.AddAsync`/`UpdateAsync`/`DeleteAsync`, `RawMaterialBrandPriceRepository.RemoveAllAsync`/`AddAllAsync`/`RepriceAsync` and the add-ins' write. Each takes the caller's `TinapayanRMSDbContext`, saves to it, and says whether the cost cascade must run. The order: the material; the old brand prices go (so a unit only they were in can be removed); its units, removed first, then updated, then added (so a removed unit of measure can come back as a new row); the new brand prices, then the reprice, compared with the cost from before the save so at most one price is logged; the add-ins. Each step saves as it goes, so the next step's checks see what it wrote. The cascade runs once, at the end, on the same context and transaction, so a refusal anywhere rolls all of it back. The caller's entities are only read, so a rolled-back save never leaves an id on them. `RawMaterialSavePersistenceTests` covers the whole save.

- **After a command changes a row's computed fields, refresh that row and re-point the selection at it**: re-fetch it (`GetByIdAsync`), update the list (`_cache.AddOrUpdate(refreshed)`), and set the `Selected*` property to the refreshed instance. A selection left on the stale object silently desyncs the form from what the list shows.
- **`UpdateAsync` applies fields one by one onto a tracked, freshly loaded entity, never `dbContext.Set<T>().Update(incoming)` on an object the caller built.** `Update()` marks *every* property Modified, so a material built from the form's fields (which never sets the stored costs, since the server owns them) would overwrite them on every rename. Load the tracked entity by id, copy across only the user-editable fields, leave every computed field alone, then `SaveChangesAsync`. If an edited field feeds a stored figure, the same method works it out again: an alternative unit's multiplier feeds the cost, which `RawMaterialUnitRepository.UpdateAsync` reprices.
- **`ExecuteDeleteAsync` doesn't wrap a failure in `DbUpdateException` the way `SaveChangesAsync` does**: it issues a raw `DELETE` outside the change tracker, so a foreign key's refusal surfaces as `Npgsql.PostgresException`, and a test of it expects that. Where a refusal should name what's in the way, the repository looks first and refuses with a `BusinessRuleException` before the key would (`RawMaterialRules.EnsureNotInUse`, the product and sub-assembly delete checks).
- **FluentValidation is a thin, UI-facing pre-check alongside, never in place of, the `ApplicationCore` rules.** One `AbstractValidator<T>` per entity with a Save form (`RawMaterial`, `RawMaterialUnit`, `RawMaterialBrandPrice`, `RawMaterialCategory`, `ProductCategory`, `UnitOfMeasure`, `SubAssemblyRole`, `SubAssembly`, `Product` and `CostingParameters`, which also checks Settings' costing defaults) runs the rules the repository enforces: **a validator calls the rule itself** (`RuleValidation.Satisfies`, which fails with the rule's own message), so the form and the save can't word a check differently, and writes a check of its own only where no rule exists (a category picked, a description's length). A Save command runs the validator first and, on failure, sets `ErrorMessage` and returns before calling the repository, whose own checks stay the last line of defence. A replace-all set of lines gets no validator of its own: that cross-row validation lives in the rules class the repository calls.
- **`ScreenState`** is every screen's base: `ErrorMessage` and `SuccessMessage` (the toasts), the interactions the screen answers (`ConfirmDelete`, `ConfirmUnsavedChanges`, `ExportToExcel`), `ApplyRefresh`/`IsRefreshing` and `ApplyRestore`/`IsRestoring` with `IsBusyApplying` for either (so the undo history records none of a load's or an undo's writes), and the helpers every database-touching command goes through, each counted by the screen's `BackgroundWork` (`Work`, which `WhenIdleAsync` waits on in tests):

Never a bare `Observable.Switch(...).Subscribe()`: an error reaching `Switch` ends the subscription, and from then on no pick would load anything until the app restarted. A load cancelled by a newer value isn't a failure, whatever it threw on its way out.
  - **A screen's parts run their actions through the same helpers** (`IScreenPartHost`, which `ScreenState` implements explicitly: `Work`, `RunSafelyAsync`, `LoadLatest`, `ShowError`, `ShowSuccess`, `ShowFailure`), so what a part does is shown, logged and waited for as the screen's own (Conventions, a screen's part owns its tab).
  - Every command that calls a repository Delete is wrapped in `RunWithConfirmationAsync`, every Add/Update/Save in `RunSafelyAsync` (with the validator first, when there is one); a command that only changes an in-memory edit list, or `NewCommand`, is left unwrapped. A task nothing awaits (`_ = …`, or a component's `InvokeAsync`) deals with its own failure, through `RunSafelyAsync` on a screen: otherwise it only reaches a warning in the log, and the click that started it just does nothing.
- **A failure is shown on its screen in plain words, and the screen carries on.** What's shown comes from `Failure.Of` (`Infrastructure/Services`): a `BusinessRuleException`'s message as written; PostgreSQL's errors by SQLSTATE (a unique violation read as "That name is already in use." or "That abbreviation is already in use." by the index's name; a restrict or foreign-key violation as something in use or a reference gone; a check, not-null, out-of-range or too-long refusal; a deadlock or serialization failure, which Npgsql raises inside a `DbUpdateConcurrencyException` during `SaveChanges`; a timeout; a column or table missing, meaning the database is behind this version; and the connection errors); a sharing or lock violation on a file (`HResult` 0x80070020 or 0x80070021) as a file open elsewhere, a missing file as missing, and a `PostgresToolException` in the tool's words; and anything else, a bug, as "Something went wrong, and the details went to the log: …". A refusal is logged as a warning, anything else as an error with its stack. Tests: `LoadFailureTests` (on `FailingDbContextFactory`, which refuses contexts while it's set, or holds a read on its way) and `FailureTests` (real database errors).
- **Confirmations are the screen's dialogs**: `ScreenBase` answers a screen state's `ConfirmDelete` and `ConfirmUnsavedChanges` with `ConfirmationHost`'s dialog, and a name asked for with `PromptHost`, one of each per page (`MainLayout`), so a screen state only asks.
- **Logging.** Serilog writes a daily rolling file, `%LocalAppData%\TinapayanRMS\Maui\logs\tinapayanrms-<date>.log`, kept 31 days, set up in `MauiProgram`, with EF Core's and ASP.NET Core's Information left out. Each start names the build (`AppVersion`: the version and, in a published copy, its commit), which Settings → Database shows as **App Version**. **What fails with nothing to catch it is logged too** (`UnhandledFailures`, since 2026-11-13; MAUI logs none of it): an exception that ends the process (fatal), a task that failed with nothing awaiting it (a warning), an exception on the window's thread (WinUI's `UnhandledException`, fatal, hooked by the WinUI `App`) and a command run nothing awaited that failed (a menu's item or a key, `ScreenCommandBase.UnawaitedRunFailed`: an error, shown as a toast). A task a component starts without waiting for it goes through `TaskForgetting.Forget(logger)`, which logs its failure as it happens, and every `invokeMethodAsync` in `app.js` has a `.catch`.
- **A screen that fails gives way to a panel, not the page** (`ScreenErrorBoundary`, an `ErrorBoundaryBase` around `MainLayout`'s `@Body`, since 2026-11-13): an exception that escapes a screen is logged, and the screen shows "This screen ran into a problem it didn't expect" with **Open It Again** (`Recover`, as another address does too), while the title bar, the tabs and the other screens carry on. The screen state is the page's, so the screen opens again as it was, unsaved changes included, and the window's close still asks about them (`UnsavedChangesGuard` keeps a form whose screen went while it held unsaved changes); the page's error bar, whose Reload builds every screen state afresh, is left for a failure outside the screens.
- **A start that fails** is logged as fatal (`MauiProgram`), says why in Windows' message box with the log's folder (`StartupMessage`: it used to just disappear), and ends the app. A database that can't be reached isn't one: the window opens, and each screen's load says so in its error notice; a database missing this version's migrations shows a banner over every screen (`StartupTasks`).
- **One copy of the app on the PC** (`SingleInstance`, since 2026-11-13 across sign-ins: the user's choice, asked). Two copies side by side would each run the hourly backups, write the same view-state file and save over each other's settings. Within a Windows sign-in it's one copy per folder (a `Local\` mutex): started again, it brings the open window forward, and a copy run from source still runs beside the installed one. Across sign-ins, the app open in another Windows session refuses the start with a message box (`OneCopyPerPc`, over the running processes' sessions: the installer puts each user's copy in their own folder, so a mutex named after the folder never met another user's). Another PC isn't stopped: the check a form's Save makes, below, keeps two PCs from saving over each other's records. **Closing the window ends the process there and then** (`App`): left to end by itself, it stayed for 17 to 22 seconds after the window had gone, and a start in that time found it and exited with no window to bring forward. So **the window doesn't close while Settings → Database is backing up, copying or restoring** (`IBusyWork`, asked by `UnsavedChangesGuard`, which says why in an error toast): a restore cut short between renaming the database aside and the restored copy into its place left nothing under the database's name. Should the app end there anyway (a power cut), `StartupTasks` first renames `<database>_replaced` back (`DatabaseBackups.RecoverInterruptedRestoreAsync`).
- **A form's Save is refused over a save made since it opened the record** (optimistic concurrency, on the three records a form edits at length: products, raw materials and sub-assemblies), so another PC on the same database is never written over unseen. The token is the record's **`UpdatedAt`**, which every save of the record itself stamps (its form, a rename or move from the list, a product's Save relining a sub-assembly it links) and a cost the cascade moves doesn't (that's `CostUpdatedAt`), so a price saved elsewhere refuses nobody. It's stamped to the whole microsecond (`TinapayanRMSDbContext.LocalNow`), what PostgreSQL keeps, so a time stamped is the time read back.
  - **The check.** The form keeps the time it took (`RecordScreenState.SavedVersion`) and sends it as the record's `UpdatedAt`; the repository's update compares it with what's stored, after the writes' lock, and refuses with `SavedSinceException`, a `BusinessRuleException` (`SavedVersionRules.EnsureNotSavedSince`). A saved record no save has stamped yet is sent as `SavedVersionRules.NeverSaved`, so the first save stamped on it since refuses this one. While the form holds unsaved changes, a rename or a move of its record from the screen's list is checked the same way (a `SavedVersionCheck`, from `IRecordListHost.ShowingSavedVersion`). A save that sends no time isn't checked: a new record, or a caller that isn't a form.
  - **A refused Save, rename or move** leaves what's typed on the form and reads the screen's lists again (`OnActionFailedAsync`, `ReadListsAgainAsync`), so the record opened next is the one saved now. Opening it again without saving shows what was saved (Revert does on Products), and the next Save goes through.
  - **A load that finds the record saved since** (`FollowSavedVersion`): with nothing typed, the form loads the record again, whoever saved it; with something typed, it takes the new time only when the window itself has just saved that record, checked as it was written (`IRecordListHost.LoadAfterSavingAsync`), and otherwise keeps the time it took, so its Save is refused.
- **Export to Excel is answered by the screen, as a confirmation is.** A screen state only asks: `ScreenState.ExportToExcelAsync(title)` raises the `ExportToExcel` interaction and reports the path it gets back ("Saved … in …"), inside `RunSafelyAsync`, so a file open in Excel is an error notice. The screen (Reports, the Price Simulator) answers with the grid's own export (`ExportToExcelAsync(asMemoryStream: true)`), so the sort, the filters and the columns showing come with it, and saves the workbook where Windows' Save dialog says (`IFileDialogs`, `ExcelWorkbook`).

- **Vim keys: an opt-in key layer in the manner of Vimium**, a navigation layer rather than Vim editing inside fields, on in Settings → Keyboard (`vim-keys` in the view state). The keys are read in the page (`Components/wwwroot/vim.js`), in the capture phase, before any control sees them, from the key table the components send as the keys are turned on (`Vim/VimKeymap`), so the keys and the cheat sheet can't drift apart; everything is done as a hand would, a key moving the cursor, clicking, or pressing the arrow it stands for, so a list or table needs no Vim code of its own. The command line (`Vim/VimCommandLine`), Ctrl+R ='s sums (`Vim/VimExpression`) and the hint labels (`Vim/HintLabels`) are C# the page calls into. [docs/plan/maui-app.md](docs/plan/maui-app.md) has what the web view changes (Ctrl+N is its own, so Ctrl+J and Ctrl+K move through a list). Tests: `Components.Tests/Vim` and `VimKeysStateTests`.

## Reactive Costing Cascade

The core design problem is that a price change on any ingredient or packaging material must ripple up through everything that uses it, automatically. The cascade has two starting points, one per raw material type, and both end at the product:

```
Brand prices change for a purchased ingredient
  → its CostPerBaseUnit (per gram) recomputed; its buffered cost stays the fixed amount it is until the screen sends a new one
    → every made or linked ingredient that depends on it recomputed, up every level (a made one's sub-assembly lines and add-ins, a linked one's link)
  ─ stored above this line, worked out on read below it ─
      → every sub-assembly using a changed ingredient, from its lines
        → every ProductSubAssemblyUsage of that sub-assembly ─────┐
                                                                  ├→ Product cost (+ wastage, labor, overhead, admin)
Brand prices change for a packaging material                      │    → markup and VAT → selling price
  → its CostPerBaseUnit recomputed (stored)                       │
    → every PackagingLine using it ───────────────────────────────┘
```

**Only raw materials' costs are stored**: a purchased one's from its brand prices, and a made or linked one's by the cascade. Everything above them, a sub-assembly's batch weight and cost included, is worked out from its lines whenever it's read, so the one propagator ends at the ingredients. EF Core is the single source of truth: nothing lives only in an in-memory observable.

**Quantity Required hangs off the end of the cascade** and adds nothing to it: a plain multiplier where the branches meet (`CalculateMaterialCost` multiplies the usages' cost per piece by it and adds the packaging once), so a product that sells in boxes of 8 moves whenever its piece does.

**Two costs go up the tree side by side**: the true `CostPerBaseUnit` and the `BufferedCostPerBaseUnit`. A purchased material's buffered cost is a fixed amount (Buffered cost under RawMaterial): `RawMaterialRules.ApplyBrandPrices` sets it only on a first price, and the Raw Materials Save writes it otherwise. Every write through the cascade sets both: `IngredientCostPropagator` runs `IngredientBomRules.CalculateCost` twice per made ingredient (true costs, then buffered costs, with nothing of its own on top, and its stored `CostBufferPercent` set to 0 in the same pass). Everything downstream reads the buffered one, except the screens' **Unbuffered** switch, which prices what it shows and prints from the true `CostPerBaseUnit`, on read only. A buffer edit is one more way a cost changes: `RawMaterialRepository.UpdateAsync` reprices a purchased material's buffered cost itself and asks for the cascade for an ingredient whose buffer changed.

**Made ingredients nest; nothing else does.** A made ingredient's recipe can use another made ingredient, to any depth, so that part of the cascade needs a dependency order, components before the ingredients built from them. Sub-assemblies don't nest (a `SubAssemblyLine` only ever references an ingredient), and a sub-assembly is never a node: a made ingredient's BOM is read as its sub-assembly's lines plus its add-ins (`IngredientBoms`), expanded to ingredient edges, and it's costed from those lines' ingredients' costs, never from a sub-assembly's batch cost (buffered only, and outside the order). A linked ingredient's link is one more edge (`linked → linked-to`, beside every `made → component`), so egg white is recomputed after the egg and a made ingredient using egg white after egg white.

**The ingredient branch**: `IngredientCostGraph.GetDependentsInOrder` (`ApplicationCore`, pure: the graph turned round once (`DependentsOf`), a reverse BFS from the changed ingredients together to every ingredient that transitively depends on any of them (`GetDependents`), then one DFS topological sort of that set; `IngredientCostRules.ReachedBy` takes a list of materials the same way, for the Price Simulator, Reports' Cost Drivers and the MCP server) and `IngredientCostPropagator.RecomputeAndPropagateAsync` (`Infrastructure`, the orchestrator, given one changed ingredient or the set one save changed): it loads every ingredient and every BOM line once, walks one dependency order over everything the changed ones reach (each ingredient recomputed once), recomputing each made ingredient's costs from its lines (`IngredientCostRules.Recompute`, over `IngredientBomRules.CalculateCost`) and each linked one's from its linked-to ingredient's already-fresh costs (`RawMaterialRules.LinkedCost`, taking its buffer percent), reading each component's cost off the already-loaded, already-correct dictionary, never re-walking its tree, then saves once. It loads ingredients only, since packaging never takes part.
  - **Every write that can change an ingredient's cost calls it**, on its own context: `RawMaterialRepository` (add, update and Save, including a made ingredient's weight loss or add-ins and a linked one's link or shares), `RawMaterialBrandPriceRepository` (new prices), `RawMaterialUnitRepository.UpdateAsync` (a corrected multiplier its costed price is in), and `SubAssemblyLineRepository.SetLinesAsync`, which every line write goes through (the Sub-Assemblies Save, a product's Save relining a linked one, a role adopting one): it checks each made ingredient made from the sub-assembly for a loop through the new lines (`IngredientBomRules.EnsureNotInOwnRecipe`, then `IngredientDependencies.EnsureNoCycleAsync`) and cascades it. A made ingredient's own Save checks the whole after every part is written (`RawMaterialRepository.EnsureMadeIngredientFitsAsync`). A sub-assembly a made ingredient is made from can't be deleted (`SubAssemblyRules.EnsureNoMadeIngredientMadeFrom`) or adopted by a product (`SubAssemblyRepository.SingleUse`).
- **The cascade runs in the transaction of the save that causes it.** The propagator is an internal static class that takes the caller's context, and every caller runs it before `CommitAsync`, so a save and its cascade commit together or not at all; a cascade that failed after its save had committed would leave the stored costs above it stale for good, since saving again unchanged doesn't cascade (`CostCascadeTransactionPersistenceTests`, which fail a cascade part-way with a save interceptor). A stored cost is set at the column's scale (`RawMaterialRules.StoredCost`), so a figure worked out again from unchanged inputs isn't written or dated again.

**Products, packaging, composites and add-ins need no propagation at all.** A usage's cost per piece and weight per piece, a packaging line's cost, a product's cost and wastage, a composite's lines and a usage's add-ins are plain `ProductRules`/`CostingRules` functions, and `SavedProductReader` reads, over the ingredients' and packaging materials' stored costs, worked out fresh every time a screen asks. As long as the raw materials' costs are right, which the propagator and the brand price repository see to, a product's cost is right too, with nothing to propagate into. A sub-assembly's own batch is its lines alone; an add-in moves only the linking usage's effective batch (`ProductRules.CalculateEffectiveBatch`). `ReactiveCostCascadeTests` pins it end to end: a price change several levels deep reaches a product's cost per piece, an add-in's ingredient repriced moves the linking usage and leaves the sub-assembly's own batch as it was, and a sub-assembly's lines changed reprice the made ingredients made from it.

**A product on another screen picks a change up when its tab is shown again**: each tab loads on show and merges what it reads (Application Architecture). There's no cross-screen live push, by choice: revisit only if that gap is ever reported as a real problem.

**Recalculate Costs is the safety net for a change made outside the app**: Settings → Costing Defaults → **Recalculate Costs** (`ICostRecalculator`, `CostRecalculator`) recomputes every made and linked ingredient in dependency order (`IngredientCostGraph.InDependencyOrder`, the cascade's own ordering for a whole set), in one transaction, and says how many were wrong. Purchased materials aren't touched: their cost comes straight from their own saved prices. Settings is a tab like any other, so a save on another screen, or another PC's on the same database, can come while it runs: it takes its turn behind it, as every write takes its turn behind another (the writes' lock, Application Architecture). Its **Stored Costs** card sits beside the Costing Defaults card, wrapping under it in a narrow window (`Pages/Settings/CostingDefaults.razor`), and the tab scrolls.

**The Price Simulator runs the cascade's maths without storing it**: `IngredientCostRules.Recompute`, which the propagator stores, is applied by `IngredientCostRules.Reprice` to copies (`RawMaterial.ShallowCopy`) of the materials a simulated change reaches, in `IngredientCostGraph` order, so a simulation can't price an ingredient differently from how a real change would cascade. `PriceChangeSimulation` (Pricing) prices every product with those copies, for the screen and for the MCP server's `simulate_price_changes` alike. Its report names the changes reaching each product with `IngredientCostRules.ReachedBy`, the graph `Reprice` walks. Reports' Cost Drivers and Raw Materials' Dependents shares work out what a material brings the same way (`MaterialCostShares`: every product priced with the material at no cost, against as it is).

## Development Environment

- Development happens directly on a local Windows machine with the .NET 11 SDK (11.0.100) and PostgreSQL 18 (EDB's installer, service `postgresql-x64-18`, `localhost:5432`). The app, `dotnet ef` and the tests connect as the `tinapayanrms` role (`CREATEDB`, not a superuser), whose password is in `%APPDATA%\postgresql\pgpass.conf`, so no connection string carries one; the installed Recipe API connects as `tinapayanrms_reader` (Tech Stack). `psql`, `pg_dump` and `pg_restore` are in `C:\Program Files\PostgreSQL\18\bin`, which isn't on the PATH. The same server holds the sibling projects' databases. SQL Server Express and LocalDB are still installed, holding the data from before the move to PostgreSQL, unused.
  - **`TinapayanRMSDbContext.Configure` is the one place the provider is set up**, for the app, `dotnet ef` and the tests: Npgsql with snake_case names (`UseSnakeCaseNamingConvention`), and `SetPostgresVersion(18, 0)`, since Npgsql 11 otherwise writes its SQL and migrations for PostgreSQL 16.
  - **Collation and timestamps**: every text column has the nondeterministic ICU collation `case_insensitive` (`und-u-ks-level2`), so the unique name indexes and the name sort are case-insensitive and accent-sensitive. Every `DateTime` is `timestamp without time zone`, since the app stamps local time (`TinapayanRMSDbContext.LocalNow()`, from its `Clock`, the system's unless a test passes a `TestClock`).
  - **Dapper SQL** is snake_case. An id list is an `int[]` with `unnest`. A recursive CTE is `WITH RECURSIVE`, and since PostgreSQL lets a recursive query name itself only once, `RawMaterialRepository`'s `feeds` follows recipe and link edges through one union; a loop left by an edit outside the app is stopped with `CYCLE`.
  - **Npgsql 11**: a deadlock (40P01) or serialization failure (40001) raised during `SaveChanges`, even inside the app's own transaction, comes as a `DbUpdateConcurrencyException` with the `PostgresException` inside, which `Failure` reads before its "changed or deleted on another screen" case, so a clash between two serializable `ProductVersionRepository` saves says the database was busy.
- Building a runnable app needs the `SYNCFUSION_LICENSE_KEY` user environment variable, since the build compiles the key in (Tech Stack). The solution builds without it, but that window opens with Syncfusion's licence notice, and `dotnet publish` fails outright. Building needs the .NET MAUI workload, `maui-windows` (`dotnet workload list`).
- **Docker is not used anywhere in the project**: not for development, testing, or deployment.
- **A Debug build opens the web view's developer tools on F12** (`AddBlazorWebViewDeveloperTools`), the console showing what a component's script threw. The app's log is `%LocalAppData%\TinapayanRMS\Maui\logs\`.
- EF Core migrations are generated with `dotnet ef migrations add`, never written by hand, and applied to the local database with `dotnet ef database update`, both from the repo root with `--project src/TinapayanRMS.Infrastructure`; that project's design-time `TinapayanRMSDbContextFactory` supplies the DbContext.
- **Work is done** when the solution builds without errors or warnings, all tests pass, and any new migration applies cleanly to the local database, with the manuals updated (Conventions).
- **In-app backups go to `%ProgramData%\TinapayanRMS\Backups`**: `pg_dump` custom-format `.backup` files (`DatabaseBackups`, `PostgresTools`). `pg_dump` writes them as the user running the app, so `BackupFolder` gives `BUILTIN\Users` Modify. A restore goes into a `<db>_restoring` scratch database, is brought up to date there, and is swapped in by renaming, so a refused or failed restore never touches the data. A restore takes a safety backup of the database first.
  - **A new backup never takes a file name already in the folder.** Names go to the second (`BackupRules.FileNameFor`, `yyyyMMdd_HHmmss`), so a safety backup taken within a second of the one before it, as when the safety backup just made is restored straight away, would overwrite the very file about to be restored. `BackupRules.FreeFileNameFor` moves the time on a second at a time while the name is taken (`DatabaseBackups.FreePath` checks the folder); the name keeps its format, so `TryParse`, the list's order and the pruning are unchanged. Copy In does the same.

## Conventions

- **This guide describes the app as it is now.** PLAN.md and `docs/plan/` say what the code does and why, in the present tense. When a decision changes, rewrite what's here, and add the change to the build plan's dated log, which keeps the history (when it changed, who asked, and what it replaced); git keeps the old text. Where a "why not X" explains the code (an alternative that was tried or weighed and not taken), it stays, without its story.
- **The user manual follows the app.** `docs/user-manual.md` is written for the shop's staff: current behaviour only, labels in bold exactly as the screen shows them, amounts without a currency symbol, and no code names. A change users can see (a screen, button, field, menu item, rule or cost formula) updates it in the same change.
- **The developer manual follows the code.** `docs/developer-manual.md` is written for developers new to the codebase: prerequisites, setup, architecture, patterns, testing, and steps for common changes. A change to anything it describes (the setup, commands, solution layout, architecture, a pattern or convention, or a type or file it names) updates it in the same change. Like the user manual, it describes only what's true now; this guide is the source of truth where the two differ.
- **Comments say what the code does and why**, in the present tense, with no date and no account of who asked or how a bug was found.
- The layered architecture is fixed: `Domain` has no external dependencies, business and costing rules live in `ApplicationCore`, the pricing of a saved product in `Pricing`, and EF Core and other I/O stay in `Infrastructure`.
- **A screen's state is a plain class of the app's own, with no MVVM library** (since 2026-11-16, when ReactiveUI went): it and its parts and rows are `ObservableState`s, its commands `ScreenCommand`s, its questions `Interaction`s, its derived values plain getters, and what follows a change is called by the setter that made it, while what only the user's edit sets off is a method the page calls (`Pick`, `ChangeType`), never a setter. Don't bring an MVVM toolkit back (ReactiveUI, CommunityToolkit.Mvvm): a Blazor screen draws itself whole on any change, which is all the notification it needs. The developer manual's "Screen state" has the rules.
- **Every file goes in the folder for its kind, and the folder is its namespace** (Solution Structure). A new screen's page goes in `Components/Pages/` with its state in a folder for the screen in `Presentation/`, a new repository in `Repositories/` with its interface in `ApplicationCore/Interfaces/`, a new rule in `Rules/` with its test in `tests/…/Rules/`, and so on. Nothing goes at a project root except app-startup plumbing.
- **Prefer a Syncfusion Blazor component over a plain HTML control where one fits** (`SfGrid`, `SfTab`, `SfDialog`, `SfChart`, `SfSidebar`, `SfToast`), so the screens take the theme consistently; but what's typed into goes through the app's own fields (`TextField`, `NumberField`, `PickField`, `LineGrid`), for the reasons in [docs/plan/maui-app.md](docs/plan/maui-app.md). Adopting a new Syncfusion component needs its package added to `TinapayanRMS.Components`, at `SyncfusionVersion`, and its name on the list in `Components/wwwroot/syncfusion.js` unless it has no script (`SyncfusionScriptsTests` says which); its styles are in the theme's stylesheet already.
- **Quantities show 1 decimal and keep what's typed**: every Qty, Qty per Purchase Unit and Grams box shows 1 decimal (`NumberField`'s `Format="N1"`), and the number typed is kept, to the 4 places the database keeps, so 0.1667 reads 0.2.
- **No currency symbol on a monetary value**: amounts are bare numbers (`ToString("N4")` in a component, `$"{cost:N4}"` in a screen state), and a field label names the money without a "(₱)" suffix. Decimals: **2 for every per-piece costing figure on the Products screen** (the header's Material Cost and Base Cost, and the Costing card's rows, in the tile captions as well as the summary table, and the Packaging section's header figure), 2 for a per-purchase-unit amount or a price, and 4 only for a per-base-unit cost (a raw material's cost per gram, a packaging line's unit cost) and the recipe tabs' own Cost per piece.
- **An input's label goes on its left in a stacked form**, as on a desktop app: each field is a row with its label in front of it (`FormRow`: muted, centred on its box), the labels lining up down the form. The three main screens' header fields are one row each, every label in an `Auto` column before its field, 16 px under the header's read-only figures (Products: Product Name, Category, Quantity Required and Current Price; Raw Materials: Name, Type, Category, Source or Base Unit and, for a made ingredient, Weight Loss %; Sub-Assemblies: Name and Role). **The exception**: side-by-side strips of fields (the Linked Cost, Purchase Cost and Usage Example rows) keep the label above the input, since a label beside every box doesn't fit one row at 1366 px. Read-only figures keep a small label over the value: header figures and stat tiles.
- **Names are stored without spaces at either end**: PostgreSQL's `case_insensitive` collation counts a space at the end, so `"Flour "` would get past the unique index beside `"Flour"`. The repositories store names through `ProductRules.StoredName`, `RawMaterialRules.StoredName` and `UnitOfMeasureRules.NormalizeName`/`NormalizeAbbreviation`, and the Saves trim as well, for what they say about the name afterwards. Tests: `StoredNamePersistenceTests`.
- **A figure a read divides by has a check constraint, and one bad row can't fail the others' reads.** A packaging line at a quantity of 0, which only an edit outside the app can leave, would throw in the read every product's pricing goes through, failing Reports, Print, the Recipe API and the MCP tools for every product. So each such figure has a check constraint mirroring the rule the repository checks first (`CK_PackagingLines_AuthoredQuantity`, on the figure typed, since the other is worked out and 1 / 30,000 rounds to 0 at 4 places; `CK_SubAssemblyLines_Grams`, `CK_UsageAddInLines_Grams`, `CK_IngredientAddInLines_Grams`, `CK_RawMaterialUnits_BaseUnitsPerUnit`, `CK_CostingParameters_Percents`, `CK_RawMaterials_WeightLossPercent`: a made ingredient's weight loss under 100%, since the cost per gram divides by what the recipe makes less it, and at 100% it would cost nothing), a backup holding such a row fails its migration and is refused before it takes the database's place, and `ProductRules.ReconcileReciprocal` gives 0 for 0 rather than throwing, so `EnsureValidPackagingLines` refuses such a line by name. Likewise a loop left by an edit outside the app (a composite holding itself, packaging links coming round) is read cut and flagged, never refused for every product. Tests: `QuantityCheckConstraintTests`, `PackagingLineRowTests`, `ProductRulesTests`.
- **Decimal precision**: keep `decimal` values at full precision through the whole cascade, and round only for display and for the final selling price; rounding each per-piece cost before summing adds up to drift. Every `decimal` column is `numeric(18,4)`, set once in `TinapayanRMSDbContext.ConfigureConventions`, so a new column can't fall back to an unconstrained `numeric`. **The exception is a material's costs per base unit** (`CostPerBaseUnit`, `BufferedCostPerBaseUnit`), `numeric(28,20)`: a buffered cost typed per bag is divided down to per gram, and 4 decimals would round it (₱1,297.37 a 25 kg bag would come back ₱1,297.50); they're shown rounded. **A stored figure worked out in memory is set at its column's scale** (`RawMaterialRules.StoredCost`, 20 places, rounded half away from zero, worked out at full precision before that), or it never compares equal to the stored value, and an unchanged cost reads as a change. **A `double` never turns into a `decimal` by a plain conversion**: since .NET 11 a cast, `Convert.ToDecimal` or `new decimal(double)` keeps the double's exact binary value (28.35 is 28.349999999999997868371792719), with no switch to turn it back. Every typed number comes through `NumberField`, which reads its text as a `decimal`, never through a `double`, and refuses to be bound to anything but a `decimal` or an `int` (with their nullables). **No number below the screens is a `double` or a `float`**: `DecimalNumbersTests` (Components.Tests) fails on one in a field, property, parameter, return value or local variable anywhere in Domain, ApplicationCore, Infrastructure, Pricing or Presentation, its one named exception the History tab's chart points (`VersionTrendPoint`), made from the decimals as they're drawn since the chart plots doubles. The Excel export's cells are the other edge: Excel holds a number as a double. A data-driven test's fractional `decimal` values come from a `[MethodDataSource]` method as `m` literals, since `[Arguments]`, an attribute, can only pass a `double`. **Every rounding names its midpoint mode** (`Math.Round(value, places, MidpointRounding.…)`), since one that names none takes a half to the even digit where a shown number (`N2`) and a stored cost (`StoredCost`) go away from zero: a figure compared with what's shown (`IsBelowTargetMarkup`, the buffer checks, Margin Erosion's drop, a shared recipe's impact) rounds half away from zero, so a markup shown at its target is never flagged short of it; one that feeds a typed or saved figure (a piece size, grams from a baker's %, a scaled batch, a standard unit's multiplier, a typed amount's percent, the buffer boxes) says `ToEven`, the mode it always had, so nothing saved moves. `RoundingModeTests` (Components.Tests) reads every method's IL below the screens and fails on a rounding that names no mode.
- **A rule throws `BusinessRuleException`** (`ApplicationCore/Rules`): every check whose message is for the user, in the rules classes, the repositories and the screens' own form checks. It derives from `InvalidOperationException`, so code catching that still catches it; what it adds is that a screen can tell a refusal from a bug, since EF Core, Npgsql and the framework throw `InvalidOperationException` for bugs and failures too. Only the startup configuration errors (`MauiProgram`'s, `DatabaseHost`'s and `ReadOnlyConnection`'s) stay `InvalidOperationException`.
- **Use modern C# 15 / .NET 11 idioms** rather than older patterns still valid in the language: primary constructors, collection expressions (`[..]`), required members, file-scoped namespaces, pattern matching, and `record`/`record struct` for immutable data shapes.
  - **A fixed set of cases is a `closed` class or record**: the list trees' nodes (`ProductTreeNode`, `RawMaterialTreeNode`, `SubAssemblyTreeNode`), `RecipeTab`, `PrintScope`, `RecipeTabChoice`, `TreeDrop`, `MoveUndo`, `ProductCategoryFilter`, `PackagingLinkDraft`, `PackagingLinkTarget` and `SectionPlacement`, one sealed record per case, nested in the closed one and carrying only its own data (`new PrintScope.Folder(folder)`), in place of a `Kind` enum beside fields only some kinds use, two nullable ids with one of them set, or flags that overlap. A switch over one names every case, and `null` when null can come, never `_`: then a new case is a CS8509 warning at each switch that misses it. A `Kind` enum stays where it's data rather than a shape (`VimCommandKind`, in the command table) or where every kind carries the same fields (`VimKeys`' `PlaceKind`).
  - **`union` for a value that's one of some types already there.** A union is a struct that holds its case in `Value`; the tree selections and Print choices are still classes: they were written for bindings that couldn't see through `Value`, and nothing has needed them changed since. `PreparedPrintout(ProductPrintout, PrintProblem)` is one: what `ProductsState.PreparePrintout` gives the Print tab, the pages, why the open form can't give them, or an empty union (`default`) while there's nothing to print. A union suits a value that's one of some types already there; a set of cases made up for the purpose stays a closed record. An empty union matches `case null`. In a `?:` whose other branch is a case, write `default(PreparedPrintout)`: a bare `default` takes the case's type and becomes a null printout. Tests read the case through `Value` (`Value.Should().BeOfType<ProductPrintout>().Subject`).
  - **A closed record that's shown seals its `ToString`** (`ProductCategoryFilter`, the Products list's category filter, which a screen reader reads out); otherwise each case's record `ToString` reads "Category { Label = … }".
  - **`BeEquivalentTo` over a closed base type has no members to compare** and throws "No members were found": pass `o => o.ComparingByValue<TBase>()`, so the cases' record equality decides, or use `Equal` where the order is fixed.
  - **Collection expression arguments** (`[with(StringComparer.Ordinal), .. keys]`) for a collection made with a comparer or a capacity; a `ToHashSet(comparer)` or `ToDictionary(..., comparer)` at the end of a query stays as it is. **Labeled `break` and `continue`** take the place of a flag or a `goto` out of nested loops (IDE0410 finds those).
  - **.NET 11's library additions take the place of hand-written code**: `Enumerable.FullJoin` pairs a version's lines, add-ins, products and packaging lines with another's (`ProductVersionRules.Paired`; a full outer join pairs a repeated key with every match, so it suits keys a unique index makes come once on each side); `Process.RunAndCaptureTextAsync` runs `pg_dump` and `pg_restore` (`PostgresTools.RunAsync`), reading both pipes as the tool runs and stopping one that's cancelled; and `Process.StartAndForget` starts the app again after a restore. `ProcessStartInfo.KillOnParentExit` is left off, since a tool stopped with the app would leave a half-written file (`.partial`, which the backups' list never shows).
- **A record screen's state is one class over its parts, never a partial class** (`ProductsState`, `RawMaterialsState`, `SubAssembliesState`, one file each since 2026-11-14): the screen keeps its form's own fields, which record it shows, loading, Save, the order an undo puts its parts back in, and what spans them; each other piece is a part, a class of its own the screen holds as a get-only property: its list (`ProductsList`, `RawMaterialsList`, `SubAssembliesList`, each a `RecordList`) and its tabs and cards (Products' `Recipe`, `UsageForm`, `Packaging`, `ComponentsTable`, `Costing`, `VersionHistory` and `NewProductPlace`; Raw Materials' `PurchaseCost`, `Units`, `Recipe`, `UsageExample`, `PriceLog` and `Dependents`; Sub-Assemblies' `Batch`, `PackagingSet` and `Dependents`). The constructor makes the parts, then the subscriptions in the order they were made, since two following one property run in that order and several run as they're made: a part subscribes only to what it holds alone, and what reaches from one part to another, or to the form, is the screen's. The commands come last, in any order, get-only. Opening a record, by id from its address or by name from `:e`, is the base class's (`RecordScreenState.OpenRecord`): each screen says how its list finds and picks one. The developer manual's "Screen state" has the detail.
- **A screen's part owns its tab, commands and all** (`ProductPackaging`, the Products screen's Packaging tab): its state, its commands and the logic only they use. Each change is one undo step of the screen's form, which the part records through the screen's `IUndoRecorder` (the `AsUndoStep` extension). What it needs of its screen comes through one interface of its own that the screen implements explicitly (`IProductPackagingHost`: the cost basis, the other products, the costs worked out again), on top of `IScreenPartHost`, the screen's runners and messages, which `ScreenState` implements, or of `IFormPartHost`, which adds the undo recorder, whether a load or an undo is writing the form, a confirmation and a load's merge, and which `RecordScreenState` implements; a list's is on top of `IRecordListHost`. Its repositories come through its constructor, and so do the lists the screen loads that it reads, collections each load merges into (`ProductPackaging` takes the packaging materials). It keeps and puts back its own share of an undo step (`ProductPackaging.Capture` and `Restore`, a `PackagingSnapshot`), and works out what's only its own (`ProductCosting`: the costs, their captions, the cost basis). What spans parts stays with the screen: loading (its reads, where there are many, in a reader of their own: `ProductsLoadReader`), Save, the order an undo puts the parts back in, and gathering what the costs are worked out from. The developer manual's "Screen state" has the detail.
- **Reads through Dapper, writes through EF Core.** **Every public repository read method is plain SQL run by Dapper**, returning the entity objects with their navigations filled in, as an EF `Include` chain would. The exceptions are reads that share an EF query with a save's own check, so that what a screen shows and what a save refuses can't disagree: a made ingredient's BOM (`IngredientBoms`, which `IngredientBomLineRepository` reads as the cascade and the cycle checks do) and `SubAssemblyRoleRepository.CountOwnershipChangesAsync` (`SubAssemblyRepository.SingleUse`, what changing a role then adopts). **Everything else stays in EF Core**: every write, the schema and every migration, and a read inside a save that either loads an entity to change it (it must be tracked for `SaveChangesAsync`) or checks a condition through an EF expression (`SubAssemblyRepository.GetLinkedByAsync(dbContext, Expression, …)` behind `EnsureNoneLinkedElsewhereAsync`, the existence and uniqueness checks). An untracked graph read that a save also needs is shared: it takes the save's DbContext and runs through Dapper *in that context's transaction* (`DapperReads.Command` passes `Database.CurrentTransaction`), e.g. `PackagingLineRepository.ResolveEffectiveAsync`, used by both `GetEffectiveForProductAsync` and `ProductCloner`. Never write through Dapper: a Dapper write would skip `IngredientCostPropagator` and the `CostUpdatedAt` stamp, leaving stored costs stale.
  - **The pieces**, in `Infrastructure/Queries/`: `DapperReads` borrows a DbContext's connection (so the connection string and the tests' `CreateDbContextFactory()` work unchanged; Dapper opens and closes it when EF hasn't) and has the factory- and context-level `QueryAsync`/`QuerySingleOrDefaultAsync`/`ReadAsync`; `Columns.Of<T>(alias)` is every entity's column list, **Id first** (a multi-mapped join splits on `Id`); `RawMaterialReads` loads materials with their category, base unit and units (largest first), alone or under packaging lines or set lines; `SubAssemblyReads` loads sub-assemblies with their role and owner; `IngredientBoms` is the made ingredients' BOMs.
  - **`Columns` must list exactly EF's columns**: a property left out reads back as its default with no error. `ColumnsTests` compares every list against EF's design-time model (no database), so a new or renamed property fails that test until `Columns` has it; that's what Infrastructure's `InternalsVisibleTo TinapayanRMS.Infrastructure.Tests` is for.
  - **Every name in the SQL is snake_case**: a table is its `DbSet`'s name and a column its property's (`raw_materials.cost_per_base_unit`), and `DapperReads` turns on `MatchNamesWithUnderscores`. A table rename needs the SQL updated by hand (the persistence tests catch it).
  - **Mechanics**: Dapper maps `date` to `DateOnly` and a string column to an enum stored by name on its own, but for `ProductStage`, which `ProductStageTypeHandler` reads (Innovation's former name too; `DapperReads` registers it, with `SqlMapper.Settings.PreferTypeHandlersForEnums` on). Join an optional navigation with `LEFT JOIN`; Dapper returns null for a split whose first column (its `Id`) is null. A list of ids is one `@ids` parameter (`DapperReads.IdList`, an `int[]` Npgsql sends as one array) read by `IN (DapperReads.IdsTable)` (`unnest`). A collection navigation (a material's `Units`) is a second query stitched on by id, not a join, because `GridReader`'s multi-mapping is synchronous only. There's no identity resolution: a material on two lines is two objects. A read that returns lines in order says so with `ORDER BY`.
  - **A recursive query over links people make** (made and linked ingredients, composites, packaging links) stops where a row comes round again, with `CYCLE <column> SET is_cycle USING path` after the CTE: the app refuses such a loop, but one made outside it would run until the command timed out. A `UNION` would end it too, but PostgreSQL sizes a `UNION`'s hash table from its row estimate, here thousands of times too high, which made Dependents noticeably slower.
- **A screen state's load that makes several reads runs them in one `Task.Run`**: each `await` on the UI thread comes back to it before the next read starts, and while the screen is drawing each return waits its turn, so eight sequential reads cost eight waits. `ProductsState.LoadProductDetailAsync` reads everything a product's detail shows through `SavedProductReader.ReadDetailAsync` (repositories only, no screen state) inside one `Task.Run`, and applies the `ProductDetail` it returns after a single return to the UI thread; `RawMaterialsState.LoadDetailsAsync` does the same for a raw material (`ReadDetailAsync`, `RawMaterialDetail`). The record screens' `LoadCommand`s start their list reads together, each in its own `Task.Run`, and await them with `Task.WhenAll` (Products about a dozen, Raw Materials and Sub-Assemblies five each, Raw Materials' with the products using the material showing).
- **Correctness and performance take priority over brevity or convenience.** Favour the approach that is provably correct and doesn't waste allocations, database round trips or UI-thread work, even where a shorter alternative exists: query only the columns and rows needed rather than materialize more and filter in memory, and avoid needless intermediate collections in hot paths like the costing cascade.
