# TinapayanRMS — Project Guide & Build Plan

Product recipe management & costing app for Tinapayan Festival Bakeshoppe. Tracks ingredient expenses, recipe/product margins, and cascades ingredient and packaging price changes up through sub-assemblies and finished products automatically.

## Tech Stack

- **Language / Runtime**: C# 14, .NET 10 (`net10.0`; `net10.0-windows10.0.19041.0` for the UI and Tests projects — ReactiveUI.WPF requires at least that Windows SDK version, and the bare `net10.0-windows` moniker resolves to `windows7.0`, which is too low)
- **UI**: WPF, styled with **Syncfusion Essential Studio for WPF 34.2.7** and Syncfusion's Windows11Light theme (the official `Syncfusion.Themes.Windows11Light.WPF` package), accent-recoloured at runtime
- **MVVM**: ReactiveUI (24.x). This version requires explicit builder-pattern initialization before any `ReactiveObject` is touched — `RxAppBuilder.CreateReactiveUIBuilder().WithCoreServices().WithWpf().BuildApp()` — done once per process by `src/TinapayanRMS.UI/ReactiveUIBootstrapper.cs`. It also dropped `System.Reactive` as a dependency, so that package is referenced directly wherever Rx LINQ operators (`.Select`, `.Where`, …) are used on an `IObservable<T>`.
  - **`ReactiveCommand.Create`/`CreateFromTask`'s parameterless overloads return `ReactiveCommand<RxVoid, RxVoid>`** (`ReactiveUI.Primitives.RxVoid`), not `ReactiveCommand<Unit, Unit>` — this fork doesn't use `System.Reactive.Unit` for that. Import the type via a using-alias (`using RxVoid = ReactiveUI.Primitives.RxVoid;`), never `using ReactiveUI.Primitives;` wholesale — that namespace also carries its own C# 14 extension-member `Select`/`Where`/`Subscribe`, which collide (CS0121, ambiguous call) with `System.Reactive.Linq`'s the moment both are in scope over the same observable.
- **Reactive collections**: DynamicData
- **Persistence**: EF Core 10.0.12 → SQL Server (db name `TinapayanRMS`)
- **DI / Hosting**: `Microsoft.Extensions.Hosting` + `Microsoft.Extensions.DependencyInjection`, wired via `HostBuilder` in `src/TinapayanRMS.UI/CompositionRoot.cs`, called from `App.xaml.cs`
- **Validation**: FluentValidation
- **Logging**: Serilog (rolling file sink)
- **Charts**: Syncfusion SfChart (`Syncfusion.SfChart.WPF`) for margin/price-trend reporting — replaces the originally-planned LiveCharts2
- **Testing**: xUnit v3, AwesomeAssertions, Respawn. Integration tests run against a locally installed SQL Server instance (such as LocalDB or SQL Server Express), and Respawn resets that database between tests. `AwesomeAssertions` replaces `FluentAssertions`: FluentAssertions 8+ requires a paid commercial license for use in a for-profit product, and AwesomeAssertions is a same-API, MIT-licensed fork of the last free FluentAssertions 7 release, created for exactly this situation. `NSubstitute` was referenced but never used — the suite exercises real repositories against a real Respawn-reset database rather than mocking — and its package reference was removed during a code-quality pass.
- **Solution format**: `.slnx`
- **`dotnet test`**: the .NET 10 SDK dropped VSTest support for `dotnet test`; running under the new Microsoft.Testing.Platform mode needs a `test.runner` setting in `global.json` at the repo root (already added). Run tests with `dotnet test --solution TinapayanRMS.slnx`.
- **Syncfusion license key**: read from the `SYNCFUSION_LICENSE_KEY` Windows user environment variable and registered in `App`'s static constructor (`src/TinapayanRMS.UI/App.xaml.cs`), before anything else in the process touches a Syncfusion type. Running the app or its tests on another machine requires that variable to be set there too.

**Folder = namespace, grouped by kind.** Every folder inside a project is a sub-namespace of it (`src/TinapayanRMS.UI/ViewModels/` → `TinapayanRMS.UI.ViewModels`). A new file goes in the folder for its kind, never at the project root. Only app-startup plumbing (`App`, `CompositionRoot`, `ReactiveUIBootstrapper`, `ConfirmDeleteHandlerRegistration`) and the DbContext pair live at a project root. Code in a sub-namespace sees its parent namespaces without a `using`: a View calls `RegisterNativeMessageBoxHandler` from `TinapayanRMS.UI`, and a repository uses `TinapayanRMSDbContext` from `TinapayanRMS.Infrastructure`. Sibling folders need a `using`. The solution was reorganized into this layout after the Phase 16 UI work: projects moved into `src/`/`tests/`, and each project's files went from flat to grouped by kind. Moving the entities to `TinapayanRMS.Domain.Entities` left the EF model unchanged (`dotnet ef migrations has-pending-model-changes` reported no changes), because table names come from the DbContext, not from entity namespaces. `Migrations/` was therefore left untouched.

The Windows11Light theme is not a project in the solution: it's Syncfusion's official `Syncfusion.Themes.Windows11Light.WPF` NuGet package (see Syncfusion UI Framework below).

## Domain Model

- **UnitOfMeasure**: `Id`, `Name`, `Abbreviation` — nothing else. **No unit is seeded or protected by a fixed id** — the table starts empty on a fresh database, and the shop owner adds every unit they need (gram, piece, mm, cm, in, m, or any custom unit like a sack or roll) in Settings → Units of Measure (see Application Architecture below), the same as any other user-managed lookup. **A unit carries no conversion factor of its own.** Conversions live on each raw material instead (see Multi-unit materials below): every material has a **base unit** its quantities and costs are tracked in (always the gram for an ingredient; chosen per packaging material), plus any number of **alternative units**, each defined as a multiple of that base unit. Length units (`IsLengthUnit`/`MillimetersPerUnit`/`LengthConversion`) were removed on 2026-09-13 to make way for this.
- **RawMaterial: ingredients and packaging share one table, told apart by `Type` (`Ingredient` or `Packaging`).** Merged on 2026-09-13 at the user's request ("the difference between the two is too thin"). Until then they were two tables, `Ingredient` and `PackagingMaterial`, each with its own category, unit and price history tables, and the schema itself kept packaging out of recipes. The merge kept the three differences that are real, as rules on the type:
  - **Base unit**: an ingredient's is always the gram, so its `BaseUnitId` is null — recipes, BOMs and sub-assembly weights all add up grams. A packaging material picks its own (`BaseUnitId` required).
  - **Source**: only an ingredient can be `Made` (a BOM and a weight loss); packaging is always `Purchased`.
  - **Where it can be used**: sub-assembly lines and BOM lines take ingredients only; a product's packaging lines take packaging only.
  - `RawMaterialRules.EnsureFieldsMatchType`/`EnsureFieldsMatchSource` run in `RawMaterialRepository` before every save, backed by two check constraints (`CK_RawMaterials_BaseUnitMatchesType`, `CK_RawMaterials_OnlyIngredientsAreMade`). Type and source are fixed once created (`EnsureTypeUnchanged`/`EnsureSourceUnchanged`). Each line repository checks every line's type (`EnsureUsableInRecipes`/`EnsureUsableAsPackaging`) before it replaces anything, with a message naming the material, and the pickers only offer the right type. A name is unique across both types.
  - The line entities kept their role names: `SubAssemblyLine.Ingredient`, `IngredientBomLine.Ingredient`/`ComponentIngredient` and `PackagingLine.PackagingMaterial` are all `RawMaterial`s, and each line's unit is `UnitId` (a `RawMaterialUnit`). `IngredientCostPropagator`, `SubAssemblyCostPropagator` and `IngredientQuantityConverter` kept theirs too, since they only ever deal with ingredients.
  - **`CostPerBaseUnit`** (stored, derived): the cost of one base unit — one gram, for an ingredient (it was `Ingredient.CostPerGram`). It's the value every sub-assembly line and BOM line uses, whichever the source.
- **Multi-unit materials** (built 2026-09-13, from the user's Ingredients mockup):
  - **`RawMaterialUnit`** (`RawMaterialId` Cascade, `UnitOfMeasureId` Restrict, `BaseUnitsPerUnit` > 0, `Description`; unique per material + unit; never a packaging material's own base unit). It merged `IngredientUnit` (`GramsPerUnit`) and `PackagingMaterialUnit`. The base unit never has a row: **an empty unit means the base unit** everywhere a unit is optional (price entries, recipe lines, packaging lines), so nothing depends on a "gram" row existing in Units of Measure.
  - `UnitConversionRules.ToBaseQuantity(quantity, multiplier?)` / `CostPerBaseUnit(price, multiplier?)` / `EnsureValidMultiplier` are the only conversion formulas.
  - **At most two alternative units per item** (`UnitConversionRules.MaxAlternativeUnits`, a user requirement added right after the feature shipped): `RawMaterialUnitRepository.AddAsync` counts the material's units and rejects a third (`EnsureCanAddAlternativeUnit`; `RawMaterialRepository.SaveAsync` adds units through the same check, after removing the ones a save drops), and the Raw Materials screen disables Add Alternative Unit at two (`CanAddUnit`, set when the unit rows are rebuilt). Editing an existing unit is unaffected.
  - **Every price entry records the unit it was priced in** (`UnitId?`), so switching from buying bags to buying packs leaves the old per-bag prices correct. The stored cost is per base unit only: `CostPerBaseUnit` = latest price ÷ that price's unit multiplier. `CurrentCost`, `PurchaseUnitId` and `PurchaseUnitQty` were dropped from both material tables before the merge: a latest price is meaningless without its unit, and storing the unit on the material would make a material ↔ unit FK cycle. The detail screen reads the latest price and its unit from the price history it already loads.
  - **Correcting a multiplier ripples.** `RawMaterialUnitRepository.UpdateAsync` (and the screen's Save, through the same shared write method) recomputes the material's `CostPerBaseUnit` if its latest price is in that unit. For an ingredient it also rewrites `Grams` on every recipe line entered in the unit (`ExecuteUpdateAsync`, one transaction with the unit), then calls `IngredientCostPropagator.RecomputeAndPropagateAsync` — which already reaches every dependent made ingredient and sub-assembly. A packaging material needs nothing more: packaging lines are costed on read.
  - **A unit in use can't be deleted**: the repository counts price entries and lines (recipe lines for an ingredient's unit, packaging lines for a packaging material's) first and says which (Restrict FKs back that up).
  - **A packaging material's base unit is fixed once it has alternative units, prices or packaging lines** (`RawMaterialRules.EnsureBaseUnitCanChange`, checked in `RawMaterialRepository.UpdateAsync`), since all of them are measured in it.
- **RawMaterialCategory** (Flour, Dairy, Boxes, Ribbons, …): one user-editable list for both types, merged from `IngredientCategory` and `PackagingCategory` (a packaging category named like an ingredient one joined it). Managed in Settings → Categories — see Application Architecture below.
- **Ingredients** (`Type = Ingredient`):
  - **The base unit for every ingredient is the gram.** Every weight total is in grams: sub-assembly lines' and BOM lines' `Grams`, sub-assembly total weights, and weight-per-piece. Recipe lines can be *entered* in an alternative unit (see IngredientBomLine / SubAssemblyLine), but they're always stored in grams too.
  - **`Source`**: `Purchased` or `Made`. It is set when the ingredient is created and can't change afterwards, so an ingredient's cost always comes from exactly one place.
  - **`Units`**: its alternative units (a 25 kg bag is `BaseUnitsPerUnit = 25000`, an egg piece `50`). Either source can have them; only a purchased one is priced in them.
  - **Purchased** ingredients are priced through `RawMaterialPriceHistory`, each entry in one of the ingredient's units (or per gram). `CostPerBaseUnit = latest price ÷ grams in its unit`.
  - **Made** ingredients are produced in-house from a bill of materials (BOM):
    - They have no price history.
    - **`WeightLossPercent`**: weight lost while making the ingredient (e.g. water boiled off syrup). At least 0 and less than 100, enforced by `RawMaterialRules.EnsureFieldsMatchSource`.
    - Output grams = `Σ BOM line grams × (1 − WeightLossPercent / 100)`.
    - Cost per gram = `Σ (BOM line grams × component cost per gram) / output grams`. The formula itself is `IngredientBomRules.CalculateCost`; a component's cost used here is whatever's currently stored on it — see the propagation note below for why that's always safe to read directly rather than walking the tree every time.
    - Example: simple syrup made from 1000g sugar (₱0.09/g, so ₱90) and 500g water (₱0, i.e. never priced — see PLAN.md's PriceHistoryRules note: a literal ₱0 price entry is rejected, so "free" means unpriced, not a zero entry), with 20% weight loss, gives 1500 × 0.8 = 1200g. It costs ₱90 / 1200 = ₱0.075/g.
- **IngredientBomLine**: one component of a made ingredient. It has `IngredientId` (the made ingredient), `ComponentIngredientId` (a raw material of the Ingredient type, purchased or made), the amount as entered (`Quantity` in `UnitId?`, one of the component's own units — Restrict), and `Grams` (that amount in grams, computed by `IngredientQuantityConverter` on save and kept in step when the unit's multiplier is corrected). `IngredientBomRules.EnsureValidLines` rejects an empty set, non-positive grams, or the same component twice (combine it into one line instead).
  - BOMs can nest to any depth: caramel can be made from syrup, and syrup from sugar. `IngredientBomRules.EnsureNoCycle` blocks an ingredient from appearing anywhere in its own BOM tree, checked at save time by walking the *other* made ingredients' current BOM graph.
  - `IngredientId`'s FK is Cascade (deleting the made ingredient takes its own BOM lines with it); `ComponentIngredientId`'s FK is Restrict (deleting an ingredient that's in use as a component is blocked — remove it from the BOM first). Both can't be Cascade: SQL Server rejects two cascade paths from the same table to the same parent table.
  - BOM lines use ingredients only, never packaging (`RawMaterialRules.EnsureUsableInRecipes`, checked by `IngredientBomLineRepository.SetLinesAsync`).
- **Packaging materials** (`Type = Packaging`):
  - `BaseUnitId` (FK to UnitOfMeasure; `StandardUnitId` until 2026-09-13) is its base unit, set per material: typically a count unit (piece) for boxes and wrappers, a length unit (cm) for ribbon. No rule restricts which unit that can be — the shop owner is trusted to pick a sensible one — but it's fixed once anything is measured in it (see Multi-unit materials).
  - `Units` are its alternative units (a pack of 100 boxes is `BaseUnitsPerUnit = 100`, a 1000 cm ribbon roll `1000`), and `CostPerBaseUnit` its stored cost.
  - Always purchased, and priced through `RawMaterialPriceHistory` like a purchased ingredient.
  - Packaging lines can be entered in the base unit or any alternative unit (see PackagingLine).
- **RawMaterialPriceHistory** (merged from `IngredientPriceHistory` and `PackagingPriceHistory`): a price timeline for each purchased material. Made ingredients have none. A price is entered **per unit** (the price of one sack or one pack, as on the supplier's receipt) and records that unit; no unit means per base unit. The material's stored cost per base unit is recalculated from the latest entry. "Latest" is by date, then by id — and a price added on the same date as the current latest one wins (`PriceHistoryRules.FindLatestAfterAdding`; before 2026-09-13 an unsaved entry's id of 0 lost that tie, so a second same-day price never became current — the ingredient migration healed the stored costs). A new ingredient price runs the ingredient cost cascade; a new packaging price needs nothing more, since products cost packaging lines on read.
- **SubAssemblyRole**: an editable lookup table (`Id`, `Name`, `SortOrder`), seeded with Dough, Filling, Topping, Inclusion and Finishing. More roles, such as Glaze, can be added later. `SortOrder` sets the order of a product's recipe tabs. A role can't be deleted while any sub-assembly uses it.
- **SubAssembly** + **SubAssemblyLine**: a sub-assembly is an in-house recipe that products use directly, such as a dough, a filling or a topping. Its lines are the ingredients that make it up.
  - `RoleId` (FK to `SubAssemblyRole`, required): each sub-assembly has exactly one role, so custard is always a Filling, and the Filling tab only offers filling sub-assemblies. To use the same recipe in another role, create a separate sub-assembly.
  - A sub-assembly's role can only be changed while no product uses it. Changing it would move the sub-assembly to a different tab in every product that uses it, and break that tab's links.
  - Each line has an FK to an ingredient (a `RawMaterial` of the Ingredient type — `SubAssemblyLineRepository` rejects packaging), the amount as entered (`Quantity` in `UnitId?`, one of that ingredient's units — "3 pc of egg"), and `Grams` (that amount in grams). Line cost = grams × the ingredient's `CostPerBaseUnit`, its cost per gram.
  - A sub-assembly has a total weight in grams (the sum of its line grams) and a total ingredient cost.
- **Product** + **ProductSubAssemblyUsage**: a finished product is built from distinct sub-assemblies. It can use several sub-assemblies in the same role (e.g. an ube filling and a cheese filling), but each sub-assembly only once.
  - Each usage stores **`WeightPerPiece`** (grams). The UI accepts either weight-per-piece or yield (piece count) as input, but only `WeightPerPiece` is stored.
  - Yield is derived per usage: `Yield = SubAssembly.TotalWeight / WeightPerPiece`.
  - Usage cost per piece = `SubAssembly.TotalCost × WeightPerPiece / SubAssembly.TotalWeight`. For example, 100g/₱24 filling used at 10g/piece gives ₱2.40/piece, yield 10.
  - Rescaling a sub-assembly batch changes the yield, but the grams in each piece stay the same.
  - A product has **no yield of its own**. Each usage row has its own yield, and those will usually differ between a product's sub-assemblies. That's expected, not an error.
  - Product material cost per piece = the sum of all its usages' cost-per-piece, plus its packaging lines' cost-per-piece.
  - Sub-assembly and product weights are raw input weights, and baking/moisture loss is not modeled for them. Made ingredients are the only place weight loss is modeled (`WeightLossPercent`).
- **PackagingLine**: one packaging material used by a product.
  - FK to a `RawMaterial` of the Packaging type (`PackagingLineRepository` rejects an ingredient), so packaging price changes cascade like ingredient price changes.
  - **`UnitId?`** (`PackagingMaterialUnitId` before the raw materials merge): the unit the line's quantities are entered in — one of the material's own units, or its base unit when empty. Quantities are stored as entered, in that unit. (A length-only `EntryUnitId` existed until the length units were removed on 2026-09-13; this general unit replaced it the same day.)
  - **`QtyPerPiece`**: amount of the packaging material used by one finished piece, in the line's unit (12.7 for 12.7 cm of ribbon, `0.1667` for a 6-piece box, 1 for a label).
  - **`PiecesPerPackagingUnit`**: finished pieces served by one of the line's unit of the packaging material (6 for that box).
  - **`AuthoredField`**: records which of the two the user typed. The other is recalculated as its reciprocal on every edit. Ribbon is naturally entered as `QtyPerPiece`, a box as `PiecesPerPackagingUnit`.
  - Cost per piece = `CostPerBaseUnit × QtyPerPiece` converted to base units (`ProductRules.CalculatePackagingLineCostPerPiece(costPerBaseUnit, qtyPerPiece, baseUnitsPerEntryUnit?)`), computed on read.
  - Example: a ribbon costs ₱45.00 per roll. Its base unit is cm and a roll holds 1000 cm, so it costs ₱0.045 per cm. One product uses 12.7 cm per piece (₱0.5715); another is entered as 0.08 m per piece (8 cm → ₱0.36).
  - Storing both directions differs from `ProductSubAssemblyUsage` on purpose. People describe packaging quantities both ways, but they describe recipe weights only one way.
- **CostingParameters**: labor, overhead, margin %, VAT. **Always independent per product**, even for derived/linked products.

### Derived products (Phase 10)

Some products derive from others (e.g. Special Ensaymada Small from Special Ensaymada Big, differing only in weight; or products sharing a dough sub-assembly but differing in toppings). Deriving supports two real mechanisms:

- **Clone** (`IProductCloner.CloneAsync`): a one-time, fully independent copy of whatever a source product currently shows (its *effective* usages/packaging lines, resolved through any tab links it has — a clone never inherits a link, only the data), plus its `CostingParameters` as a starting point. Nothing about the clone stays connected to the source afterward.
- **Live Template** (`ProductTabLink`): one of a product's **tabs** is linked to the same tab on another product and reads through to it instead of owning rows. A **tab** is one role on one product, identified by (`ProductId`, `SubAssemblyRoleId`) — it holds all of that product's sub-assemblies in that role. Each product also has one **Packaging** tab for its packaging lines. Because a sub-assembly's role can't change while products use it (enforced since Phase 8), a tab's identity stays the same for the life of the product.
  - Linking is chosen **per tab**, not all-or-nothing: linking the Filling tab links both the ube and the cheese filling usages in it, but the Dough tab can stay independent. Any tab's link can be repointed to a different product or removed at any time, separately for each tab.
  - **Unlinking a tab never loses data**: it first materializes whatever the tab currently shows (resolved through the link) into the product's own owned rows, then removes the link — the product ends up with an independent copy of exactly what it was displaying a moment before, not an empty tab.
  - Live templating covers recipe tabs and the Packaging tab, but **never** `CostingParameters` (labor/overhead/margin/VAT), which always stay independent per product — there's no tab, and no link mechanism, for costing.
  - Chains are allowed (C's tab linked to B's tab linked to A's tab) and resolved recursively at read time; a cycle is rejected when a link is created (`ProductTabLinkRules.EnsureNoCycle`), not just at read time.
- The **"same sub-assembly, different weight"** state named in the original design turned out not to need a third schema mode: two products simply having `ProductSubAssemblyUsage` rows that reference the same `SubAssemblyId` with different `WeightPerPiece` was already possible from Phase 8 onward (nothing enforces usages be unique across products). It's reached naturally through either of the two real mechanisms — Clone-then-edit-the-weight, or Live-Template-then-unlink-then-edit-the-weight (unlinking freezes the same `SubAssemblyId` as an owned row, immediately editable) — so no separate feature was built for it.

## Syncfusion UI Framework

The app is styled with **Syncfusion Essential Studio for WPF 34.2.7**, licensed via the `SYNCFUSION_LICENSE_KEY` environment variable, and Syncfusion's **Windows11Light** theme.

- **The theme is Syncfusion's official `Syncfusion.Themes.Windows11Light.WPF` package (Phase 16).** It depends only on `Syncfusion.SfSkinManager.WPF` and `Syncfusion.Licensing`, and it styles every Syncfusion control, so adopting a new control never needs theme work. It replaced a trimmed in-repo theme project (see "Why the theme is no longer trimmed" below) — briefly via a locally packed Theme Studio export, then this package, which is the same theme.
  - **Every Syncfusion package is pinned to the same version, currently `34.2.7`.** The theme package requires `SfSkinManager`/`Licensing` at its own version, NuGet rejects the mismatch as a downgrade (`NU1605`), and Syncfusion doesn't support mixing versions across its assemblies — so upgrading any Syncfusion package means upgrading all of them together in `TinapayanRMS.UI.csproj`. The `34.2.2` → `34.2.7` upgrade (a patch within the 34.2 release) kept the same license key: no license popup at startup. A move to a new feature release (e.g. 34.3) needs a new key from the Syncfusion account.
  - **One theme gap is patched in the app**: the theme's `SfTextBoxExt` style — unlike its `ComboBoxAdv`, `DoubleTextBox` and `DateTimeEdit` styles — never sets `VerticalContentAlignment`, so the text sits against the top of the box at the 32px `SizeMode="Touch"` height. `App`'s static constructor calls `Control.VerticalContentAlignmentProperty.OverrideMetadata(typeof(SfTextBoxExt), new FrameworkPropertyMetadata(VerticalAlignment.Center))`, changing the type's default so every instance (including future ones) is centred without a `Style` on the control; it must run before any `SfTextBoxExt` exists. Verified at runtime: `VerticalContentAlignment=Center`, value source `Default`.
  - **A second `SfTextBoxExt` theme gap: its text sat about 5px further right than the other fields.**
    - The theme's `SfTextBoxExt` template puts a fixed `Margin="10,0,0,0"` on `PART_ContentHost`. `DoubleTextBox`'s template uses 3px of padding instead.
    - Measured in an off-screen replica with the same theme and Touch size, a Name box's text started 13px from its left edge. A `DoubleTextBox` started at 8px and a `ComboBoxAdv` at 7px.
    - The template passes `Padding` (the theme sets -1) to the text presenter inside that margin. `App`'s `AlignTextBoxText` class handler, on `SfTextBoxExt.Loaded`, sets a left padding of -6, which moves the text to 8px.
    - That padding has to be a local value. The theme sets `Padding` through the control's default style (value source `DefaultStyle`), which outranks an `OverrideMetadata` default. A `SetCurrentValue` at `Loaded` was tried first and didn't survive.
    - A `Padding` set in XAML still wins.
  - **A third `SfTextBoxExt` theme gap: its watermark sat at the top of the box, 4px right of typed text.** The template shows `Watermark` in a plain `ContentControl`, whose default template honors neither `VerticalContentAlignment` nor `Padding`, so neither fix above reaches it. `App.xaml`'s `AlignedWatermarkTemplate`, set as the box's `WatermarkTemplate`, centers the hint and moves it 4px left. Measured with the same text typed and as the watermark (a true-size capture with the blinking caret filtered out by keeping each pixel's brightest value across frames), both now start 8px in and cover the same rows. Give it to any `SfTextBoxExt` with a `Watermark`; today that's the Raw Materials search box.
- **Core control set**: the app adopts `SfDataGrid` (lists/grids), `Syncfusion.SfInput.WPF`'s edit controls (`ComboBoxAdv`, `AutoComplete`, `MaskedTextBox`, `DateTimeEdit`, `CurrencyTextBox`, and others), `ButtonAdv`, `TabControlExt`, `DockingManager`/`Ribbon` for the app shell, and `SfChart` for reporting. `TinapayanRMS.UI` takes its own `PackageReference`s (pinned to the shared Syncfusion version above) for exactly these.
  - **`DateTimeEdit`'s bindable date property is `DateTime`, not `Value`** (`Syncfusion.Windows.Shared.DateTimeEdit`, in `Syncfusion.Shared.WPF`) — it doesn't follow the `Value`-property convention `DoubleTextBox`/`IntegerTextBox` use. Confirmed by reflecting over the built assembly (`[System.AppDomain]::CurrentDomain.GetAssemblies() | Where Name -eq Syncfusion.Shared.WPF`, then `.GetType(...).GetProperties()`) rather than guessing again after the compiler rejected `Value`.
  - **Every editable `DoubleTextBox` binds `Value` with `UpdateSourceTrigger=PropertyChanged`** (2026-09-13). Without it the typed value reaches the ViewModel only when the box loses focus: the Syncfusion DoubleTextBox skill says to bind this way "for live updates", and Syncfusion's unit-converter showcase does.

- **Per-monitor DPI awareness (`src/TinapayanRMS.UI/app.manifest`, wired via `<ApplicationManifest>`)**. On its own WPF is only *system*-DPI-aware: it renders at the scale the primary monitor had at sign-in, and on a monitor with a different scale Windows bitmap-stretches the whole window. That was reported as "the app is a little blurry on the secondary monitor": the dev machine's primary is 1920×1080 at 125% and its secondary 1366×768 at 100%, so the window rendered at 120 DPI and was shrunk by 0.8. The manifest declares `dpiAwareness` `PerMonitorV2, PerMonitor`, plus the legacy `dpiAware` `true` that only pre-1607 Windows reads. WPF then re-renders natively at each monitor's DPI and handles `WM_DPICHANGED` itself. That needs no code — none of the native-helper/`DisableDpiAwareness` scale-transform approach from Microsoft's Windows 8.1-era article. Layout is unchanged, since everything is in DIPs (the window is 1400×800 physical px on the 100% monitor either way); only sharpness changes. Things that would need extra per-DPI work if ever added: bitmap image assets, `HwndHost`/`WindowsFormsHost`, `RenderTargetBitmap`; the app has none today.
  - **Verified** by querying the running window before and after the manifest: `GetWindowDpiAwarenessContext` went from System aware to Per-monitor V2, and `GetDpiForWindow` on the secondary from 120 to 96. A zoomed before/after crop of the same grid text showed the blur gone. **`PrintWindow` can't show this kind of blur**: it captures the window's own surface at its render DPI, before Windows stretches it. A DPI-scaling check has to capture the screen itself (`CopyFromScreen`, with the window kept topmost via `SWP_NOACTIVATE` so it doesn't take focus).

The trade-off: Syncfusion controls theme normally via `SetTheme`, while plain framework controls (`CheckBox`, `Expander`, `ProgressBar`) keep the OS default look.
- **App-level design tokens (Phase 16)**, in `App.xaml`, alongside the icon templates: a small neutral scale plus the accent (`PageBackgroundBrush` `#F5F5F4`, `CardBackgroundBrush` `#FFFFFF`, `CardBorderBrush` `#E7E5E4`, `HeadingForegroundBrush` `#1C1917`, `MutedForegroundBrush` `#57534E`, `AccentBrush` `#B45309`, plus error/warning background+foreground pairs and two chart brushes) and keyed styles built from them (`CardStyle`, `SectionHeaderStyle`, `FieldLabelStyle`, `CaptionStyle`, `EmptyStateStyle`, `ErrorBannerStyle`/`WarningBannerStyle`, `AppTitleStyle`). **`TextBlock` has no `CharacterSpacing` property in WPF** — that's a WinUI/UWP-only property; a `Style TargetType="TextBlock"` `Setter` for it fails the build with `MC4005`, found while first writing `AppTitleStyle`. **These styles are keyed and target only native elements (`Border`, `TextBlock`) — never a `Style` with no `x:Key`, and never one whose `TargetType` is a Syncfusion control.** An implicit (unkeyed) style on a native type would leak into every Syncfusion control template that hosts one internally; a `Style` set directly on a Syncfusion control would replace its themed template outright. - **`SfChart` shape** (`Syncfusion.UI.Xaml.Charts` namespace, first used Phase 12 — confirmed by reflecting over the built `Syncfusion.SfChart.WPF.dll` the same way `DateTimeEdit` was, rather than guessing): the root `SfChart` element takes exactly one `PrimaryAxis` and one `SecondaryAxis` (property elements, not collections) plus a `Series` collection (`SfChart.Series`) of `ChartSeriesBase`-derived series (`LineSeries`, `ColumnSeries`, …) and an optional `Legend` (`SfChart.Legend`, a `ChartLegend`). Each series binds independently — `ItemsSource`, `XBindingPath`, `YBindingPath`, `Label` (the legend text) all live on `ChartSeriesBase`/`XyDataSeries`, so two series (e.g. `ColumnSeries` for "Base Cost" and another for "Selling Price") can share one `ItemsSource` and just point `YBindingPath` at different properties of the same row type. `DateTimeAxis` binds cleanly to a plain `DateTime` `XBindingPath` — project a `DateOnly` column to `DateTime` (`.ToDateTime(TimeOnly.MinValue)`) in the chart-row DTO rather than binding `DateOnly` directly, since that conversion's support wasn't worth gambling on for a type newer than the library's own value-binding internals. **A fixed, distinct color per series is just `Interior="{StaticResource ...Brush}"` on that series** (`ChartSeriesBase`) — `Palette="Custom"` plus a `ColorModel`/`ChartColorModel.CustomBrushes` list (Phase 16's Reports rework first reached for this, going by the pattern in `.claude/skills/syncfusion-wpf-charts`) is for coloring the individual *segments within one series* differently (e.g. each category's bar its own color), not for giving two separate named series — "Base Cost" and "Selling Price" here — two different fixed colors; using it for that would need the two series merged into one with a value-based color selector, which is unnecessary when `Interior` alone does the job per series. Direct value labels on a `ColumnSeries` (so a comparison doesn't rely on color alone) are `<syncfusion:ColumnSeries.AdornmentsInfo><syncfusion:ChartAdornmentInfo ShowLabel="True" /></syncfusion:ColumnSeries.AdornmentsInfo>` — the property is `AdornmentsInfo`, the element type is `ChartAdornmentInfo`.

## Application Architecture

- **Repository interfaces live in `ApplicationCore`, implementations in `Infrastructure`** (`IRawMaterialRepository`/`RawMaterialRepository`, and so on), consumed by UI ViewModels through DI. `ILookupRepository<T>` in `ApplicationCore`, with one generic `LookupRepository<T>` implementation in `Infrastructure`, covers every simple **read-only** lookup table (`UnitOfMeasure`, `IngredientCategory`, `PackagingCategory`) instead of writing a near-identical class per table. `SubAssemblyRole` turned out **not** to fit this: unlike those three, it's user-editable (Phase 7 gave it its own small embedded management panel), so it needed a dedicated `ISubAssemblyRoleRepository`/`SubAssemblyRoleRepository` with full CRUD instead. `ILookupRepository<T>` is for genuinely read-only lookups only — don't reach for it just because a table is small.
- **`TinapayanRMSDbContext` is registered with `AddDbContextFactory`, not `AddDbContext`.** ViewModels are DI singletons (`MainWindowViewModel`, `RawMaterialsViewModel`, …) so they outlive any single screen, and WPF has no ASP.NET-style per-request scope to hand a plain `AddDbContext`-registered instance to — resolving one into two singleton ViewModels at startup handed them the *same* `DbContext` instance, and two screens' tabs loading concurrently on app startup then threw `InvalidOperationException: A second operation was started on this context instance before a previous operation completed` the first time the app was actually run (not caught by the build or by any test — only by launching it). Every repository instead takes `IDbContextFactory<TinapayanRMSDbContext>` and creates-and-disposes a short-lived context per call (`await using var dbContext = await dbContextFactory.CreateDbContextAsync(cancellationToken);`), which is also naturally safe for concurrent calls from different screens. Follow this pattern for every future repository — never inject `TinapayanRMSDbContext` directly into a repository or ViewModel.
- **CRUD screen pattern** (established by `IngredientsView`/`IngredientsViewModel` and `PackagingMaterialsView`/`PackagingMaterialsViewModel`, Phase 4, merged into `RawMaterialsView`/`RawMaterialsViewModel` on 2026-09-13; card layout and right-rail arrangement reworked Phase 16): a read-only `SfDataGrid` list on the left, bound to a `DynamicData SourceCache<T,int>` via `.Connect().SortAndBind(out collection, comparer).Subscribe()` (not the obsolete `.Sort().Bind()` pair); a master-detail edit form on the right, populated from the grid's `SelectedItem` via a `WhenAnyValue` subscription; `New`/`Save`/`Delete` as `ButtonAdv`s bound to `ReactiveCommand`s. Follow this pattern for future CRUD screens rather than in-grid cell editing, which needs SfDataGrid event wiring that's much harder to get right without a live designer.
  - **Since Phase 16, the shape is a list card plus a right rail, not fixed Grid columns of bare panels.** The root `Grid` carries `PageBackgroundBrush`, `Margin="16"`, and a `StatusBanner` in row 0. Row 1 is two columns: a `*`-width list card (`CardStyle` `Border` + `SectionHeaderStyle` header + the `SfDataGrid`, `ColumnSizer="AutoWithLastColumnFill"` so every column — including money columns — fits without a horizontal scrollbar; `RawMaterialsView` uses `ColumnSizer="Star"` instead, so Name and Category share what its fixed-width Cost column leaves, and it groups its rows by type (see the Raw Materials note below). A column's `Width` accepts pixels only, as in `Width="120"`. A value of `"*"` or `"2*"` builds cleanly but crashes the app at startup with a `XamlParseException` ("* is not a valid value for Double"), so star-size through `ColumnSizer="Star"` on the grid or on a column), and a fixed ~360px right rail in a `ScrollViewer` holding, top to bottom: a Details card (the edit form), the screen's existing conditional detail card(s) (Price History, BOM, Lines) shown under their existing `Show*` flags with an `EmptyStateStyle` hint (bound through `EmptyStateVisibilityConverter`) filling the same slot when nothing is selected, and a collapsed `Expander` for any embedded lookup panel (see the note below). `UnitsOfMeasureView` and `CategoriesView`, the Settings dialog's tabs, are the simplest case — list card plus a single form card, no expander, no conditional detail card. Every number column in a grid, money included, uses `controls:NumericColumn` (`src/TinapayanRMS.UI/Controls/NumericColumn.cs`). Never use `syncfusion:GridNumericColumn` or `syncfusion:GridCurrencyColumn` directly. Money shows as a bare number (`930.00`, not `₱930.00`), so `GridCurrencyColumn` would add nothing useful: its currency editor never opens in these read-only grids, its parentheses for negatives never apply because costs are never negative, and it doesn't group thousands by default. Money columns use 2 decimals (`NumberDecimalDigits`) for totals and prices, and 4 for per-unit costs (`CostPerBaseUnit`, `CostPerPiece`). `NumericColumn` is a `GridNumericColumn` whose constructor sets the app's defaults: `NumberGroupSeparator=","`, `NumberGroupSizes="3"` and `HorizontalHeaderContentAlignment="Right"`. Out of the box, `GridNumericColumn` doesn't group thousands (`NumberGroupSizes` is `[0]`) and centres its header. A grid column is a `Freezable`, not a `FrameworkElement`, so an implicit `Style` can't carry these defaults. This was confirmed by reflecting over `Syncfusion.SfGrid.WPF` 34.2.7. Set only what differs per column (`NumberDecimalDigits`); a value set in XAML still overrides a default.
  - **`ProductsView` (Phase 8/9) no longer uses a horizontal `ScrollViewer` of fixed-width `StackPanel`s — Phase 16 replaced that with sub-tabs plus a pinned summary**, once the six-panel version pushed the Selling Price summary off-screen. Now three columns: a 300px-wide left column (Products list card, then a Product form card below it), a centre `TabControlExt` (`CloseButtonType="Hide"`, `ShowTabItemContextMenu="False"`, `ShowTabListContextMenu="False"`, every `TabItemExt` `CanClose="False"` — these are fixed sub-tabs, not user-closable top-level tabs) holding **Usages**/**Packaging**/**Costing**/**Links & Clone**, each carrying its existing panel's content verbatim, and a pinned 260px right column with the Price Summary card (Material Cost, Base Cost, Pre-VAT Price, then Selling Price large and `AccentBrush`-colored) that stays visible across every sub-tab. Both the tab strip and the summary card are visible only when `ShowProductDetail` is true; an `EmptyStateStyle` hint fills the centre otherwise. The linked-tab notices (`IsSelectedRoleLinked`/`IsPackagingLinked`) moved from inline amber `TextBlock`s into `WarningBannerStyle` banners.
- **A tab keeps its view state while the app runs, and still picks up changes made on other tabs.** Nothing is saved to disk; the state lasts for the session only.
  - **Tab content stays loaded.** `MainTabControl` has `IsDisableUnloadTabItemExtContent="True"`. By default `TabControlExt` unloads a tab's content on every switch; measured off-screen, content was unloaded twice and re-loaded three times over four switches, and never unloaded with the property set. So scroll position, sorting, sub-tabs, expanders, focus and typed text survive a switch without any code.
  - **One load trigger: tab activation.** Views don't load data on `Loaded`. `MainWindow.xaml.cs` maps each `TabItemExt` to its screen's `LoadCommand` and runs it for the tab shown at startup and on each `MainTabControl.SelectionChanged`. It ignores bubbled events whose `OriginalSource` isn't `MainTabControl`, and skips a tab whose refresh is still running.
  - **Every `LoadCommand` is a fetch-then-merge, never a clear-and-reload.** Clearing a list is what used to lose the selected row, picker choices and Products' unsaved rows on every return.
    1. All `await`s finish first.
    2. The ids of the selected row, every picker and the lookup-panel selection are recorded. A ComboBoxAdv can clear its own `SelectedItem` when its item is replaced mid-merge, so the ids must be read before merging.
    3. Inside `ApplyRefresh` (`ViewModelBase`, which sets `IsRefreshing`), the lists are merged with `CollectionMerge.MergeFrom`, and each selection and picker is re-pointed by id.
  - **`CollectionMerge`** (`src/TinapayanRMS.UI/ViewModels/CollectionMerge.cs`) keeps the existing object for every row whose values didn't change, which is what a grid's selection and scroll and a picker's `SelectedItem` are tied to. A `SourceCache` merge uses DynamicData's `EditDiff`; an `ObservableCollection` is synced in place. `HasSameValues` compares scalar properties plus those of referenced entities one level deep (so a renamed category counts as a change to an ingredient showing it). A collection the row owns (a raw material's `Units`) counts as part of the row: its elements are compared in order, the same way as the row, so an added unit — or a unit of measure renamed in Settings — replaces the row. A screen whose selected row is replaced that way rebuilds the unit rows and pickers derived from it, keeping picks by id.
  - **Selection-driven subscriptions skip while `IsRefreshing`**: form loads, "reset the detail fields" blocks, detail reloads, lookup-panel form loads, and Products' role and packaging-material pickers. Re-pointing a selection at its refreshed copy must not reload the form or throw away unsaved edits. `ReportsViewModel` isn't a `ViewModelBase` and has its own `_isRefreshing`.
  - **Products** also rebuilds its unsaved usage and packaging rows with the refreshed sub-assemblies, materials and units (`RefreshUnsavedRows`), keeping each row's numbers, so costs changed on other tabs reach the Price Summary. It also refreshes the selected product's saved usage costs and tab links.
  - **Save, Delete and the lookup panels call the same `LoadCommand`**, so an existing record stays selected after saving, and renaming a category or role updates the grid.
  - Covered by `tests/TinapayanRMS.Tests/ViewModels/`: `CollectionMergeTests`, plus Ingredients and Products refresh tests that build the ViewModel on real repositories.
  - **Fixed along the way: Products listed a role's usages twice.** `LoadProductDetailAsync` set `EditingUsageRole`, whose subscription loads the usages, then also awaited its own load. Whenever the role actually changed (the first product picked each session, for example), both loads ran side by side and each added every row, which double-counted those costs in the summary. It now loads directly only when the role didn't change, and `LoadUsagesForRoleAsync` recomputes the summary itself.
- **Embedded management panel for an editable child lookup** (`SubAssembliesView`, Phase 7): `SubAssemblyRole` is editable but has no screen of its own — it gets a small self-contained grid + form + New/Save/Delete panel living directly inside `SubAssembliesView`, with its own independent `SourceCache`, selection, and commands in `SubAssembliesViewModel` (not a separate tab, and not folded into the sub-assembly form itself). Use this shape for a future lookup that's editable but too small/tightly-coupled to its owning screen to deserve a top-level tab. **Since Phase 16 it sits inside a collapsed native `Expander`** (`IsExpanded="False"`) at the bottom of the screen's right rail, rather than an always-visible side panel — it's used rarely enough (editing categories/roles is occasional, not part of the main workflow) that keeping it collapsed by default gives the main list more room without hiding the feature. The native `Expander` is used rather than a Syncfusion accordion (`SfAccordion` would need its own package just for this), and since `ApplyThemeAsDefaultStyle` is off (see the accent-customization note above), the native `Expander` renders with the plain OS chrome rather than the theme's — functional, just not accent-styled, the same trade-off as the other native fallbacks (`CheckBox`, `ProgressBar`) noted elsewhere in this document.
  - **The same shape was reused for `IngredientCategory` (in `IngredientsView`) and `PackagingCategory` (in `PackagingMaterialsView`)** once the user asked for a way to add/edit/remove categories, which neither had before (both were originally served only by the read-only, generic `ILookupRepository<T>`).     - The purchase unit choices come from those rows, and `BaseUnitName`/`BaseUnitAbbreviation` follow the form's type and base unit, so a new packaging material shows its own unit before it's saved.
    - The cards follow the form, not the selection. Purchase Cost Setup follows the editing source and the BOM card `IsEditingMade`, so a new material shows every card before its first Save. Price History (`ShowPriceHistory`) only shows once a purchased material is saved.
  - **What Save sends** to `IRawMaterialRepository.SaveAsync(material, units, newPrice, bomLines)`:
    - A unit form left open is applied first.
    - `units` is the complete list.
    - A new price only when its unit or amount differs from the latest price (the old Save Price rule; an unsaved unit's id is 0, so it never matches). It names its unit by unit of measure, since a unit added in the same save has no id yet.
    - BOM lines only when they differ from the lines last loaded. An untouched BOM is neither replaced nor, when empty, rejected, so a made ingredient can still be saved before it has lines.
    - Afterwards `LoadCommand` runs, then a fresh copy of the material is selected, so the form reloads what was saved: units with ids, the price history and the BOM.
  - **How it saves: one context and one transaction.**
    - Every step goes through the `internal static` write methods the single-purpose repository methods now share: `RawMaterialRepository.AddAsync`/`UpdateAsync`, `RawMaterialUnitRepository.AddAsync`/`UpdateAsync`/`DeleteAsync`, `RawMaterialPriceHistoryRepository.AddAsync` and `IngredientBomLineRepository.SetLinesAsync`. Each takes the caller's `TinapayanRMSDbContext`, saves to it, and says whether the cost cascade must run.
    - Order: the material; its units, removed first, then updated, then added (so a replacement fits within the limit of two, and a removed unit of measure can come back as a new row); the price; the BOM. Each step saves as it goes, so the next step's checks see what it wrote.
    - A rejection anywhere rolls all of it back, and the cascade runs once, after the commit.
    - The caller's entities are only read, so a rolled-back save never leaves an id on them.
    - `SetLinesAsync` gained the transaction its delete-then-insert lacked.
    - The public single-purpose methods keep their behaviour, and their tests keep covering the checks; `RawMaterialSavePersistenceTests` covers the whole save.
  - **Refreshes keep unsaved units.** `LoadCommand` points each row at its refreshed unit of measure (so a rename in Settings shows) instead of rebuilding the rows from the refreshed material.
    - `NewCommand` clears the details itself: after an unsaved new material nothing was selected, so the selection subscriptions don't fire.
    - Delete Price stays immediate and reloads only the price history, where selecting the refreshed material would drop unsaved edits.
- **The Settings dialog holds the lookups every screen picks from: units of measure and categories** (2026-09-13, at the user's request: the embedded Manage categories panels were hard to find, and Units of Measure took a whole tab).
  - **It opens from a `FooterItems` entry in the navigation drawer** (the gear at the bottom of the rail). The item is `ItemType="Button"`: Syncfusion's docs say a Button-type item "is not selectable and only ItemClicked and Command actions can be performed", so opening Settings leaves the current page highlighted. Syncfusion's own `DisplayMode.xaml` demo puts Settings in `FooterItems` too.
  - **`SettingsWindow`** is a modal `Window` owned by `MainWindow`, with fixed `TabControlExt` tabs (like Products' sub-tabs: no close buttons or context menus) for `UnitsOfMeasureView` and `CategoriesView`, and a Close button (`IsCancel`, so Esc closes it too). It takes the main window's theme (`SfSkinManager.SetTheme(settings, SfSkinManager.GetTheme(this))`) and sets `SizeMode="Touch"` itself, since a new window is a new visual tree.
  - It's **built afresh each time it opens, over singleton ViewModels** (`UnitsOfMeasureViewModel`, `CategoriesViewModel`), so a tab keeps its selection and unsaved edits between visits. Anything a view hooks onto its longer-lived ViewModel is undone with it: `SettingsWindow` registers the delete confirmations and disposes them when it closes (`RegisterNativeMessageBoxHandler` returns the registration for this), and each view's focus-the-Name-box subscription lives from `Loaded` to `Unloaded`.
  - Each opening loads both lists. When it closes, `MainWindow` refreshes the screen on show so its pickers include anything added or renamed; the other tabs pick changes up when they're next shown, as for any change.
  - **Both tabs reset their form after Save and Delete**, as New does, and title it "New Unit"/"New Category" or "Edit Unit"/"Edit Category". Before, Save and Delete cleared the list selection but left the form pointing at the last record, so the next Save silently renamed it (or failed, after a Delete) instead of adding one. The user ran into this while asking how to add a category.
- **Migrations that carry data over use hand-added SQL, each verified up and down on a restored copy of the dev database** — the three multi-unit migrations and the raw materials merge (`BACKUP … COPY_ONLY` / `RESTORE … WITH MOVE`, then `dotnet ef database update --connection` on the copy):
  - `IngredientAlternativeUnits`: each purchase unit + `PurchaseUnitQty` becomes an `IngredientUnit`, prices are linked to it, `CostPerGram` is recomputed from the true latest price (healing the same-day bug), then the old columns are dropped. The scaffold dropped the columns first; the operations were reordered so the SQL runs in between.
  - `RecipeLinesInAlternativeUnits`: `Quantity = Grams` for existing lines.
  - `PackagingMaterialAlternativeUnits`: rewritten by hand — the scaffold took `PurchaseUnitQty → CostPerBaseUnit` for a rename (both decimals). A purchase unit other than the base unit becomes a `PackagingMaterialUnit` with prices linked to it; a purchase unit equal to the base unit turns prices into per-base-unit prices; `CostPerBaseUnit` comes from the latest price. `Down` restates everything in the old one-purchase-unit shape, including packaging lines entered in an alternative unit.
  - `MergeRawMaterials` (the raw materials merge): rewritten by hand — the scaffold dropped the eight old tables before creating the four new ones. It creates `RawMaterialCategories`, `RawMaterials`, `RawMaterialUnits` and `RawMaterialPriceHistories` first, copies everything across in one SQL batch (table variables map old packaging ids to new ones), then drops the old tables. Ingredient rows keep their ids (`IDENTITY_INSERT`), so recipe lines, BOM lines and their units still point at them; packaging materials, units and prices get new ids after them, and packaging lines follow. A packaging category joins the ingredient category of the same name (case-insensitively, like the unique index), and a packaging material named like an ingredient gets " (packaging)" appended, since names are now unique across both. `Down` splits the tables back by type with every id kept, each category going to both old category tables. Verified on a restored copy of the dev database — the user's 4 ingredients, 5 categories, 5 units and 5 prices came through with identical ids and costs — then with packaging data seeded into the old schema (a category differing only in case, a material named like an ingredient, units, prices per unit and per base unit, and packaging lines in both): up, down and up again. The dev database was backed up (`COPY_ONLY`) before the migration was applied to it.
  - Always run `dotnet ef migrations has-pending-model-changes` after hand-editing, and rebuild Infrastructure before `database update --no-build` — a build from before `migrations add` doesn't contain the new migration, and EF then reports pending model changes.
- **Off-screen renders verify the card layouts without touching the user's monitor:** a file-based app (`#:project` the UI csproj) creates `new App()` + `InitializeComponent()` for the resources, builds the real ViewModel against a database (read-only), selects an item, and renders through a `VisualBrush` so the scrolled detail column comes out in full. Set `SfSkinManager.SetSizeMode(window, SizeMode.Touch)` as `MainWindow` does, or inputs render at the compact height. For demo data, render against a restored copy, never the dev database.
- **After a command changes a row's server-computed fields (Phase 5: `DeletePriceCommand` changing `Ingredient.CurrentCost`/`CostPerGram`), refresh that one row rather than reloading the whole screen**: re-fetch it via the repository's `GetByIdAsync`, `_cache.AddOrUpdate(refreshed)` to update the grid, and reassign the `Selected*` property to the refreshed instance — `SfDataGrid` tracks selection by reference, so leaving `Selected*` pointing at the stale object silently desyncs the form/detail panel from what the grid now shows.
- **`UpdateAsync` must apply fields one by one onto a tracked, freshly-loaded entity — never `dbContext.Set<T>().Update(incoming)` on an object the caller built from scratch.** `Update()` marks *every* property Modified, so an `Ingredient`/`PackagingMaterial` built by a Save command's form fields (which never sets `CurrentCost`/`CostPerGram`, since those are server-owned) would silently overwrite them back to null/0 on every plain rename — a real bug found in Phase 6 while wiring `WeightLossPercent` through the same path, present in both `IngredientRepository` and `PackagingMaterialRepository` since Phase 4 and fixed in both at once. The fix is the same shape every time: load the tracked entity by id, copy across only the user-editable fields, leave every server-computed field untouched, then `SaveChangesAsync`. A related, easy-to-miss corollary: if a user-editable field feeds a server-computed one, the `UpdateAsync` that edits it must recompute that derived field too — it doesn't get another chance to until the next price entry. Originally `PurchaseUnitQty` feeding `CostPerGram`; since the multi-unit work it's an alternative unit's multiplier, which `RawMaterialUnitRepository.UpdateAsync` applies to the cost (and, for ingredients, to recipe-line grams).
- **`ExecuteDeleteAsync` doesn't wrap a failure in `DbUpdateException` the way `SaveChangesAsync` does** — it issues a raw `DELETE` outside the change tracker, so a foreign-key violation surfaces as the driver's own exception (`Microsoft.Data.SqlClient.SqlException` on SQL Server) instead. A test asserting `ThrowAsync<DbUpdateException>()` around an `ExecuteDeleteAsync` call needs `SqlException` instead (found in Phase 6, verifying `IngredientBomLine`'s Restrict-delete FK).
- **FluentValidation (Phase 13) is a thin, UI-facing pre-check layer added *alongside*, never in place of, the existing `ApplicationCore` Rules classes.** One `AbstractValidator<T>` per entity that actually has an editable Save form (`Ingredient`, `IngredientUnit`, `PackagingMaterial`, `PackagingMaterialUnit`, `SubAssemblyRole`, `SubAssembly`, `Product`, `CostingParameters`, `IngredientPriceHistory`, `PackagingPriceHistory` — ten total, the two unit validators added with the multi-unit work; read-only lookups like `IngredientCategory`/`PackagingCategory`/`UnitOfMeasure` deliberately got none, since there's no Save command to guard) mirrors the same rules the repository already enforces via `if/throw`. A Save/Add command runs the validator first and, on failure, sets `ErrorMessage` and returns *before* calling the repository — the repository's own checks are untouched and remain the authoritative last line of defense, so nothing about the already-tested defensive checks changes; FluentValidation only turns an invalid Save into an immediate, friendly on-screen message instead of a thrown exception the user never sees the text of. A "replace-all" Set-lines/Set-usages command (`SaveLinesCommand`, `SaveUsagesCommand`, and the BOM lines the Raw Materials Save sends) gets no validator of its own — that cross-row validation already lives in the `ApplicationCore` Rules class the repository calls.
- **`ViewModelBase` (Phase 13)** — a shared `ReactiveObject` base class, introduced only once four CRUD ViewModels needed identical behavior (not before): `ErrorMessage`/`HasError` (an `ObservableAsPropertyHelper` derived from `ErrorMessage`, safe here specifically because `ErrorMessage` is itself a clean `RaiseAndSetIfChanged` property, not one driven by imperative collection mutations — see the OAPH lesson above), `IsBusy`, and a ReactiveUI `Interaction<string, bool> ConfirmDelete` the View fulfills with a real dialog. Two protected helpers wrap every command that touches the database: `RunSafelyAsync(Func<Task> action)` sets `IsBusy` for the call's duration and maps three exception types to a friendly `ErrorMessage` (`InvalidOperationException` → `ex.Message` verbatim, since every Rules class already writes a clear message; `DbUpdateException` → `"That name is already in use."`, the only scenario that type is ever thrown for anywhere in this app; `SqlException` → `"This item is currently in use elsewhere and can't be deleted."`, matching the `ExecuteDeleteAsync`-throws-`SqlException` behavior documented above) and lets any other exception type propagate uncaught, since that would be a real bug, not a user-facing condition to mask; `RunWithConfirmationAsync(message, action)` shows the confirmation dialog first and only calls `RunSafelyAsync` if the user agrees. Every command that calls a repository Delete method is wrapped in `RunWithConfirmationAsync`; every Add/Update-calling command is wrapped in `RunSafelyAsync` (with a validator pre-check, per the FluentValidation point above, when one exists for that entity); a Set-lines/Set-usages command is `RunSafelyAsync` only; a command that only mutates an in-memory edit list (`Add*Line`/`Remove*Line`/`Add*Usage`/`Remove*Usage`) or `NewCommand` is left unwrapped, since it's reversible pre-Save and carries no exception risk. `ProductsViewModel`'s tab-link commands (`LinkTabCommand`/`UnlinkTabCommand`) and `CloneCommand` are `RunSafelyAsync` only, not confirmation-gated — none of them destroy data (unlinking specifically *materializes* the tab's data rather than removing it, per the Phase 10 note above).
- **Serilog (Phase 13)** writes a daily rolling file to `logs/tinapayanrms-.log` under the app's base directory, 31-day retention, configured once via a static `Log.Logger` built in `App`'s static constructor (so even a licensing failure in that same constructor gets logged) and registered in DI as a `Serilog.ILogger` singleton. Each `ViewModelBase`-derived class calls `logger.ForContext(GetType())` once, in the shared base constructor, to get a per-class-named logger without needing a separate DI registration per ViewModel. `App.OnStartup` also hooks `DispatcherUnhandledException`/`AppDomain.UnhandledException` to log any exception that reaches those handlers.
- **Confirmation dialogs stay in the View, via a shared extension method, not baked into each View's constructor by hand.** `ConfirmDeleteHandlerRegistration.RegisterNativeMessageBoxHandler(this ViewModelBase)` wires a `ViewModelBase`'s `ConfirmDelete` interaction to a native `MessageBox.Show(..., MessageBoxButton.YesNo, MessageBoxImage.Warning)` in one place; every affected View's constructor calls `viewModel.RegisterNativeMessageBoxHandler();` once, right after setting `DataContext`.
- **A "replace-all" editor's referenced-entity validation must run *before* `ExecuteDeleteAsync`, never only implicitly via a dictionary lookup or a database FK constraint afterward** — a real, latent bug found and fixed in Phase 14's coverage audit. `PackagingLineRepository.SetLinesAsync` and `ProductSubAssemblyUsageRepository.SetUsagesForRoleAsync` (both Phase 8) already got this right: they build a lookup of the referenced entities that actually exist and loop over the incoming rows checking each one, throwing a friendly `InvalidOperationException` immediately, all *before* the old rows are deleted. `SubAssemblyLineRepository.SetLinesAsync` (Phase 7) and `IngredientBomLineRepository.SetLinesAsync` (Phase 6) did not: both deleted the existing lines first and only discovered a bad reference afterward — the former via a plain dictionary indexer throwing a raw, unfriendly `KeyNotFoundException`; the latter via the database's own `Restrict` FK constraint throwing `DbUpdateException` at `SaveChangesAsync`. In both cases the existing, valid rows were already gone by the time the rejection happened, with no transaction to roll them back. Neither path had a test covering "the new set references something that doesn't exist," which is exactly why it went unnoticed since Phase 6/7. Fixed by moving the existence-check dictionary/set build (and a `foreach` loop throwing `InvalidOperationException` per missing id) to before the `ExecuteDeleteAsync` call in both repositories, matching the established correct shape, with a regression test in each asserting the *existing* lines survive a rejected replacement.
- **A native `ProgressBar`, not a Syncfusion busy-indicator control, for Phase 13's busy-during-save indicator** — deliberate: the app references no Syncfusion busy-indicator package, and adding one for one small piece of UX polish wasn't worth it. A plain `ProgressBar IsIndeterminate="True" Height="4"` bound to `IsBusy` via `BooleanToVisibilityConverter`, placed in a status-bar row above each screen's content alongside the `ErrorMessage` `TextBlock`, is the sanctioned native-control fallback per the Conventions section below.
  - **Retrofitting a status-bar row onto an existing `Grid` needs `Grid.Row` added to every pre-existing child, not just the new row itself.** WPF defaults an unset `Grid.Row` to `0`; inserting a new `RowDefinition="Auto"` above the existing content and giving only the *new* status-bar element `Grid.Row="0"` leaves every already-existing child (which never had an explicit `Grid.Row` before, back when there was only one row) silently defaulting to `Grid.Row="0"` too, overlapping the status bar. Caught and fixed in `IngredientsView.xaml` by re-reading the file after the first edit; applied correctly from the start in `PackagingMaterialsView.xaml` and `SubAssembliesView.xaml` afterward. `ProductsView.xaml` doesn't use a column-based `Grid` at all (its panels are a horizontally-scrolling `ScrollViewer` of `StackPanel`s, per the CRUD screen pattern note above) — for that shape, wrap the existing `ScrollViewer` in an outer two-row `Grid` (status bar in row 0, the untouched `ScrollViewer` in row 1) instead of touching every inner panel.
  - **Sending synthetic `WM_LBUTTONDOWN`/`WM_LBUTTONUP` directly to a window's `HWND` (via `SendMessage`/`PostMessage`, with screen-to-client-translated coordinates) doesn't reliably drive a Syncfusion `ButtonAdv`'s click, even though it targets the exact window and never touches the real screen cursor** (tried in Phase 13, verifying the new validation/confirmation wiring while the user had a game occupying the foreground — see the "can't win against a real foreground app" lesson above). Syncfusion's WPF controls also don't expose the standard UI Automation `InvokePattern` (`GetSupportedPatterns` on a `ButtonAdv` returns only `SynchronizedInputPattern`), so `AutomationElement`-based invocation doesn't work either. Both were dead ends for exercising a write-path command without either real OS focus or a real physical click — which matches, and reinforces, the existing Phase 5/7 guidance to rely on integration tests plus a line-by-line binding review for write paths when the app can't safely be given real focus.

## Reactive Costing Cascade

The core design problem is that a price change on any ingredient or packaging material must ripple up through everything that uses it, automatically. The cascade has two starting points, one per raw material type, and both end at the product:

```
Price entry added for an ingredient
  → purchased ingredient's CostPerBaseUnit (per gram) recomputed
    → every made ingredient that uses it recomputed, up every level of the BOM tree
      → every SubAssemblyLine using a changed ingredient recomputed
        → SubAssembly.TotalCost recomputed
          → every ProductSubAssemblyUsage of that sub-assembly recomputed ─┐
                                                                           ├→ Product total cost recomputed
Price entry added for a packaging material                                 │    → Product margin / selling price recomputed
  → packaging material's CostPerBaseUnit recomputed                        │
    → every PackagingLine using it recomputed ─────────────────────────────┘
```

The original idea was to model this with DynamicData `SourceCache<T>`s joined via `.Connect()`/`.InnerJoin()`/`.TransformMany()`, so derived observable collections update themselves. **That's not what got built.** Phase 6 established a different, simpler pattern first — a pure ordering function plus a stateful database orchestrator, described below — and it worked well enough that Phase 11 extended the *same* shape to the sub-assembly branch instead of introducing DynamicData joins partway through. EF Core stays the single source of truth throughout; nothing here lives only in an in-memory observable.

The one nesting exception is made ingredients: their BOMs nest to any depth, so that part of the cascade can't be a fixed one-hop join. An ingredient's cost can change from a new price entry, a BOM line edit, or a `WeightLossPercent` edit; when it does, the made ingredients that depend on it need recomputing in dependency order, components before the ingredients built from them. Sub-assemblies don't nest (a `SubAssemblyLine` only ever references an `Ingredient`, never another `SubAssembly` — Phase 7), so that branch needed no ordering logic at all, just "recompute every sub-assembly touched."

**Ingredient branch — implemented Phase 6** as `IngredientCostGraph.GetDependentsInOrder` (`ApplicationCore`, pure graph logic, no I/O — reverse-BFS from the changed ingredient to find every made ingredient that transitively depends on it, then a DFS-based topological sort restricted to that set) and `IngredientCostPropagator.RecomputeAndPropagateAsync` (`Infrastructure`, the orchestrator: loads every ingredient and every BOM line once, calls the graph function, walks the resulting order recomputing each ingredient's cost per gram (`CostPerBaseUnit`) from its own lines — reading each component's cost directly off the already-loaded, already-correct dictionary, never re-walking that component's own tree — then a single `SaveChangesAsync`). Every write path that can change an ingredient's cost calls it: `RawMaterialPriceHistoryRepository`'s add/update/delete (for an ingredient's price), `RawMaterialRepository.UpdateAsync` when `Source == Made` (a `WeightLossPercent` edit), `RawMaterialUnitRepository.UpdateAsync` when an ingredient unit's multiplier changes, and `IngredientBomLineRepository.SetLinesAsync`. (Before the raw materials merge these were `IngredientPriceHistoryRepository` and `IngredientRepository`.) It loads ingredients only (`Type == Ingredient`), since packaging never takes part.

**Sub-assembly branch — implemented Phase 11** as `SubAssemblyCostPropagator.RecomputeAndPropagateAsync` (`Infrastructure`, taking the *set* of ingredient ids whose cost just changed — no per-ingredient ordering needed, since sub-assemblies don't nest: finds every `SubAssemblyLine` referencing any of them, groups by `SubAssemblyId`, and recomputes each affected sub-assembly's `TotalWeight`/`TotalCost` from *all* of its own lines' current ingredient costs — not just the changed line — in one loaded-once-saved-once pass). `IngredientCostPropagator` calls it at the end of its own run, passing `changedIngredientId` itself (whose own cost the caller already updated, for a Purchased ingredient) unioned with every made ingredient it just recomputed — so this one call, from the existing three ingredient-branch write paths, now reaches every sub-assembly transitively affected, at any BOM depth.

**Product and packaging branches needed no propagation code at all.** Neither `ProductSubAssemblyUsage`'s cost-per-piece, `PackagingLine`'s cost-per-piece, nor a product's total material cost is stored anywhere (Phase 8's "derived values are computed on read" decision) — they're plain `ProductRules` functions reading `SubAssembly.TotalCost` and the packaging material's `CostPerBaseUnit` fresh every time a screen asks. As long as those two columns are correct — which the ingredient and sub-assembly propagators now guarantee, and which the price history repository has guaranteed for packaging since Phase 5 (`RawMaterialPriceHistoryRepository` since the raw materials merge, which skips the ingredient cascade for a packaging price) — a product's displayed cost is automatically correct too, with nothing to propagate into. Verified end-to-end (`ReactiveCostCascadeTests.cs`): a price change several BOM levels deep reaches a sub-assembly's `TotalCost` with no direct edit to that sub-assembly, and a product's live-computed cost-per-piece reflects it immediately, with zero product-level or packaging-level code involved.

This does mean a product **already on screen** only reflects a price change made from a *different* screen once the user reselects it (or navigates back to it) — there's no cross-screen live push. That's the one piece of the original DynamicData-joins vision this phase deliberately didn't build; revisit only if that specific UX gap is ever reported as a real problem, not preemptively.

These controls can have several control templates selected by a mode property, each honoring a genuinely different subset of properties, so the "does this control support X" question is really "does the template for the mode I'm in support X".
  - **`SfNavigationDrawer` is the worked example** (Phase 15, `MainWindow`'s navigation drawer): it has two control templates selected by `DisplayMode`. The `Compact`/`Expanded` template draws the drawer's **own built-in hamburger toggle** (a `ToggleButton` two-way bound to `IsOpen`, so no toggle button of your own is needed) and renders the `Items` collection through a `NavigationView`. The `Default` template has **neither** — no toggle at all, and it presents `DrawerContentView` instead, ignoring `Items` entirely. Setting `Items` under `DisplayMode="Default"` compiles fine and the drawer's own chrome still themes correctly, so it looks like a theming problem, but nothing from `Items` ever renders. `MainWindow` uses `DisplayMode="Compact"`: a `CompactModeWidth`-wide icon rail that expands to `DrawerWidth` over the content.
  - **A `NavigationItem`'s icon goes in `Icon` (a real element), not `IconTemplate`, and the element has to center itself** — `HorizontalAlignment="Center" VerticalAlignment="Center"`, as every icon in Syncfusion's own `DisplayMode.xaml` demo does. The item template drops the icon into a fixed-size `ContentPresenter` with a negative left margin, so an unaligned glyph renders visibly off-center. In compact mode the icon is the *only* thing visible for each destination, so every item needs one.
  - **`TabControlExt.CloseMode="Hide"` (Phase 16), not the default `Delete`, is what actually makes "close a tab, reopen it from the drawer" work.** The first implementation (Phase 15) left `CloseMode` at its default and had the drawer's click handler re-add the closed `TabItemExt` instance to `MainTabControl.Items` if it was missing (`if (!Items.Contains(tab)) Items.Add(tab);`). That compiled, selected the right content, and even looked right in a quick check — but a real close-then-reopen cycle (caught only once the user actually did it) showed the tab's *content* switching in correctly while its *header* never reappeared in the strip at all: `TabControlExt`'s header strip doesn't regenerate a header for a `TabItemExt` instance that has ever actually left `Items` under `Delete` mode, even when the exact same instance is re-added later. `CloseMode="Hide"` (`Syncfusion.Windows.Tools.Controls.CloseMode`, confirmed against `Syncfusion.Tools.WPF.xml`'s member docs) sidesteps the whole problem: a closed tab is only `Visibility.Collapsed`, never removed from `Items`, so `ShowTab` just needs `tab.Visibility = Visibility.Visible;` before selecting it — the instance was never invalid to begin with. This also fixed a smaller side effect of the `Delete`-mode workaround: a reopened tab used to land at the *end* of the tab strip (`Items.Add` appends) instead of back in its original position, since `Hide` mode never reorders `Items` at all. (Syncfusion also ships a fully built alternative for exactly this scenario — `TabListContextMenuOptions` including `ShowHiddenItems` on the tab-list dropdown menu, which lists and restores hidden tabs on its own — but the app keeps the `SfNavigationDrawer` as the single reopen affordance rather than offering two different ones for the same action.)

## Conventions

- The layered architecture is fixed: `Domain` has no external dependencies, business and costing rules live in `ApplicationCore`, and EF Core and other I/O stay in `Infrastructure`.
- The MVVM toolkit is **ReactiveUI**, not CommunityToolkit.Mvvm. Use `ReactiveObject`, `ReactiveCommand`, `WhenAnyValue`, etc.
- **Every file goes in the folder for its kind, and the folder is its namespace** (see Solution Structure). A new View goes in `Views/` with its ViewModel in `ViewModels/`, a new repository in `Repositories/` with its interface in `ApplicationCore/Interfaces/`, a new rule in `Rules/` with its test in `tests/…/Rules/`, and so on. Nothing goes at a project root except app-startup plumbing.
- **Prefer Syncfusion controls over native WPF controls whenever a Syncfusion equivalent is available** (e.g. `ButtonAdv` over `Button`, `TabControlExt` over `TabControl`, `ComboBoxAdv`/`SfDataGrid`/the `SfInput.WPF` edit controls over their native counterparts), so the whole UI picks up the Windows11Light theme consistently. Fall back to a native control only when no Syncfusion equivalent exists. Adopting a new Syncfusion control only needs its package added to `TinapayanRMS.UI` — the packaged theme already covers every control Theme Studio knows about.
- **Decimal precision**: keep `decimal` values at full precision through the whole cascade, and round only for display and for the final selling price. Rounding each per-piece cost before summing adds up to drift. Enforced once for every `decimal` column via `TinapayanRMSDbContext.ConfigureConventions` (`decimal(18,4)`, set in Phase 4 when the first `decimal` columns were added), rather than per-property — a future column can't silently fall back to SQL Server's `decimal(18,2)` default and truncate a fractional cost.
- **Use modern C# 14 / .NET 10 idioms** rather than older patterns still valid in the language: primary constructors, collection expressions (`[..]`), required members, file-scoped namespaces, pattern matching, and `record`/`record struct` for immutable data shapes, in line with what's already in the codebase (e.g. `CategoryPersistenceTests`'s primary constructor, `WellKnownUnitOfMeasureIds`'s collection expression). Don't reach for an older, more verbose equivalent just because it's more familiar.
- **Correctness and performance take priority over brevity or convenience.** Favor the approach that is provably correct and doesn't waste allocations, database round-trips, or UI-thread work, even if a shorter or simpler alternative exists — e.g. querying only the columns/rows actually needed rather than materializing more and filtering in memory, and avoiding unnecessary intermediate collections in hot paths like the reactive costing cascade.
- This document is a living plan. Update it as phases complete or decisions change, so it stays the single source of truth for the project.
