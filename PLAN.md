# TinapayanRMS — Project Guide & Build Plan

Product recipe management & costing app for Tinapayan Festival Bakeshoppe. Tracks ingredient expenses, recipe/product margins, and cascades ingredient and packaging price changes up through sub-assemblies and finished products automatically.

## At a glance

- **What it is**: a Windows desktop app (WPF on .NET 11, Syncfusion, ReactiveUI) over PostgreSQL 18 through EF Core, for one bakeshop.
- **Layers**: `Domain` (the entities), `ApplicationCore` (the `*Rules` classes, repository interfaces, validators), `Infrastructure` (EF Core and Dapper, the repositories, the cost propagators, `ProductCloner`, the unit of work), `Pricing` (how a saved product is read and priced, and the saves that record product versions) and `UI` (the screens and their ViewModels, printing, export, the Vim keys). Two servers share the lower layers: the MCP server and the Recipe API.
- **Costs**: a raw material's cost per base unit is stored, and the cascade keeps a made or linked one's current (Reactive Costing Cascade). A sub-assembly's batch and a product's cost and selling price are worked out on read.
- **Screens**: Raw Materials, Sub-Assemblies and Products (with its Recipe, Costing, Scaling, Clone and History tabs), then Reports, Price Simulator and Print, and the Settings dialog. Production planning is TinapayanBMS's, which reads the recipes through the Recipe API.
- **Saves**: a screen's Save writes its whole form in one transaction, and a save that records product versions writes them in that same transaction (`VersionedSaves`, `IUnitOfWork`).

## Tech Stack

- **Language / Runtime**: C# 15, .NET 11 (`net11.0`; `net11.0-windows10.0.19041.0` for the UI and UI.Tests projects: ReactiveUI.WPF needs at least that Windows SDK version, and the bare `net11.0-windows` moniker resolves to `windows7.0`). The SDK is pinned in `global.json` to 11.0.100-rc.3.26522.148, a preview. The change in .NET 11 that matters to this code: a `double` converts to a `decimal` at its exact binary value (Conventions, "Decimal precision"). Runtime async is on (Build settings, below).
- **UI**: WPF, styled with **Syncfusion Essential Studio for WPF 35.1.43** and Syncfusion's Windows11Light theme (the official `Syncfusion.Themes.Windows11Light.WPF` package), accent-recoloured at runtime.
- **MVVM**: ReactiveUI (26.x). It needs explicit builder initialization before any `ReactiveObject` is touched (`RxAppBuilder.CreateReactiveUIBuilder().WithCoreServices().WithWpf().BuildApp()`), done once per process by `src/TinapayanRMS.UI/ReactiveUIBootstrapper.cs`. `WithWpf()` binds the main-thread scheduler to the `Application`'s dispatcher, or with no `Application` (the tests) to the calling thread's, and throws if there is none, so the bootstrapper touches `Dispatcher.CurrentDispatcher` first when `Application.Current` is null. ReactiveUI doesn't bring `System.Reactive`, so that package is referenced directly wherever Rx LINQ operators are used on an `IObservable<T>`.
  - **Parameterless commands are `ReactiveCommand<RxVoid, RxVoid>`** (`ReactiveUI.Primitives.RxVoid`), not `ReactiveCommand<Unit, Unit>`. Import the type with a using alias (`using RxVoid = ReactiveUI.Primitives.RxVoid;`), never `using ReactiveUI.Primitives;`: that namespace carries its own extension-member `Select`/`Where`/`Subscribe`, which collide (CS0121) with `System.Reactive.Linq`'s.
  - **Property observation and binding are in `ReactiveUI.Binding`**, a source-generated engine: `WhenAnyValue`, `ToProperty`, `ObservableAsPropertyHelper<T>` and `Interaction<TInput, TOutput>` live there. The package adds `ReactiveUI.Binding` as a global using to every consuming project. Its `ObservedProperty.Switch` collides (CS0121) with Rx's `Switch` over an `IObservable<IObservable<T>>`, so the ViewModels call `Observable.Switch(source)` rather than `source.Switch()`.
- **Reactive collections**: DynamicData.
- **Persistence**: EF Core 11 (11.0.0-rc.3) on PostgreSQL 18 (`localhost:5432`, role `tinapayanrms`, database `tinapayanrms`) through Npgsql (`Npgsql.EntityFrameworkCore.PostgreSQL` 11.0.0-rc.3, with `EFCore.NamingConventions` making every table and column snake_case), for writes, the schema and migrations; **Dapper** (2.1.x) for reads (Conventions, "Reads through Dapper, writes through EF Core").
- **DI / Hosting**: `Microsoft.Extensions.Hosting` and `Microsoft.Extensions.DependencyInjection`. Infrastructure's `DatabaseHost` is the host the app and both servers start from; the app adds its services in `src/TinapayanRMS.UI/CompositionRoot.cs`, called from `App.xaml.cs`.
- **Validation**: FluentValidation.
- **Logging**: Serilog (rolling file sink).
- **Charts**: Syncfusion SfChart (`Syncfusion.SfChart.WPF`). No screen draws a chart: Reports shows summary grids instead. The package reference stays for when a chart comes back.
- **Excel export**: Syncfusion's grid converter, `Syncfusion.DataGridExcelExport.WPF`, which brings XlsIO (and PDF) with it, at `$(SyncfusionVersion)` like every Syncfusion package. The licence key covers `Platform.Excel` as well as `Platform.WPF`, so a workbook carries no trial notice.
- **Testing**: xUnit v3, AwesomeAssertions, Respawn. Integration tests run against the local PostgreSQL server, and Respawn (`DbAdapter.Postgres`) resets each test project's database between tests. Nothing is mocked. AwesomeAssertions rather than FluentAssertions: FluentAssertions 8+ needs a paid licence for a for-profit product, and AwesomeAssertions is a same-API, MIT-licensed fork of the last free release.
- **MCP server for AI assistants**: `src/TinapayanRMS.Mcp`, a Model Context Protocol server over stdio on the official C# SDK (`ModelContextProtocol` 2.3.1). It gives an AI coding assistant what SQL can't, a product's cost and price, which are worked out on read: `list_products`, `get_product_costing` and `simulate_price_changes` (`Tools/CostingTools`). It builds its host with `DatabaseHost` and prices with `TinapayanRMS.Pricing`, so the tools can't price differently from the screens. **It can't write**: `ReadOnlyConnection` sets `default_transaction_read_only` on its connection to the dev database, so PostgreSQL refuses a write whatever runs it. Claude Code starts it from `.mcp.json` through `scripts/Start-McpServer.ps1`, which builds Release and runs a copy of the build from `bin/Release/runs/<hash>`, so a running server holds only its copy and never blocks a build. One start builds at a time (a named mutex), a copy no server runs from goes at the next start, and the server ends with the script. It builds as it starts, so Claude Code waits 2 minutes for it (`MCP_TIMEOUT` in `.claude/settings.json`). Its JSON rounds decimals to 6 places (`ToolJson`), where full precision ran to 28 digits. Tested by `TinapayanRMS.Mcp.Tests`, on its own database and on the read-only connection. See the developer manual's "Checking costs from an AI assistant".
- **Recipe API for the shop's other apps**: `src/TinapayanRMS.RecipeApi`, a read-only HTTP API (ASP.NET Core minimal APIs on Kestrel, JSON under `/api/v1`) on port 5290 of every address, so TinapayanBMS (`../TinapayanBMS`, the app that weighs ingredients out ahead of mixing and plans production) can read the recipes on this PC or across the LAN. **An API in this repo**, rather than TinapayanBMS reading this database directly, which would tie it to this schema and have it work batches out again; TinapayanBMS is a repo of its own. Like the MCP server, it builds its host with `DatabaseHost` (`RecipeApiHost.AddRecipeApi` puts the web server on top), prices with `TinapayanRMS.Pricing`, and reads through `ReadOnlyConnection`; installed, it also connects as `tinapayanrms_reader`, a role that can't write (`Database:ReadOnlyUser`, made by `scripts/New-DatabaseReader.ps1`). Endpoints: `status`, `ingredients`, `boms`, `categories`, `products`, `products/recipes`, `mixes`, `mixes/details`, `mixes/{id}` and `materials`. The records it sends are `Contracts/RecipeContracts.cs`, which the other apps copy, so a change adds rather than renames or removes. Every request has to carry the key (`RecipeApi:Key` in `recipeapi.json`, sent as `X-Api-Key`); with none set, only this PC is answered. What fails comes back as `{ error }`: a 503 in `Failure`'s fixed sentence for a database that can't be used, and a 500 with a fixed sentence for anything else. `status` reads the database, so its answer means that's there too. Installed by `scripts/Install-RecipeApi.ps1`, which starts it hidden at sign-in as the signed-in user, so it reads that user's `pgpass.conf`, and, run as an administrator, opens port 5290 to the local subnet on private networks. Tested by `TinapayanRMS.RecipeApi.Tests` (`tinapayanrms_test_recipeapi`), in memory through ASP.NET Core's `TestServer`. See the developer manual's "The Recipe API".
- **The pricing has a project of its own, so the servers have no UI in them.** `src/TinapayanRMS.Pricing` (`net11.0`, on ApplicationCore) holds `SavedProductReader` and what it builds: a saved product is read as immutable `PricedSection`s and `PricedPackagingLine`s, whose figures come from the same `SectionFigures.Of` and `PricedPackagingLine.Price` the screens' editable rows use, along with `ProductCostSummary`, `PackagingLinkTarget`, `PurchaseUnit`, `BaseUnitText`, `TriedPriceChange` and `PriceSimulatorProductRow`. Its `Versions/` holds the product versions' snapshot and the saves that record them (`VersionedSaves`). The editable rows (`ProductUsageEdit`, `PackagingLineRow`, `SimulatedPriceChange`, `ObservableRow`), printing and comparing stay in `UI/ViewModels`. A project rather than a folder in ApplicationCore, since these rows carry display text that doesn't belong beside the rules. The servers are on plain `net11.0`, which can't reference a Windows project, so WPF, Syncfusion and ReactiveUI can't creep back into them: the API builds at about 10 MB and the MCP server at 14 MB.
- **Solution format**: `.slnx`.
- **Build settings**: `Directory.Build.props` at the repo root sets `TargetFramework` (`net11.0`), `ImplicitUsings` and `Nullable` for every project, plus a `WindowsTargetFramework` property that the UI and UI.Tests projects use as their `TargetFramework`.
  - **Runtime async** is on for every project (`<Features>$(Features);runtime-async=on</Features>`): .NET 11 runs `async` methods itself, so the compiler no longer turns them into state machines. It's still an opt-in compiler feature in RC3. To turn it off, delete that one line.
  - **The commit stays out of everyday builds**: with it in, each commit's hash went into every assembly's version and its Source Link file, so the first build after any commit recompiled every project, and the MCP server, which builds as it starts, missed Claude Code's wait. `EnableSourceControlManagerQueries` and `EnableSourceLink` are off unless `_IsPublishing`, which `dotnet publish` sets, so a published copy still carries its commit (`1.0.0+<hash>`, its Product version).
  - **`tests/Directory.Build.props`** imports it and adds what every test project shares: `IsPackable=false`, the `Xunit` global using, and the xUnit v3, AwesomeAssertions, test SDK and coverage packages, only to projects whose name ends in `.Tests`, so `TinapayanRMS.Tests.Common` stays a plain library (it takes `xunit.v3.extensibility.core`, since `xunit.v3` would make it a test executable).
  - **`Directory.Packages.props`** enables Central Package Management: every package version is a `PackageVersion` there (EF Core, Microsoft.Extensions and Syncfusion through the `EFCoreVersion`/`MicrosoftExtensionsVersion`/`SyncfusionVersion` properties), and a project's `PackageReference` has no `Version`. `CentralPackageTransitivePinningEnabled` is on, so a `PackageVersion` also overrides a transitive dependency: the "Transitive pins" group lifts `Microsoft.EntityFrameworkCore.Relational` to `EFCoreVersion`, because `EFCore.NamingConventions` asks for EF Core 10 and every project should run the one EF Core Npgsql's provider takes. Drop a pin once the package that brings it no longer needs it. A `.csproj` holds only what's unique to it.
  - **Code analysis**: `AnalysisLevel` is `latest-recommended`, the SDK's built-in .NET analyzers at their Recommended rule set (the Default set reported nothing, and All about 1,700 warnings, mostly style). The root `.editorconfig` marks `Migrations/` as generated code, and turns off CA1707 in `tests/`, whose method names use underscores, and CA1716 everywhere (it flags `IPriceHistoryEntry.Date` for being a Visual Basic keyword). Warnings aren't errors, but the build has none; keep it that way.
- **`dotnet test`**: the .NET SDK's `dotnet test` has no VSTest support; `global.json`'s `test.runner` setting runs it on Microsoft.Testing.Platform. Run the tests with `dotnet test --solution TinapayanRMS.slnx`.
- **Syncfusion license key**: compiled into the app at build time from the `SYNCFUSION_LICENSE_KEY` Windows user environment variable, so an installed copy runs without the variable. The UI project adds it as an `AssemblyMetadata` item named `SyncfusionLicenseKey` when the variable is set, and its `RequireSyncfusionLicenseKey` target fails `dotnet publish` when it isn't. `App`'s static constructor reads that attribute, falls back to the variable, throws with neither, and registers the key before anything else in the process touches a Syncfusion type. The key is readable from the published assembly, as it would be with Syncfusion's own advice of a string literal in code; the build-time step only keeps it out of git. Building the app, or running its licensed UI tests, on another machine still needs the variable there.

**Folder = namespace, grouped by kind.** Every folder inside a project is a sub-namespace of it (`src/TinapayanRMS.UI/ViewModels/` → `TinapayanRMS.UI.ViewModels`). A new file goes in the folder for its kind, never at the project root. Only app-startup plumbing (`App`, `AppStartup`, `CompositionRoot`, `ReactiveUIBootstrapper`, the guards, Infrastructure's `DatabaseHost` and `ReadOnlyConnection`, and the servers' `Program` and `RecipeApiHost`), the DbContext pair, and `TinapayanRMS.Pricing`, one kind of thing throughout, live at a project root. Code in a sub-namespace sees its parent namespaces without a `using`: a View calls `RegisterNativeMessageBoxHandler` from `TinapayanRMS.UI`, and a repository uses `TinapayanRMSDbContext` from `TinapayanRMS.Infrastructure`. Sibling folders need a `using`. Table names come from the DbContext, not from entity namespaces, so moving an entity between namespaces leaves the EF model unchanged.

The Windows11Light theme is not a project in the solution: it's Syncfusion's official `Syncfusion.Themes.Windows11Light.WPF` NuGet package (see Syncfusion UI Framework below).

## Domain Model

- **UnitOfMeasure**: `Id`, `Name`, `Abbreviation`, nothing else. **No unit is seeded or protected by a fixed id**: the table starts empty on a fresh database, and the shop owner adds every unit they need (gram, piece, mm, or a sack or roll) in Settings → Units of Measure, as any other user-managed lookup. **A unit carries no conversion factor of its own.** Conversions live on each raw material instead (Multi-unit materials, below): every material has a **base unit** its quantities and costs are tracked in (always the gram for an ingredient; chosen per packaging material), plus any number of **alternative units**, each a multiple of that base unit.
  - **Standard units have a fixed multiplier.** `ApplicationCore/Rules/StandardUnitRules` recognises a unit by its name or abbreviation, whatever the case, across mass (mg, g, kg/kilo, oz, lb), length (mm, cm, m, in, ft) and volume (ml, l). When the unit and the material's base unit are the same kind, the multiplier is fixed: a kilogram of an ingredient is 1,000 g, an inch of ribbon in centimetres is 2.54. Anything else is typed: a bag, a litre of an ingredient (only its density says how many grams), a kilogram of wrappers counted in pieces. The fixed multiplier is rounded to the 4 places the column keeps (an ounce is 28.3495 g), so a saved one reads back equal, and one that rounds to 0 (a milligram of a kilogram) is left to type.
  - `RawMaterialUnitRepository.AddAsync`/`UpdateAsync` save a standard unit at its fixed multiplier whatever was sent (`MultiplierToSaveAsync`). On the screen a row takes it as the unit is picked, renamed into one in Settings, or the base unit or type changes under it (`RawMaterialUnitRow.ApplyStandardMultiplier`), and neither the Alternative Units grid's Multiplier cell (`CanTypeMultiplier`) nor Purchase Cost Setup's Qty per Purchase Unit (`CanTypeQuantity`, via `IBrandPriceRowHost.IsMultiplierFixed`) can be typed into for one (`controls:GridCellEditing.AllowWhen`).
- **RawMaterial: ingredients and packaging share one table, told apart by `Type` (`Ingredient` or `Packaging`).** The differences that are real are rules on the type:
  - **Base unit**: an ingredient's is always the gram, so its `BaseUnitId` is null, and recipes, BOMs and sub-assembly weights all add up grams. A packaging material picks its own (`BaseUnitId` required).
  - **Source**: only an ingredient can be `Made` (made from a sub-assembly, with add-ins and a weight loss) or `Linked` (a share of another ingredient's cost); packaging is always `Purchased`.
  - **Where it can be used**: sub-assembly lines and a made ingredient's add-ins take ingredients only; a product's packaging lines take packaging only.
  - `RawMaterialRules.EnsureFieldsMatchType`/`EnsureFieldsMatchSource` run in `RawMaterialRepository` before every save, backed by two check constraints (`CK_RawMaterials_BaseUnitMatchesType`, `CK_RawMaterials_OnlyIngredientsAreMade`). Type and source are fixed once created (`EnsureTypeUnchanged`/`EnsureSourceUnchanged`). Each line repository checks every line's type (`EnsureUsableInRecipes`/`EnsureUsableAsPackaging`) before it replaces anything, with a message naming the material, and the pickers only offer the right type. A name is unique across both types.
  - The line entities keep their role names: `SubAssemblyLine.Ingredient`, `IngredientBomLine.Ingredient`/`ComponentIngredient` and `PackagingLine.PackagingMaterial` are all `RawMaterial`s. A packaging line's unit is `UnitId` (a `RawMaterialUnit`); recipe lines have no unit, since they're in grams (Ingredients, below). `IngredientCostPropagator` is named for ingredients because it only ever deals with them.
  - **`CostPerBaseUnit`** (stored, derived): the true cost of one base unit (one gram, for an ingredient).
  - **Buffered cost**: a per-material **`CostBufferPercent`** (0–100; a new one starts at Settings' default, see Costing defaults; `RawMaterialRules.EnsureValidCostBuffer`, the validator, and `CK_RawMaterials_CostBufferPercent`) is a cushion for price swings, waste and yield variation. **`BufferedCostPerBaseUnit`** (stored, derived) is the cost with it on top (`RawMaterialRules.BufferedCost`, the only buffer formula). **It's the value every sub-assembly line, BOM rollup and packaging line uses**, so products are costed and priced with it; `CostPerBaseUnit` stays the true cost, shown beside it on the Raw Materials screen and in Price History.
    - Purchased: **a fixed amount**. Brand prices don't move it. `ApplyBrandPrices` only works it out, as `CostPerBaseUnit × (1 + buffer / 100)`, the first time the material is priced (while it's still 0), and sets it back to 0 when the last price goes. Otherwise it changes only when the screen sends a new one: typed, or from typing the Cost Buffer % (the dearest brand as typed with the % on top). `RawMaterialRepository.UpdateAsync` writes the form's amount (0 sent means "work it out from the cost and the %", and `SaveAsync` does that from the new prices when it has them) and cascades an ingredient whose buffered cost changed. `EnsureValidBufferedCost` (and the validator) rejects a negative amount; one below the cost is allowed, and the screen warns about it. So a price change alone reaches product costs only through the true cost, and the buffered cost everything is costed with waits for the screen to send a new one. `CostBufferPercent` is kept as the % that puts the buffer back on top, and `TargetCostBufferPercent` as the one last typed (Raw Materials' Re-apply Target).
    - Made: the BOM rollup of the components' *buffered* costs, and nothing more. **A made ingredient adds no buffer of its own**, so a buffer is counted once however deep the tree. `RawMaterialRules.StoredCostBufferPercent` is the one place that says so: `RawMaterialRepository`'s Add and Update store a made ingredient's `CostBufferPercent` as 0 whatever the form sends (refusing it instead would leave a row that has one unsaveable, since the screen has no buffer box for a made ingredient), and `IngredientCostPropagator` sets it to 0 on every recompute, which cleans a *dependent* made row the propagator reaches without a save. A linked part of a made ingredient inherits 0%, which is right: it takes a share of an already-buffered cost.
    - Linked: the same share of the linked-to ingredient's buffered cost as its true cost is of the true cost (`LinkedCost(linkedTo.BufferedCostPerBaseUnit, …)`), so a part follows the linked-to ingredient's fixed amount.
    - It's stored, not computed on read, because a made ingredient's buffered cost isn't a multiple of its own true cost once its components have buffers.
- **Multi-unit materials**:
  - **`RawMaterialUnit`** (`RawMaterialId` Cascade, `UnitOfMeasureId` Restrict, `BaseUnitsPerUnit` > 0, `Description`; unique per material + unit; never a packaging material's own base unit). The base unit never has a row: **an empty unit means the base unit** everywhere a unit is optional (price entries, packaging lines), so nothing depends on a "gram" row existing in Units of Measure. Recipe lines take no unit at all: an ingredient's alternative units price it and work in the Usage Example, but a recipe is always written in grams.
  - `UnitConversionRules.ToBaseQuantity(quantity, multiplier?)` / `CostPerBaseUnit(price, multiplier?)` / `EnsureValidMultiplier` are the only conversion formulas.
  - **Any number of alternative units per material.** Nothing in the schema or the rules limits them.
  - **Every price records the unit it was priced in** (`UnitId?`), both a brand price and a price history entry, so switching from buying bags to buying packs leaves the old per-bag prices correct. The stored cost is per base unit only: `CostPerBaseUnit` = the dearest brand price ÷ its unit's multiplier. The material stores no purchase unit or current price: a price is meaningless without its unit, and storing the unit on the material would make a material ↔ unit FK cycle.
  - **Correcting a multiplier reprices.** `RawMaterialUnitRepository.UpdateAsync` (and the screen's Save, through the same shared write method) reprices the material from its brand prices when one is in that unit (`RawMaterialBrandPriceRepository.RepriceAsync`, which also logs a new cost in price history); for an ingredient whose cost moved that way it then calls `IngredientCostPropagator.RecomputeAndPropagateAsync`, which reaches every dependent made ingredient. Recipe lines are in grams, so nothing else moves. A packaging material needs nothing more: packaging lines are costed on read.
  - **A unit in use can't be deleted**: the repository counts price entries, and for a packaging material's unit its packaging lines and its packaging sets' lines, first and says which (Restrict FKs back that up). An ingredient's unit is never on a line.
  - **A packaging material's base unit is fixed once it has alternative units, prices or packaging lines** (`RawMaterialRules.EnsureBaseUnitCanChange`, checked in `RawMaterialRepository.UpdateAsync`), since all of them are measured in it.
- **RawMaterialCategory** (Flour, Dairy, Boxes, Ribbons, …): one user-editable list for both material types, **each category typed** (`Type`, a `RawMaterialCategoryType` stored by name): `Ingredient`, `Made` (made ingredients only) or `Packaging`. Managed in Settings → Material Categories, which has a Type column and a Type picker on its form (Application Architecture, below).
  - **A material goes only in a category of its kind**: `RawMaterialRules.CategoryTypeFor(type, source)` says which (a made ingredient a Made one, any other ingredient an Ingredient one, packaging a Packaging one) and `MaterialTypeOf` which material type a category holds. `EnsureCategoryMatchesType` takes the source too ("Flour is an ingredient category. Put this made ingredient in a Made category."), in `RawMaterialRepository`'s add, update and `MoveAsync`, after the type and source checks.
  - **A category's type can change while everything in it fits the new one** (`EnsureCategoryTypeCanChange(name, newType, materialsThatDontFit)`, in `RawMaterialCategoryRepository.UpdateAsync`), so an ingredient category of made ingredients alone can become Made in Settings. A made ingredient left in an ingredient category still loads, but its Save is refused with the message above until it's moved.
  - **Raw Materials screen**: the Category picker offers the categories of `CategoryTypeFor(EditingType, EditingSource)`, and a new material's type or source changed under one of another type empties it (only while `CanChangeTypeAndSource`: loading a saved one sets its category before its source). A Made category's folder (`RawMaterialFolderNode.CategoryType`; its `Type` is Ingredient, so it sits in Ingredients) offers **New Made Ingredient Here**; the Ingredients folder, the empty space and the toolbar's New Category drop-down offer **New Made Category…**. Move To, drags (`RawMaterialTree.MoveTo`/`MovesTo`) and a category typed into the picker all follow `CategoryTypeFor`, so made ingredients and the others never move together. Covered by `RawMaterialRulesTests`, `CategoryPersistenceTests`, `RawMaterialMovePersistenceTests` and `RawMaterialsViewModelTreeTests.A_Made_categorys_folder_starts_made_ingredients_and_takes_only_them`.
- **ProductCategory** (Breads, Cakes, Pastries, …): a user-editable list **of its own**, not shared with `RawMaterialCategory`, so a Category picker never mixes Flour and Boxes with Cakes. `Product.CategoryId` is **optional**, and a product without one is listed as Uncategorized. Its FK is **Set Null**, not Restrict like a raw material's, so deleting a category leaves its products uncategorized (the delete confirmation says so). A category can set the Wastage % its products are priced with (Costing defaults, below). Managed in Settings → Product Categories, or added from the Products header's Category picker. `ProductRepository` reads it with the product and writes it in add, update and `SaveAsync`; `ProductCloner` gives a clone its source's category.
- **Product stage** (`Product.Stage`, a `ProductStage` stored by name): `ResearchAndDevelopment` or `Production`, the Products list's two top-level folders. A clone and a variant start in Research and Development, the CLR default (`ProductCloner`); a product started by New goes in the stage Settings gives a new product, Production unless it says otherwise (`CostingDefaults.NewProductStage`). The column's database default is Production, and `HasSentinel((ProductStage)(-1))` makes EF always write the product's own stage. Only moving a product in the list changes a saved product's stage (dragging it to another folder, or its right-click menu's Promote, Send Back and Move to; `IProductRepository.MoveAsync`, which sets the stage and the category together, for any number of products in one save, and stamps `UpdatedAt`); the form's Save never writes it (`UpdateAsync`, `SaveAsync`). **A new product's is Save's to write**: `SaveAsync` copies `Stage` for a product it adds, so New Product Here on a Production folder files the product there, and the header says so until it's saved.
- **Deleted products** (`Product.DeletedAt`, nullable): a **soft delete**, in two steps. A deleted product waits in the Products list's **Deleted folder**, and **keeps holding what it uses**, so a restore never finds a hole.
  - `IProductRepository.DeleteAsync` stamps `DeletedAt` and changes nothing else: stage, category, recipe, packaging, links, costing and `UpdatedAt` all stay. `RestoreAsync` clears it. A category deleted in the meantime has already left the product uncategorized (`SetNull`). `DeletePermanentlyAsync` is the hard delete with its cascades. Both deletes are refused while another product, deleted or not, links its packaging or holds it in a composite (`EnsureNothingLeansOnAsync`), so a restore never needs a check.
  - **Reads**: `GetAllAsync` returns only the products in use, and `GetDeletedAsync` the deleted ones. `GetByIdAsync` and `GetByIdsAsync` return either. Every screen but Products reads `GetAllAsync`, so Reports, Print, the Price Simulator, the Recipe API and every picker leave deleted products out. There's no EF global query filter, because it would also hide them from the "in use" checks.
  - **Named as deleted where it's in the way**: `ProductRules.ListedName` gives "Cheese Roll (deleted)" in the Sub-Assemblies Used By and its refusals (`SubAssemblyRepository`'s `LinkRow`), Raw Materials' Used By (`GetUsedByAsync`), the delete refusals, and a composite's role refusals. A Used By tile for one opens its row in the Deleted folder.
  - **Its name stays taken** (the unique index covers it): Add, Update, Rename and a clone refuse it first with "A deleted product is named Mamon. Restore it from the Deleted folder, or delete it permanently there first." (`ProductRules.EnsureNameNotHeldByDeleted`). A deleted product can't be newly linked for packaging or put in a composite; each refuses by name.
  - Covered by `DeletedProductPersistenceTests`, and on the screen by `ProductTreeTests` and `ProductsViewModelTreeTests`.
- **Ingredients** (`Type = Ingredient`):
  - **The base unit for every ingredient is the gram.** Every weight total is in grams: sub-assembly lines' and BOM lines' `Grams`, a sub-assembly's batch weight, and weight per piece. **Recipe lines are entered in grams only**: sub-assembly lines and add-ins have no unit picker.
  - **`Source`**: `Purchased`, `Made` or `Linked`. It's set when the ingredient is created and can't change afterwards, so an ingredient's cost always comes from exactly one place.
  - **`Units`**: its alternative units (a 25 kg bag is `BaseUnitsPerUnit = 25000`, an egg piece `50`). Any source can have them; only a purchased one is priced in them.
  - **Purchased** ingredients are priced through their brand prices (`RawMaterialBrandPrice`), each in one of the ingredient's units (or per gram). `CostPerBaseUnit` = the costed brand's price ÷ grams in its unit (the dearest, unless `PreferredBrand` names one; see RawMaterialBrandPrice).
  - **Made** ingredients are produced in-house **from a sub-assembly, with add-ins of their own**, so a recipe is written once, on the Sub-Assemblies screen, and both a made ingredient and products can use it.
    - **`RawMaterial.SubAssemblyId`** (FK Restrict, indexed): the recipe it's made from. Required for a made ingredient and null for any other (`RawMaterialRules.EnsureFieldsMatchSource`, the validator, `CK_RawMaterials_SubAssemblyMatchesSource`). Only a recipe kept on the Sub-Assemblies screen: not a packaging set, not a product's own (`SubAssemblyRules.EnsureLinkableByMadeIngredient`). Several made ingredients can be made from one sub-assembly, each with its own add-ins and weight loss, and products can link the same one.
    - **Add-ins: `IngredientAddInLine`** (`IngredientId` Cascade, `AddInIngredientId` Restrict, `Grams`, `SortOrder`; unique per made ingredient and add-in), the made ingredient's own extras on top of the recipe, as a product's linked usage has `UsageAddInLine`. None is fine; each needs positive grams, comes once, and isn't already in the recipe (`IngredientBomRules.EnsureValidAddIns`, sharing `AddInRules` with `ProductRules.EnsureValidAddIns`). They belong to the made ingredient: the sub-assembly's lines and totals never include them.
    - **Its bill of materials is read, never stored**: the sub-assembly's lines, then the add-ins (`IngredientBomLine`, below).
    - They have no brand prices or price history.
    - **`WeightLossPercent`**: weight lost while making the ingredient (e.g. water boiled off syrup). At least 0 and less than 100 (`RawMaterialRules.EnsureFieldsMatchSource`). **The screen starts a new made ingredient at 3%**, the usual shrink in the shop (`??=` on the source change, so a saved material keeps what it was saved with), and the box caps at 0–99.99 to match the rule. A cleared box saves 0, a legitimate value.
    - Output grams = `Σ BOM line grams × (1 − WeightLossPercent / 100)`.
    - Cost per gram = `Σ (BOM line grams × component cost per gram) / output grams`. The buffered cost per gram is the same formula over the components' buffered costs, with nothing of its own on top. The formula is `IngredientBomRules.CalculateCost`; a component's cost is whatever's currently stored on it, which the cascade keeps current (Reactive Costing Cascade), so it's read directly rather than by walking the tree.
    - Example: simple syrup from 1000 g sugar (₱0.09/g, so ₱90) and 500 g water (unpriced: a literal ₱0 brand price is refused, so "free" means unpriced), with 20% weight loss, makes 1500 × 0.8 = 1200 g, at ₱90 / 1200 = ₱0.075/g.
  - **Linked** ingredients are parts of another ingredient, costed as a share of its cost. An egg is bought by the 1,500 g tray at ₱135 (₱0.09/g); egg white is 70% of its weight and carries 30% of its cost, egg yolk 30% of the weight and 70% of the cost. A made ingredient can't do this: a BOM spreads cost by weight only.
    - **`LinkedToId`** (self-referencing FK, Restrict, so an egg can't be deleted while a part links to it), **`WeightSharePercent`** and **`CostSharePercent`** (each above 0, at most 100). Only a linked ingredient has them, and it has no price history, no BOM and no weight loss (`RawMaterialRules.EnsureFieldsMatchSource`, the validator, `CK_RawMaterials_LinkMatchesSource`). The link and shares can be edited after creation; the source can't.
    - **Cost per gram = linked-to cost per gram × cost share ÷ weight share** (`RawMaterialRules.LinkedCost`, the only place the formula is). White: 0.09 × 30/70 = ₱0.038571; yolk: 0.09 × 70/30 = ₱0.21. 1,050 g of white and 450 g of yolk cost ₱40.50 + ₱94.50 = ₱135, the whole tray. It doesn't depend on the unit the egg was priced in.
    - **The cost share is of the linked-to ingredient's unbuffered cost, and the buffered cost is the same share of its buffered cost**, so a part follows the linked-to ingredient's fixed amount, and a buffer is never counted twice.
      - **The part shows the linked-to ingredient's `CostBufferPercent`, stored on it and kept in step**: `RawMaterialRepository` sets it from the linked-to ingredient's on add and update, whatever the form sent (`EnsureValidLinkAsync` returns it), and `IngredientCostPropagator` copies it again every time the part is recomputed. A buffer edit already cascades, so it reaches every part, down a chain of links; relinking takes the new ingredient's. Storing it keeps everything that reads `CostBufferPercent` (the Usage Example, the list) right without knowing about links.
      - The Linked Cost card shows the inherited percent read-only (bound to `EditingLinkedTo.CostBufferPercent`); it's changed on the linked-to ingredient.
    - **The parts of one ingredient take at most 100% of its weight and at most 100% of its cost** (`RawMaterialRules.EnsureLinkSharesFit`, checked by `RawMaterialRepository` on add and update against the *other* parts, so a part never counts against itself). Less is fine: the shell is neither white nor yolk. The message names the other parts: "Egg Yolk (30%) already takes 30% of Egg's weight, so Egg White can take at most 70%."
    - **Ingredients only**: the target must be another ingredient (`EnsureValidLinkTarget`, which also refuses a link to itself), purchased, made or itself linked. Packaging stays purchased-only; `CK_RawMaterials_OnlyIngredientsAreMade` already covers it.
    - **A link is one more edge in the cost graph** (Reactive Costing Cascade), so a cycle can't close through a mix of recipes and links: linking egg white to a meringue base made from egg white is refused, and so is a made ingredient whose recipe uses a part linked to it. `IngredientDependencies.LoadAsync` builds the combined graph for both checks (`IngredientBomRules.EnsureNoCycle`).
- **IngredientBomLine**: one component of a made ingredient, **a read model, not a table**: a line of the sub-assembly it's made from, or one of its add-ins (`IsAddIn`). `Infrastructure/Queries/IngredientBoms` is the one definition, which the cascade, the cycle check, `IngredientBomLineRepository` and the Recipe API's `/boms` all read, so everything that reads a BOM (the Price Simulator, the Scaling tab) sees the recipe and the add-ins together.
  - BOMs nest to any depth: caramel can be made from syrup, and syrup from sugar. `IngredientBomRules.EnsureNoCycle` keeps an ingredient out of its own BOM tree, checked at save time against the *other* made ingredients' current graph.
  - BOM lines are ingredients only, never packaging (`RawMaterialRules.EnsureUsableInRecipes`).
- **Packaging materials** (`Type = Packaging`):
  - `BaseUnitId` (FK to UnitOfMeasure) is its base unit, set per material: typically a count unit (piece) for boxes and wrappers, a length unit (cm) for ribbon. No rule restricts which unit that can be, but it's fixed once anything is measured in it (Multi-unit materials).
  - `Units` are its alternative units (a pack of 100 boxes is `BaseUnitsPerUnit = 100`, a 1000 cm ribbon roll `1000`), and `CostPerBaseUnit` its stored cost.
  - Always purchased, and priced through brand prices like a purchased ingredient.
  - Packaging lines can be entered in the base unit or any alternative unit (PackagingLine).
- **RawMaterialBrandPrice**: what each brand of a purchased material costs now. `Brand` is optional free text (trimmed, max 100, `null` when blank); `UnitId` is one of the material's units or `null` for per base unit; `Price` is per unit and positive (`CK_RawMaterialBrandPrices_Price`). **The material is costed at the dearest brand per base unit** (`RawMaterialRules.ApplyBrandPrices`/`FindDearestBrandPrice`), so costing stays conservative, **unless its Cost From names a brand** (`RawMaterial.PreferredBrand`), when it's that brand's dearest price. A brand is priced once per unit, whatever its case (`EnsureDistinctBrandPrices`); the same brand in two units is fine. `RawMaterialBrandPriceRepository.SetAsync` (and the screen's Save) replaces them all, reprices and cascades.
- **RawMaterialPriceHistory**: **a log of the prices a purchased material has been costed at.** `RawMaterialBrandPriceRepository.RepriceAsync` adds an entry, dated today, with the costed brand's price, unit and `Brand`, whenever brand prices move the cost; a Save that leaves the cost as it was logs nothing, and one that leaves no prices logs nothing either. **Deleting an entry only tidies the log** and never reprices. Made and linked ingredients have none.
  - **An unchanged cost has to compare equal.** A cost that doesn't come out even (170 ÷ 240 = 0.708333…) is worked out to 28 places and stored to 20, so every stored cost per base unit is set through `RawMaterialRules.StoredCost` (20 places, rounded half away from zero); otherwise a Save that changed nothing would read the cost as changed, log the same price again, and the cascade would re-date a made ingredient's cost (`StoredCostPrecisionPersistenceTests`).
- **SubAssemblyRole**: an editable lookup table (`Id`, `Name`, `SortOrder`, `IsPackaging`, `IsProductOwned`), seeded with Dough, Filling, Topping, Inclusion and Finishing. More roles can be added in Settings → Roles. `SortOrder` sets the order of a recipe's sections. A role can't be deleted while any sub-assembly uses it.
  - **The Packaging role**: seeded at **Id 6** with `IsPackaging = true`, the only role with the flag. A standalone sub-assembly in it is a **packaging set** (Packaging sets, below). The code checks the flag, never the name, so the role can be renamed; `SubAssemblyRoleRepository.DeleteAsync` refuses to delete it, and nothing in Settings can clear the flag (`UpdateAsync` writes only `Name` and `IsProductOwned`).
  - **Product-owned roles (`IsProductOwned`)**: a checkbox on Settings → Roles (and a read-only Product-owned column in its grid) for the roles a product can own a sub-assembly in, such as Filling, Topping or Pan Greasing; never the Packaging role (`SubAssemblyRoleValidator`, `SubAssemblyRules.EnsureProductOwnedAllowed`, in `AddAsync`/`UpdateAsync`, and the checkbox is disabled for it). See "Product-owned sub-assemblies" under SubAssembly. Not seeded.
- **SubAssembly** + **SubAssemblyLine**: a sub-assembly is an in-house recipe that products use directly, such as a dough, a filling or a topping. Its lines are the ingredients that make it up.
  - **Kept on the Sub-Assemblies screen, or a product's own.** A sub-assembly with no owner (`OwnerProductId` null) is made and edited on the Sub-Assemblies screen, and every product using it links it. One with an owner (`OwnerProductId`, Cascade from `Product`) is that product's own: its lines are edited in the product (`ProductUsageEdit.IsOwned`), it isn't on the Sub-Assemblies screen (`GetStandaloneAsync` leaves it out, and `SaveStandaloneAsync`/`DeleteStandaloneAsync` refuse it), and taking it out of the recipe or deleting the product deletes it. `SaveStandaloneAsync` writes the name, role, then the lines through `SubAssemblyLineRepository.SetLinesAsync`, in one transaction.
  - **A new section becomes a sub-assembly on Save.** A section typed in the Products screen's Recipe Structure (New, Copy an existing one, or Make a Copy of a linked one) goes to `SetRecipeAsync` as a `NewSubAssemblyDraft(RoleId, Lines, AuthoredField, AuthoredValue, SectionName)` with an `Id` (0 for new, else the product's own saved one, rewritten in place) and a `Placement` (`SectionPlacement`, one case for each thing the form can ask): `ByRole` (the product's own in a product-owned role, otherwise kept on the Sub-Assemblies screen and linked), `ProductsOwn` (its own whatever its role: an unlinked section, or a clone's copy of its source's own), `MoveToSubAssemblies` and `MoveToInHouse(MadeIngredientDraft)` (below). A saved one of the product's own is released only when it moves **out of a product-owned role** into one that isn't (the stored role's flag is read before `RoleId` changes); one unlinked in a plain role stays its own wherever it moves. `RecipeDraft` carries `(New, Linked, Components)`.
  - **Its name is the product's and the role's** (`SubAssemblyRules.StandaloneNameFor`): "Cheese Roll Dough", and with the section's own name after them when it has one that isn't just the role's, "Cheese Roll Filling: Cheese". The product's name is read inside the save's transaction, so a new or renamed product saves under its new name. **A name already taken gets the next number**, "Cheese Roll Dough 2" (`UniqueStandaloneName`, case- and space-insensitively, against every sub-assembly and the ones the same save just made), cut short to fit 100 characters with its number. Renaming a product later leaves the names of the sub-assemblies it saved to the Sub-Assemblies screen alone; **its own are renamed with it**, and with their role (`ProductRepository.UpdateAsync`, which `SaveAsync` runs even without a recipe, and `SubAssemblyRoleRepository.UpdateAsync`, whether or not the role is product-owned), when they're named after them (`SubAssemblyRules.IsNamedAfter`, numbered or cut to fit or not: one named otherwise keeps its name). Renames go through `SubAssemblyRepository.RenameAsync`: a throwaway name first, then the new ones, so two can swap.
  - **How a section goes by its name in a recipe** (`SubAssemblyRules.LabelIn`): a product's own by its **stored** label (`SubAssembly.SectionName`), never parsed back out of its name, since a name numbered when the plain one was taken ("Cheese Roll Filling 2") would read as a section called all of that; a linked one by `SectionLabel(name, productName, roleName)`, less the "Cheese Roll Filling: " it was saved under from that product (the tab reads "Filling: Cheese"), nothing at all when it's exactly "Cheese Roll Filling" (it goes by its role alone), and another product's by its whole name ("Filling: Ube Bun Filling"). Save, Clone and a role made product-owned write `SectionName`, and a role made not product-owned clears it. A version snapshot keeps each section's label (`VersionSection.Label`). `SetRecipeAsync`, `EnsureDistinctWhereLinkedAsync` and the Products form all read labels the same way.
  - **A product can have several sub-assemblies in one role, its own and linked together, as long as they can be told apart** (`SubAssemblyRules.EnsureSectionsDistinct`, in `SetRecipeAsync` and on the Products form's Apply): within a role no two go by the same label (case- and space-insensitively), and at most one goes without. A section's own name is optional, trimmed, at most 100 characters (`EnsureValidSectionName`). **A new role or name can't leave a linking product unable to tell its sections apart**: a rename or a new role on the Sub-Assemblies screen is refused when a product linking it would then have two in a role by one label, naming that product (`SubAssemblyRepository.EnsureDistinctWhereLinkedAsync`).
  - **Removing a section, or deleting the product, keeps a linked sub-assembly**: `SetRecipeAsync` only replaces the usages, a product's usages cascade, and the usage's sub-assembly FK is Restrict. What's left unused stays on the Sub-Assemblies screen until it's deleted there. **It can't be deleted from under a product that links it**: its Delete there is refused while any product uses it, naming them (`EnsureNoneLinkedElsewhereAsync`, `SubAssemblyRules.EnsureNotLinkedElsewhere`: "Cream Loaf Mini links Sweet Dough. Make a copy of it there, or remove it there, first.").
  - **Product-owned sub-assemblies**, in a role whose `IsProductOwned` is set, or unlinked into a product:
    - **Copy only**: another product can copy one (the Copy picker lists it as "Cheese Roll Filling: Cheese — Cheese Roll (Filling)", `GetLinkableAsync` bringing each one's owner) but never link it (`SubAssemblyRules.EnsureLinkable` in `SetRecipeAsync`; the Link picker leaves it out), so nothing but its product uses it, and it can be changed or removed freely. **Its product's variants link it** (Create Variant, below), the one exception.
    - **Turning a role product-owned** (`SubAssemblyRoleRepository.UpdateAsync`, one transaction, after a confirmation saying how many move, `CountOwnershipChangesAsync`): each of its sub-assemblies on the Sub-Assemblies screen that exactly one product's recipe uses becomes that product's own, keeping its name (`AdoptSingleUseAsync`), and that product's add-ins on it are merged into its lines, after its own. Used by several, or none, it stays. **Turning it off** releases every one products own in it to the Sub-Assemblies screen, still linked by the same product (`ReleaseOwnedAsync`); merged add-ins stay merged, which the confirmation says, and unlinked ones go too, since nothing tells them apart without a column. The Products screen picks either up on its next refresh: with nothing typed it reads the product again, so what Save compares against is how it's saved now.
    - **Clone and Create Variant give the new product its own copy of each owned section** (named after the new product; lines, piece size and what it went by), drafted `ProductsOwn`, and link what the source links (`ProductCloner.DerivedRecipe`).
  - **What a linked section's form offers** (Products):
    - **Make a Copy** and **Unlink** (`UnlinkCommand`), which both build the copy in `CopyOfLinked`, its add-ins merged into its lines. Make a Copy follows the role (the product's own in a product-owned role, otherwise kept on the Sub-Assemblies screen and linked). Unlink makes the copy **the product's own whatever its role**: its Role and Name show at once in place of the linked badge (`ProductUsageEdit` takes `isOwn`; `IsOwned` is `LinkedName is null && (SubAssemblyId > 0 || isOwn)`), and Save sends it as `ProductsOwn`. The one it was linked to stays on the Sub-Assemblies screen as it was.
    - **Undo puts the form back clean.** `UndoHistory` keeps, beside each step, the settled snapshot as it stood when the step was taken (`TryUndo`/`TryRedo(out restore, out settled)`), and `ProductsViewModel.RestoreSnapshot` ends by rebasing that snapshot's form and tabs (`WithFormOf`) onto it. So undoing an Unlink or a Make a Copy stops offering Save, while typing put back that wasn't yet in the recipe still counts. The recipe, costing and header stay as settled now, so a costing-defaults rebase in between isn't lost. Raw Materials and Sub-Assemblies don't rebase their forms.
    - **Change the link in place**: an Edit glyph beside the badge (`StartChangingLinkCommand`) swaps it for a searchable picker (`ChangeLinkOptions`: the Sub-Assemblies screen's recipes the recipe doesn't use yet, any role, never packaging or a product's own) and a cancel glyph (`CancelChangingLinkCommand`). Picking one (`ChangeLinkTarget`) runs `ChangeLinkAsync`, which reads the new one's lines and replaces the section in place (`ReplaceUsage`, one undo step), so it keeps its tab, which takes the new one's role and name. The piece size (the typed figure) and add-ins carry over, less any add-in the new recipe already has, which a toast names. Lines edited in the old link's form but not saved go with it. Save writes the new link; the old sub-assembly stays on the Sub-Assemblies screen.
    - **Its lines are edited in the product**, and written with the product's Save, so Undo and Revert cover the change; Save asks first, naming the other products using it. The lines grid is typed into like an own one's (`ProductsViewModel.IsFormLinesEditable`; only a link being picked shows its lines read-only), and its role and name stay the Sub-Assemblies screen's. `ProductUsageEdit` keeps the lines as last read (`SavedLines`), and only when `AreLinkedLinesEdited` (ingredients, grams and base ticks, not costs) does `CurrentRecipe` send them, as `LinkedUsageDraft.Lines` (null otherwise), so a product's Save never puts back lines the Sub-Assemblies screen changed since. `SetRecipeAsync` checks them with `EnsureValidLines` up front, checks this product's add-ins against them rather than the stored ones, and relines the sub-assembly before writing the add-ins, all in the product's transaction. A refresh keeps lines changed here (`WithLinked`). Save reads `GetStandaloneLinkedByAsync` and asks through `ConfirmDelete`: "Save changes the lines of Cream Loaf Dough, also used by Cream Loaf. Their recipes and costs change with it. Save anyway?"; declined, nothing is written and the change stays in the form. Not checked, as on the Sub-Assemblies screen: a new line that *another* product has as an add-in on the same sub-assembly.
  - **What a section of the product's own offers**:
    - **Move to Sub-Assemblies**, Unlink's reverse, in any role (`MoveToSubAssembliesCommand`, shown by `IsEditingOwnedUsage`). It applies whatever is typed into the form first (`ApplyUsageForm`; a refused one stays, with the message), so what moves is what shows, then marks the section (`ProductUsageEdit.IsReleasing`, via `Released()`), in one undo step. Until Save the section is still edited here, with a "Moves to Sub-Assemblies on Save" badge. Save sends it as `MoveToSubAssemblies`, which `SetRecipeAsync` puts ahead of the role: a saved one keeps its id, name and the lines just written, loses its owner, and the product links it at the same piece size; a new one is kept on the Sub-Assemblies screen, named after the product. In a product-owned role it stays there; only turning the role's flag off and on again would adopt it back. The Packaging tab has the same for the product's own packaging lines (Derived products, below).
    - **Move to In-House** (`MoveToInHouseCommand`, shown by `CanMoveEditingUsageToInHouse`): Save moves the section to the Sub-Assemblies screen as Move to Sub-Assemblies does (`SectionPlacement.MoveToInHouse` is a move there too: `MovesToSubAssemblies`), keeping its lines and baker's percentages, links the product to it at the same piece size, and adds a made ingredient made from it (`RawMaterialRepository.AddMadeAsync(dbContext, made, subAssemblyId)`, 0% loss, no add-ins, so it costs per gram what the recipe does; the real loss is set on the Raw Materials screen afterwards). The prompt (`PromptForMadeIngredient`, built by `MadeIngredientPrompt.RequestFor`) asks for the name, starting with the section's saved name, and a Made category, read fresh on each click and starting on In-House when one has that name; with no Made category it says to add one; a taken name is refused (`SubAssemblyRules.EnsureValidMadeIngredientName`). Its badge reads "Moves to Sub-Assemblies and In-House on Save, as …", and the snapshot compares `ToMadeIngredient`, so Undo stops offering Save. **On the Sub-Assemblies screen** the list's **Make In-House Ingredient…** (`MakeInHouseIngredientCommand`, `ISubAssemblyRepository.AddMadeIngredientAsync`) adds a made ingredient made from a recipe there, and leaves the recipe, its products and their versions alone.
    - **Why made ingredients and sub-assemblies both exist**: a `SubAssemblyLine` only references an ingredient, so a made ingredient is the only way one recipe goes inside another (Butter Icing is a line in many toppings), and only a made ingredient has a weight loss. Nesting sub-assemblies instead was rejected: the cascade's two fixed steps would become one mixed ordering.
  - `RoleId` (FK to `SubAssemblyRole`, required): each sub-assembly has exactly one role, so custard is always a Filling. It can change at any time; every recipe using the sub-assembly then shows it in the new role's place.
  - Each line has an FK to an ingredient (a `RawMaterial` of the Ingredient type, refused otherwise) and `Grams`. Line cost = grams × the ingredient's `BufferedCostPerBaseUnit`. `SubAssemblyRules.EnsureValidLines` refuses no lines, non-positive grams or an ingredient twice, so a sub-assembly always has a batch.
  - **A sub-assembly's batch weight and cost are worked out on read** from its lines (`SubAssemblyRules.CalculateTotals`), never stored, so there's nothing to keep in step when a line or an ingredient's cost changes.
  - **Baker's percentage: `SubAssemblyLine.IsFormulaBase`.** Each line reads as a percentage of the ticked lines' total weight, the formula's 100% base, usually the flour. `SubAssemblyRules.FormulaBaseWeight` sums the ticked lines and `CalculateBakersPercent(grams, baseWeight)` gives the figure, **null when nothing is ticked**. The sum of every line's percentage ("whole formula 201.5%" under the table) is the number a batch is scaled by (`flour = target ÷ (total% ÷ 100)`).
    - **Per line, not per ingredient**, rather than an `IsFlour` flag on the raw material: sugar is the base of a syrup and an extra in a dough, two flours tick together and make 100% between them, and it never depends on a user-editable category. Named `IsFormulaBase` because "base" already means a *unit of measure* in this codebase (`BaseUnitId`, `CostPerBaseUnit`); the column header is "Base".
    - **Nothing about cost changes.** Grams are the source of truth; the tick is a reading of the batch, never stored as a figure.
    - **Lines travel as `RecipeLine`** (`ApplicationCore/Interfaces/RecipeLine.cs`), a `readonly record struct (IngredientId, Grams, IsFormulaBase = false, AuthoredBakersPercent = null)` with an **implicit conversion from the `(IngredientId, Grams)` tuple**, so tests write `[(flourId, 1000m)]`. The same conversion makes a *lossy* projection compile silently (`.Select(l => (l.IngredientId, l.Grams))` drops the tick and the typed percentage without an error), so the places that rebuild lines from existing data name them explicitly: `ProductsViewModel.CurrentRecipe()` (miss it and ticks never save, and `IsSameRecipe` never sees the change), `SubAssembliesViewModel`'s save, and `ProductCloner`'s own-copy branch. Anything that carries sub-assembly lines from one place to another has to do the same.
    - **Add-ins have no tick** and stay on the plain tuple (`LinkedUsageDraft.AddIns`, `UsageAddInLineRepository`): an add-in is never part of the base. Each still gets a percentage, **read against the linked recipe's base**: 100 g of buttermilk on a dough's 1,000 g of flour reads 10.0, and the whole-formula figure includes it.
    - **Typed either way, and whichever was typed stays put.** A line's grams or its baker's percentage can be typed; the other is worked out. **`SubAssemblyLine.AuthoredBakersPercent`** (nullable) records a typed percentage, null when the grams were typed, the same idea as a usage's `AuthoredField`/`AuthoredValue`. When the base weight changes, a line typed as a percentage has its grams worked out again (`SubAssemblyRules.GramsFromBakersPercent`), and a line typed in grams keeps them while its percentage moves: on 1,000 g of flour, water typed as 65% and eggs typed as 100 g; double the flour and the water is 1,300 g, still 65%, while the eggs stay 100 g at 5%.
      - **Grams are still stored for every line** and still all that's costed. A typed percentage is worked back into grams the moment the base changes, in the form, and saved that way, so the stored grams are never stale. `GramsFromBakersPercent` rounds to the 4 decimals grams are stored in, so reopening a saved line reproduces exactly what was worked out; unrounded, a line could come back a ten-thousandth off and make a recipe nobody touched look changed.
      - **Any change to the base weight counts**: a base line's grams, a tick, or a base line added or removed. Ticking a line into the base makes it a grams line (the base is 100% between its lines by definition), and `EnsureValidLines` refuses a base line carrying a percentage. With nothing ticked, a typed percentage keeps its last grams and waits: tick the flour again and the line follows it.
      - **Where it can't be typed, it won't open**: on a base line, and while nothing is ticked (`IngredientLineRow.CanTypeBakersPercent`). SfDataGrid's `AllowEditing` is one setting per column, so `controls:GridCellEditing` (a grid-level `IsEnabled`, and `AllowWhen` naming a `bool` property of the row on the column, as `MappingName` names the value) cancels `CurrentCellBeginEdit` on the rows that say no. The row's setter ignores such a value too, as a backstop.
      - **Carried everywhere lines are**: `RecipeLine.AuthoredBakersPercent`, `SectionLine`, `ProductUsageEdit.ShowsSameAs`, the three line-copying projections above, `Repriced`, and both add rows' item factories, which hand a new line the current base so a percentage can be typed into it straight away.
      - **Add-ins can be typed either way, but only grams are kept.** An add-in's base is the linked recipe's, which can change on another screen; remembering a typed percentage would mean working its grams out on every read, in Products and Reports alike, from a base those screens don't load.
    - **With nothing ticked, the column shows absolute percentage**: `SubAssemblyRules.CalculateAbsolutePercent(grams, batchWeight)`, a line's share of the whole batch, so the lines come to 100 between them. `IngredientLineRow.Percent` reads baker's percentage while `BaseWeight > 0` and absolute percentage against `BatchWeight` otherwise; `ApplyFormulaBase` hands every row both weights, and the batch counts the rows with an ingredient picked (`IngredientLineRow.BatchWeightOf`).
      - **The header follows** (`SubAssembliesViewModel.PercentHeader`, `ProductsViewModel.UsageFormPercentHeader`, both from `IngredientLineRow.PercentHeader`), through a **`HeaderTemplate`** (`PercentHeaderTemplate` in each view) whose `TextBlock` binds the view's `DataContext` by `RelativeSource AncestorType=UserControl`. Not a bound `HeaderText`: every Products tab has its own `UsageFormPanel` and grid, and a changed `GridColumnBase.HeaderText` only reaches the header cell through the grid's row generator, which doesn't redraw the header of the grid a newly shown tab brings in. The caption under the table says "Absolute %: each line's share of the batch. Tick the base — usually the flour — for baker's %."
      - **Read-only.** `CanTypeBakersPercent` is false without a base; the row's setter checks it before a cleared value, so a line whose typed baker's percentage is waiting for a base to come back doesn't lose it.
      - **On a linked recipe with add-ins, both tables divide by the whole batch**: the recipe's lines and the add-ins together come to 100%. With a base, add-ins are read against the recipe's base.
    - Not modelled: a preferment (a sponge made as a made ingredient) ticked as the base counts its whole weight, not the flour inside it; and true hydration, counting the water in milk and eggs.
- **Packaging sets: SubAssembly in the Packaging role + SubAssemblyPackagingLine.** A standalone sub-assembly whose role has `IsPackaging` holds packaging materials **per set** instead of ingredients in grams: a gift box with its ribbon and tag, or the 8 bags and the box that make up an "Ensaymada Box of 8".
  - **`SubAssemblyPackagingLine`** (`SubAssemblyId` Cascade, `PackagingMaterialId` Restrict to a `RawMaterial` of the Packaging type, `UnitId?` Restrict to a `RawMaterialUnit`, `QtyPerSet` > 0 in that unit; unique per set + material; `CK_SubAssemblyPackagingLines_QtyPerSet`). A table of its own, not `SubAssemblyLine`, which is ingredients in grams and feeds the cost cascade.
    - **`UnitId?`**: the unit the quantity is entered in, one of the material's own alternative units, or its base unit when empty, as `PackagingLine.UnitId` has it. The quantity is stored as typed and converted at cost time, so 1 roll stays 1 roll rather than the 1,000 cm it comes to, and correcting the roll's multiplier reprices the line without rewriting it. `SubAssemblyRepository.SaveStandalonePackagingAsync` refuses a unit that isn't that material's own, with the message `PackagingLineRepository.SetLinesAsync` uses, and `RawMaterialUnitRepository.DeleteAsync` counts set lines beside packaging lines before it lets a unit go.
  - **Costed on read**, like a product's packaging lines. A set has no ingredient lines, so the cost propagator never meets one.
  - **Standalone only.** A recipe section never takes the Packaging role (`SubAssemblyRules.EnsureRecipeRole`, in `SetRecipeAsync`; the Products form's role picker leaves it out), and `GetLinkableAsync` leaves sets out of the recipe link/copy picker.
  - **The kind is fixed once saved**, as a raw material's type is: `SubAssemblyRules.EnsureKindUnchanged` refuses moving a saved recipe to the Packaging role or a saved set to a recipe role. `SaveStandaloneAsync` refuses the Packaging role; `SaveStandalonePackagingAsync` requires it (one transaction: name and role through the shared `StageStandaloneAsync`, then `SubAssemblyRules.EnsureValidPackagingLines` (at least one line, positive quantities, no material twice) and `RawMaterialRules.EnsureUsableAsPackaging` per material, then the lines replaced).
  - **Used by a product's packaging, one whole set per sellable unit**, linked or copied from the Products screen's Add Sub-Assembly ("Link the packaging" under Derived products). A packaging material's base unit is fixed once a set uses it too (`RawMaterialRepository.UpdateAsync`'s `hasLines`).
  - **Deleting a linked set is refused**, naming the products (`DeleteStandaloneAsync`, the wording of `EnsureNotLinkedElsewhere`), and `GetStandaloneLinkedByAsync` counts packaging links, so the screen's Used By names them.
- **Product** + **ProductSubAssemblyUsage**: a finished product is built from distinct sub-assemblies, its own and linked ones. It can use several in one role, e.g. an ube filling and a cheese filling, told apart by their labels (SubAssembly, above), and each sub-assembly only once.
  - **`Description`** (optional, at most 500 characters: `ProductValidator.MaxDescriptionLength`, which `ProductConfiguration`'s `HasMaxLength` also uses) and **`UpdatedAt`** (`DateTime?`, local time) for the Products screen's header. `UpdatedAt` is stamped by `ProductRepository`'s add and update, so by the screen's Save and by a clone when it's made; null shows as "—".
  - **`CurrentPrice`** (`decimal?`, per sellable unit, VAT included): what the shop charges now, entered in the Products header beside the computed Selling Price and saved with the product (null until entered; `ProductValidator` refuses a negative one). A clone copies it. It prices nothing: the header shows the **Markup %** it earns, `CostingRules.CalculateMarkupPercentFromPrice` (VAT taken out first, then the markup on the base cost, `(CurrentPrice ÷ (1 + VAT%) − BaseCost) ÷ BaseCost`), the same definition as the costing's Margin, so the computed Selling Price gives back exactly the Margin %.
  - **Each usage has its own piece size, as total weight, yield and weight per piece.** The user types either the **weight per piece** (grams) or the **yield** (pieces per batch), and the other is worked out from the batch's total weight. A usage stores only what was typed: **`AuthoredField`** (`UsageAuthoredField.WeightPerPiece` or `Yield`) and **`AuthoredValue`** (≥ 0, `CK_ProductSubAssemblyUsages_AuthoredValue`).
    - **Neither figure is required**: a section goes into the recipe, and saves, before how much of it a piece takes is known, stored as `AuthoredValue` 0. `ProductRules.EnsureValidUsages` and the check constraint refuse only a negative; an unsized section has a batch but costs the product nothing per piece, and the form's caption says so.
    - **The pieces share out the whole batch: no shrinkage.** What's lost making a product is a cost on it, the Wastage % (Costing defaults, below), not a smaller batch, so `ResolvePieceSize` and `CalculateUsageCostPerPiece` divide the effective batch's total weight. A saved version's sections may still hold a `ShrinkagePercent` in their JSON, which `ProductVersionContent.FromJson` ignores.
    - **A section added in a product-owned role starts at a yield of 1.** Such a section is written for the one piece it goes into, so the add form opens with `AuthoredField` `Yield` and `AuthoredValue` 1 where any other role opens unsized (`ProductsViewModel.StartingPieceSize`), New and Copy alike; a Link stays unsized, its batch being shared. With the yield stored, the weight per piece is the Grams column's total and goes on following the lines after Save. It's the role's start, not an entry: while neither figure has been typed it follows the role picked (`IsPieceSizeAsStarted`), and a form still at it counts as untouched (`IsUsageFormUntouched`); both are worked out from the form rather than remembered, so they hold for a form an undo put back. Saved sections are left as they are.
  - **`ProductRules.ResolvePieceSize(authoredField, authoredValue, totalWeight)`** is the one formula: weight typed → `Yield = TotalWeight / WeightPerPiece`; yield typed → `WeightPerPiece = TotalWeight / Yield`. It's worked out on every read, never stored, which is what makes **the typed figure stay put when the batch changes**: a 60 g piece stays 60 g and the yield moves; a 24-piece yield stays 24 and each piece gets heavier or lighter. Being computed on read, a line edit in one recipe never has to update other products' rows. A batch that weighs nothing has no other figure (0). Every caller passes the effective batch's weight (`SectionFigures.Of`, for `ProductUsageEdit` and saved products, and `ProductUsageForm`'s `Recompute` and `FollowPieceSize`), so the rule stays one line.
  - Usage cost per piece = `TotalCost × WeightPerPiece / TotalWeight` (the effective batch's, worked out from its lines and add-ins), the same as `TotalCost ÷ Yield`. For example, 100 g / ₱24 of filling used at 10 g a piece gives ₱2.40 a piece, yield 10. A per-line share of a piece, should one be wanted, must divide by the usage's *effective* batch (`ProductRules.CalculateEffectiveBatch`), not the sub-assembly's own, or a linked usage's add-ins would be left out of every line's share.
  - **UsageAddInLine: a product's own extras on top of a sub-assembly it links.** The same dough goes into several products, but one wants ube flavouring and another pandan colour; without add-ins the only way would be Make a Copy, which breaks the link, so the dough would stop being shared.
    - `UsageAddInLine` (`UsageId` Cascade, `IngredientId` Restrict, `Grams`; unique per usage + ingredient) hangs off the **usage**, not the sub-assembly: two products linking the same dough each keep their own set, and neither moves the dough's own lines.
    - **Add-ins go into the batch**: the usage's **effective batch** is the sub-assembly's plus its add-ins (`ProductRules.CalculateEffectiveBatch`, over `SubAssemblyRules.CalculateTotals`), so 1,700 g of dough with 20 g of flavouring is a 1,720 g batch and a piece takes its weight-per-piece share of the whole thing. The typed figure still stays put, so adding a flavouring moves the other one.
    - **Linked usages only.** A section of the product's own has no add-ins: its extras just go in its lines, and a second table there would be two ways to do one thing.
    - **An ingredient the linked recipe already has is refused** (`ProductRules.EnsureValidAddIns`, rather than merging the grams): "Water is already in Variety Bread Dough. Add-ins are only for what its recipe doesn't have — change how much it uses where Variety Bread Dough is kept, or make this product a copy of it." Checked in the form as Apply is pressed, and again in `SetRecipeAsync`'s pre-flight and `UsageAddInLineRepository.SetLinesAsync` as it writes. An empty set is valid: most linked usages take the recipe as it is.
      - That guard is load-bearing: since an add-in can never duplicate a base ingredient, **Make a Copy and Unlink concatenate the base lines and the add-ins** into the new sub-assembly's lines without a merge step, and the result always passes `EnsureValidLines`. The batch it was showing is the batch it keeps.
    - **Written with the rest of the recipe**: `LinkedUsageDraft.AddIns` (an `init` property). `SetRecipeAsync` adds the linked usages together, saves once so every one has the id its add-ins need, then writes each one's lines. `ProductSubAssemblyUsageRepository.GetAddInsForProductAsync` reads them back. Everything that prices a product goes through `SavedProductReader` or `ProductUsageEdit`, both on `CalculateEffectiveBatch`, so no figure leaves add-ins out.
  - A product has **no yield of its own**. Each usage has its own yield, and those usually differ between a product's sub-assemblies. That's expected, not an error.
  - Product material cost per piece = the sum of all its usages' cost per piece; its packaging lines are per sellable unit (Quantity Required, below).
  - Sub-assembly and product weights are raw input weights; baking and moisture loss aren't modelled for them. Made ingredients are the only place weight loss is (`WeightLossPercent`), and Wastage % is the product's allowance for what's lost making it.
- **PackagingLine**: one packaging material used by one whole sellable unit of a product: its wrapper, its box, its label, its ribbon. "Unit" throughout this bullet means that sellable unit, which is one finished piece unless the product's `QuantityRequired` says otherwise.
  - FK to a `RawMaterial` of the Packaging type (`PackagingLineRepository` refuses an ingredient).
  - **`UnitId?`**: the unit the line's quantities are entered in, one of the material's own units, or its base unit when empty. Quantities are stored as entered, in that unit.
  - **`QtyPerUnit`**: amount of the packaging material used by one sellable unit, in the line's unit (12.7 for 12.7 cm of ribbon, `0.1667` for a 6-piece box, 1 for a label). **Typed, and never rescaled**: changing a product's `QuantityRequired` from 8 to 12 doesn't touch it, so the packaging is revisited by hand. The Packaging tab's caption says which unit the figures are for (`ProductsViewModel.CostUnitCaption`).
  - **`UnitsPerPackagingUnit`**: sellable units served by one of the line's unit of the packaging material (6 for that box).
  - **`AuthoredField`**: which of the two the user typed; the other is recalculated as its reciprocal on every edit. Ribbon is naturally entered as `QtyPerUnit`, a box as `UnitsPerPackagingUnit`. Its members are stored as ints, so they may be renamed but **never reordered**.
  - The unique index is **`{ProductId, PackagingMaterialId}`**: one line per material per product; a material a unit takes twice belongs on one line at the combined quantity.
  - Cost per unit = `BufferedCostPerBaseUnit × QtyPerUnit` converted to base units (`ProductRules.CalculatePackagingLineCost(costPerBaseUnit, qtyPerUnit, baseUnitsPerEntryUnit?)`), computed on read. It's a cost per *sellable unit*, so `CalculateMaterialCost` adds it once however many pieces that unit holds.
  - Example: a ribbon costs ₱45.00 per roll. Its base unit is cm and a roll holds 1000 cm, so it costs ₱0.045 per cm. One product uses 12.7 cm per piece (₱0.5715); another is entered as 0.08 m per piece (8 cm → ₱0.36).
  - Storing both directions differs from `ProductSubAssemblyUsage` on purpose: people describe packaging quantities both ways, but recipe weights only one way.
- **Quantity Required** (`Product.QuantityRequired`): how many finished pieces make one sellable unit. 1 for a product sold by the piece, which is nearly all of them; 8 for "Ensaymada Box of 8". `int`, defaulting to 1 in the CLR and in the database, `CK_Products_QuantityRequired` keeping it positive, and `ProductValidator` refusing anything below 1 on the screen.
  - **The recipe is authored per piece, costing and pricing are per sellable unit, and this is the bridge.** `ProductRules.CalculateMaterialCost(usageCostsPerPiece, quantityRequired, packagingCosts)` = `usageCostsPerPiece.Sum() × quantityRequired + packagingCosts.Sum()`: only the usages are multiplied, since a packaging line is already for one whole unit.
  - **`ProductConfiguration` sets `HasDefaultValue(1).HasSentinel(-1)`.** The sentinel moves "leave it to the database" off 0, which EF would otherwise take it to be: without it a product explicitly saved as 0 pieces would be quietly stored as 1 on an insert while being refused on an update.
  - **A pack is a product**: a variant of the single, with a Quantity Required and packaging of its own, so it has a price, a markup, a category and a row in the list like any product.
  - **The worked example**, which `ProductQuantityRequiredPersistenceTests` pins: Ensaymada takes 10 g of a 1,000 g / ₱50 dough, so ₱0.50 of recipe a piece. "Ensaymada Box of 8" is **Create Variant** of it (the recipe linked, so still 10 g a piece) with Quantity Required 8 and its packaging linked to a standalone **packaging set** holding the 8 bags (`QtyPerSet` 8) and the one box (`QtyPerSet` 1). Its material cost is `8 × ₱0.50 + 8 × ₱0.25 + ₱12 = ₱18`.
  - **The per-piece wrapper is written down twice**, rather than giving a product a second packaging slot. A product's packaging is its own lines **or** one `PackagingLink`, never both (`CK_PackagingLinks_OneTarget`), so a boxed variant can't read the single's wrapper *and* link a box set; the set carries both instead. Prices still follow on their own, since both point at the same `RawMaterial`; only the composition is duplicated.
  - **Pricing is linear in the sub-assembly cost** (labor, overhead and administrative are percentages of it, packaging passes straight through, margin and VAT are multiplicative), so **a unit of 8 with no packaging of its own prices at exactly 8 times the single's price**: its own packaging is the whole of the difference. Pinned by a test in `CostingRulesTests`.
  - **The Scaling tab counts sellable units too**: N units scale the recipe to N × Quantity Required pieces and the packaging to N units.
  - **Every figure on the Products screen is per sellable unit**: `ProductHeaderCard`'s Material Cost, Base Cost, Current Price and Markup %, and the whole of `CostingCard`'s breakdown. `ProductsViewModel.CostUnitCaption` ("Per piece", or "Per unit of 8 pieces") is bound into their tooltips, the breakdown's column header and the Packaging tab's caption. The recipe tabs stay per piece: a usage's weight per piece, yield and cost per piece.
  - **Typed in on `ProductDetailsCard`**, beside Current Price (a Syncfusion `IntegerTextBox`, `MinValue` 1), since that card holds the product's own typed fields and the header holds only read-only figures. Undo covers it (`ProductFormSnapshot.QuantityRequired`), a clone and a variant both copy it, and Reports' Product Cost Summary is per unit too, with a Pieces column saying how many.
- **Composite products** (`Product.IsComposite`): a product made of other products and its own packaging, such as a Pasalubong Box of 6 Ensaymada and 4 Cheese Rolls.
  - **A kind of product holding products and packaging, fixed once saved**, rather than letting any product take in whole products beside its own sub-assemblies.
    - It's picked with New ▸ New composite product, or New Composite Product (Here) in the list.
    - `CompositeProductRules.EnsureKindUnchanged`, in `ProductRepository.UpdateAsync`, refuses a change, as `RawMaterialRules.EnsureTypeUnchanged` does for a raw material.
    - `ProductComponentRepository.SetComponentsAsync` refuses products for a product of sub-assemblies.
    - **Its own sections are only in product-owned roles** (`SubAssemblyRole.IsProductOwned`, reused rather than a second per-role flag), such as a topping or a filling.
      - `CompositeProductRules.EnsureSectionRoles`, run by `SaveAsync` through `ProductComponentRepository.EnsureSectionRolesAsync`, refuses a section, new or linked, in any other role, naming it.
      - `SubAssemblyRoleRepository.UpdateAsync` refuses unticking Product-owned while a composite has a section in the role, and `SubAssemblyRepository`'s standalone save refuses moving a sub-assembly a composite links into a role that isn't product-owned. Both name the composites (`CompositesUsingRoleAsync`).
      - A composite is one unit, so a section's piece size is per whole composite, and its cost per piece joins the products' lines in the recipe cost. A composite held in another brings that whole recipe cost, sections included.
      - Clone and Create Variant copy or link its sections as any product's (`DerivedRecipe`). Raw Materials' Used By takes any product's sections (`SectionUsers`), and `RecipeUsers` climbs from there.
    - It's always **one sellable unit**, `QuantityRequired` 1. `CompositeProductRules.EnsureOneUnit` (in the static Add and Update), `ProductValidator` and `CK_Products_CompositeIsOneUnit` all enforce it.
  - **Each product brings its recipe cost, as a Box of 8 does**, rather than its recipe and its packaging, or its full base cost with only the composite's markup and VAT on top.
    - A line brings the product's Sub-assemblies (ingredients) figure for one sellable unit, × the line's quantity (`CompositeProductRules.CalculateComponentCost`).
    - Its packaging stays out, so the composite's packaging covers the box and anything wrapping the pieces, the same choice as the per-piece wrapper written into a Box of 8's set.
    - The composite's own labor, overhead, admin, wastage, markup and VAT apply to that recipe cost as for any product. So `ProductCostSummary` takes the lines, then its sections, as its `ProductCostInputs.Parts` at a quantity of 1, and every formula is unchanged; `IsComposite` and `HasOwnSections` only rename the rows (`PartsTitle` "Products (ingredients)", or "Products and sub-assemblies (ingredients)" with sections).
    - Pricing stays linear: products at the same percentages and a composite with no packaging price at exactly the sum of their prices. `SavedProductReaderCompositeTests` pins it: 2.50 → 5.096 and 5.00 → 10.192 make 12.50 → 25.48.
  - **Include each product's packaging** (`Product.IncludesComponentPackaging`), off by default, for pieces that go into the box already wrapped.
    - **It joins the composite's packaging, not its recipe cost**: labor, overhead and administrative, percentages of the recipe alone, don't go on it, as for any packaging. So products at the same percentages still price at exactly the sum of their prices with their packaging in, which `SavedProductReaderCompositeTests` pins.
    - A line brings its product's Packaging figure for one sellable unit × its quantity (`CompositeProductRules.CalculateComponentPackagingCost`). A composite held in another brings all of its Packaging figure, its own products' included when it has the box ticked, so it nests the way the recipe cost does.
    - `SavedProductReader.ReadComponentCostsAsync` returns `ComponentCosts`: recipe and packaging, buffered and unbuffered, from the one read. `ProductCostSummary` takes it as `ProductCostInputs.ComponentPackaging` (null when not ticked), keeps `OwnPackaging` apart for the Packaging tab's caption, and names the row `PackagingTitle`, "Packaging (own and products')" when ticked, on screen and in print.
    - Only a composite can have it: `CompositeProductRules.EnsureComponentPackagingOnComposite` in the static Add and Update, and `CK_Products_ComponentPackagingOnComposite`. Clone and Create Variant copy it.
    - Raw Materials' Used By climbs for it: `PackagingCosts` in `UsedBySql` goes from every product whose packaging cost the material is in to each composite with the box ticked holding it, and on up. It's a CTE of its own because a packaging link takes only the linked product's lines, so `PackagingUsers` mustn't climb through composites.
  - **Composites nest, with a loop check.**
    - `CompositeProductRules.EnsureNoCycle`/`Contains` check every other composite's lines, in `SetComponentsAsync`. The message names both: "Party Package can't go into Pasalubong Box: it already contains Pasalubong Box, so …".
    - The picker leaves out the composite and every composite holding it.
    - A composite holding itself, as only an edit outside the app can leave one, is read with the loop cut where it closes (the product that comes round again brings nothing there, `ComponentCosts.None`) and flagged (`ProductDetail.HoldsItself`), which the Products screen says when it opens it (`CompositeProductRules.HoldsItselfText`); Save goes on refusing the loop. Refusing the read instead would fail every product's read in a batch: the list, Reports, Print and both servers.
  - **At least two different products** (`CompositeProductRules.MinimumProducts`): six of one product is a Box of 6. A new composite saved with a null recipe (the form's unchanged-recipe shortcut sends none) counts as holding none, so the rule can't be skipped. The public `AddAsync` refuses a composite: only `SaveAsync` writes one with its products.
  - **Quantity**: a whole number, 1 or more, counting the component's sellable units. 1 of "Ensaymada Box of 8" is the whole box and brings 8 pieces' recipe. Every variant is a product of its own, so each is a line of its own.
  - **Storage**: `ProductComponent`. `ProductId` cascades. `ComponentProductId` is Restrict: a product in a composite can't be deleted, and `ProductRepository.DeleteAsync` names the composites before the key would refuse ("Pasalubong Box holds this product. Take it out there first."). `Quantity` is an int above 0, and `SortOrder` records the dragged order. It's unique per composite and product, with `CK_ProductComponents_Quantity` and `CK_ProductComponents_NotItself`.
  - **Written as the recipe**: `RecipeDraft.Components` is an init property. `ProductComponentRepository` is static, like `UsageAddInLineRepository`; its reads are `IProductRepository.GetComponentsAsync` and `GetAllComponentsAsync`.
  - **Worked out on read, nothing stored**: `SavedProductReader.ReadDetailAsync` reads a composite's lines and prices each product through itself, recursively (`ProductDetail.Components`, `SavedComponent`). So a composite's line always matches its product's own Costing tab, in Reports and Print as on the screen. `ReadComponentCostsAsync(ids)` serves the screen.
  - **Clone and Create Variant** give the copy the same products at the same quantities (`SetComponentsAsync`). Create Variant still links the packaging.
  - **Raw Materials' Used By** climbs `ProductComponents` for an ingredient, however deep. For packaging it climbs only into composites that include their products' packaging (above).
  - Tests: `CompositeProductRulesTests` and `ProductValidatorTests`; `CompositeProductPersistenceTests` and a case in `RawMaterialUsedByPersistenceTests`; `SavedProductReaderCompositeTests`, `ProductsViewModelCompositeTests`, a case in `PrintTabViewModelTests`, two in `ProductPrintLayoutTests`, and the tree-menu tests.

  - **A column, not the Id order**: EF Core inserts several rows in one batch, and the database doesn't promise to hand out identities in that order, so Id order would only be the insert order by habit. - **CostingParameters**: a product's labor, overhead and administrative (office, permits, bookkeeping) percentages, at least 0, and its margin %. **Always independent per product**, even for derived and linked products. **Labor, overhead and administrative are percentages of the sub-assembly (ingredient) cost per piece alone, packaging left out** (`CostingRules.CalculateCostFromSubAssemblyPercent`): 25% labor on ₱20 of sub-assemblies is ₱5. Packaging still goes into the base cost, just not into these three: what they pay for is making the recipe, not wrapping it.
  - **The VAT is the shop's**: `CostingDefaults.VatPercent` (`CK_CostingDefaults_VatPercent`), read live with every product as the wastage is (`ProductDetail.VatPercent`). The Costing tab shows it greyed; Settings changes it, repricing every product. A version snapshot keeps the shop's VAT it was priced with (`ProductVersionContent.VatPercent`; schema 2 and before kept the product's own in their costing, read through `VatThen`), and the History tab lists a change in it, or in the wastage, after the product's own changes (`ProductVersionRules.ShopChanges`), never counted as one.
  - **Apply Costing Defaults** on the Products list's menu, for the products picked, sets their labor, overhead, administrative and markup percentages to the defaults once it's confirmed, in one unit of work with a version of each one it changes, noted "Costing defaults applied" (`VersionedSaves.ApplyCostingAsync`); the product on the form has its unsaved changes saved or thrown away first, and shows its new costing after.
  - **Costing defaults** (`CostingDefaults`): a table of one row (`Id` 1, never an identity, `CK_CostingDefaults_SingleRow`), edited on Settings' **Costing Defaults** tab (`CostingDefaultsView`/`CostingDefaultsViewModel`, checked by `CostingParametersValidator`, and `CostingRules.EnsureValidParameters` in `CostingDefaultsRepository.SetAsync`). It holds two kinds of setting:
    - **Starting values for something new**, which never reach what's saved:
      - **Labor, overhead, administrative and markup %**, a new product's costing. `ProductsViewModel` reads them with every `LoadCommand` (Settings closing reloads the screen on show), and `StartNewProduct` puts them in the Costing fields while what Save compares against stays at none, so the product's first Save writes them as its own `CostingParameters` (all-zero defaults write nothing). A new product still showing the defaults it started with takes up changed ones on the next load; one whose costing was typed into keeps it. A saved product, a clone and a variant keep their own (a saved product without a row shows zeros).
      - **New Products In** (`NewProductStage`, a picker over `CostingDefaultsViewModel.Stages`), the stage New files a product in, Production unless set (`DefaultNewProductStage`). Stored by name as `Product.Stage` is, with `HasSentinel((ProductStage)(-1))`, so EF always writes the stage picked, Research and Development (the CLR default) included. It's only New's (and New Composite Product's, from the empty space): New Product Here keeps its folder's, and a clone or a variant starts in Research and Development.
      - **Cost Buffer %** (`CostBufferPercent`), a new raw material's, 0 to 100 (`RawMaterialRules.EnsureValidCostBuffer` in `SetAsync`, `CK_CostingDefaults_CostBufferPercent`), 10% unless set (`DefaultCostBufferPercent`), with `HasSentinel(-1m)` so EF always writes it, 0 included. `RawMaterialsViewModel` reads it with every `LoadCommand`, and `ClearForm` (New, New … Here, after Delete) starts `EditingCostBufferPercent` at it. A new material still showing the default takes a changed one on the next load, with `History.Rebase` so it stays clean (`RefreshDefaultCostBuffer`). Only a purchased material keeps it: a linked one inherits and a made one stores 0.
    - **Figures every product is priced with, saved ones included**, so a change reprices them all:
      - **VAT %** (above).
      - **Wastage %** (`WastagePercent`), 0 to 100 (`CostingRules.EnsureValidWastage`, `CK_CostingDefaults_WastagePercent`), 3% unless set (`DefaultWastagePercent`), with `HasSentinel(-1m)`. **A product category can set its own** (`ProductCategory.WastagePercent`, Settings → Product Categories; blank keeps the shop's), and a product is priced with its category's or the shop's (`IProductRepository.GetCategoryWastageForProductsAsync`). It's a **cost allowance** added on top (₱100 × 3% = ₱3), not a physical loss (₱100 ÷ 0.97), a percentage of the **sub-assembly (ingredient) cost per piece alone**, as labor, overhead and administrative are, with those three still on the ingredients before it: `BaseCost = SubAssemblies + Wastage + Packaging + Labor + Overhead + Administrative` (`CostingRules.CalculateSellingPrice`'s `wastagePercent`; `ProductCostSummary.Wastage`/`WastagePercent`/`WastageShare`). `SavedProductReader` stamps `ProductDetail.WastagePercent` on every detail it reads, so Reports, Print, the Price Simulator, composites and both servers have it; the Products screen keeps it from each `LoadCommand` for the live Costing tab (`RefreshCostingDefaults`, which reprices the open product when it changed).
        - **Added once, never at each level of a composite**: a composite's products bring their recipe cost before their wastage (`ComponentCosts` holds `SubAssemblies`), and the composite adds it on all of it, at its own category's figure, never its products', so a composite of products at their own percentages is still priced at exactly what they are together.
        - **Shown** as a **Wastage (3% of sub-assemblies)** row under the sub-assemblies on the Costing tab's breakdown (read-only: Settings owns it), the same line on a printout's costing and the Price Simulator report's, and a **Wastage Cost** column on Reports. The Price Simulator's Raw Material Cost (`ProductCostSummary.Material`) leaves it out, as it leaves labor out.
        - **A version keeps the wastage it was priced with** (`ProductVersionContent.WastagePercent`, null for one saved before there was a wastage, which prices with none), and its today figures take today's (`ProductVersionHistory.WastageNow`). It's the shop's, like a material's price, so it isn't part of a version's recipe (`IsSameRecipe`).
        - Tests whose figures are about something else call `PersistenceTestBase.WithoutWastageAsync()` (or `SetWastageAsync`) first.
      - **Price rounding** (`PriceRoundingStep`: none, 0.25, 0.50, 1, 5 or 10, `CostingRules.PriceRoundingSteps`): the selling price rounded up to the next multiple of it (`CostingRules.RoundPriceUp`; up, never down, so a rounded price still earns at least its markup), as `ProductCostSummary.RoundedSellingPrice`, a price the shop would charge.
    - Tests: `CostingRulesTests`, `CostingDefaultsPersistenceTests`, `CostingDefaultsViewModelTests`, and the screens' tests of each setting (`ProductsViewModelRefreshTests`, `ProductsViewModelTreeTests.New_files_a_product_in_the_stage_Settings_gives_a_new_one_and_follows_it_when_it_changes`, `RawMaterialsViewModelRefreshTests.A_new_material_starts_at_Settings_cost_buffer_and_an_untouched_one_follows_it_when_it_changes`, `SavedProductReaderCompositeTests`, `ProductsViewModelVersionTests`).
- **ProductVersion: a product's version history.** A version on **every save that changes a product's recipe or price**, each version's cost shown **as it was then and at today's prices**, and **view and compare, Restore and Notes**.
  - **Table `product_versions`**: `Id`, `ProductId` (Cascade: a product deleted for good takes its history; the Deleted folder keeps it), `Number` (1, 2, 3 … per product, unique with `ProductId`, `CK_ProductVersions_Number` ≥ 1), `SavedAt`, `Note` (optional, at most `ProductVersionRules.MaxNoteLength`, trimmed, blank stored as null), and `Content`, the snapshot as JSON text.
  - **A snapshot is self-contained** (`ApplicationCore/Interfaces/ProductVersionContent.cs`, written and read by source-generated JSON, `ToJson`/`FromJson`, with a `Schema` number so an old snapshot can still be read): the product's quantity required, current price, whether a composite includes its products' packaging, its costing percentages, each section (its sub-assembly's id and name, its label, whether it's the product's own, its role, piece size, lines and add-ins), the shop's VAT and wastage then, its packaging link and the lines it showed (resolved through the link, so a link changed later doesn't change the version), a composite's products with what each brought then, and **every material it uses with its costs then** (both bases, base unit and alternative units). It points at nothing, so a deleted material, sub-assembly or role leaves old versions readable. The name, description, category and stage are kept for display but aren't part of a version's recipe.
  - **Written with the save that makes it, in one transaction** (`Pricing/Versions/VersionedSaves`, over `IUnitOfWork`): `SaveProductAsync` calls `ProductRepository.SaveAsync`, reads the product's `ProductDetail` back inside the same transaction, turns it into the content (`ProductVersionSnapshot.From`) and writes it with `IProductVersionRepository.AddAsync`. A version that can't be written takes the save back with it, and the screen shows the error. `SaveSubAssemblyAsync` (the Sub-Assemblies screen's Save), `MakeProductFromAsync` (Clone and Create Variant) and `ApplyCostingAsync` (Apply Costing Defaults) work the same way.
  - **Only a change of recipe or price makes a version** (`ProductVersionRules.IsSameRecipe`, checked by `AddAsync` against the latest): its sections, lines, add-ins, piece sizes, packaging, products, costing percentages, quantity required and current price. Prices of materials don't count (that's what the today column is for), nor do the name, description or category, so a rename records nothing, nor the shop's VAT and wastage. "Changed" has one definition: `IsSameRecipe` is `ProductVersionRules.Changes` finding nothing to list, so a version never appears with an empty list of changes.
  - **The first version is the product as it was before**: a save of a product with no versions yet first records it as it stood (`Note` "Before version history began", `SavedAt` its `UpdatedAt`), priced at the costs of that moment, so there's something to go back to.
  - **A save elsewhere records the products it changes** (`ProductVersionRecorder`). Sub-Assemblies' Save, and a Products Save that edits shared lines or packaging others link, snapshot every product reading through what's saved (`CaptureAsync`, over `IProductRepository.GetProductsReadingAsync`: usages, packaging links to a set, and packaging links to a product followed recursively in one CTE) and, after the save, record a version of each one whose recipe changed (`RecordChangesAsync`, through `AddRangeAsync`: one transaction, every product's latest in one query), with a baseline first for one with no history. Notes: "{sub-assembly} changed on Sub-Assemblies", "Changed when {product} was saved". The success notice names them (`RecordedMessage`, three named, the rest counted). A Products Save captures only when it writes linked lines (`AreLinkedLinesEdited`) or packaging (`ChangedLines`, `ChangedPackagingLink`), since nothing else it writes is read by another product; a price-only Save would otherwise read every product sharing its dough, twice. Not recorded: a role change or rename (not part of a recipe), a material's cost (the Today columns), and a composite's held products' recipes (only their quantities are its recipe).
  - **A clone or a variant starts its history** with its first version, noted "Cloned from X, version N" / "Variant of X, version N" (`RecordMadeFromAsync`); the number only when the source as saved is its latest version. Its first Save then records no baseline.
  - **Figures, then and today, are worked out on read, by the code the screen prices with**: `ProductVersionSnapshot.ToDetail` rebuilds a `ProductDetail` from the content, and `SavedProductReader.Build` prices it. Then: its materials at their costs then, and its products at what they brought then. Today: the materials as they are now in their place (`Build`'s `materialsById`, the Price Simulator's way in), and each product at its recipe cost now (`ReadComponentCostsAsync`); a material deleted since keeps its cost then. Both at the screen's cost basis (buffered, or unbuffered when switched).
  - **The History tab** (the Products screen's details tab after Clone, `ProductsViewModel.HistoryTab`; a saved product only): a table of versions, newest first (Version, Saved, Note, Base Cost and Suggested Price then and today, Current Price), the note typed into the table and saved as it's left (`IProductVersionRepository.SetNoteAsync`); under it the picked version's **changes** against the one picked in **Compare With** (the version before, the product as it's saved now, or any other version, always read older to newer; `VersionComparison`, equal by value so a re-read keeps the pick), as lines such as "Dough: Bread Flour 500 g → 450 g", "Packaging: Paper Bag added, 1 pc", "Margin %: 30 → 35"; beside them **Cost Over Time**, an `SfChart` of Base Cost, Suggested Price and Current Price then, from the second version on (`ProductVersionHistory.Trend`; no current price is `NaN`, a gap); and **Restore**. Read when the tab is shown, after every Save, and for a product picked while it shows; hidden, its versions are cleared, so showing it reads them. `ProductsViewModel.LoadCommand` re-reads a showing tab, so a version recorded from Sub-Assemblies shows when Products is shown again.
  - **Restore loads a version into the form as unsaved edits**, in one undo step (`RestoreSnapshot`), so Save keeps it and Undo takes it back. It puts back the sections, packaging, products, costing percentages, quantity required, current price and whether a composite includes its products' packaging; the name, description, category and stage stay as they are. Section by section:
    - **The product's own** keeps its sub-assembly's id when the product still owns it (rewritten in place by Save); otherwise it comes back as a new section of the product's own.
    - **A linked one is linked again as it is now**: Save never writes a version's lines into a sub-assembly other products may share. When its lines have changed since, the message says so.
    - **A sub-assembly deleted since** comes back as a new section with the version's lines, which Save treats as any new section in its role.
    - **Packaging**: the link, when what it linked still exists; otherwise the lines it showed, as the product's own. A line in an alternative unit deleted since is put in base units.
    - **Refused, naming them**, while a material, role or product it needs no longer exists: nothing is changed.
    - **The section tab showing opens its form afterwards**, as showing it would, and what Save measures against moves onto that form (`RebaseSettledForm`): only the recipe, packaging, costing and price put back count as changes.
  - **Print Version, and Print while the tab shows, prints the version picked.** As Print on the Scaling tab prints the scaled recipe, `PreparePrintout` returns `VersionPrintout`: the version priced at its costs then and the screen's cost basis, titled "Almond Cheese Bread (Version 2)", dated with its save, its footer note `ProductPrintout.VersionNote`, its category and stage the product's now. The form isn't applied first, and isn't changed. With no version picked, Print says so and the Print tab doesn't open.
  - **Reports' Margin Erosion** reads each product's latest version as of a date (`IProductVersionRepository.GetLatestAsOfAsync`, one query) against its markup now.

A material's lines go when it's deleted, rather than blocking the delete, since a scenario is only a trial; one no longer bought (its source changed) is left out when the scenario opens, and the screen says which.
  - **`IPriceScenarioRepository`**: `GetAllAsync` (newest first, then by name, each with its lines, two queries), `SaveAsync(name, lines, savedAt)` (an upsert by name, ignoring case: an existing scenario keeps its name and has its lines replaced, in one transaction; `PriceScenarioRules.EnsureValid` first), `DeleteAsync`.

The two sides share the card's rows, so headings, captions and the two 200-high tables line up. `SimulatedPriceChange.ToScenarioLine` gives the typed one of Change % and New Price, and `Open(line)` types it back. ### Derived products

Some products derive from others (e.g. Special Ensaymada Small from Special Ensaymada Big, differing only in weight; or products sharing a dough but differing in toppings). Recipes are shared through links to sub-assemblies, and copied through Copy, Make a Copy and Clone:

- **Link a sub-assembly** (Add Sub-Assembly ▸ **Link an existing one**): a product uses a sub-assembly kept on the Sub-Assemblies screen, as it is, through a `ProductSubAssemblyUsage` of it. Its lines follow every change made there, and can be changed in the product too (SubAssembly, "Its lines are edited in the product"); the **piece size is the linking product's own**, so Small and Big can share a dough at 30 g and 60 g a piece. Links don't chain (only a sub-assembly on the Sub-Assemblies screen, or for a variant its source's own, can be linked), so there's nothing to cycle. **Make a Copy** or **Unlink** splits a section off.
- **Copy a sub-assembly** (**Copy an existing one**): a new section starting from another sub-assembly's lines and role, not its name. If the recipe already has that role, the form starts on the first role it doesn't. Nothing connects it to its source afterward.
- **The three ways in** are Add Sub-Assembly's drop-down items, **New sub-assembly**, **Link an existing one** and **Copy an existing one**, and a link's or copy's form is titled with the one picked ("Link an existing sub-assembly"). A new one's form has no title: in its place the **Moves to Sub-Assemblies on Save** badge shows while its role is neither product-owned nor packaging (`IsFormNewMovingToSubAssemblies`). Its picker, **Existing Sub-Assembly**, lists the Sub-Assemblies screen's first (`GetLinkableAsync`), as "Butter Glaze — Sub-Assemblies (Finishing)". A linked section's badge reads "From Sub-Assemblies" (`ProductUsageEdit.SourceNameOf`, the one place that names where a linked sub-assembly comes from), or for a variant's link to its source's own "Ensaymada Big Filling, from Ensaymada Big" (`LinkedOwner`, `LinkedFromToolTip`), and opens where it's kept (`OpenLinkedSourceCommand`: the Sub-Assemblies screen, or the source product). A new, unsaved product is offered them too: `RefreshLinkableOptions` matches `OwnerProductId is null` first, since a null owner compared with a new product's null id would otherwise count as its own.
- **Link the packaging** (`PackagingLink`, table `packaging_links`, one per product): a product's packaging reads through to a **packaging set** (`LinkedSubAssemblyId`, Restrict) or another product's packaging (`LinkedProductId`) instead of owning lines; `CK_PackagingLinks_OneTarget` requires exactly one. It resolves every line the target has.
  - **One set per sellable unit**: `PackagingLineRepository.ResolveEffectiveAsync` returns the set's lines as unsaved `PackagingLine`s of the product being resolved (`UnitId` and `QtyPerUnit` the set line's own, `AuthoredField = QtyPerUnit`, the material with its units), so the Products screen, the cost summary, Reports and an unlink's copy take them unchanged.
  - **Chains** (C's packaging linked to B's linked to A's) are resolved recursively at read time and end at a set, which links nothing; a cycle is refused when a link is made (`PackagingLinkRules.EnsureNoCycle`). One left by an edit outside the app is read as no packaging and flagged (`ProductDetail.PackagingLinkedRoundInALoop`, `PackagingLinkRules.LinkedRoundInALoopText`), which the Products screen says when it opens it; refusing the read instead would fail every product's pricing in a batch. A clone or an unlink, which copy the lines, still refuse it (`PackagingLinkRules.LoopText`). A product whose packaging another links can't be deleted until that link goes.
  - **Made in the Recipe Structure's Packaging tab, saved with Save**, so an unsaved product can link too. The Link picker offers only what the Sub-Assemblies screen keeps, packaging sets (and standalone recipes for a recipe section), never another product's packaging, which Copy still offers (`RefreshLinkableOptions`). Nothing in the app makes a new link to another product's packaging; one that exists reads through as any link does.
  - **`IProductRepository.SaveAsync` takes a `PackagingLinkDraft?`** (a closed record: `Set(SubAssemblyId)`, `OtherProduct(ProductId)`, `None` or `NewSet`; null leaves the link alone), written in the same transaction just before the lines (`PackagingLinkRepository.SetAsync`, sharing the product and set checks with `SetLinkAsync`/`SetSubAssemblyLinkAsync`). `None` only drops the link; unlike `RemoveLinkAsync` it copies nothing, since the form sends the lines it holds.
  - **Storage**: the product's packaging is its `PackagingLines` or its one `PackagingLink`, never a `SubAssembly` row, so `EnsureRecipeRole` keeps the Packaging role off a product's own sub-assemblies.
  - **Unlinking never loses data.** On the Packaging tab it's **Make a Copy** (`CopyPackagingCommand`): the lines showing become the product's own, and Save writes both the unlink and the lines (`ChangedLines` writes them whenever the product was linked when loaded, even if they match). `IPackagingLinkRepository.RemoveLinkAsync` likewise materializes the lines it shows before it removes the link.
  - The banner reads "Linked to Gift Box Set (Sub-Assemblies)". The Products `LoadCommand` refetches linked packaging's lines while the form still shows the link as saved, so a set edited on the Sub-Assemblies screen shows on return; own lines and an unsaved link choice aren't touched, since they may hold unsaved edits.
  - **Move to Sub-Assemblies on the Packaging tab**, Make a Copy's reverse. While the packaging is the product's own lines (`CanMovePackaging`), the tab's top row has **Move to Sub-Assemblies** at the far right, the same spot as a recipe section's form. `MovePackagingToSubAssembliesCommand` checks the lines (`CurrentLines`: a half-filled line, or none, is refused with the message) and sets `IsPackagingMoving`, in one undo step (`ProductFormSnapshot.IsPackagingMoving`); a "Moves to Sub-Assemblies on Save" badge takes the linked badge's place, and the lines are still typed into until Save. `ShowPackagingLink`, which every load, Delete Sub-Assembly, Make a Copy and add go through, ends it; `RestoreSnapshot` puts it back after. Save sends `PackagingLinkDraft.NewSet` with the lines, and `ProductRepository.SaveAsync` runs `PackagingLinkRepository.LinkNewSetAsync` in place of the link-then-lines pair, after the recipe: the lines become a standalone set in the Packaging role (found by its flag), named `StandaloneNameFor(product, role, null)` made unique ("Ensaymada Packaging", "… 2"), each line's quantity per sellable unit its quantity per set in the same unit and order, through `SubAssemblyRepository.SavePackagingSetAsync`, so every set check applies; the product's lines are deleted and its packaging links the set. Costs don't change. The top row keeps the button's height (`MinHeight="34"`) with the badge in it, so the table doesn't jump. Covered by `PackagingSetPersistenceTests` and `ProductsViewModelPackagingTests`.
- **Clone** (`IProductCloner.CloneAsync`, one transaction): a one-time copy of a product as saved. It **links every sub-assembly the source links**, at the same piece sizes, with the source's add-ins as its own, and **gets its own copy of each of the source's own** (named after the clone; `ProductCloner.DerivedRecipe`, each drafted `ProductsOwn`). Its packaging is copied as it shows, resolved through any link, except **a packaging set the source links directly, which stays linked**, like a recipe's sub-assemblies, since it's kept apart to be shared. It copies the quantity required, description, category, current price, costing parameters, a composite's products and whether it includes their packaging. A source with two sections in one role that can't be told apart is refused.
- **Create Variant** (`IProductCloner.CreateVariantAsync`, one transaction): a product whose recipe is **linked instead of copied**, for Ensaymada Small from Ensaymada Big. It's the Clone tab's second button, beside Clone, sharing its New Product Name.
  - **A variant links every sub-assembly the source uses**, at the source's piece sizes, with the source's add-ins on each as its own: **the source's own** (product-owned roles, or unlinked into its own) and **the ones it links** from the Sub-Assemblies screen (a dough, sponge or batter). **It has no packaging**, neither linked nor copied: it's given its own afterward, a packaging set for a Box of 8, which is what makes a variant the way to add a pack. `ProductCloner.VariantRecipe` builds the recipe; Clone and Create Variant share one core (`CreateFromAsync`), and differ only in the recipe and the packaging. The quantity required, description, category, current price and costing parameters are copied, as for Clone.
  - **Only Create Variant links another product's own.** `ProductSubAssemblyUsageRepository.SetRecipeAsync`'s `linksOthersOwn` is passed by the cloner alone. Every other save runs `SubAssemblyRules.EnsureLinkable`, except on a sub-assembly the product already links, so a variant keeps its links through its own saves, and one it drops can't be linked again. The Link picker leaves products' own out.
  - **The source can't pull one out from under a variant.** `SetRecipeAsync` refuses to drop one of the product's own that another product links (`EnsureNoneLinkedElsewhereAsync`, the Sub-Assemblies screen's message), before anything is written, and `ProductRepository.EnsureNothingLeansOnAsync` refuses deleting the product, to the Deleted folder or for good, while one of its own is linked elsewhere. Moving one to the Sub-Assemblies screen, or a role losing product-owned, releases it, and the variant's link follows.
  - **The Products screen names where it's kept.** `SubAssemblyReads` brings every sub-assembly's owner, usages included, and `ProductUsageEdit.LinkedOwner` carries it (kept through `With`, `Released`, `WithLinked`, `WithLinkedForm` and a version restore). A variant can change the linked lines as for any link, and Save writes them to the source's own.
  - Covered by `ProductVariantPersistenceTests`, the composite and Quantity Required persistence tests, and `ProductsViewModelRefreshTests.Create_Variant_makes_a_product_that_links_the_sources_own_with_no_packaging_and_shows_it`.
- **`CostingParameters`** always stay independent per product: nothing links them.

## Application Architecture

- **Repository interfaces live in `ApplicationCore`, implementations in `Infrastructure`** (`IRawMaterialRepository`/`RawMaterialRepository`, and so on), consumed by UI ViewModels through DI. Every lookup table has a repository of its own, since each is edited in the Settings dialog: `IUnitOfMeasureRepository`, `IRawMaterialCategoryRepository`, `IProductCategoryRepository` and `ISubAssemblyRoleRepository` with full CRUD, and `ICostingDefaultsRepository` for its one row. Don't bring in a generic repository just because a table is small.
- **Each operation makes its own short-lived `TinapayanRMSDbContext`.** ViewModels are DI singletons (`MainWindowViewModel`, `RawMaterialsViewModel`, …), and WPF has no per-request scope, so a context injected into them would be shared by two screens loading at once ("A second operation was started on this context instance…"). Every repository takes `IDbContextFactory<TinapayanRMSDbContext>` and creates and disposes a context per call (`await using var dbContext = await dbContextFactory.CreateDbContextAsync(cancellationToken);`), which is also safe for concurrent calls from different screens. Never inject `TinapayanRMSDbContext` directly into a repository or ViewModel.
  - **The factory is also the unit of work.** `SharedTransactionDbContextFactory` (`Infrastructure/Services`) is registered as both `IDbContextFactory<TinapayanRMSDbContext>` and `IUnitOfWork`. `RunAsync(work)` opens one connection with a Serializable transaction (`ProductVersionRepository` numbers versions under Serializable) and puts it in a static `AsyncLocal`. Every context made on that flow, by any factory instance for the same connection string, is built on that connection with `UseTransaction`, so tests' many factories join too. A repository's own transaction is begun with `BeginOrJoinTransactionAsync` (`Services/Transactions.cs`), which inside a run hands back a part whose commit and dispose do nothing. No repository rolls back by hand or catches a database error and carries on, which a shared PostgreSQL transaction couldn't survive (a failed statement aborts it).
    - **Reads inside a run go one at a time**: they share one connection. `SavedProductReader.ReadDetailsAsync`/`ReadComponentCostsAsync` and `ProductVersionRecorder`'s snapshots read in sequence. The batching that keeps the number of queries fixed however many products there are is what matters for speed (68 products: every detail read in 31 ms).
    - **`VersionedSaves`** (`Pricing/Versions`) holds the saves that record versions, each in one run: the Products Save (baseline, `ProductRepository.SaveAsync`, the product read back and its version, then the sharing products' versions), Clone and Create Variant with their first version, the Sub-Assemblies Save with its products' versions, and Apply Costing Defaults. A version that can't be recorded takes the save back with it. Pinned by `SharedTransactionDbContextFactoryTests` and `VersionedSavesTests`.
- **Startup time.** On the published app the window appears in under a second; what kept the UI thread busy was building every screen, theming and laying it out, and EF Core building its model on the first query. Three things keep it down:
  - **`PublishReadyToRun`** in the UI project (it has the `win-x64` runtime identifier ReadyToRun needs). Only `dotnet publish` uses it.
  - **A compiled EF Core model** in `Infrastructure/CompiledModels/`, made by `dotnet ef dbcontext optimize --project src/TinapayanRMS.Infrastructure --output-dir CompiledModels --namespace TinapayanRMS.Infrastructure.CompiledModels` and regenerated by the same command after every model change (rather than the `Microsoft.EntityFrameworkCore.Tasks` build step, which would regenerate it on every build). EF Core finds it through the generated `[assembly: DbContextModel]` attribute, so `Configure` has no `UseModel`, and the design-time commands still build the model from `OnModelCreating`. A stale one compiles and runs (it finds properties by name), so `CompiledModelTests` compare it with the configured model: its `ShortDefault` debug view (entities, properties, keys, relationships, indexes) and a listing of its tables, columns, store types, keys, foreign keys and indexes. They don't use the migrations differ, which needs design-time data the compiled model leaves out.
  - **Screens are made on first show** ("A tab's screen is made the first time it's shown", below).
  - The first start after a publish is still slower, since Windows reads and scans each new file once.
- **The screens' shape.** The three main screens (Raw Materials, Sub-Assemblies, Products) are a **list card** on the left (a search box, a toolbar, and the records in a folder tree, `ListTree`) beside a **header card** (the record's title, New, Save, Delete and its figures, with the fields typed in under them) over a card of **details in tabs**. The Settings dialog's tabs (Units of Measure, Material Categories, Product Categories, Roles) are the simple case: a list card and a form card. A screen's root `Grid` carries `PageBackgroundBrush` and `Margin="16"`, with an `ErrorToast` (and on the main screens a `SuccessToast`) laid over the whole Grid, taking no row of its own. A large screen is split into card `UserControl`s in a folder named after it, each inheriting the screen's DataContext.
  - **Every number column in a grid, money included, uses `controls:NumericColumn`** (`Controls/NumericColumn.cs`), never `syncfusion:GridNumericColumn` or `syncfusion:GridCurrencyColumn` directly. `NumericColumn` is a `GridNumericColumn` whose constructor sets the app's defaults: `NumberGroupSeparator=","`, `NumberGroupSizes="3"` and `HorizontalHeaderContentAlignment="Right"` (out of the box it doesn't group thousands and centres its header). A grid column is a `Freezable`, not a `FrameworkElement`, so an implicit `Style` can't carry these defaults. Set only what differs per column (`NumberDecimalDigits`); a value set in XAML still overrides a default.
  - **Money shows as a bare number** (`930.00`, not `₱930.00`), so `GridCurrencyColumn` would add nothing: its editor never opens in read-only grids, its parentheses for negatives never apply, and it doesn't group thousands by default. Money columns use 2 decimals for totals and prices, and 4 for per-unit costs (`CostPerBaseUnit`, `CostPerPiece`). A packaging line's own total (`PackagingLineRow.CostPerUnit`) counts as a total, at 2; its Unit Cost stays at 4.
  - **A column's `Width` takes pixels only** (`Width="120"`). `"*"` builds cleanly but crashes the app at startup with a `XamlParseException` ("* is not a valid value for Double"); star-size through `ColumnSizer="Star"` on the grid or on a column.
- **Grids show lines both ways, and a grid with height to spare is padded with empty rows down to its bottom edge.**
  - **`GridLinesVisibility="Both"` is set locally on the grids** (the property's default is Both, but the Windows11Light style sets Horizontal, and the app doesn't give Syncfusion controls a `Style`, which would replace the theme's). The two recipe section tables draw their Total row under the grid, so each total cell but the last has a right divider (`SectionTotalDividerStyle`, `CardBorderBrush`) carrying the grid's vertical lines through it. The ingredient pickers' pop-up grids keep their look.
  - **`CurrentCellBorderBrush="{StaticResource AccentBrush}"` and `CurrentCellBorderThickness="1"` are set on the grids too**: `SfGridBase` registers the brush with a hardcoded black default that the Windows11Light accent recolour doesn't reach. A fractional thickness such as 1.5 renders as 2 (`UseLayoutRounding` snaps it up to a whole device pixel), so only a whole-number step reads thinner.
  - **The tables lines are typed into show a row header (`ShowRowHeader="True"`)**: an arrow on the current row, a pencil while a row is edited and + on the add row. The read-only lists don't. The app's grid behaviours go by row index and `GetFirstColumnIndex`, which counts the header, so they need nothing for it.
  - **Rows are dragged into order**: `controls:GridRowReordering.IsEnabled="True"` (`Controls/GridRowReordering.cs`) is on the grids lines are typed into and saved from (Sub-Assemblies' lines and a packaging set's, the Products section form's lines, add-ins and packaging, the Packaging tab, the Components table, and the made ingredient's add-ins), not on Alternative Units or Purchase Cost Setup, whose order means nothing. The order is the ViewModel collection's, which Save writes (Domain Model: Line order), and it needs nothing else to count as a change: every form snapshot compares its lines with `SequenceEqual`, so a move is an undo step, marks the form dirty, and an undo puts the order back.
    - **It turns on the grid's own row drag** (`AllowDraggingRows`, `AllowDrop`, `RowDropIndicatorMode="Line"`), which starts from the row header or any cell not being typed into, once the mouse has moved the system drag distance, so selecting text in an open cell never drags the row. A plain click still opens the cell (`EditTrigger="OnTap"`).
    - **Each press decides whether the grid can drag** (`ArmOnLinePress`, on the grid's `PreviewMouseDown`): only a press on a line of a grid whose lines can be changed sets `AllowDraggingRows`. Once armed, `GridCell` calls `ProcessOnDragStarting` on every mouse move until the button comes up, and that logs Syncfusion telemetry each time (a new client and an HTTP post per call), so a drag that could only be refused (a read-only grid, the add row) would post on every move.
    - **Every drop is handled by the behaviour**, because the grid's own doesn't reorder anything that's saved: within one grid it moves the record in `View.Records` only, so the bound `ObservableCollection` never moves, and across grids it moves a row into any other grid whose items are the same type, which the recipe lines and add-ins are. So `Drop` is always `Handled`, and the line is moved in the collection with `ObservableCollection<T>.Move` (found by reflection, since the behaviour knows the collection as an `IList`), bracketed by the grid's `GridUndoSteps` recorder. A single Move notification, not a remove and an insert, keeps the row selected and never takes a formula-base line out of the batch for a moment, which would set off the baker's-percentage recomputation twice.
    - **The drop's `TargetRecord` is a record index in the view, not the item**, and the line grids allow sorting, so it's resolved through `View.Records[i].Data`. A sorted view is unsorted on the drop (`SortColumnDescriptions.Clear()`), so the grid shows the order that was just changed.
    - **Refused:** a drag from a read-only grid (`AllowEditing` false: a linked packaging), a drag in from another grid (`IsFromOutSideSource`, with `DragOver` handled so no drop line shows), and a drop on the add row or below it, where `ResolveToRecordIndex` finds no record. Selection is `Single`, so one line moves at a time.
  - **A line can be put in above the current one**: `controls:GridRowInserting.IsEnabled="True"` (`Controls/GridRowInserting.cs`) on Sub-Assemblies' lines, and the Products section form's lines and add-ins. It works on any grid with a `GridAddNewRow.ItemFactory`.
    - **One routed command, `GridRowInserting.InsertLine`, with a command binding on each grid.** The Insert key is the command's own gesture. The Insert Line or Insert Add-In button under each table reaches it through `CommandTarget="{Binding ElementName=…Grid}"`, and Vim's `O` (`VimAction.OpenAbove`) calls `InsertAbove` itself. The command is refused while a cell is being typed into, where Insert is the text box's own key; a button click has already ended that edit, because focus leaving the grid commits it (`GridEditCommit`).
    - **The new line is the grid's `ItemFactory` item**, as the add row's is, so it prices itself and reads its percentage against the current base. It goes in above the line the current cell is on, or at the bottom from the add row or with no current cell. The open edit is committed first (`GridEditCommit.Commit`), so a half-typed add row is added and an untouched one dropped; the current row is read before that commit, which moves the current cell. A sorted view is cleared, as a drag does. The insert is one undo step (`GridUndoSteps`).
    - **The first column (the ingredient picker) is open as the command returns**: the grid is laid out (`UpdateLayout`) so the new line has its row, the current cell is moved onto it and scrolled to, and the cell's edit begins, all before the command returns. Deferring any of it lets a key typed straight after land on the wrong line, a burst of Inserts undo each other's opens, or a grid hidden in between still open a cell; synchronous, the new cell takes every key after the Insert, so a held Insert puts in one line and `CanExecute` refuses the repeats. An insert costs a few milliseconds whatever the number of lines, since the grid only lays out the rows in view.
    - **A line left blank stays a blank line**, rather than being dropped as an untouched add row is: a drop would be a second undo step. A blank line costs nothing: `IngredientLineRow.CompleteLines` leaves it out at Save, and Undo or Remove Line takes it away. It does mark the form as changed.
    - Covered by `GridRowInsertingTests` (in an `OffscreenGrid`) and `Capital_o_types_a_new_line_put_in_above_the_current_one` in `VimKeysGridTests`.
  - **Every grid's header row fits its text.** The theme fixes `HeaderRowHeight` at 24, sized for 12px text, and the app's text is 2 larger (`BodyFontSize = 14`), so descenders were cut. `Controls/GridHeaderHeight`, registered once from `App`'s static constructor (class handlers on `SfDataGrid` for `Loaded` and `SizeChanged`), sets each grid's `HeaderRowHeight` (a local value, unless its XAML sets one) from a realized header cell's own font, padding and border: 26 today. **The header cell's font isn't the grid's** (the theme gives `GridHeaderCellControl` its `BodyTextStyle` while the grid's `FontSize` stays 12), and a grid hidden when it loads has no header cell, so it's fitted the first time it's sized, once per grid (`IsFitted`), which covers the multi-column drop-downs' lists too. **A grid whose headings wrap sets `GridHeaderHeight.Lines`**, and its header row fits that many lines. Covered by `GridHeaderHeightTests`: rendering a themed control in the test host needs `PackUriHelper.UriSchemePack` touched and an `Application` created first, or the theme's `pack://` resources throw "The URI prefix is not recognized".
  - **Keyboard focus in a grid sits on a cell, never on the whole grid.** `Controls/GridKeyboardFocus`, registered once from `App`'s static constructor (class handlers on `SfDataGrid`, so every grid gets it without XAML): a grid's `FocusVisualStyle` is null (a local value, unless its XAML sets one), so WPF draws no dotted rectangle round the grid when it takes focus by keyboard; and when the grid itself takes keyboard focus by keyboard (`InputManager.MostRecentInputDevice`, so a click is left alone), `PlaceCurrentCell` gives a grid without a current cell one in the first column: on the selected row, else the first line, else an empty table's add row (without starting a line). A row-selecting list (`NavigationMode="Row"`) only gets one on its selected row, since selecting a row there opens it in the form, which tabbing past mustn't do. Covered by `GridKeyboardFocusTests`.
  - **`controls:GridFillerRows.IsEnabled="True"`** (`Controls/GridFillerRows.cs`) pads the grids with height to fill: the Settings lists, Price History, Purchase Cost Setup, Reports, Find, the Price Simulator, the History tab and the tables lines are typed into. Not on the recipe section tables, which are sized to their rows.
    - **The empty rows are drawn, not added to the grid.** `Controls/GridFillerLayer`, a `FrameworkElement` that's never hit-tested, is put in the grid's template, in the root `Grid` that holds the `ScrollViewer` and its `VisualContainer`, across all its rows, so it's drawn and clipped with the grid and under anything over it on the screen (an error toast, the Vim hints). Live rows (`GridUnBoundRow`s) would be selected, edited, given the current cell and frozen as footers, each needing a guard, and crashed the app; drawn, the grid never knows they're there, and a click or drop below the rows lands on the grid's own empty space.
    - **Where:** the rows' space is measured on the row scroll axis (`ScrollRows` `RenderSize` against `TotalExtent`), and the columns come from the column scroll axis's visible lines (`ScrollColumns.GetVisibleLines()`: `Origin`/`Corner` where a column's cells are, `ClippedOrigin`/`ClippedCorner` what's shown), so the lines follow column widths, the row header and horizontal scrolling. **Down to the grid's bottom edge, the last row cut off by it**: `FillerRowCount` rounds up, less a hair for fractional layout, and the layer's viewport clip cuts the last row as the grid cuts its own.
    - **When:** on the grid's `LayoutUpdated` while it's loaded and shown (`IsVisible`), `GridFillerLayer` works out a `FillerLayout` and, only when it differs from the last, replaces its `DrawingGroup`'s content. That redraws without `InvalidateVisual`, so no layout pass follows, and the padding changes in the same layout pass as the grid: records added or removed, a group expanded (`ExpandAllGroup` raises nothing), the window resized. A new template (a theme change) leaves the layer in the old one, so it's checked and re-inserted each time. `LayoutUpdated` is raised after every layout pass in the app, so a grid loaded but not shown skips the work; showing it again is a layout pass, which brings it up to date.
    - **What it draws matches the theme's cells pixel for pixel.** A theme cell is a `Border` with `BorderThickness` 0,0,1,1 in `BorderAlt`, which is also the grid's own `BorderBrush`, and `SnapsToDevicePixels`, which gives the cell snapping guidelines at its own bounds only. So each empty cell is drawn as that border's shape: a strip down its right side and one along its bottom that stops short of it, under a `GuidelineSet` of that cell's own edges, so at 125% a line is a full pixel and a faint quarter, as the real cells' are. One guideline set for the whole drawing would snap some lines 2 px wide; whole-row and whole-column rectangles would darken the crossings (the brush is see-through); a clip per column at a fractional edge would shave the line it cut. A column is clipped only on a side scrolled under the row header, never on the grid's own edge, which the viewport's clip already takes.
    - **Tests.** `GridFillerRowsDrawingTests` renders a themed grid padded with drawn rows beside the same grid holding that many blank records, at 96 and 120 dpi, with and without a row header, scrolled sideways under it, and under an add row, and compares them pixel by pixel (allowing 2 levels in 255 where the last column's line meets the right edge at 125%, and 4 in the pixel row the bottom edge cuts). `GridFillerRowsLayoutTests` checks the padding follows lines added and removed, and a resize, in the same layout pass, and that a hidden grid's padding waits until it's shown. `GridFillerRowsGroupedTests` and `GridFillerRowsCurrentCellTests` check a grouped grid's rows and the current cell are never disturbed.
  - **A current cell on the add row stays on it when the lines above it go** (`UntouchedAddRowSelectionController.PutCurrentCellBackOnAddRow` in `Controls/GridAddNewRow.cs`). When the last lines go while the add row's cell is current (Ctrl+Z back to no lines, another material with none), SfDataGrid moves the add row up but leaves `CurrentRowColumnIndex` where the add row was: the add row keeps its outline, but the next key moves from the stale index, and Left, Right and Tab each left no cell current. `ProcessSourceCollectionChanged` notes whether the current cell was on the add row and, one `Background` dispatcher pass later, moves it back if it's now past the add row; until the add row is laid out the grid can't find its cell. Every grid with an add row sets `GridAddNewRow.DropWhenUntouched`, so every one has the fix. Covered by `GridAddNewRowCurrentCellTests`.
  - **Grid tests run in a real window**: `Fixtures/OffscreenGrid` shows an `SfDataGrid` off-screen on an STA thread of its own and pumps the dispatcher, so an exception the grid throws from a dispatcher callback surfaces in the test as it would close the app. It needs `SYNCFUSION_LICENSE_KEY` (an unlicensed control shows a dialog) and skips without it. **Every test class that builds a real `SfDataGrid` or `SfTreeGrid`, themed ones included, goes in one xUnit collection, `OffscreenGridCollection`, so they run one at a time.** Side by side, their windows competed for focus and current-cell tests failed at random, and Syncfusion keeps whether the current cell has been validated in one static flag for the whole process (`ValidationHelper.IsCurrentCellValidated`): a themed grid beside an edit could set it, so the edit's commit skipped the validation that writes an Explicit binding's value. The app has one UI thread and one edit at a time, so it never meets this.
  - **When the app closes on an exception from a grid**, the Windows Application event log (`.NET Runtime`, event 1026) keeps the full stack and the app's log the warnings before it; fuzzing a real `SfDataGrid` off-screen (random sequences of what the screens do to a grid, with the app's behaviours attached, until one throws) is how such a crash is reproduced, and the sequence found becomes the test.
- **Classes are sealed unless they're a base class** (`AppWindow` is the base of the windows), and hot lookups use `FrozenDictionary` (`BackupRules.Suffixes`, `StandardUnitRules.ByName`, looked up by span through `GetAlternateLookup` so a trimmed unit name isn't allocated). LINQ is left alone where it costs nothing measurable.
- **A purchased material can be costed at a brand picked instead of the dearest.** `RawMaterial.PreferredBrand` (nullable, 100 characters), kept trimmed for a purchased material and null for any other (`RawMaterialRepository.StoredPreferredBrand`), is **Cost From** on the Purchase Cost Setup card (`EditingPreferredBrand`, `CostFrom`/`CostFromOptions`, `ViewModels/CostFromOption`; in the form snapshot, so Undo takes it back). `RawMaterialRules.FindCostBrandPrice` picks the price the cost comes from: the dearest per base unit of that brand's prices (matched as brands are), else the dearest of all, which is also the fallback when the brand picked has no price left. It's the one rule `ApplyBrandPrices` (so the Save, `RawMaterialBrandPriceRepository.SetAsync` and a unit's new multiplier), the price history entry `RepriceAsync` logs, `PurchaseUnit.Of` (the Price Simulator's current price, the Recipe API's `/materials`) and the form's live figures (`CostBrandIndex`) all use, so nothing downstream of `CostPerBaseUnit` changes: the cascade starts from it. The Raw Materials Save always sends a purchased material's brand prices, so a change of Cost From alone reprices it and cascades. **There's no average**: price history, the simulator's current price and the purchase unit each need the one brand price the cost comes from. Reports' Cost Buffers column is **Brand Cost**. `RestoreSnapshot` raises `TypedCostBufferPercent`, so an Undo puts the Cost Buffer % box back too.
- **Find, Ctrl+K, looks up any record by name from anywhere.** The title bar's magnifier (before Back) or Ctrl+K opens `Views/QuickFindWindow`, a modal dialog over `ViewModels/QuickFindViewModel`: the names of every raw material, standalone sub-assembly and undeleted product, read afresh each time it opens, matched word by word ignoring case and accents, best first (`QuickFindViewModel.Match`), at most 50, with each record's kind and category or role. Enter or a double-click opens the pick on its own screen through `MainWindow.OpenOnAsync`, as the links between screens do, so the screen left asks about its unsaved changes first. Names only, not categories or descriptions; product-owned sub-assemblies aren't listed (they open with their product). The Vim keys see a text box, so the dialog types in Insert, and Esc closes it from Normal. Tests: `QuickFindViewModelTests`.
- **Automatic backups are checked every hour and can be copied to a second folder.** `ViewModels/AutomaticBackups` takes the day's backup if it's due (`IDatabaseBackups.BackUpDailyIfDueAsync`) when the window shows and on an hourly `DispatcherTimer` in `App` (`CheckEvery`), so a copy left open over midnight takes the next day's. With a second folder chosen (Settings → Database → Also Copy To, `OpenFolderDialog`; kept per Windows user under `backup-copy-folder` in the view-state file), each new automatic backup is copied there (`CopyToAsync`) and that folder's automatic backups beyond the newest 14 are deleted (`BackupRules.AutomaticToDelete` over the files `BackupRules.TryParse` names; nothing else there is touched). Choosing the folder copies the newest automatic backup at once. `DatabaseBackupsViewModel` takes the service as an optional last parameter. Tests: `AutomaticBackupsTests`, with a stand-in `IDatabaseBackups` writing files (taking a real backup is `DatabaseBackupsTests`').
- **A backup can't hang, pass for a whole one, or fail unnoticed.**
  - `PostgresTools.RunAsync` gives every run `--no-password` and a timeout (`DefaultTimeout`, half an hour, then `TimeoutException`). With no password available, `pg_dump` would wait at a prompt on a console nobody can see, for ever, holding `DatabaseBackups._turn`, so Back Up Now and Restore would wait behind it. `--no-password` goes first, since `pg_restore`'s file comes last and older tools stop reading options there.
  - `pg_dump` makes its file before it connects, so a run cut short would leave a file under the backup's own name, counted as the day's backup. It writes `<name>.backup.partial` (`BackupRules.PartialSuffix`), named by `File.Move` once it has finished. `List` only matches `*.backup`, so a partial file is never listed or counted; `FreePath` won't reuse its name; and `DeleteAbandonedPartials` removes one over a day old (`PartialAbandonedAfter`, longer than a tool may run, so it's never one another copy of the app is writing). `CopyAsync` does the same, flushed to disk first, so a USB stick pulled out part-way leaves the file it would have replaced as it was.
  - **What went wrong is kept**: a failed copy to the second folder or a failed automatic backup is logged, kept in the view-state file (`backup-problem`, `backup-copy-problem`) so a restart can't make backups look fine, and shown in amber on the Database tab (`BackupProblemText`, `CopyProblemText`); the backup itself still stands when only the copy failed. `OverdueWarningAsync` also says so in a message, once a run, but only when the last automatic backup failed and the newest backup of this database is three days old or more (`BackupRules.Newest`, which leaves out one copied in, since its name dates when it arrived; `IsOverdue`, `OverdueAfter`): a single failure may well put itself right at the next hourly check.
  - Tests: `DatabaseBackupsTests` (a real `pg_dump` with no password, and one blocked by a table lock until its timeout), `PostgresToolsTests`, `AutomaticBackupsTests`, `BackupRulesTests`.
- **A form with unsaved changes is never left without asking**: Save, Don't Save or Cancel, with Print exempt, since it shows the unsaved edits by design.
  - **The question.** `ViewModelBase.ConfirmUnsavedChanges` (`Interaction<string, UnsavedChangesAnswer>`), answered by `RegisterNativeMessageBoxHandler` with a Yes / No / Cancel `MessageBox` ("Save the changes to Pandesal?"). `AskAboutUnsavedChangesAsync` asks only while `History.IsDirty`, turns away a second question while one is up, and reads a Save as done when `History.IsDirty` is false after `SaveCommand`, so a refused Save keeps the user on the form with its error. Whatever fails on the way (Don't Save reading the record back with the database down) shows on the form, which isn't left: whoever's asking is on the way to another screen and has no notice of its own (`LoadFailureTests`).
  - **Each screen asks itself** (`IUnsavedChangesScreen`, on `ProductsViewModel`, `RawMaterialsViewModel` and `SubAssembliesViewModel`) before its form shows another record: a row picked in the list (`TreeSelectionChanged` hands it to `PickAfterAskingAsync`, which yields so the tree finishes its change, puts the list back on the record showing, then asks), New and the list's New … Here, `:e`, the `Open*Async` methods the links use, and on Products Clone, Create Variant, Restore from the Deleted folder and Sub-Assemblies' New Product (`StartNewProductFromAsync`). Don't Save there needs no undoing: the next record replaces the form. Sub-Assemblies' Copy doesn't ask, since the copy holds the edits.

Print's `NavigationScreen` has Products' form, so moving between those two asks nothing. `TabControlExt` has no selection change to cancel, so `TurnBackToUnsaved` selects the tab left again inside `SelectionChanged` (under `_isTurningBack`, recording and loading nothing), asks on the dispatcher, and shows the tab picked once the changes are saved or thrown away; Don't Save then reverts the screen (`ResolveUnsavedChangesAsync(revert: true)`: Products' Revert without its confirmation, Raw Materials re-reading the material, Sub-Assemblies re-reading its lines), so the edits aren't there to come back to. A form answered for while closing isn't asked about again until that close ends: Don't Save leaves it unsaved for the app to close over.

The screens' own (`_ = RunSafelyAsync(...)` for a list pick and `:e`, and `CommitCategoryTextAsync`) show it in their error notices.

- **A tab keeps its view state while the app runs, and still picks up changes made on other tabs.** Nothing of it is saved to disk but the lists' closed folders (`FolderMemory`).
  - **Tab content stays loaded.** `MainTabControl` has `IsDisableUnloadTabItemExtContent="True"`; by default `TabControlExt` unloads a tab's content on every switch. So scroll position, sorting, sub-tabs, expanders, focus and typed text survive a switch without any code.
  - **A tab's screen is made the first time it's shown.** `MainWindow` holds a factory per tab (`_screenFactories`) and `CreateScreen` runs it from `MainTabControl.SelectionChanged`. That's in time: `TabControlExt.OnSelectionChanged` raises the event before its `UpdateSelectedItem` makes the content presenter for the selected tab, which it finds by the tab's `Content`; a presenter made while the content was still null would stay in the panel, empty, beside the one made later. The control also does that from `LayoutUpdated` and its generator's status change, before any `SelectionChanged`, so the first open tab's screen is made in the constructor. Nothing reaches a view before its tab shows: each view's interaction handlers and command subscriptions serve only its own screen, `ProductPrintView` reads `PrintSet` through `WhenAnyValue`, which hands it the current set on subscribing, and a link from another screen calls the target ViewModel's `Open*` and then shows the tab.

  - **Every `LoadCommand` is a fetch-then-merge, never a clear-and-reload**, since clearing a list loses the selected row, picker choices and unsaved rows.
    1. All `await`s finish first.
    2. The ids of the selected row, every picker and the lookup-panel selection are recorded. A ComboBoxAdv can clear its own `SelectedItem` when its item is replaced mid-merge, so the ids must be read before merging.
    3. The lists are merged with `CollectionMerge.MergeFrom`, and each selection and picker is re-pointed by id.
  - **`CollectionMerge`** (`ViewModels/CollectionMerge.cs`) keeps the existing object for every row whose values didn't change, which is what a grid's selection and scroll and a picker's `SelectedItem` are tied to. A `SourceCache` merge uses DynamicData's `EditDiff`; an `ObservableCollection` is synced in place, by a key of any type, rows sharing a key matched in order. `HasSameValues` compares scalar properties plus those of referenced entities one level deep (so a renamed category counts as a change to an ingredient showing it). A collection the row owns (a raw material's `Units`) counts as part of the row: its elements are compared in order, so an added unit, or a unit of measure renamed in Settings, replaces the row. A screen whose selected row is replaced that way rebuilds the unit rows and pickers derived from it, keeping picks by id.
  - **Re-pointing a selection at its refreshed copy must not reload the form or throw away unsaved edits.** On the three main screens a pick is the selection setter's alone (`_picks`, and the Products form's `ModePicks`, `RolePicks`, `SourcePicks` and `LinkTargetPicks`), and a load re-points quietly (`RepointSelection`, `ShowRole`, `ShowSource`, `ShowType`, `ShowSubAssembly`), so nothing reacts to it (the developer manual's "ViewModels"). The Settings screens' selection subscriptions still skip while a merge runs (`ApplyRefresh`, `IsRefreshing`). `ReportsViewModel` has no selection to re-point: its Load replaces the summaries outright.
  - **Products** also rebuilds its unsaved rows with the refreshed sub-assemblies, materials and units, keeping each row's numbers, so costs changed on other tabs reach the recipe sections and the cost summary (`RefreshRecipeRows`): a section of the product's own keeps its unsaved lines and is only repriced; a linked section is refetched (`ISubAssemblyRepository.GetByIdsAsync` and its lines, one query each), since the Sub-Assemblies screen may have changed its lines, name or role, and is rebuilt only when it changed (`CollectionMerge.HasSameValues`); each keeps its own piece size, and the sections are re-sorted if a role or name moved one. Who links the product's own sub-assemblies and its packaging link are refreshed too.
  - **Save, Delete and the lookup panels call the same `LoadCommand`**, so an existing record stays selected after saving, and renaming a category or role updates the list.
  - Covered by `CollectionMergeTests`, `ScreenLoadsTests`, and the screens' refresh tests, which build the ViewModels on real repositories.
- **A drop-down cell writes its pick when the edit commits, never as it's typed.** `AutoCompleteDropDownRenderer.OnInitializeEditElement` makes the column's `UpdateTrigger` Explicit before the base builds the edit binding, so Syncfusion's `CreateEditBindingBase` keeps it and the grid pushes the value only in the commit's validation (`renderer.UpdateSource`, when it changed), never on Esc. `UpdateSource` skips the push when the box holds text that names nothing, so retyping a line's ingredient as text that matches none leaves the line as it was; emptied text still clears it. With the default trigger the control's `SelectedValue` would push each change, and text matching nothing (which clears the pick, `AllowNullInput`) would empty the line as it was typed; Vim's Esc commits a cell (`VimKeys.Escape` → `GridEditCommit.Commit`), so the commit has to be the guard. A row that prices itself as its ingredient is picked does so as the cell's edit ends. Covered by `GridAddNewRowTabTests`.

Left to the grid, Tab only ended the cell's edit, so the row stayed an add row with its values in. An untouched add row is left to the grid, so Tab still leaves the table. It's on every grid with `DropWhenUntouched`, the app's line tables, and a line row needs a parameterless constructor for `GridAddNewRow.IsUntouched` to tell an untouched add row from a typed one. Covered by `GridAddNewRowTabTests`.

Reports has no record.

- **The Sub-Assemblies screen**: its design notes are in **[docs/plan/sub-assemblies-screen.md](docs/plan/sub-assemblies-screen.md)**.
- **A "replace-all" child collection editor** (every `SetLinesAsync`, `ProductSubAssemblyUsageRepository.SetRecipeAsync`): the UI builds up an in-memory list of lines and one Save sends the *whole* list, and the repository deletes the parent's rows and inserts the new set, then saves once. Simpler and less error-prone than diffing an edited collection against the database, and how a person edits a recipe (the whole line list at once). **Every check runs before anything is deleted** (the lines, and every record they refer to), so a refused set leaves the old one untouched. **Delete the old rows with `ExecuteDeleteAsync`**, not `ToListAsync` + `RemoveRange`: every row is discarded, never mutated first, so loading them buys nothing but a round trip. It runs at once, so call it before the `AddRange`/`SaveChangesAsync` that follows. **The set a method replaces must match what the UI edits as one unit**: a product's recipe is edited whole, so `SetRecipeAsync(dbContext, productId, RecipeDraft)` (called by `ProductRepository.SaveAsync` and `ProductCloner`, inside their transactions) replaces all of a product's usages, and adds, updates, relines or deletes its own sub-assemblies to match: the usages go, then the dropped sub-assemblies (their lines cascade), then kept ones are updated before new ones are added (so a new one can take a name a kept one gave up), each relined through `SubAssemblyLineRepository.SetLinesAsync`.
- **A query that needs only the latest row of a growing table asks for that row** (`OrderByDescending(…).FirstOrDefaultAsync()` over an index), never loads the table to pick it in C#.
- **What can be worked out on read isn't stored.** A usage stores only its typed figure; its yield, its cost per piece, a sub-assembly's batch weight and cost, a packaging line's cost and a product's cost and price are `SubAssemblyRules`/`ProductRules`/`CostingRules` functions called fresh, so nothing has to be kept in step. Only a raw material's costs are stored, because a made ingredient's buffered cost isn't a multiple of its true cost (Reactive Costing Cascade).
- **Cost-plus pricing, not gross margin on price** (`CostingRules.CalculateSellingPrice`): `BaseCost = SubAssemblyCost + Wastage + PackagingCost + Labor + Overhead + Administrative`, where wastage, labor, overhead and administrative are each their percentage of `SubAssemblyCost`, the sub-assemblies alone, not the packaging. That's why `CalculateSellingPrice` takes the sub-assembly cost and the packaging cost as **two parameters** rather than one material cost: only the first is the base for the percentages, and both go into the base cost. It takes the percentages and works the pesos out itself, so every caller prices the same way. `PreVatPrice = BaseCost × (1 + Margin%/100)`, `SellingPrice = PreVatPrice × (1 + VAT%/100)`: separate steps, never folded into one formula, so the shop owner can check each by hand. `PercentOf(part, whole)` (0 when the whole is 0) serves every "% of the price" on the Products screen and changes no price. Gross-margin pricing (margin as a % of the *final* price, `price = cost / (1 − margin%)`) would be a different, explicitly chosen mode: don't swap the maths in `CalculateSellingPrice`.
- **An in-memory reciprocal (`1m / 6m`) is rounded to 4 places on its round trip through a `numeric(18,4)` column**: `PackagingLine`'s two quantities are exact reciprocals in `ProductRules.ReconcileReciprocal`, but the column stores `0.1666666…` as `0.1667`. Harmless at money scale, but a test asserting a reciprocal that has been through the database must assert the rounded value.
- **A link that reads through to another record resolves recursively at read time, with a visited-set guard, rather than copying data on write** (`PackagingLineRepository.ResolveEffectiveAsync`): it follows a product's `PackagingLink` chain to whatever holds the lines, and returns those. The write path refuses a cycle (`PackagingLinkRules.EnsureNoCycle`), and the read carries its own `HashSet<int>` of visited ids, since an edit outside the app could still leave one. **Unlinking materializes what it shows into owned rows before removing the link** (`PackagingLinkRepository.RemoveLinkAsync`): read the effective lines while the link still resolves, delete the link, *then* write the rows, so a product never shows less than it did a moment before.
- **`ObservableAsPropertyHelper` (`ToProperty`) and `this.RaisePropertyChanged(nameof(...))` on the same property don't mix**: raising an OAPH-backed property doesn't recompute it, so a bound control reads back whatever the pipeline last pushed. Use `ToProperty` only when every input is itself an observable property; when the real driver is an imperatively changed collection, use a plain property and an explicit recompute.
- **A value that can never be typed is shown in a `TextBlock`, not a read-only text box.** WPF connects every `TextBox` (and so every `SfTextBoxExt`, `DoubleTextBox`, …) to Windows' Text Services Framework after its first layout, whatever its `Focusable` or `IsReadOnly`, with no per-control opt-out, and each change of its text then waits on text services through COM (`TextStore.RequestLock`), for as long as the input methods, touch keyboard or assistive tools active take: a read-only box redrawn on every pick cost the Products screen a large share of its redraw, and likely the freezes seen on the user's own machine. A box that is only *sometimes* read-only stays a text box, greyed (below).
- **A read-only number box greys its text**: `controls:ReadOnlyText.IsGreyed`, bound to the same flag as the box's `IsReadOnly` (or `"True"` for one that always is), paints the text in `ReadOnlyForegroundBrush`, so a value edited elsewhere doesn't look typeable. Used by Linked Cost's inherited Cost Buffer %, and Purchase Cost Setup's Quantity per Purchase Unit (read-only for the base unit and a saved alternative unit, whose multiplier is edited in Alternative Units) and Cost Buffer ₱ (read-only until a price above 0 is entered). A `DoubleTextBox` never draws its text with `Foreground`: a non-zero value uses `PositiveForeground`, and 0 uses `ZeroColor` once `ApplyZeroColor` is on, so those three are set, and turning it off **clears** them, which returns the theme's own colour exactly.
- **Picking another record swaps its details in one pass, with nothing empty drawn between, and a quick second pick never mixes two records' details.**
  - **Products**: picking another product only sets `AreDetailsReady` to false and leaves the previous product's details showing; `LoadProductDetailAsync` clears them (`ClearDetailsForAnother`) and applies the new ones in the same dispatcher turn, then sets it back. **The recipe's tabs are taken over in place** (`ClearDetailsForAnother(keepRecipeTabs: true)`, and `ReplaceUsages` replaces the sections index for index, adding or removing only the difference), since `TabControlExt` builds a whole `TabItemExt`, template and all, for every tab added; the form is closed first, so no tab carries the previous product's form over, and the recipe opens on its first tab. Picking none (New) clears at once; a read that fails clears everything (`keepRecipeTabs: false`) rather than leave the previous product's details under the new name.
  - **Raw Materials**: one `LoadDetailsAsync` reads a material's price history, brand prices and BOM together on the thread pool, a newer pick cancels it (`LoadLatest`), and `ShowDetails` replaces the grids in one pass without clearing them first. Save sends every brand row, so a mix of two materials' brand prices would write one material's prices onto the other.
  - **While `AreDetailsReady` is false** (a fraction of a second) the details aren't the form's: the details tabs ignore the mouse (`IsHitTestVisible`, no visual change), and Save returns without saving, since it would write the previous record's details under the picked one's id. Save has no `canExecute` for it on purpose: the button would grey for that moment on every pick. A new record's first Save isn't another record: the reload sets the detail id before selecting it.
  - Tests: `Picking_another_product_keeps_the_previous_details_until_its_own_arrive_and_Save_waits_for_them`, `Picking_another_product_keeps_the_recipe_tabs_and_opens_the_form_on_its_first_section`, `A_second_pick_before_the_first_ones_details_arrive_shows_only_its_own`, `Picking_another_material_keeps_the_previous_details_until_its_own_arrive_and_Save_waits_for_them`.

Close any copy the user has open first. What driving it takes:
  - **Make the script per-monitor DPI aware first** (`SetThreadDpiAwarenessContext(-4)`, per-monitor v2): the monitors differ in scale, and a DPI-unaware script gets scaled window rects and captures, and WPF resizes a window moved onto the other monitor. The process call fails once the host (PowerShell) is already system-aware, so it's the thread's. Set the size again once the window is on the secondary monitor.
  - **Bringing the window to front needs `AttachThreadInput` around `SetForegroundWindow`**, in the same tool call as the click that follows, then detach; check with `WindowFromPoint` before clicking. Even that can't win against an app the user is using, which keeps taking focus back: then stop, since the user is busy on that monitor. Never send keys before the app's window is found, or they go to whatever is in front.
  - **`PrintWindow`, not `CopyFromScreen`**, captures the app's window whatever is on top of it. `SfDataGrid` sometimes renders only its first columns in a `PrintWindow` capture taken right after a load or a tab switch, a capture-timing artefact, not a binding fault.
  - **Syncfusion's inputs need real input.** UI Automation's `ValuePattern.SetValue` sets a `DoubleTextBox`'s text without committing it to the bound property: click into it, send real keystrokes (`keybd_event`). `ComboBoxAdv` items expose no SelectionItem pattern and carry no text until the drop-down opens (a separate window, found under the desktop root by the app's process id): open it with a real click near its right edge, then click the item; with the item's position known, Down presses pick it. `ButtonAdv` has no Invoke pattern, and a `WM_LBUTTONDOWN` sent to its window doesn't click it either, so buttons need real clicks. Look labels up inside the panel being filled, since a grid header can share a form label's text, and don't Tab out of a number box into an editable picker, whose drop-down then swallows the next click.
- **The Raw Materials screen (`RawMaterialsView`/`RawMaterialsViewModel`)**: the list beside the selected material's cards. Its design notes are in **[docs/plan/raw-materials-screen.md](docs/plan/raw-materials-screen.md)**.
- **One Save writes the whole material.**
  - **The screen edits everything in memory.**
    - Alternative units are rows over the form's own copies of the units (Id 0 until saved). Save checks them first (`EnsureValidUnitRows`): every row has a unit ("Pick a unit for every alternative unit, or remove the empty row.") and a positive multiplier (naming Quantity per Purchase Unit for a unit added there, else Alternative Units), then `RawMaterialUnitValidator`, not the base unit, not already listed. Remove only drops the row.
    - The purchase unit choices (`PurchaseUnitOptions`, `PurchaseUnitChoice` records keyed by unit of measure id, `0` for the base unit) are the base unit and every unit of measure, and `BaseUnitName`/`BaseUnitAbbreviation` follow the form's type and base unit, so a new packaging material shows its own unit before it's saved.     - **An alternative unit can also be added from Purchase Cost Setup.** The unit cell lists every unit of measure by name (a packaging material's base unit and a unit named like an ingredient's gram left out), and picking one the form doesn't have adds it as a row straight away. The row's Qty per Purchase Unit is then its multiplier: typeable only for a unit not saved yet (`BrandPriceRow.CanTypeQuantity`, through `controls:GridCellEditing.AllowWhen`), read-only for the base unit and saved units, whose multiplier is corrected in the Alternative Units grid, since that reprices. A packaging material's unit picked this way and then made its base unit moves its rows onto the base unit and takes the added row away again (`MoveBrandRowsOntoTheBaseUnit`). A unit added that way stays only while a brand row is in it (`DropUnusedAddedUnits`), so trying units out leaves nothing behind. Save refuses one whose quantity is still empty. The grid's add row edits the screen's own row (`NewBrandPriceRow`, through `controls:GridAddNewRow.ItemFactory`), which talks to the screen through `IBrandPriceRowHost`: a unit picked there is added before the row is committed, and its buffered price follows the buffer.
    - The cards follow the form, not the selection: Purchase Cost Setup follows the editing source, the Recipe card (`IsEditingMade`) and the Linked Cost card (`IsEditingLinked`), so a new material shows every card before its first Save.   - **What Save sends** to `IRawMaterialRepository.SaveAsync(material, units, brandPrices, addIns)`:
    - An edit still open in a grid is committed when focus leaves it (`controls:GridEditCommit.OnFocusLeave`), so clicking Save includes it.
    - `units` is the complete list.
    - For a purchased material, every brand row (a row left entirely blank is skipped), each naming its unit by unit of measure, since a unit added in the same save has no id yet. A row missing its unit or price, in a unit the form doesn't have, or repeating a brand in the same unit is refused first. `null` for any other material, which leaves brand prices alone.
    - A made ingredient's add-ins only when they differ from the ones last loaded; untouched add-ins aren't replaced.
    - Afterwards `LoadCommand` runs, then a fresh copy of the material is picked, so the form reloads what was saved: units with ids, the brand prices, the price history and the BOM.
  - **How it saves: one context and one transaction.** Every step goes through the `internal static` write methods the single-purpose repository methods share: `RawMaterialRepository.AddAsync`/`UpdateAsync`, `RawMaterialUnitRepository.AddAsync`/`UpdateAsync`/`DeleteAsync`, `RawMaterialBrandPriceRepository.RemoveAllAsync`/`AddAllAsync`/`RepriceAsync` and the add-ins' write. Each takes the caller's `TinapayanRMSDbContext`, saves to it, and says whether the cost cascade must run. The order: the material; the old brand prices go (so a unit only they were in can be removed); its units, removed first, then updated, then added (so a removed unit of measure can come back as a new row); the new brand prices, then the reprice, compared with the cost from before the save so at most one price is logged; the add-ins. Each step saves as it goes, so the next step's checks see what it wrote. The cascade runs once, at the end, on the same context and transaction, so a refusal anywhere rolls all of it back. The caller's entities are only read, so a rolled-back save never leaves an id on them. `RawMaterialSavePersistenceTests` covers the whole save.
  - **Refreshes keep unsaved units.** `LoadCommand` points each row at its refreshed unit of measure (so a rename in Settings shows) instead of rebuilding the rows from the refreshed material. Delete Price stays immediate and reloads only the price history, where reloading the material would drop unsaved edits; it changes no cost, so nothing else reloads.

A change that moves data is tried on a restored copy of the dev database (a backup from Settings → Database, restored into a scratch database) before it's applied to the real one. After adding a migration, run `dotnet ef migrations has-pending-model-changes`, regenerate the compiled model, and rebuild Infrastructure before `database update --no-build`, since a build from before `migrations add` doesn't contain the new migration.
  - **A raw material's stored costs are `numeric(28,20)`** (`HasPrecision` in `RawMaterialConfiguration`), so a buffered cost typed per bag or kilo is kept as typed once divided down to the base unit. 28 digits in all is what a .NET `decimal` holds, so any stored value reads back without overflowing; a larger scale, such as `numeric(38,28)`, would overflow on reading anything from ₱8 up. Every other cost is `numeric(18,4)`, the convention `ConfigureConventions` sets.
- **After a command changes a row's computed fields, refresh that row and re-point the selection at it**: re-fetch it (`GetByIdAsync`), update the list (`_cache.AddOrUpdate(refreshed)`), and set the `Selected*` property to the refreshed instance. `SfDataGrid` tracks selection by reference, so a selection left on the stale object silently desyncs the form from what the grid shows.
- **`UpdateAsync` applies fields one by one onto a tracked, freshly loaded entity, never `dbContext.Set<T>().Update(incoming)` on an object the caller built.** `Update()` marks *every* property Modified, so a material built from the form's fields (which never sets the stored costs, since the server owns them) would overwrite them on every rename. Load the tracked entity by id, copy across only the user-editable fields, leave every computed field alone, then `SaveChangesAsync`. If an edited field feeds a stored figure, the same method works it out again: an alternative unit's multiplier feeds the cost, which `RawMaterialUnitRepository.UpdateAsync` reprices.

Where a refusal should name what's in the way, the repository looks first and refuses with a `BusinessRuleException` before the key would (`RawMaterialRules.EnsureNotInUse`, the product and sub-assembly delete checks).

A Save command runs the validator first and, on failure, sets `ErrorMessage` and returns before calling the repository, whose own checks stay the last line of defence. A replace-all set of lines gets no validator of its own: that cross-row validation lives in the rules class the repository calls.

A load cancelled by a newer value isn't a failure, whatever it threw on its way out.

## Reactive Costing Cascade

The core design problem is that a price change on any ingredient or packaging material must ripple up through everything that uses it, automatically. The cascade has two starting points, one per raw material type, and both end at the product:

```
Price entry added for an ingredient
  → purchased ingredient's CostPerBaseUnit (per gram) recomputed
    → every made ingredient that uses it recomputed, up every level of the BOM tree (its sub-assembly's lines and its add-ins)
  ─ stored above this line, worked out on read below it ─
      → every sub-assembly using a changed ingredient, from its lines
        → every ProductSubAssemblyUsage of that sub-assembly ─────┐
                                                                  ├→ Product total cost
Price entry added for a packaging material                        │    → Product margin / selling price
  → packaging material's CostPerBaseUnit recomputed (stored)      │
    → every PackagingLine using it ───────────────────────────────┘
```

Only raw materials' costs are stored: a purchased one's from its prices, and a made or linked one's by the cascade. Everything above them, a sub-assembly's batch weight and cost included since 2026-11-05, is worked out from its lines whenever it's read, so the one propagator ends at the ingredients.

**Quantity Required hangs off the end of that cascade** (2026-09-20), and adds nothing to it. It is a plain multiplier applied where the branches meet — `CalculateMaterialCost` multiplies the usages' cost per piece by it and adds the packaging once — so a product that sells in boxes of 8 moves whenever its piece does, with no propagator of its own. Nothing about it is stored derived, and no write path has to know it exists.

This replaced packs (2026-09-18 to 2026-09-20), which hung off the same end: a pack was priced from the product's material cost per piece by `PackMaterialCost = materialCostPerPiece × PiecesPerPack + that pack's own line costs`. The one cost that was a pack's alone was its own packaging lines (`PackagingLine.PackId` set), which rode the packaging branch exactly as the per-piece lines did, and `PackagingLineRepository.GetEffectiveForProductAsync` returned `PackId is null` lines only to keep the per-piece figure honest. With packs gone every packaging line is the product's, and that filter went with them.

The original idea was to model this with DynamicData `SourceCache<T>`s joined via `.Connect()`/`.InnerJoin()`/`.TransformMany()`, so derived observable collections update themselves. **That's not what got built.** Phase 6 established a different, simpler pattern first — a pure ordering function plus a stateful database orchestrator, described below — and it worked well enough that Phase 11 extended the *same* shape to the sub-assembly branch instead of introducing DynamicData joins partway through (that branch went on 2026-11-05, below). EF Core stays the single source of truth throughout; nothing here lives only in an in-memory observable.

**Two costs go up the tree side by side** (since the buffered cost, 2026-09-14): the true `CostPerBaseUnit` and the `BufferedCostPerBaseUnit`. A purchased material's buffered cost is a fixed amount since 2026-09-19 (see Buffered cost under RawMaterial): `RawMaterialRules.ApplyBrandPrices` sets it only on a first price, and the Raw Materials Save writes it otherwise. Every write through the cascade sets both: `IngredientCostPropagator`, which runs `IngredientBomRules.CalculateCost` twice per made ingredient (true costs, then buffered costs — with nothing of its own on top since 2026-09-21, and its stored `CostBufferPercent` normalised to 0 in the same pass). Everything downstream reads the buffered one: a sub-assembly's batch cost and line costs, and packaging line costs, in Products and Reports. The one exception is on read only: the Products screen's **Unbuffered** switch (2026-09-29) prices what it shows and prints from the true `CostPerBaseUnit` instead. Nothing stored changes, and the propagator doesn't know it exists. A buffer edit is one more way a cost changes: `RawMaterialRepository.UpdateAsync` reprices a purchased material's buffered cost itself and asks for the cascade for any ingredient whose buffer changed (packaging needs none, as below).

The one nesting exception is made ingredients: their BOMs nest to any depth, so that part of the cascade can't be a fixed one-hop join. An ingredient's cost can change from a new price entry, a BOM line edit, a `WeightLossPercent` edit, or a linked ingredient's link or share edit; when it does, the made ingredients that depend on it need recomputing in dependency order, components before the ingredients built from them. Sub-assemblies don't nest (a `SubAssemblyLine` only ever references an `Ingredient`, never another `SubAssembly` — Phase 7), so they needed no ordering logic at all: the cascade recomputed every sub-assembly touched until 2026-11-05, and nothing has needed to since.

**Made ingredients made from sub-assemblies needed no new ordering either** (2026-10-27). A made ingredient's BOM is read as its sub-assembly's lines plus its add-ins (`IngredientBoms`), expanded to ingredient edges, so a sub-assembly is never a node: `IngredientCostGraph`, `IngredientCostRules.Recompute`/`Reprice` and `IngredientBomRules.CalculateCost` are unchanged, and the "nesting sub-assemblies needs one mixed ordering" objection recorded under Move to In-House doesn't arise. A made ingredient is costed from its lines' ingredients' costs, never from a sub-assembly's batch cost, which is buffered only and would break the dependency order. **The one new trigger** is a sub-assembly's lines changing, which now changes the BOM of every made ingredient made from it: `SubAssemblyLineRepository.SetLinesAsync`, which every line write goes through (the Sub-Assemblies Save, a product's Save relining a linked one, role adoption), checks each such made ingredient for a loop through the new lines (`IngredientBomRules.EnsureNotInOwnRecipe`, by name, then `IngredientDependencies.EnsureNoCycleAsync`) and cascades it (`IngredientCostPropagator.RecomputeAndPropagateAsync`) on the caller's context, before its transaction commits. A made ingredient's own Save checks the same as a whole after every part is written (`RawMaterialRepository.EnsureMadeIngredientFitsAsync`). A sub-assembly a made ingredient is made from can't be deleted (`SubAssemblyRules.EnsureNoMadeIngredientMadeFrom`) or adopted by a product when its role turns product-owned (`SubAssemblyRepository.SingleUse`). Covered by `MadeIngredientLinkPersistenceTests` (which replaced `IngredientBomLinePersistenceTests`), three `ReactiveCostCascadeTests` and `CostCascadeTransactionPersistenceTests.A_sub_assembly_line_edit_whose_made_ingredients_cascade_fails_is_not_saved_either`.

**Ingredient branch — implemented Phase 6** as `IngredientCostGraph.GetDependentsInOrder` (`ApplicationCore`, pure graph logic, no I/O — reverse-BFS from the changed ingredient to find every made ingredient that transitively depends on it, then a DFS-based topological sort restricted to that set) and `IngredientCostPropagator.RecomputeAndPropagateAsync` (`Infrastructure`, the orchestrator, given one changed ingredient or the set one save changed (Re-apply Target Buffers, a sub-assembly several made ingredients are made from): loads every ingredient and every BOM line once, calls the graph function for each changed one, walks one dependency order over everything they reach (each ingredient recomputed once, however many changed) recomputing each ingredient's cost per gram (`CostPerBaseUnit`) from its own lines — reading each component's cost directly off the already-loaded, already-correct dictionary, never re-walking that component's own tree — then a single `SaveChangesAsync`). Every write path that can change an ingredient's cost calls it: `RawMaterialPriceHistoryRepository`'s add/update/delete (for an ingredient's price), `RawMaterialRepository.UpdateAsync` when `Source == Made` (a `WeightLossPercent` edit), `RawMaterialUnitRepository.UpdateAsync` when an ingredient unit's new multiplier reprices it (its latest price is in that unit), and `IngredientBomLineRepository.SetLinesAsync`. (Before the raw materials merge these were `IngredientPriceHistoryRepository` and `IngredientRepository`.) It loads ingredients only (`Type == Ingredient`), since packaging never takes part.

**Linked ingredients needed no new ordering** (2026-09-16). A linked ingredient's link is one more edge in the same graph: `IngredientCostPropagator` adds `linked → linked-to` beside every `made → component` before calling `IngredientCostGraph.GetDependentsInOrder`, which is unchanged, so egg white is recomputed after the egg and a made ingredient using egg white after egg white. In the walk, a linked ingredient is costed with `RawMaterialRules.LinkedCost` from its linked-to ingredient's already-fresh true cost, takes that ingredient's buffer percent, and its buffered cost is its cost with that percent on top, and a made one with the BOM rollup as before. A linked ingredient that's itself the changed one is recomputed first, as a made one is: `RawMaterialRepository` asks for the cascade when a linked ingredient is added or updated.

**Sub-assembly branch — implemented Phase 11, removed 2026-11-05** (at the user's request, from an independent review of the code). `SubAssemblyCostPropagator` kept each sub-assembly's stored `TotalWeight`/`TotalCost` current: `IngredientCostPropagator` called it at the end of every run with the ingredients it had changed, `SubAssemblyLineRepository.SetLinesAsync` set them with each line save, and Recalculate Costs recomputed them all. Product costing never read them: it prices every section from its lines (`SectionFigures.Of`, through `SubAssemblyRules.CalculateTotals`), at the buffered or the true cost as the screen asks, which a buffered-only stored total couldn't serve. Their only readers were the Recipe API's mix batch weight, `SubAssemblyRepository.GetLinkableAsync`'s `total_weight > 0` filter and two list-row properties nothing bound, so the columns went (migration `DropStoredSubAssemblyTotals`) with the propagator: the API sums a mix's lines, and the filter asks for a line (`EXISTS`, the same thing, since a line's grams are positive by a check constraint). Every stored total in the dev data matched its lines the day they went.

**Product and packaging branches needed no propagation code at all.** Neither `ProductSubAssemblyUsage`'s cost-per-piece, `PackagingLine`'s cost-per-piece, a product's total material cost, nor its wastage (the shop-wide `CostingDefaults.WastagePercent` of its sub-assemblies, since 2026-10-23, read with every product) is stored anywhere (Phase 8's "derived values are computed on read" decision) — they're plain `ProductRules` functions reading the ingredients' costs (through each section's lines) and the packaging material's `CostPerBaseUnit` fresh every time a screen asks. As long as the raw materials' costs are correct — which the ingredient propagator guarantees, and which the price history repository has guaranteed for packaging since Phase 5 (`RawMaterialPriceHistoryRepository` since the raw materials merge, which skips the ingredient cascade for a packaging price) — a product's displayed cost is automatically correct too, with nothing to propagate into. Verified end-to-end (`ReactiveCostCascadeTests.cs`): a price change several BOM levels deep reaches a sub-assembly's cost with no direct edit to that sub-assembly, and a product's live-computed cost-per-piece reflects it immediately, with zero product-level or packaging-level code involved. Since 2026-09-14 a usage's weight per piece is itself computed on read (`ProductRules.ResolvePieceSize`, from the typed figure and the current batch weight), so a product that typed a yield sees its piece weight, and so its cost per piece, move when the owner changes the batch — with nothing to propagate either. Sub-assembly ownership didn't change the cascade at all: a linked product reads the same lines.

**Composite products needed no propagation either** (2026-09-29). A composite stores only its lines (a product and a quantity). What each line brings is its product's recipe cost, and its packaging cost when the composite includes its products' packaging, worked out on read through `SavedProductReader` like the product's own figures, so a price change reaches a composite the moment it reaches the products it holds, however deep. The Products screen reads the lines' costs again with every `LoadCommand`.

**Add-ins needed no propagation either, for the same reason** (2026-09-16). A `UsageAddInLine` stores only `UsageId`, `IngredientId` and `Grams`; its cost is `Grams × the ingredient's BufferedCostPerBaseUnit`, read fresh, and no derived total about it is stored anywhere. So the propagator is untouched, and a sub-assembly's own batch is its `SubAssemblyLines` alone — an add-in must never move the batch of a sub-assembly another product owns; only the linking usage's effective batch takes it (`ProductRules.CalculateEffectiveBatch`). `ReactiveCostCascadeTests` pins both halves: repricing an add-in's ingredient moves the linking usage's cost per piece, and leaves the sub-assembly's own batch cost exactly where it was.

**The cascade runs in the transaction of the save that causes it** (2026-10-03, after a code review). The propagators (two until 2026-11-05) were DI singletons that each opened a context of their own, so every write path committed first and cascaded after: a cascade that failed part-way (a dropped connection, a timeout, the app closed mid-way) left the save in and the stored costs above it stale, and nothing put them right, since saving again unchanged doesn't cascade. They became internal static classes that take the caller's context, and every caller (`RawMaterialRepository`'s add, update and Save, `RawMaterialBrandPriceRepository.SetAsync`, `RawMaterialUnitRepository.UpdateAsync`, `IngredientBomLineRepository.SetLinesAsync`) runs them before `CommitAsync`: a save and its cascade commit together or not at all (`CostCascadeTransactionPersistenceTests`, which fail a cascade part-way with a save interceptor). A stored cost is set at the column's scale (`RawMaterialRules.StoredCost`), so a figure worked out again from unchanged inputs isn't written or dated again. The dev database had nothing out of step the same day (70 sub-assemblies, 5 made ingredients, checked by SQL).

**Recalculate Costs is the safety net for a change made outside the app** (2026-10-03): Settings → Costing Defaults → **Recalculate Costs** (`ICostRecalculator`, `CostRecalculator`) recomputes every made and linked ingredient in dependency order (`IngredientCostGraph.InDependencyOrder`, the cascade's own ordering for a whole set), in one transaction, and says how many were wrong (every sub-assembly's stored totals after them, until those went on 2026-11-05). Purchased materials aren't touched: their cost comes straight from their own saved prices. Settings is a modal dialog, so no save on another screen can run while it does. Its card, **Stored Costs**, sits to the right of the Costing Defaults card, each 420px wide and 16px apart in a `WrapPanel` (2026-10-06, at the user's request; it was under it). Settings opens 1000 wide, room for both; narrowed toward its 760 minimum, Stored Costs wraps under the defaults, and the tab scrolls (a `ScrollViewer`, which the stacked cards lacked: Recalculate Costs was cut off at the window's default size).

**The Price Simulator runs the cascade's math without storing it** (2026-10-03). A made or linked ingredient's costs are worked out by `IngredientCostRules.Recompute` (ApplicationCore), which `IngredientCostPropagator` stores and `IngredientCostRules.Reprice` applies to copies (`RawMaterial.ShallowCopy`) of the materials a simulated change reaches, in `IngredientCostGraph` order. One piece of code for both, so a simulation can't price an ingredient differently from how a real change would cascade. Its report (2026-10-06) names the changes reaching each product with `IngredientCostRules.ReachedBy`, the same dependency graph `Reprice` walks. No stored sub-assembly figure is involved: product costing prices every section from its lines' per-gram costs.

This does mean a product **already on screen** only reflects a price change made from a *different* screen once the user reselects it (or navigates back to it) — there's no cross-screen live push. That's the one piece of the original DynamicData-joins vision this phase deliberately didn't build; revisit only if that specific UX gap is ever reported as a real problem, not preemptively.

## Conventions

- **The user manual follows the app** (2026-09-27). `docs/user-manual.md` is written for the shop's staff: current behaviour only, labels in bold exactly as the screen shows them, amounts without a currency symbol, and no code names. A change users can see (a screen, button, field, menu item, rule or cost formula) updates it in the same change. PLAN.md keeps the history; the manual never mentions what used to be.
- **The developer manual follows the code** (2026-10-02, at the user's request). `docs/developer-manual.md` is written for developers new to the codebase: prerequisites, setup, architecture, patterns, testing, and steps for common changes. A change to anything it describes (the setup, commands, solution layout, architecture, a pattern or convention, or a type or file it names) updates it in the same change. Like the user manual, it describes only what's true now; PLAN.md keeps the history, and is the source of truth where the two differ.
- The layered architecture is fixed: `Domain` has no external dependencies, business and costing rules live in `ApplicationCore`, and EF Core and other I/O stay in `Infrastructure`.
- The MVVM toolkit is **ReactiveUI**, not CommunityToolkit.Mvvm. Use `ReactiveObject`, `ReactiveCommand`, `WhenAnyValue`, etc.
- **Every file goes in the folder for its kind, and the folder is its namespace** (see Solution Structure). A new View goes in `Views/` with its ViewModel in `ViewModels/`, a new repository in `Repositories/` with its interface in `ApplicationCore/Interfaces/`, a new rule in `Rules/` with its test in `tests/…/Rules/`, and so on. Nothing goes at a project root except app-startup plumbing.
- **Prefer Syncfusion controls over native WPF controls whenever a Syncfusion equivalent is available** (e.g. `ButtonAdv` over `Button`, `TabControlExt` over `TabControl`, `ComboBoxAdv`/`SfDataGrid`/the `SfInput.WPF` edit controls over their native counterparts), so the whole UI picks up the Windows11Light theme consistently. Fall back to a native control only when no Syncfusion equivalent exists. Adopting a new Syncfusion control only needs its package added to `TinapayanRMS.UI` — the packaged theme already covers every control Theme Studio knows about.
- **Grid quantities show 1 decimal and take up to 4** (2026-09-18, at the user's request): every Qty, Qty per Purchase Unit and Grams column is `NumberDecimalDigits="1" TypedDecimalDigits="4"`, 4 being what the database keeps. On its own, NumberDecimalDigits caps both what a grid's DoubleTextBox editor shows and what can be typed into it, so 1 would round every quantity typed to a tenth. `NumericColumn.TypedDecimalDigits` needs `controls:NumericEditing.IsEnabled="True"` on the grid, whose `NumericEditRenderer` gives that column's editor MaximumNumberDecimalDigits (which only caps what's typed) in place of NumberDecimalDigits; the cell outside editing still shows the column's decimals, so 0.1667 reads 0.2.
- **No currency symbol on a monetary value** (2026-09-22, at the user's request): amounts are shown as bare numbers — `StringFormat='{}{0:N4}'` in XAML, `$"{cost:N4}"` in a ViewModel, `CurrencySymbol=""` on a `CurrencyTextBox` — and a field label names the money without a "(₱)" suffix. Decimals: **2 for every per-piece costing figure on the Products screen** — the header’s Material Cost and Base Cost, and the Costing card’s Sub-assemblies, Packaging, Labor, Overhead, Administrative, Subtotal, Markup and VAT, in the tile captions as well as the summary table (2026-09-22, at the user’s request), and the Packaging section’s header figure with them — 2 for a per-purchase-unit amount or a price, and 4 only for a per-base-unit cost (a raw material’s cost per gram, a packaging line’s unit cost) and for the recipe tabs’ own Cost per piece.
- **An input's label goes on its left in a stacked form** (2026-09-24, at the user's request: "Since this is a desktop app and not a mobile app, let's make a practice that the label/textblock be placed on the left of the TextBox for input"). Wherever fields stack one under another, each field is a row with its label in an `Auto` column (`FormLabelStyle` in App.xaml: muted, centred on its box, 6 px before it, narrowed from 12 at the user's request the same day) and the input in a `*` column. The label column lines up down the form with `SharedSizeGroup` under `Grid.IsSharedSizeScope` when the rows are separate containers. Done in Settings (Categories, Product Categories, Roles, Units, Costing Defaults), the Products Costing tab, Clone, the Recipe Structure form (source picker, Role and Name, the piece-size column), Reports and the New Category dialog, whose label is now just "Name". **Two exceptions, the user's choice:** side-by-side strips of fields keep `FieldLabelStyle` above the input, because a label beside every box doesn't fit one row at 1366 px. That now covers only the Linked Cost, Purchase Cost and Usage Example rows. The three screens' header fields were exceptions too until later the same day, when the user asked for their labels on the left as well. Each is one row, with each label in an `Auto` column before its field, 16 px under the header's read-only figures. **Products:** Product Name, Category, Quantity Required and Current Price. At 1366 px that leaves Product Name about 190 px, so a long name scrolls in its box. **Raw Materials:** Name, Type, Category, Source (an ingredient) or Base Unit (packaging, moved out of the Base Unit tile 2026-09-26) and, for a made ingredient, Weight Loss %, whose box went from 120 to 80 px wide to make room. **Sub-Assemblies:** Name and Role, which used to share a row with the batch totals. The totals (Batch Weight, Batch Cost, Cost per g, or a packaging set's Set Cost, first in its row) now sit above the fields, each label over its figure. Read-only figures keep a small label over the value: header figures and stat tiles.
- **Names are stored without spaces at either end** (2026-11-03, at the user's request, from a code review). PostgreSQL's `case_insensitive` collation counts a space at the end, where SQL Server's ignored it, so since the move `"Flour "` got past the unique index beside `"Flour"`, and the Products and Raw Materials Saves and the Units of Measure form sent names as typed. The repositories now store them through `ProductRules.StoredName`, `RawMaterialRules.StoredName` and `UnitOfMeasureRules.NormalizeName`/`NormalizeAbbreviation`, and the two Saves trim as well, for what they say about the name afterwards. The dev database had none to put right. Tests: `StoredNamePersistenceTests`.
- **A figure a read divides by has a check constraint, and one bad row can't fail the others' reads** (2026-11-03, same review). One `packaging_lines` row with a quantity of 0 threw `DivideByZeroException` in `PackagingLineRow.FromSaved`, so `SavedProductReader.ReadAllAsync`, and with it Reports, Print sets, the Recipe API's `/products/recipes` and the MCP tools, failed for every product. Typing can't get there (the grids cap a quantity at the column's 4 decimals, and `CompleteLines` refuses 0), only an edit outside the app. Migration `QuantityAndPercentChecks` adds `CK_PackagingLines_AuthoredQuantity` (on the figure typed: the other is worked out, and 1 / 30,000 rounds to 0 at 4 places), `CK_SubAssemblyLines_Grams`, `CK_UsageAddInLines_Grams`, `CK_IngredientAddInLines_Grams`, `CK_RawMaterialUnits_BaseUnitsPerUnit` and `CK_CostingParameters_Percents`, each mirroring the rule the repository checks first. The dev database had no row any of them refuses. A backup holding such a row now fails `BringUpToDateAsync`'s migration, so it's refused before it takes the database's place. `ProductRules.ReconcileReciprocal` also gives 0 for 0 rather than throwing, so `EnsureValidPackagingLines` refuses such a line by name. Tests: `QuantityCheckConstraintTests`, `PackagingLineRowTests`, `ProductRulesTests`.
- **Decimal precision**: keep `decimal` values at full precision through the whole cascade, and round only for display and for the final selling price. Rounding each per-piece cost before summing adds up to drift. Enforced once for every `decimal` column via `TinapayanRMSDbContext.ConfigureConventions` (`numeric(18,4)`, set in Phase 4 when the first `decimal` columns were added, as `decimal(18,4)` on SQL Server until 2026-10-21), rather than per-property — a future column can't silently fall back to the provider's default (an unconstrained `numeric` on PostgreSQL, `decimal(18,2)` on SQL Server). **The exception is a material's costs per base unit** (`CostPerBaseUnit`, `BufferedCostPerBaseUnit`), `decimal(28,20)` since 2026-09-19 at the user's request ("it should be displayed in a rounded version to two decimal places. internally we will not limit the precision"): a buffered cost typed per bag is divided down to per gram, and 4 decimals would round it (₱1,297.37 a 25 kg bag came back ₱1,297.50). **A stored figure worked out in memory is set at its column's scale** (2026-10-03): a cost per base unit through `RawMaterialRules.StoredCost` (20 places; a sub-assembly's stored totals went through `TinapayanRMSDbContext.Stored`, 4, until they went on 2026-11-05), rounded half away from zero as SQL Server rounds, and worked out at full precision before that. At full precision it never compared equal to the stored value, so an unchanged cost read as a change (see RawMaterialPriceHistory). **A `double` never turns into a `decimal` by a plain conversion** (2026-10-24, on the move to .NET 11). Since .NET 11 a cast, `Convert.ToDecimal` or `new decimal(double)` keeps the double's exact binary value (28.35 is 28.349999999999997868371792719; .NET 10 rounded to 15 digits), with no switch to turn it back. Every number box and grid editor holds a `double`, so a typed figure would reach the ViewModel that way: a two-way `DoubleTextBox` or `PercentTextBox` binding takes `DecimalValueConverter`, and `NumericColumn` sets `ParsingMode` `Decimal`, both going through the number's shortest round-trip text. A theory's fractional `decimal` values go in `TheoryData` as `m` literals, since `[InlineData]` can only pass a `double`.
- **A rule throws `BusinessRuleException`** (`ApplicationCore/Rules`, 2026-10-03): every check whose message is for the user, in the Rules classes, the repositories and the screens' own form checks. It derives from `InvalidOperationException`, which they threw before, so tests expecting that still pass. `RunSafelyAsync` used to show every `InvalidOperationException` as a rule, and EF Core, SqlClient and the framework throw those for bugs and failures too ("Sequence contains no elements", a connection pool that ran out). Only the two startup configuration errors in `App` and `CompositionRoot` stay `InvalidOperationException`.
- **Use modern C# 15 / .NET 11 idioms** rather than older patterns still valid in the language: primary constructors, collection expressions (`[..]`), required members, file-scoped namespaces, pattern matching, and `record`/`record struct` for immutable data shapes, in line with what's already in the codebase (e.g. `CategoryPersistenceTests`'s primary constructor, `WellKnownUnitOfMeasureIds`'s collection expression). Don't reach for an older, more verbose equivalent just because it's more familiar.
  - **C# 15 (2026-10-25, on .NET 11).** **A fixed set of cases is a `closed` class or record**: the list trees' nodes (`ProductTreeNode`, `RawMaterialTreeNode`, `SubAssemblyTreeNode`) and `RecipeTab`, and what was a `Kind` enum beside fields only some kinds use (`PlanIssue`, `PrintScope`, `RecipeTabChoice`) or two nullable ids with one of them set (`PackagingLinkDraft`, which also had an `IsNewSet` flag, and `PackagingLinkTarget`, 2026-10-30) or flags that overlapped (`NewSubAssemblyDraft`'s `IsOwn`, `Release` and `ToMadeIngredient`, now its `SectionPlacement`), now one sealed record per case, nested in the closed one and carrying only its own data (`PlanIssue.BrokenLink(int IngredientId)`, `new PrintScope.Folder(folder)`). A switch over one names every case, and `null` when null can come, never `_`: then a new case is a CS8509 warning at each switch that misses it (checked by taking an arm out of `CaptureTabChoice`). A `Kind` enum stays where it's data rather than a shape (`VimCommandKind`, in the command table) or where every kind carries the same fields (`VimKeys`' `PlaceKind`).
  - **`union` only for a value no XAML binds.** A union is a struct that holds its case in `Value`, which WPF's bindings, `SelectedItem` and `DisplayMemberPath` don't see through, so the bound tree selections and Print choices stay classes. The first is `PreparedPrintout(ProductPrintout, PrintProblem)` (2026-10-30), what `ProductsViewModel.PreparePrintout` gives the Print tab: the pages, why the open form can't give them, or an empty union (`default`) while there's nothing to print, which was a `(ProductPrintout?, string?)` with a fourth combination that couldn't happen. A union suits a value that's one of some types already there (the printout); a set of cases made up for the purpose stays a closed record. An empty union matches `case null`. In a `?:` whose other branch is a case, write `default(PreparedPrintout)`: a bare `default` takes the case's type and becomes a null printout. Tests read the case through `Value` (`Value.Should().BeOfType<ProductPrintout>().Subject`).
  - **A closed record that's shown seals its `ToString`** (`PrintScope`, the Print dropdown's choice, which a screen reader reads out). Otherwise each case's record `ToString` reads "Folder { Label = … }".
  - **`BeEquivalentTo` over a closed base type has no members to compare** and throws "No members were found". Pass `o => o.ComparingByValue<PlanIssue>()`, so the cases' record equality decides (`ProductionPlanRulesTests`), or use `Equal` where the order is fixed.
  - **Collection expression arguments** (`[with(StringComparer.Ordinal), .. keys]`) for a collection made with a comparer or a capacity; a `ToHashSet(comparer)` or `ToDictionary(..., comparer)` at the end of a query stays as it is. **Labeled `break` and `continue`** take the place of a flag or a `goto` out of nested loops; IDE0410 finds those, and there are none.
  - **.NET 11's library additions take the place of hand-written code** (2026-10-30). `Enumerable.FullJoin` pairs a version's lines, add-ins, products and packaging lines with another's (`ProductVersionRules.Paired`, which was a hand-written `PairBy`). A full outer join pairs a repeated key with every match, so it suits keys that come once on each side, as a unique index makes them here. `Process.RunAndCaptureTextAsync` runs the backups' `pg_dump` and `pg_restore` (`PostgresTools.RunAsync`), reading both pipes as the tool runs and stopping one that's cancelled, and `Process.StartAndForget` starts the app again after a restore. `ProcessStartInfo.KillOnParentExit` is left off: `pg_dump` writes straight to the final `.backup` file, so stopping it with the app would leave a half-written file the Backups list shows.
- **Reads through Dapper, writes through EF Core** (2026-09-18/19, at the user's request, following the "pragmatic CQRS" split in boldsign.com/blogs/ef-core-vs-dapper). **Every public repository read method is plain SQL run by Dapper**, returning the same entity objects (with the same navigations filled in) that the EF `Include` chains used to, so ViewModels, `ProductRules` and `CostingRules` didn't change and the repository interfaces didn't either. **Everything else stays in EF Core**: every write, the schema and every migration, and a read inside a save that either loads an entity to change it (it must be tracked for `SaveChangesAsync`) or checks a condition through an EF expression (`SubAssemblyRepository.GetLinkedByAsync(dbContext, Expression, …)` behind `EnsureNoneLinkedElsewhereAsync`, the existence and uniqueness checks). An untracked graph read that a save also needs is shared instead of duplicated: it takes the save's DbContext and runs through Dapper *in that context's transaction* (`DapperReads.Command` passes `Database.CurrentTransaction`), e.g. `PackagingLineRepository.ResolveEffectiveAsync`, used by both `GetEffectiveForProductAsync` and `ProductCloner`. A Dapper write would bypass `IngredientCostPropagator`, leaving stored costs stale, and would surface a unique-name violation as `SqlException` rather than the `DbUpdateException` `ViewModelBase` maps to "That name is already in use." The pieces, in `Infrastructure/Queries/`: `DapperReads` borrows a DbContext's connection (so the connection string and the tests' `CreateDbContextFactory()` work unchanged; Dapper opens and closes it when EF hasn't) and has the factory- and context-level `QueryAsync`/`QuerySingleOrDefaultAsync`/`ReadAsync`; `Columns.Of<T>(alias)` is every entity's column list, **Id first** (a multi-mapped join splits on `Id`); `RawMaterialReads` loads materials with their category, base unit and units (largest first), alone or under product packaging lines or set lines; `SubAssemblyReads` loads sub-assemblies with their role and owner. **`Columns` must list exactly EF's columns**: a property left out reads back as its default with no error, which EF never did. `tests/TinapayanRMS.Infrastructure.Tests/Queries/ColumnsTests` compares every list against EF's design-time model (no database), so a new or renamed property fails that test until `Columns` has it; that's what Infrastructure's `InternalsVisibleTo TinapayanRMS.Infrastructure.Tests` is for. Every name in the SQL is snake_case (2026-10-21): a table is its `DbSet`'s name and a column its property's, both in snake_case (`raw_materials.cost_per_base_unit`), and `DapperReads` turns on `MatchNamesWithUnderscores` so Dapper maps them back. A table rename needs the SQL updated by hand (the persistence tests catch it). Mechanics: Dapper 2.1 maps `date` to `DateOnly` and a string column to an enum stored by name (`HasConversion<string>()`) on its own. Join an optional navigation with `LEFT JOIN`; Dapper returns null for a split whose first column (its `Id`) is null. A list of ids is one `@ids` parameter (`DapperReads.IdList`, an `int[]` Npgsql sends as one array) read by `IN (DapperReads.IdsTable)` (`unnest`; `STRING_SPLIT` on SQL Server before 2026-10-21, which kept it under SQL Server's 2,100-parameter limit). A collection navigation (a material's `Units`, a pack's `Lines`) is a second query stitched on by id, not a join, because `GridReader`'s multi-mapping is synchronous only; everything else is one query. As with an untracked EF query, there's no identity resolution: a material on two lines is two objects, each with its own `Units` list. A read EF left unordered now has an explicit `ORDER BY` on its `Id` (packaging lines, usages, BOM lines, `GetByIdsAsync`), which is the order EF's collection-include queries produced anyway. A recursive query over links people make (made and linked ingredients, composites, packaging links) stops where a row comes round again, with `CYCLE <column> SET is_cycle USING path` after the CTE (2026-11-04, from a code review): the app refuses such a loop, but one made outside it ran until the command timed out after 30 seconds. A `UNION` would end it too, but PostgreSQL sizes a `UNION`'s hash table from its row estimate, there thousands of times too high, which made Used By about 20 ms slower.
- **A ViewModel load that makes several reads runs them in one `Task.Run`** (2026-09-19, at the user's request). Each `await` on the UI thread comes back to it before the next read starts, and while WPF is drawing, each return waits its turn, so eight sequential reads cost eight waits. `ProductsViewModel.LoadProductDetailAsync` reads everything a product's detail shows in `ReadProductDetailAsync` (repositories only, no ViewModel state) inside one `Task.Run`, returns a `ProductDetail` record, and applies it after a single return to the UI thread; `RawMaterialsViewModel.LoadDetailsAsync` does the same for a raw material's price history, brand prices and BOM (`ReadDetailAsync`, `RawMaterialDetail`). Measured in the app against the dev database: the median click went from about 330 ms to 260 ms until the UI was idle, the first click from about 650 ms to 450 ms. The reads still show 45–100 ms although the SQL takes about 15 ms: that one return waits for WPF to finish drawing the cleared panel, which no change to the reads can remove. EF and Dapper were measured the same way and performed alike (roughly 150–800 ms a click, either way).
- **Correctness and performance take priority over brevity or convenience.** Favor the approach that is provably correct and doesn't waste allocations, database round-trips, or UI-thread work, even if a shorter or simpler alternative exists — e.g. querying only the columns/rows actually needed rather than materializing more and filtering in memory, and avoiding unnecessary intermediate collections in hot paths like the reactive costing cascade.
