# TinapayanRMS — Project Guide & Build Plan

Product recipe management & costing app for Tinapayan Festival Bakeshoppe. Tracks ingredient expenses, recipe/product margins, and cascades ingredient and packaging price changes up through sub-assemblies and finished products automatically.

## Tech Stack

- **Language / Runtime**: C# 14, .NET 10 (`net10.0`; `net10.0-windows10.0.19041.0` for the UI and Tests projects — ReactiveUI.WPF requires at least that Windows SDK version, and the bare `net10.0-windows` moniker resolves to `windows7.0`, which is too low)
- **UI**: WPF, styled with **Syncfusion Essential Studio for WPF 34.2.7** and Syncfusion's Windows11Light theme (the official `Syncfusion.Themes.Windows11Light.WPF` package), accent-recoloured at runtime
- **MVVM**: ReactiveUI (24.x). This version requires explicit builder-pattern initialization before any `ReactiveObject` is touched — `RxAppBuilder.CreateReactiveUIBuilder().WithCoreServices().WithWpf().BuildApp()` — done once per process by `src/TinapayanRMS.UI/ReactiveUIBootstrapper.cs`. It also dropped `System.Reactive` as a dependency, so that package is referenced directly wherever Rx LINQ operators (`.Select`, `.Where`, …) are used on an `IObservable<T>`.
  - **`ReactiveCommand.Create`/`CreateFromTask`'s parameterless overloads return `ReactiveCommand<RxVoid, RxVoid>`** (`ReactiveUI.Primitives.RxVoid`), not `ReactiveCommand<Unit, Unit>` — this fork doesn't use `System.Reactive.Unit` for that. Import the type via a using-alias (`using RxVoid = ReactiveUI.Primitives.RxVoid;`), never `using ReactiveUI.Primitives;` wholesale — that namespace also carries its own C# 14 extension-member `Select`/`Where`/`Subscribe`, which collide (CS0121, ambiguous call) with `System.Reactive.Linq`'s the moment both are in scope over the same observable.
- **Reactive collections**: DynamicData
- **Persistence**: EF Core 10.0.12 → SQL Server (db name `TinapayanRMS`)
- **DI / Hosting**: `Microsoft.Extensions.Hosting` + `Microsoft.Extensions.DependencyInjection`, wired via `HostBuilder` in `src/TinapayanRMS.UI/CompositionRoot.cs`, called from `App.xaml.cs`
- **Validation**: FluentValidation
- **Logging**: Serilog (rolling file sink)
- **Charts**: Syncfusion SfChart (`Syncfusion.SfChart.WPF`) for margin/price-trend reporting — replaces the originally-planned LiveCharts2
- **Testing**: xUnit v3, AwesomeAssertions, Respawn. Integration tests run against a locally installed SQL Server instance (such as LocalDB or SQL Server Express), and Respawn resets that database between tests. `AwesomeAssertions` replaces `FluentAssertions`: FluentAssertions 8+ requires a paid commercial license for use in a for-profit product, and AwesomeAssertions is a same-API, MIT-licensed fork of the last free FluentAssertions 7 release, created for exactly this situation. `NSubstitute` was referenced but never used — the suite exercises real repositories against a real Respawn-reset database rather than mocking — and its package reference was removed during a code-quality pass.
- **Solution format**: `.slnx`
- **`dotnet test`**: the .NET 10 SDK dropped VSTest support for `dotnet test`; running under the new Microsoft.Testing.Platform mode needs a `test.runner` setting in `global.json` at the repo root (already added). Run tests with `dotnet test --solution TinapayanRMS.slnx`.
- **Syncfusion license key**: read from the `SYNCFUSION_LICENSE_KEY` Windows user environment variable and registered in `App`'s static constructor (`src/TinapayanRMS.UI/App.xaml.cs`), before anything else in the process touches a Syncfusion type. Running the app or its tests on another machine requires that variable to be set there too.

**Folder = namespace, grouped by kind.** Every folder inside a project is a sub-namespace of it (`src/TinapayanRMS.UI/ViewModels/` → `TinapayanRMS.UI.ViewModels`). A new file goes in the folder for its kind, never at the project root. Only app-startup plumbing (`App`, `CompositionRoot`, `ReactiveUIBootstrapper`, `ConfirmDeleteHandlerRegistration`) and the DbContext pair live at a project root. Code in a sub-namespace sees its parent namespaces without a `using`: a View calls `RegisterNativeMessageBoxHandler` from `TinapayanRMS.UI`, and a repository uses `TinapayanRMSDbContext` from `TinapayanRMS.Infrastructure`. Sibling folders need a `using`. The solution was reorganized into this layout after the Phase 16 UI work: projects moved into `src/`/`tests/`, and each project's files went from flat to grouped by kind. Moving the entities to `TinapayanRMS.Domain.Entities` left the EF model unchanged (`dotnet ef migrations has-pending-model-changes` reported no changes), because table names come from the DbContext, not from entity namespaces. `Migrations/` was therefore left untouched.

The Windows11Light theme is not a project in the solution: it's Syncfusion's official `Syncfusion.Themes.Windows11Light.WPF` NuGet package (see Syncfusion UI Framework below).

## Domain Model

- **UnitOfMeasure**: `Id`, `Name`, `Abbreviation` — nothing else. **No unit is seeded or protected by a fixed id** — the table starts empty on a fresh database, and the shop owner adds every unit they need (gram, piece, mm, cm, in, m, or any custom unit like a sack or roll) in Settings → Units of Measure (see Application Architecture below), the same as any other user-managed lookup. **A unit carries no conversion factor of its own.** Conversions live on each raw material instead (see Multi-unit materials below): every material has a **base unit** its quantities and costs are tracked in (always the gram for an ingredient; chosen per packaging material), plus any number of **alternative units**, each defined as a multiple of that base unit. Length units (`IsLengthUnit`/`MillimetersPerUnit`/`LengthConversion`) were removed on 2026-09-13 to make way for this.
- **RawMaterial: ingredients and packaging share one table, told apart by `Type` (`Ingredient` or `Packaging`).** Merged on 2026-09-13 at the user's request ("the difference between the two is too thin"). Until then they were two tables, `Ingredient` and `PackagingMaterial`, each with its own category, unit and price history tables, and the schema itself kept packaging out of recipes. The merge kept the three differences that are real, as rules on the type:
  - **Base unit**: an ingredient's is always the gram, so its `BaseUnitId` is null — recipes, BOMs and sub-assembly weights all add up grams. A packaging material picks its own (`BaseUnitId` required).
  - **Source**: only an ingredient can be `Made` (a BOM and a weight loss) or `Linked` (a share of another ingredient's cost); packaging is always `Purchased`.
  - **Where it can be used**: sub-assembly lines and BOM lines take ingredients only; a product's packaging lines take packaging only.
  - `RawMaterialRules.EnsureFieldsMatchType`/`EnsureFieldsMatchSource` run in `RawMaterialRepository` before every save, backed by two check constraints (`CK_RawMaterials_BaseUnitMatchesType`, `CK_RawMaterials_OnlyIngredientsAreMade`). Type and source are fixed once created (`EnsureTypeUnchanged`/`EnsureSourceUnchanged`). Each line repository checks every line's type (`EnsureUsableInRecipes`/`EnsureUsableAsPackaging`) before it replaces anything, with a message naming the material, and the pickers only offer the right type. A name is unique across both types.
  - The line entities kept their role names: `SubAssemblyLine.Ingredient`, `IngredientBomLine.Ingredient`/`ComponentIngredient` and `PackagingLine.PackagingMaterial` are all `RawMaterial`s. A packaging line's unit is `UnitId` (a `RawMaterialUnit`); recipe lines have had no unit since 2026-09-14 (they're in grams — see Ingredients). `IngredientCostPropagator` and `SubAssemblyCostPropagator` kept theirs too, since they only ever deal with ingredients. (`IngredientQuantityConverter`, which turned recipe lines entered in a unit into grams, went with those units on 2026-09-14.)
  - **`CostPerBaseUnit`** (stored, derived): the true cost of one base unit — one gram, for an ingredient (it was `Ingredient.CostPerGram`).
  - **Buffered cost** (2026-09-14, at the user's request): a per-material **`CostBufferPercent`** (0–100, default 0; `RawMaterialRules.EnsureValidCostBuffer`, the validator, and `CK_RawMaterials_CostBufferPercent`) is a cushion for price swings, waste and yield variation. **`BufferedCostPerBaseUnit`** (stored, derived) is the cost with it on top (`RawMaterialRules.BufferedCost`, the only buffer formula). **It's the value every sub-assembly line, BOM rollup and packaging line uses**, so products are costed and priced with it; `CostPerBaseUnit` stays the true cost, shown beside it on the Raw Materials screen and in Price History.
    - Purchased: `CostPerBaseUnit × (1 + buffer / 100)`, set by `ApplyLatestPrice` with the true cost, and by `RawMaterialRepository.UpdateAsync` when the buffer changes.
    - Made: the BOM rollup of the components' *buffered* costs, then its own buffer on top, so buffers stack up the tree (the user's choice; leave a made ingredient at 0% to count each buffer once).
    - Linked: its share of the linked-to ingredient's *true* cost, then the linked-to ingredient's buffer **percent**, which it inherits, on top — `CostPerBaseUnit × (1 + buffer / 100)`, as for a purchased one.
    - It's stored, not computed on read, because a made ingredient's buffered cost isn't a multiple of its own true cost once its components have buffers.
- **Multi-unit materials** (built 2026-09-13, from the user's Ingredients mockup):
  - **`RawMaterialUnit`** (`RawMaterialId` Cascade, `UnitOfMeasureId` Restrict, `BaseUnitsPerUnit` > 0, `Description`; unique per material + unit; never a packaging material's own base unit). It merged `IngredientUnit` (`GramsPerUnit`) and `PackagingMaterialUnit`. The base unit never has a row: **an empty unit means the base unit** everywhere a unit is optional (price entries, packaging lines), so nothing depends on a "gram" row existing in Units of Measure. Recipe lines take no unit at all (2026-09-14): an ingredient's alternative units price it and work in the Usage Example, but a recipe is always written in grams.
  - `UnitConversionRules.ToBaseQuantity(quantity, multiplier?)` / `CostPerBaseUnit(price, multiplier?)` / `EnsureValidMultiplier` are the only conversion formulas.
  - **At most two alternative units per item** (`UnitConversionRules.MaxAlternativeUnits`, a user requirement added right after the feature shipped): `RawMaterialUnitRepository.AddAsync` counts the material's units and rejects a third (`EnsureCanAddAlternativeUnit`; `RawMaterialRepository.SaveAsync` adds units through the same check, after removing the ones a save drops), and the Raw Materials screen disables Add Alternative Unit at two (`CanAddUnit`, set when the unit rows are rebuilt). Editing an existing unit is unaffected.
  - **Every price entry records the unit it was priced in** (`UnitId?`), so switching from buying bags to buying packs leaves the old per-bag prices correct. The stored cost is per base unit only: `CostPerBaseUnit` = latest price ÷ that price's unit multiplier. `CurrentCost`, `PurchaseUnitId` and `PurchaseUnitQty` were dropped from both material tables before the merge: a latest price is meaningless without its unit, and storing the unit on the material would make a material ↔ unit FK cycle. The detail screen reads the latest price and its unit from the price history it already loads.
  - **Correcting a multiplier reprices.** `RawMaterialUnitRepository.UpdateAsync` (and the screen's Save, through the same shared write method) recomputes the material's `CostPerBaseUnit` if its latest price is in that unit; for an ingredient whose cost moved that way it then calls `IngredientCostPropagator.RecomputeAndPropagateAsync`, which reaches every dependent made ingredient and sub-assembly. Recipe lines are in grams, so nothing else moves (until 2026-09-14 it also rewrote the `Grams` of every recipe line entered in the unit). A packaging material needs nothing more: packaging lines are costed on read.
  - **A unit in use can't be deleted**: the repository counts price entries, and for a packaging material's unit its packaging lines, first and says which (Restrict FKs back that up). An ingredient's unit is never on a line.
  - **A packaging material's base unit is fixed once it has alternative units, prices or packaging lines** (`RawMaterialRules.EnsureBaseUnitCanChange`, checked in `RawMaterialRepository.UpdateAsync`), since all of them are measured in it.
- **RawMaterialCategory** (Flour, Dairy, Boxes, Ribbons, …): one user-editable list for both types, merged from `IngredientCategory` and `PackagingCategory` (a packaging category named like an ingredient one joined it). Managed in Settings → Categories — see Application Architecture below.
- **Ingredients** (`Type = Ingredient`):
  - **The base unit for every ingredient is the gram.** Every weight total is in grams: sub-assembly lines' and BOM lines' `Grams`, sub-assembly total weights, and weight-per-piece. **Recipe lines are entered in grams only** (2026-09-14, at the user's request): sub-assembly lines and BOM lines have no unit picker. Until then a line could be entered in an ingredient's alternative unit ("3 pc of egg") and stored in both; migration `ProductOwnedSubAssemblies` dropped `Quantity`/`UnitId` and kept the grams.
  - **`Source`**: `Purchased`, `Made` or `Linked`. It is set when the ingredient is created and can't change afterwards, so an ingredient's cost always comes from exactly one place.
  - **`Units`**: its alternative units (a 25 kg bag is `BaseUnitsPerUnit = 25000`, an egg piece `50`). Either source can have them; only a purchased one is priced in them.
  - **Purchased** ingredients are priced through `RawMaterialPriceHistory`, each entry in one of the ingredient's units (or per gram). `CostPerBaseUnit = latest price ÷ grams in its unit`.
  - **Made** ingredients are produced in-house from a bill of materials (BOM):
    - They have no price history.
    - **`WeightLossPercent`**: weight lost while making the ingredient (e.g. water boiled off syrup). At least 0 and less than 100, enforced by `RawMaterialRules.EnsureFieldsMatchSource`.
    - Output grams = `Σ BOM line grams × (1 − WeightLossPercent / 100)`.
    - Cost per gram = `Σ (BOM line grams × component cost per gram) / output grams`. The buffered cost per gram is the same formula over the components' buffered costs, times `(1 + its own buffer / 100)`. The formula itself is `IngredientBomRules.CalculateCost`; a component's cost used here is whatever's currently stored on it — see the propagation note below for why that's always safe to read directly rather than walking the tree every time.
    - Example: simple syrup made from 1000g sugar (₱0.09/g, so ₱90) and 500g water (₱0, i.e. never priced — see PLAN.md's PriceHistoryRules note: a literal ₱0 price entry is rejected, so "free" means unpriced, not a zero entry), with 20% weight loss, gives 1500 × 0.8 = 1200g. It costs ₱90 / 1200 = ₱0.075/g.
  - **Linked** ingredients (2026-09-16, at the user's request: "Raw Material cost link to another raw material") are parts of another ingredient, costed as a share of its cost. An egg is bought by the 1,500 g tray at ₱135 (₱0.09/g); egg white is 70% of its weight and carries 30% of its cost, egg yolk 30% of the weight and 70% of the cost. A made ingredient couldn't do this: a BOM spreads cost by weight only.
    - **`LinkedToId`** (self-referencing FK, Restrict: an egg can't be deleted while a part links to it; the driver's `SqlException` shows as "in use elsewhere"), **`WeightSharePercent`** and **`CostSharePercent`** (each above 0, at most 100). Only a linked ingredient has them, and it has no price history, no BOM and no weight loss (`RawMaterialRules.EnsureFieldsMatchSource`, the validator, `CK_RawMaterials_LinkMatchesSource`). The link and shares can be edited after creation, like a weight loss; the source can't.
    - **Cost per gram = linked-to cost per gram × cost share ÷ weight share** (`RawMaterialRules.LinkedCost`, the only place the formula is). White: 0.09 × 30/70 = ₱0.038571; yolk: 0.09 × 70/30 = ₱0.21. 1,050 g of white and 450 g of yolk cost ₱40.50 + ₱94.50 = ₱135, the whole tray. It doesn't depend on the unit the egg was priced in. Stored costs keep 4 decimals (`decimal(18,4)`), so white is stored as ₱0.0386 — the same limit every stored cost per gram has.
    - **The cost share is of the linked-to ingredient's unbuffered cost** (the user's rule, 2026-09-16: "the Cost Share must be the percentage of the unbuffered cost not the buffered one"), **and the part inherits the linked-to ingredient's `CostBufferPercent`** (2026-09-17: "i want the linked ingredient to inherit the buffer cost %"). Egg at ₱0.09/g with a 10% buffer gives yolk (30% / 70%) ₱0.21/g, buffered ₱0.231/g. The percent, not the buffered cost, is what's inherited: the share is still taken before any buffer, so it never counts twice, and a made linked-to ingredient's stacked buffered rollup doesn't leak in.
      - **Stored on the part, kept in step.** `RawMaterialRepository` sets a linked ingredient's `CostBufferPercent` from the linked-to ingredient's on add and update, whatever the form sent (`EnsureValidLinkAsync` returns it), and `IngredientCostPropagator` copies it again every time the part is recomputed. A buffer edit on an ingredient already cascades, so it reaches every part, down a chain of links; relinking takes the new ingredient's. Storing it keeps everything that reads `CostBufferPercent` (the Usage Example, the list) right without knowing about links.
      - The Linked Cost card shows the inherited percent read-only (bound to `EditingLinkedTo.CostBufferPercent`); it's changed on the linked-to ingredient.
      - History: it first shipped stacking the buffers the way a made ingredient's do (the share of the egg's *buffered* cost, then the part's own buffer); on 2026-09-16 the share moved to the unbuffered cost with only the part's own buffer on top; on 2026-09-17 the part's own buffer gave way to the inherited one.
    - **The parts of one ingredient take at most 100% of its weight and at most 100% of its cost** (the user's choice; `RawMaterialRules.EnsureLinkSharesFit`, checked by `RawMaterialRepository` on add and update against the *other* parts, so a part never counts against itself). Less is fine — the shell is neither white nor yolk. The message names the other parts: "Egg Yolk (30%) already takes 30% of Egg's weight, so Egg White can take at most 70%."
    - **Ingredients only** (the user's choice): the target must be another ingredient (`EnsureValidLinkTarget`, which also refuses a link to itself), purchased, made or itself linked. Packaging stays purchased-only; `CK_RawMaterials_OnlyIngredientsAreMade` already covers it.
    - **A link is one more edge in the cost graph** (see Reactive Costing Cascade), so a cycle can't close through a mix of BOMs and links: linking egg white to a meringue base made from egg white is refused, and so is a BOM that uses a part linked to the ingredient being made. `IngredientDependencies.LoadAsync` builds the combined graph for both checks (`IngredientBomRules.EnsureNoCycle`).
    - Verified in the app on the secondary monitor, against a throwaway migrated database (dropped afterwards), with real clicks and keystrokes: a seeded Egg Yolk loaded into the Linked Cost card; Egg White was created as Linked to Egg, 75% / 30% was refused with "Egg Yolk (30%) already takes 30% of Egg's weight, so Egg White can take at most 70%.", and 70% / 30% saved at ₱0.0386 with the other-parts caption showing 100% of the weight and cost.
- **IngredientBomLine**: one component of a made ingredient. It has `IngredientId` (the made ingredient), `ComponentIngredientId` (a raw material of the Ingredient type, purchased or made), and `Grams`, the amount. `IngredientBomRules.EnsureValidLines` rejects an empty set, non-positive grams, or the same component twice (combine it into one line instead).
  - BOMs can nest to any depth: caramel can be made from syrup, and syrup from sugar. `IngredientBomRules.EnsureNoCycle` blocks an ingredient from appearing anywhere in its own BOM tree, checked at save time by walking the *other* made ingredients' current BOM graph.
  - `IngredientId`'s FK is Cascade (deleting the made ingredient takes its own BOM lines with it); `ComponentIngredientId`'s FK is Restrict (deleting an ingredient that's in use as a component is blocked — remove it from the BOM first). Both can't be Cascade: SQL Server rejects two cascade paths from the same table to the same parent table.
  - BOM lines use ingredients only, never packaging (`RawMaterialRules.EnsureUsableInRecipes`, checked by `IngredientBomLineRepository.SetLinesAsync`).
- **Packaging materials** (`Type = Packaging`):
  - `BaseUnitId` (FK to UnitOfMeasure; `StandardUnitId` until 2026-09-13) is its base unit, set per material: typically a count unit (piece) for boxes and wrappers, a length unit (cm) for ribbon. No rule restricts which unit that can be — the shop owner is trusted to pick a sensible one — but it's fixed once anything is measured in it (see Multi-unit materials).
  - `Units` are its alternative units (a pack of 100 boxes is `BaseUnitsPerUnit = 100`, a 1000 cm ribbon roll `1000`), and `CostPerBaseUnit` its stored cost.
  - Always purchased, and priced through `RawMaterialPriceHistory` like a purchased ingredient.
  - Packaging lines can be entered in the base unit or any alternative unit (see PackagingLine).
- **RawMaterialPriceHistory** (merged from `IngredientPriceHistory` and `PackagingPriceHistory`): a price timeline for each purchased material. Made ingredients have none. A price is entered **per unit** (the price of one sack or one pack, as on the supplier's receipt) and records that unit; no unit means per base unit. The material's stored cost per base unit is recalculated from the latest entry. "Latest" is by date, then by id — and a price added on the same date as the current latest one wins (`PriceHistoryRules.FindLatestAfterAdding`; before 2026-09-13 an unsaved entry's id of 0 lost that tie, so a second same-day price never became current — the ingredient migration healed the stored costs). A new ingredient price runs the ingredient cost cascade; a new packaging price needs nothing more, since products cost packaging lines on read.
- **SubAssemblyRole**: an editable lookup table (`Id`, `Name`, `SortOrder`), seeded with Dough, Filling, Topping, Inclusion and Finishing. More roles, such as Glaze, can be added in Settings → Roles. `SortOrder` sets the order of a recipe's sections. A role can't be deleted while any sub-assembly uses it.
- **SubAssembly** + **SubAssemblyLine**: a sub-assembly is an in-house recipe that products use directly, such as a dough, a filling or a topping. Its lines are the ingredients that make it up.
  - **Owned by the product it's made in** (`OwnerProductId`, Cascade from `Product`; 2026-09-14, at the user's request — until then sub-assemblies were a library of their own, on a Sub-Assemblies screen, and any product picking one shared it without anything saying so). A product's own sub-assembly is made and edited only inside its recipe on the Products screen; the owner always uses it. Another product can **link** it (a usage of it — live, with read-only lines and its own piece size) or **copy** it (an independent sub-assembly of its own). See Derived products below.
  - **Or standalone: `OwnerProductId` null** (2026-09-15, at the user's request: "a Subassembly not owned by any product but can use for linking or cloning"). It's made and edited on the restored **Sub-Assemblies screen** (see Application Architecture), and every product using it links it, since none owns it. Products link or copy it exactly as they do another product's. `ISubAssemblyRepository.SaveStandaloneAsync`/`DeleteStandaloneAsync` write it (one transaction: name, role, then the lines through `SubAssemblyLineRepository.SetLinesAsync`), and refuse a product's own; `SetRecipeAsync` refuses a standalone one listed as a product's own.
  - **Its name is unique within its owner** (index `(OwnerProductId, Name)`), so a copy can keep its source's name. `SubAssemblyRules.EnsureValidOwnedNames` rejects a blank name or two of one product's own with the same name (case- and space-insensitively); `SubAssemblyRules.UniqueName` gives a copy that would clash "Name (copy)", "Name (copy 2)", ….
    - **Standalone names are unique among themselves** (`SubAssemblyRules.EnsureStandaloneNameAvailable`, case- and space-insensitively), and can match a product's own. The same index enforces it: it has `HasFilter(null)`, because EF's SQL Server convention would otherwise add `WHERE [OwnerProductId] IS NOT NULL` to a unique index on a nullable column, and SQL Server's unique index treats NULLs as equal.
  - `RoleId` (FK to `SubAssemblyRole`, required): each sub-assembly has exactly one role, so custard is always a Filling. The owner can change it at any time; every recipe using the sub-assembly then shows it in the new role's place. (Until 2026-09-14 a role could only change while no product used the sub-assembly, since that broke role-tab links; those links are gone.)
  - Each line has an FK to an ingredient (a `RawMaterial` of the Ingredient type — rejected otherwise) and `Grams`. Line cost = grams × the ingredient's `BufferedCostPerBaseUnit`, its buffered cost per gram. `SubAssemblyRules.EnsureValidLines` rejects no lines, non-positive grams or an ingredient twice, so a sub-assembly always has a batch.
  - **Baker's percentage: `SubAssemblyLine.IsFormulaBase`** (2026-09-16, at the user's request: "a checkbox column to mark the ingredient as a reference, then find the total of all ingredients with check and use that as the divisor"). Each line is read as a percentage of the ticked lines' total weight — the formula's 100% base, usually the flour. `SubAssemblyRules.FormulaBaseWeight` sums the ticked lines and `CalculateBakersPercent(grams, baseWeight)` gives the figure, **null when nothing is ticked**: a glaze or a filling needn't have a base, and a blank is the honest answer, not a nought. The sum of every line's percentage — "whole formula 201.5%" in the caption under the table — is the number a batch is scaled by (`flour = target ÷ (total% ÷ 100)`).
    - **Per line, not per ingredient** (the user's design, over an `IsFlour` flag on the raw material). Sugar is the base of a syrup and an extra in a dough; two flours tick together and make 100% between them; and it never depends on the `Flour` category, which is user-editable free text and was already drifting (Cornstarch was filed under Butter). Named `IsFormulaBase` because "base" already means a *unit of measure* throughout this codebase (`BaseUnitId`, `CostPerBaseUnit`); the column header is "Base".
    - **Nothing about cost changes.** Grams stay the source of truth; the tick is a reading of the batch, never stored as a figure, and `TotalWeight`/`TotalCost` don't move.
    - **Lines travel as `RecipeLine`** (`ApplicationCore/Interfaces/RecipeLine.cs`), a `readonly record struct (IngredientId, Grams, IsFormulaBase = false)` that replaced the `(int IngredientId, decimal Grams)` tuple in `OwnedSubAssemblyDraft.Lines`, `ISubAssemblyRepository.SaveStandaloneAsync`, `SubAssemblyRules.EnsureValidLines` and `SubAssemblyLineRepository.SetLinesAsync`. It has an **implicit conversion from the old tuple**, so the ~120 call sites writing `[(flourId, 1000m)]` compiled untouched (only three test helpers that declared the tuple type themselves changed). The same conversion makes a *lossy* projection compile silently — `.Select(l => (l.IngredientId, l.Grams))` drops the tick without an error — so the three places that rebuild lines from existing data name it explicitly: `ProductsViewModel.CurrentRecipe()` (miss it and ticks never save, and `IsSameRecipe` never even sees the change), `SubAssembliesViewModel`'s save, and `ProductCloner`'s own-copy branch. Anything that carries sub-assembly lines from one place to another in future has to do the same.
    - **Add-ins have no tick** and stay on the plain tuple (`LinkedUsageDraft.AddIns`, `UsageAddInLineRepository`): an add-in is never part of the base. Each still gets a percentage, **read against the linked recipe's base**, not its own weight — 100 g of buttermilk on a dough's 1,000 g of flour reads 10.0, and the whole-formula figure includes it. BOM lines are untouched: a BOM is a yield calculation with weight loss, not a baker's formula, and uses its own `(ComponentIngredientId, Grams)` tuple.
    - **Typed either way, and whichever was typed stays put** (2026-09-16, at the user's request: "make typing percentages to get grams and vice versa work two ways", and their choice of what happens after). A line's grams or its baker's percentage can be typed; the other is worked out. **`SubAssemblyLine.AuthoredBakersPercent`** (nullable) records a typed percentage, null when the grams were typed — the same idea as a usage's `AuthoredField`/`AuthoredValue`, and chosen over "percentages always win" and "grams always win". When the base weight changes, a line typed as a percentage has its grams worked out again from it (`SubAssemblyRules.GramsFromBakersPercent`), and a line typed in grams keeps them while its percentage moves: on 1,000 g of flour, water typed as 65% and eggs typed as 100 g; double the flour and the water is 1,300 g, still 65%, while the eggs stay 100 g at 5%.
      - **Grams are still stored for every line** and still all that's costed. A typed percentage is worked back into grams the moment the base changes, in the form, and saved that way; the base only ever changes by editing that same formula, so the stored grams are never stale. `GramsFromBakersPercent` rounds to the 4 decimals grams are stored in, so reopening a saved line reproduces exactly what was worked out; unrounded, a line could come back a ten-thousandth off and make a recipe nobody touched look changed.
      - **Any change to the base weight counts**: a base line's grams, a tick, or a base line added or removed. A typed percentage always stays that percentage, which is the simple rule to predict. Ticking a line into the base makes it a grams line (the base is 100% between its lines by definition), and `SubAssemblyRules.EnsureValidLines` refuses a base line carrying a percentage. With nothing ticked, a typed percentage keeps its last grams and its percentage waits: tick the flour again and the line follows it.
      - **Where it can't be typed, it won't open**: on a base line, and while nothing is ticked (`IngredientLineRow.CanTypeBakersPercent`). SfDataGrid's `AllowEditing` is one setting per column, so `controls:GridCellEditing` (a grid-level `IsEnabled`, and `AllowWhen` naming a `bool` property of the row on the column, the way `MappingName` names the value) cancels `CurrentCellBeginEdit` on the rows that say no. The row's setter ignores such a value too, as a backstop.
      - **A typed percentage is in bold** (`controls:GridCellEmphasis`, `When="IsPercentTyped"`), the way the Products screen's typed piece-size figure once was. Only the percentage is marked: grams are the usual way in, and bolding them on nearly every row would drown out the ones that follow the flour. It's a renderer (`EmphasisNumericRenderer`, replacing the grid's `"Numeric"` one) binding the text's `FontWeight`, not a `CellStyle`: a cell style replaces the theme's own `GridCell` style, and basing one on the theme's (`SyncfusionGridCellStyle`, as Syncfusion's ConditionalFormattingDemo does) needs its whole dictionary merged in, beside the accent colours the app sets at startup. `OnUpdateDisplayBinding` calls `OnInitializeDisplayElement`, so the override also covers recycled rows.
      - **Carried everywhere lines are**: `RecipeLine.AuthoredBakersPercent`, `SubAssemblyLineEdit`, `ProductUsageEdit.ShowsSameAs`, the three line-copying projections named above (`CurrentRecipe()`, Sub-Assemblies' save, `ProductCloner`), `Repriced`, and both add rows' item factories, which hand a new line the current base so a percentage can be typed into it straight away.
      - **Add-ins can be typed either way too, but only grams are kept.** An add-in's base is the linked recipe's, which belongs to another product and can change there without this form open; remembering a typed percentage would mean working its grams out on every read, in Products and Reports alike, from a base those screens don't load. So a percentage typed for an add-in fills in its grams and isn't kept, and isn't shown in bold.
    - Not modelled: a preferment (a sponge made as a made ingredient) ticked as the base counts its whole weight, not the flour inside it, so such a formula will disagree with a textbook — the user has a separate plan for preferments; and true hydration counting the water in milk and eggs.
  - A sub-assembly has a total weight in grams (the sum of its line grams) and a total ingredient cost, both stored and refreshed whenever its lines are saved or an ingredient's cost changes (the cascade).
  - **It can't be deleted from under a product that links it**: removing it from its owner's recipe, or deleting the owner, is refused while another product's usage points at it, and the message names those products (`SubAssemblyRules.EnsureNotLinkedElsewhere`: "Cream Loaf Mini links Sweet Dough. Make a copy of it there, or remove it there, first."). Deleting a standalone one on the Sub-Assemblies screen is refused the same way while any product uses it.
- **Product** + **ProductSubAssemblyUsage**: a finished product is built from distinct sub-assemblies, its own and linked ones. It can use several sub-assemblies in the same role (e.g. an ube filling and a cheese filling), but each sub-assembly only once. A usage whose sub-assembly's `OwnerProductId` isn't the usage's `ProductId` is a link, and so is every usage of a standalone one (null is never the product; EF's null compensation makes `ProductId != OwnerProductId` true there in SQL too).
  - **`Description`** (optional, at most 500 characters: `ProductValidator.MaxDescriptionLength`, which `ProductConfiguration`'s `HasMaxLength` also uses) and **`UpdatedAt`** (`DateTime?`, local time), both added 2026-09-14 for the Products screen's header. `UpdatedAt` is stamped by `ProductRepository`'s add and update, so by the screen's Save and by a clone when it's made. Products not saved since then have null, shown as "—".
  - **Each usage has its own piece size, as total weight, yield and weight per piece** (2026-09-14, at the user's request). The user types either the **weight per piece** (grams) or the **yield** (pieces per batch), and the other is worked out from the batch's total weight. A usage stores only what was typed: **`AuthoredField`** (`UsageAuthoredField.WeightPerPiece` or `Yield`) and **`AuthoredValue`** (> 0, `CK_ProductSubAssemblyUsages_AuthoredValue`). Until then it stored `WeightPerPiece` only; the migration carried every one over as a typed weight.
  - **`ProductRules.ResolvePieceSize(authoredField, authoredValue, totalWeight)`** is the one formula: weight typed → `Yield = TotalWeight / WeightPerPiece`; yield typed → `WeightPerPiece = TotalWeight / Yield`. It's worked out on every read, never stored, which is what makes **the typed figure stay put when the batch changes**: a 60 g piece stays 60 g and the yield moves; a 24-piece yield stays 24 and each piece gets heavier or lighter. Being computed on read, an owner's line edit never has to update other products' rows. A batch that weighs nothing has no other figure (0).
  - Usage cost per piece = `SubAssembly.TotalCost × WeightPerPiece / SubAssembly.TotalWeight`, with the resolved weight per piece. For example, 100g/₱24 filling used at 10g/piece gives ₱2.40/piece, yield 10.
  - **Per-piece line breakdown** (2026-09-14): a piece takes `WeightPerPiece / TotalWeight` of the batch, so it takes that share of every line. `ProductRules.CalculateLineGramsPerPiece` scales a line's grams and `CalculateLineCostPerPiece` its cost (grams × buffered cost per gram), with the same share. A usage's lines add up to its cost per piece and its weight per piece. The Recipe Structure showed this per line until 2026-09-16, when a sub-assembly's tab became its form. **Nothing calls these two rules now** — the Costing tab's Cost Breakdown works off `ProductCostSummary`, a piece at a time, not line by line. They're kept, with their tests, because they're the costing rule for a line's share of a piece and a per-line view is the obvious thing to want back. **If one returns, it must divide by the usage's *effective* batch** (`ProductRules.CalculateEffectiveBatch`), not the sub-assembly's stored totals, or a linked usage's add-ins would be left out of every line's share; their parameters are still named `subAssemblyTotalWeight`.
  - **UsageAddInLine: a product's own extras on top of a sub-assembly it links** (2026-09-16, at the user's request: "the first datagrid has headers containing the linked recipe and the bottom one contains some additional recipe like food colors, flavoring etc"). The same dough goes into several products, but one wants ube flavouring and another pandan colour; until then the only way was **Make a Copy**, which breaks the link, so the dough stopped being shared and the owner's changes stopped reaching it.
    - `UsageAddInLine` (`UsageId` Cascade, `IngredientId` Restrict, `Grams`; unique per usage + ingredient) hangs off the **usage**, not the sub-assembly: two products linking the same dough each keep their own set, and neither moves `SubAssembly.TotalWeight`/`TotalCost`, which stay the owner's. The only cascade path in is `Products → ProductSubAssemblyUsages → UsageAddInLines`, a chain rather than a second path, which SQL Server allows because a usage's own sub-assembly FK is Restrict.
    - **Add-ins go into the batch** (the user's choice, over "a fixed amount per piece"): the usage's **effective batch** is the sub-assembly's plus its add-ins (`ProductRules.CalculateEffectiveBatch`, over `SubAssemblyRules.CalculateTotals`), so 1,700 g of dough with 20 g of flavouring is a 1,720 g batch and a piece takes its weight-per-piece share of the whole thing. `ResolvePieceSize` and `CalculateUsageCostPerPiece` were **unchanged**: they just receive the effective figures. The typed figure still stays put, so adding a flavouring moves the other one.
    - **Linked usages only.** A sub-assembly of the product's own has no add-ins — its extras just go in its lines, and a second table there would be two ways to do one thing.
    - **An ingredient the linked recipe already has is refused** (`ProductRules.EnsureValidAddIns`, the user's choice over merging the grams): "Water is already in Variety Bread Dough. Add-ins are only for what its recipe doesn't have — change how much it uses where Variety Bread Dough is kept, or make this product a copy of it." Checked in the form the moment Apply is pressed, and again in `SetRecipeAsync`'s pre-flight and `UsageAddInLineRepository.SetLinesAsync` as it writes. An empty set is valid, unlike a sub-assembly's own lines: most linked usages take the recipe as it is.
      - That guard is load-bearing beyond validation: since an add-in can never duplicate a base ingredient, **Make a Copy and `ProductCloner`'s owned branch concatenate the base lines and the add-ins** into the new sub-assembly's lines without a merge step, and the result always passes `EnsureValidLines`. The batch it was showing is the batch it keeps. A clone of a *standalone* link stays linked, so its add-ins stay add-ins.
    - **Written with the rest of the recipe**: `LinkedUsageDraft.AddIns` (an `init` property, so the existing positional call sites are untouched). `SetRecipeAsync` adds the linked usages together, saves once so every one has the id its add-ins need, then writes each one's lines — the same "save for the id, then reline" shape the owned loop already uses. `ProductSubAssemblyUsageRepository.GetAddInsForProductAsync` reads them back, on the interface Products and Reports already inject, so no ViewModel constructor changed.
    - **`ReportsViewModel.CalculateMarginRowsAsync` had to learn about them**: it is the only place that costs a product without going through `ProductUsageEdit`, reading a sub-assembly's stored totals as the usage's batch, so without `CalculateEffectiveBatch` the margin chart silently understated every product with add-ins.
  - A product has **no yield of its own**. Each usage row has its own yield, and those will usually differ between a product's sub-assemblies. That's expected, not an error.
  - Product material cost per piece = the sum of all its usages' cost-per-piece, plus its packaging lines' cost-per-piece.
  - Sub-assembly and product weights are raw input weights, and baking/moisture loss is not modeled for them. Made ingredients are the only place weight loss is modeled (`WeightLossPercent`).
- **PackagingLine**: one packaging material used by a product.
  - FK to a `RawMaterial` of the Packaging type (`PackagingLineRepository` rejects an ingredient), so packaging price changes cascade like ingredient price changes.
  - **`UnitId?`** (`PackagingMaterialUnitId` before the raw materials merge): the unit the line's quantities are entered in — one of the material's own units, or its base unit when empty. Quantities are stored as entered, in that unit. (A length-only `EntryUnitId` existed until the length units were removed on 2026-09-13; this general unit replaced it the same day.)
  - **`QtyPerPiece`**: amount of the packaging material used by one finished piece, in the line's unit (12.7 for 12.7 cm of ribbon, `0.1667` for a 6-piece box, 1 for a label).
  - **`PiecesPerPackagingUnit`**: finished pieces served by one of the line's unit of the packaging material (6 for that box).
  - **`AuthoredField`**: records which of the two the user typed. The other is recalculated as its reciprocal on every edit. Ribbon is naturally entered as `QtyPerPiece`, a box as `PiecesPerPackagingUnit`.
  - Cost per piece = `BufferedCostPerBaseUnit × QtyPerPiece` converted to base units (`ProductRules.CalculatePackagingLineCostPerPiece(costPerBaseUnit, qtyPerPiece, baseUnitsPerEntryUnit?)`, passed the buffered cost), computed on read.
  - Example: a ribbon costs ₱45.00 per roll. Its base unit is cm and a roll holds 1000 cm, so it costs ₱0.045 per cm. One product uses 12.7 cm per piece (₱0.5715); another is entered as 0.08 m per piece (8 cm → ₱0.36).
  - Storing both directions differs from `ProductSubAssemblyUsage` on purpose. People describe packaging quantities both ways, but they describe recipe weights only one way.
- **CostingParameters**: labor, overhead, administrative (office, permits, bookkeeping; added 2026-09-14, at least 0, default 0), margin %, VAT. **Since 2026-09-15 labor, overhead and administrative are percentages of the material cost** (`LaborPercent`, `OverheadPercent`, `AdministrativePercent`, at the user's request), not pesos per piece: the material cost is the product's sub-assemblies plus its packaging per piece, and 25% labor on ₱20 of materials is ₱5 (`CostingRules.CalculateCostFromMaterialPercent`). They were `LaborCost`, `OverheadCost` and `AdministrativeCost` until then. **Always independent per product**, even for derived/linked products.

### Derived products (Phase 10; reworked 2026-09-14)

Some products derive from others (e.g. Special Ensaymada Small from Special Ensaymada Big, differing only in weight; or products sharing a dough sub-assembly but differing in toppings). Since 2026-09-14, when sub-assemblies became owned by products, deriving works like this:

- **Link a sub-assembly**: a product uses another product's sub-assembly, or a standalone one, as it is, through a `ProductSubAssemblyUsage` of it. The lines are the owner's (or the Sub-Assemblies screen's) and follow its every change (read-only in the linking product); the **piece size is the linking product's own**, so Small and Big can share a dough at 30 g and 60 g a piece. Links don't chain (only an owner's own or a standalone sub-assembly can be linked), so there's nothing to cycle. A linked section can be turned into the product's own with **Make a Copy**.
- **Copy a sub-assembly**: a new sub-assembly of the product's own, starting from another product's or a standalone one's lines, name (made unique within the product) and role. Nothing connects it to its source afterward.
- The Products form's modes read **New sub-assembly**, **Link an existing one** and **Copy an existing one** (since 2026-09-15; "…another product's" before), and its picker, **Existing Sub-Assembly**, lists standalone ones first (`GetLinkableAsync`), as "Butter Glaze — Sub-Assemblies (Finishing)". A linked standalone section's badge reads "From Sub-Assemblies" (`ProductUsageEdit.SourceNameOf`, the one place that names where a linked sub-assembly comes from). A new, unsaved product is offered them too: `RefreshLinkableOptions` matches `OwnerProductId is null` first, since a null owner compared with a new product's null id would otherwise count as its own.
- **Link the packaging** (`PackagingLink`, table `PackagingLinks`, one per product): a product's packaging reads through to another product's instead of owning lines. It's saved at once, can be repointed or removed at any time, and **unlinking never loses data**: it first materializes the lines it shows (resolved through the link) as the product's own, then removes the link. Chains are allowed (C's packaging linked to B's linked to A's) and resolved recursively at read time; a cycle is rejected when a link is made (`PackagingLinkRules.EnsureNoCycle`). A product whose packaging another links can't be deleted until that link goes.
- **Clone** (`IProductCloner.CloneAsync`, one transaction): a one-time copy of a product as saved. **Every sub-assembly it uses, its own and another product's, becomes the clone's own copy** (name, role, lines and piece size), plus its packaging as it shows (resolved through a packaging link — a clone never inherits a packaging link, only the data) and its `CostingParameters`. Until 2026-09-14 a clone pointed at the same sub-assemblies as its source, so editing one changed both.
  - **A standalone sub-assembly stays linked** (2026-09-15, the user's choice), at the same piece size: it's kept apart to be shared, so the clone follows it like its source does.
- **`CostingParameters`** (labor/overhead/administrative/margin/VAT) always stay independent per product: nothing links them.
- **Superseded (2026-09-14): role-tab Live Template links** (`ProductTabLink` with `TabKind = SubAssemblyRole`), which linked all of a product's sub-assemblies in one role to the same role on another product, weights and all. Sub-assembly links replaced them (the user's choice): they cover sharing a recipe, and each product keeps its own weight. What nothing does any more is follow the source's weights, or pick up sub-assemblies added to the source's role later. Migration `ProductOwnedSubAssemblies` turned every role-tab link into links to the sub-assemblies its role showed, at the same weights, and renamed what was left of `ProductTabLinks` (the Packaging-tab links) to `PackagingLinks`.

## Syncfusion UI Framework

The app is styled with **Syncfusion Essential Studio for WPF 34.2.7**, licensed via the `SYNCFUSION_LICENSE_KEY` environment variable, and Syncfusion's **Windows11Light** theme.

- **The theme is Syncfusion's official `Syncfusion.Themes.Windows11Light.WPF` package (Phase 16).** It depends only on `Syncfusion.SfSkinManager.WPF` and `Syncfusion.Licensing`, and it styles every Syncfusion control, so adopting a new control never needs theme work. It replaced a trimmed in-repo theme project (see "Why the theme is no longer trimmed" below) — briefly via a locally packed Theme Studio export, then this package, which is the same theme.
  - **Every Syncfusion package is pinned to the same version, currently `34.2.7`.** The theme package requires `SfSkinManager`/`Licensing` at its own version, NuGet rejects the mismatch as a downgrade (`NU1605`), and Syncfusion doesn't support mixing versions across its assemblies — so upgrading any Syncfusion package means upgrading all of them together in `TinapayanRMS.UI.csproj`. The `34.2.2` → `34.2.7` upgrade (a patch within the 34.2 release) kept the same license key: no license popup at startup. A move to a new feature release (e.g. 34.3) needs a new key from the Syncfusion account.
  - **One theme gap is patched in the app**: the theme's `SfTextBoxExt` style — unlike its `ComboBoxAdv`, `DoubleTextBox` and `DateTimeEdit` styles — never sets `VerticalContentAlignment`, so the text sits against the top of any box taller than its text (every one, at the 32px `SizeMode="Touch"` height the app used until 2026-09-15). `App`'s static constructor calls `Control.VerticalContentAlignmentProperty.OverrideMetadata(typeof(SfTextBoxExt), new FrameworkPropertyMetadata(VerticalAlignment.Center))`, changing the type's default so every instance (including future ones) is centred without a `Style` on the control; it must run before any `SfTextBoxExt` exists. Verified at runtime: `VerticalContentAlignment=Center`, value source `Default`.
  - **A second `SfTextBoxExt` theme gap: its text sat about 5px further right than the other fields.**
    - The theme's `SfTextBoxExt` template puts a fixed `Margin="10,0,0,0"` on `PART_ContentHost`. `DoubleTextBox`'s template uses 3px of padding instead.
    - Measured in an off-screen replica with the same theme and Touch size, a Name box's text started 13px from its left edge. A `DoubleTextBox` started at 8px and a `ComboBoxAdv` at 7px.
    - The template passes `Padding` (the theme sets -1) to the text presenter inside that margin. `App`'s `AlignTextBoxText` class handler, on `SfTextBoxExt.Loaded`, sets a left padding of -6, which moves the text to 8px.
    - That padding has to be a local value. The theme sets `Padding` through the control's default style (value source `DefaultStyle`), which outranks an `OverrideMetadata` default. A `SetCurrentValue` at `Loaded` was tried first and didn't survive.
    - A `Padding` set in XAML still wins.
  - **A third `SfTextBoxExt` theme gap: its watermark sat at the top of the box, 4px right of typed text.** The template shows `Watermark` in a plain `ContentControl`, whose default template honors neither `VerticalContentAlignment` nor `Padding`, so neither fix above reaches it. `App.xaml`'s `AlignedWatermarkTemplate`, set as the box's `WatermarkTemplate`, centers the hint and moves it 4px left. Measured with the same text typed and as the watermark (a true-size capture with the blinking caret filtered out by keeping each pixel's brightest value across frames), both now start 8px in and cover the same rows. Give it to any `SfTextBoxExt` with a `Watermark`; today that's the Raw Materials search box.
- **Core control set**: the app adopts `SfDataGrid` (lists/grids), `Syncfusion.SfInput.WPF`'s edit controls (`ComboBoxAdv`, `AutoComplete`, `MaskedTextBox`, `DateTimeEdit`, `CurrencyTextBox`, and others), `ButtonAdv`, `TabControlExt`, `DockingManager`/`Ribbon` for the app shell, and `SfChart` for reporting. `TinapayanRMS.UI` takes its own `PackageReference`s (pinned to the shared Syncfusion version above) for exactly these.
  - **`DateTimeEdit`'s bindable date property is `DateTime`, not `Value`** (`Syncfusion.Windows.Shared.DateTimeEdit`, in `Syncfusion.Shared.WPF`) — it doesn't follow the `Value`-property convention `DoubleTextBox`/`IntegerTextBox` use. Confirmed by reflecting over the built assembly (`[System.AppDomain]::CurrentDomain.GetAssemblies() | Where Name -eq Syncfusion.Shared.WPF`, then `.GetType(...).GetProperties()`) rather than guessing again after the compiler rejected `Value`.
  - **Every editable `DoubleTextBox` binds `Value` with `UpdateSourceTrigger=PropertyChanged`** (2026-09-13). Without it the typed value reaches the ViewModel only when the box loses focus: the Syncfusion DoubleTextBox skill says to bind this way "for live updates", and Syncfusion's unit-converter showcase does.
    - It showed up as a dead click: Add Line (the BOM and Sub-Assemblies line editors) stays disabled until the quantity is positive, and a disabled button doesn't take focus, so the first click after typing a quantity neither committed it nor added the line.
    - It also kept the Purchase Cost Setup's cost per base unit and Products' Price Summary from updating as a number is typed.
    - Verified in the app on a new made ingredient (quantity starting at 0): with the cursor still in Quantity, Add Line was already enabled, and one click added the line. Typing 1234.5 arrived intact, with no reformatting mid-typing.
    - `Value` is registered on `DoubleTextBox` itself, so unlike the `SfTextBoxExt` default in `App.xaml.cs`, `OverrideMetadata` can't change the default; set it on each new binding.
  - **`ButtonAdv` icons use `IconTemplate` (a `DataTemplate`), not `SmallIcon`/`LargeIcon`** — those two want an `ImageSource` (a bitmap/vector image file), not a font glyph. With no `IconTemplate` set, the Windows11Light theme falls back to a generic placeholder glyph on every button (reported as "always shows the letter A"). Icons are **Segoe Fluent Icons, falling back to Segoe MDL2 Assets** (`App.xaml`'s `IconFontFamily` resource) — Windows' own icon font, so no extra icon package, and it matches the theme natively. Four reusable `DataTemplate` resources in `App.xaml` (`AddIconTemplate` U+E710, `SaveIconTemplate` U+E74E, `DeleteIconTemplate` U+E74D, `RemoveIconTemplate` U+E738) cover every button so far — reuse them (`IconTemplate="{StaticResource AddIconTemplate}"`, etc.) on new screens' buttons rather than repeating the glyph markup, and add a new named template here if a future screen needs a verb these four don't cover.
  - **`ButtonAdv.Label` defaults to the literal string `"Button"` when left unset** (confirmed by reflecting on `ButtonAdv.LabelProperty`'s metadata the same way `DateTimeEdit`'s shape was confirmed) — an icon-only button (`MainWindow`'s hamburger nav toggle, Phase 15) needs `Label=""` set explicitly, or that placeholder text renders squeezed into the button's icon-sized box ("the button has text that doesn't fit"). Every other `ButtonAdv` in the app already sets a real `Label` ("New", "Save", …) so this never came up before.
- **Why the theme is no longer trimmed (Phase 16).** Through Phase 15 the theme was an in-repo project, `TinapayanRMS.Theme`, trimmed from Theme Studio's ~50-control output to the controls the app used, with the rest listed in `_ExcludedThemeFolders`. Trimming silently broke `SfDataGrid` from Phase 4 onward: the theme's `SfDataGrid/SfDataGrid.xaml` merges `ChromelessWindow/ChromelessWindow.xaml` (for the grid's own popup windows), which the trim had excluded. That dictionary therefore failed to load (`IOException: Cannot locate resource 'chromelesswindow/chromelesswindow.xaml'`), **and `SfSkinManager` swallows dictionary-load failures** — so every grid rendered with Syncfusion's unthemed generic style (14pt headers larger than the 12pt data, gridlines on every cell, no Touch-mode row heights) while every other control themed normally. It surfaced as "the grid header font is too big"; three fixes edited the theme's header style and did nothing, because that style was never applied.
  - **What found it**: a throwaway runtime diagnostic reading `DependencyPropertyHelper.GetValueSource` on a header cell's `FontSize` — it reported `DefaultStyle` (Syncfusion's generic style) rather than a theme `Style` — followed by loading `SfDataGrid.xaml` directly into a `ResourceDictionary` inside a try/catch, which surfaced the swallowed exception. **When a theme edit appears to do nothing, check at runtime whether the theme style is applied at all before editing it further.** Reading theme XAML, eyeballing screenshots, and UI Automation bounding boxes (which track row height, not font size) all misled here.
  - A scan of the trimmed theme for merged dictionaries pointing at missing folders found `SfDataGrid` was the only affected control the app used; `Ribbon` and `DockingManager` were also broken but unused. The complete theme has none of these gaps, which is why the app now uses Syncfusion's full official theme package instead.
  - Unrelated fact from the trimming era, still true: the export's "SfTabControl" folder is **not** a general tab control — it's `SfChromelessWindow`'s own tab strip (`Syncfusion.SfChromelessWindow.WPF`). The general-purpose tab control is `TabControlExt` (`Syncfusion.Tools.WPF`).
- **Syncfusion's own agent skills are installed in this repo** at `.claude/skills/syncfusion-wpf-*`, taken from [github.com/syncfusion/wpf-ui-components-skills](https://github.com/syncfusion/wpf-ui-components-skills). That repo carries 96 control skills; the ones matching this app's control set were copied in (navigation-drawer, theming, tabcontrol, datagrid, button, combobox, charts, the `SfInput` editors, plus getting-started and licensing) rather than all of them, keeping it to what's actually used. Syncfusion ships them for the cross-agent `skills` CLI (`npx skills add syncfusion/wpf-ui-components-skills`), which installs to `.agents/skills` — **a path Claude Code does not scan** — so they were copied to `.claude/skills/` instead. ## Application Architecture

- **Repository interfaces live in `ApplicationCore`, implementations in `Infrastructure`** (`IRawMaterialRepository`/`RawMaterialRepository`, and so on), consumed by UI ViewModels through DI. `ILookupRepository<T>` in `ApplicationCore`, with one generic `LookupRepository<T>` implementation in `Infrastructure`, covers every simple **read-only** lookup table (`UnitOfMeasure`, `IngredientCategory`, `PackagingCategory`) instead of writing a near-identical class per table. `SubAssemblyRole` turned out **not** to fit this: unlike those three, it's user-editable (Phase 7 gave it its own small embedded management panel), so it needed a dedicated `ISubAssemblyRoleRepository`/`SubAssemblyRoleRepository` with full CRUD instead. `ILookupRepository<T>` is for genuinely read-only lookups only — don't reach for it just because a table is small.
- **`TinapayanRMSDbContext` is registered with `AddDbContextFactory`, not `AddDbContext`.** ViewModels are DI singletons (`MainWindowViewModel`, `RawMaterialsViewModel`, …) so they outlive any single screen, and WPF has no ASP.NET-style per-request scope to hand a plain `AddDbContext`-registered instance to — resolving one into two singleton ViewModels at startup handed them the *same* `DbContext` instance, and two screens' tabs loading concurrently on app startup then threw `InvalidOperationException: A second operation was started on this context instance before a previous operation completed` the first time the app was actually run (not caught by the build or by any test — only by launching it). Every repository instead takes `IDbContextFactory<TinapayanRMSDbContext>` and creates-and-disposes a short-lived context per call (`await using var dbContext = await dbContextFactory.CreateDbContextAsync(cancellationToken);`), which is also naturally safe for concurrent calls from different screens. Follow this pattern for every future repository — never inject `TinapayanRMSDbContext` directly into a repository or ViewModel.
- **CRUD screen pattern** (established by `IngredientsView`/`IngredientsViewModel` and `PackagingMaterialsView`/`PackagingMaterialsViewModel`, Phase 4, merged into `RawMaterialsView`/`RawMaterialsViewModel` on 2026-09-13; card layout and right-rail arrangement reworked Phase 16): a read-only `SfDataGrid` list on the left, bound to a `DynamicData SourceCache<T,int>` via `.Connect().SortAndBind(out collection, comparer).Subscribe()` (not the obsolete `.Sort().Bind()` pair); a master-detail edit form on the right, populated from the grid's `SelectedItem` via a `WhenAnyValue` subscription; `New`/`Save`/`Delete` as `ButtonAdv`s bound to `ReactiveCommand`s. Follow this pattern for future CRUD screens rather than in-grid cell editing, which needs SfDataGrid event wiring that's much harder to get right without a live designer.
  - **Since Phase 16, the shape is a list card plus a right rail, not fixed Grid columns of bare panels.** The root `Grid` carries `PageBackgroundBrush`, `Margin="16"`, and an `ErrorToast` laid over the whole Grid (it takes no row of its own). The Grid is two columns: a `*`-width list card (`CardStyle` `Border` + `SectionHeaderStyle` header + the `SfDataGrid`, `ColumnSizer="AutoWithLastColumnFill"` so every column — including money columns — fits without a horizontal scrollbar; `RawMaterialsView` gives every column a fixed width instead and sizes its list card to fit them (see the Raw Materials note below). A column's `Width` accepts pixels only, as in `Width="120"`. A value of `"*"` or `"2*"` builds cleanly but crashes the app at startup with a `XamlParseException` ("* is not a valid value for Double"), so star-size through `ColumnSizer="Star"` on the grid or on a column), and a fixed ~360px right rail in a `ScrollViewer` holding, top to bottom: a Details card (the edit form), the screen's existing conditional detail card(s) (Price History, BOM, Lines) shown under their existing `Show*` flags with an `EmptyStateStyle` hint (bound through `EmptyStateVisibilityConverter`) filling the same slot when nothing is selected, and a collapsed `Expander` for any embedded lookup panel (see the note below). `UnitsOfMeasureView` and `CategoriesView`, the Settings dialog's tabs, are the simplest case — list card plus a single form card, no expander, no conditional detail card. Every number column in a grid, money included, uses `controls:NumericColumn` (`src/TinapayanRMS.UI/Controls/NumericColumn.cs`). Never use `syncfusion:GridNumericColumn` or `syncfusion:GridCurrencyColumn` directly. Money shows as a bare number (`930.00`, not `₱930.00`), so `GridCurrencyColumn` would add nothing useful: its currency editor never opens in these read-only grids, its parentheses for negatives never apply because costs are never negative, and it doesn't group thousands by default. Money columns use 2 decimals (`NumberDecimalDigits`) for totals and prices, and 4 for per-unit costs (`CostPerBaseUnit`, `CostPerPiece`). `NumericColumn` is a `GridNumericColumn` whose constructor sets the app's defaults: `NumberGroupSeparator=","`, `NumberGroupSizes="3"` and `HorizontalHeaderContentAlignment="Right"`. Out of the box, `GridNumericColumn` doesn't group thousands (`NumberGroupSizes` is `[0]`) and centres its header. A grid column is a `Freezable`, not a `FrameworkElement`, so an implicit `Style` can't carry these defaults. This was confirmed by reflecting over `Syncfusion.SfGrid.WPF` 34.2.7. Set only what differs per column (`NumberDecimalDigits`); a value set in XAML still overrides a default.

  - Like the sample, the rows are `GridUnBoundRow`s, recalculated when the grid loads, resizes, its view's records change, or a group expands or collapses. **What differs was read from the decompiled Syncfusion 34.2.7 (ilspycmd):**
    - **`ShowBelowSummary = true`.** `GridIndexResolver.ResolveUnboundRowToRowIndex` and `GridAddNewRowController.GetAddNewRowIndex` put bottom unbound rows *without* it before the add-new row, which would have sunk the add row below the filler rows. With it they're the grid's last rows.
    - **Those rows are frozen footers** (`UpdateFreezePaneRows` counts them in `FooterRows`). With a short body they follow it (`ScrollAxisBase.GetVisibleLines` starts footers at `Max(HeaderExtent, ViewSize − FooterExtent)`, and `PixelScrollAxis.ViewSize` is `Min(RenderSize, TotalDistance)`), but rows that no longer fit would be pinned over the grid's last rows. So rows that don't fit are removed at once, synchronously, when records are added, a group expands or the grid shrinks, **and after any layout pass that finds them overflowing** (see the crash notes below); adding rows waits for layout (one `Background`-priority recalculation however many triggers ask) and, when the grid grows, for 150 ms of calm.
    - **The space is measured on the row scroll axis:** `GetVisualContainer().ScrollRows` (`PixelScrollAxis`) `RenderSize` against `TotalExtent`, which counts the header, group captions and add-new row as drawn, in O(1). `GridFillerRows.FillerRowCount` (unit-tested) floors to whole rows, so filler never adds a scrollbar.
    - **Only the difference is added or removed, never `Clear()`**: `UnBoundRows`' Reset handling (and `ReCalculateUnboundRowsCount`) counts rows with `Select(cond).Count()`, which counts every row.
    - **The rows are inert.** Unbound rows are selectable, and in a single-selection list a click on one deselects the record, which clears the form beside it; in a table with `EditTrigger="OnTap"` a click anywhere begins editing the current cell (`GridCurrentCellManager.ProcessOnTapped`). A press on a filler row is handled in `PreviewMouseDown`, and `SelectionChanging`/`CurrentCellActivating` are cancelled for one (keyboard). Filler rows are recognised by position (the last rows of `VisualContainer.RowCount`), not with `SfDataGrid.GetUnBoundRow`: an unbound row's `RowIndex` isn't kept up to date as records arrive, and a first version using it swallowed clicks on the Ingredients group caption.
    - **Changing unbound rows reaches the selection** (`GridSelectionController.ProcessUnBoundRowChanged`): it ends an edit of an existing row without committing it, and adding one while the current cell is on the row above the add-new row moves the current cell onto that row. Nothing changes while `View.IsEditingItem` (tried again 150 ms later), and a current cell moved by an addition is put back (`MoveCurrentCell`) — **only from the add-new row, and only onto a record's cell that still exists** (see the crash notes below).

    2. The ids of the selected row, every picker and the lookup-panel selection are recorded. A ComboBoxAdv can clear its own `SelectedItem` when its item is replaced mid-merge, so the ids must be read before merging.

    - `units` is the complete list.
    - A new price only when its unit or amount differs from the latest price (the old Save Price rule; an unsaved unit's id is 0, so it never matches). It names its unit by unit of measure, since a unit added in the same save has no id yet.
    - BOM lines only when they differ from the lines last loaded. An untouched BOM is neither replaced nor, when empty, rejected, so a made ingredient can still be saved before it has lines.
    - Afterwards `LoadCommand` runs, then a fresh copy of the material is selected, so the form reloads what was saved: units with ids, the price history and the BOM.
  - **How it saves: one context and one transaction.**
    - Every step goes through the `internal static` write methods the single-purpose repository methods now share: `RawMaterialRepository.AddAsync`/`UpdateAsync`, `RawMaterialUnitRepository.AddAsync`/`UpdateAsync`/`DeleteAsync`, `RawMaterialPriceHistoryRepository.AddAsync` and `IngredientBomLineRepository.SetLinesAsync`. Each takes the caller's `TinapayanRMSDbContext`, saves to it, and says whether the cost cascade must run.
    - Order: the material; its units, removed first, then updated, then added (so a replacement fits within the limit of two, and a removed unit of measure can come back as a new row); the price; the BOM. Each step saves as it goes, so the next step's checks see what it wrote.
    - A rejection anywhere rolls all of it back, and the cascade runs once, after the commit.
    - The caller's entities are only read, so a rolled-back save never leaves an id on them.
    - `SetLinesAsync` gained the transaction its delete-then-insert lacked.
    - The public single-purpose methods keep their behaviour, and their tests keep covering the checks; `RawMaterialSavePersistenceTests` covers the whole save.
  - **Refreshes keep unsaved units.** `LoadCommand` points each row at its refreshed unit of measure (so a rename in Settings shows) instead of rebuilding the rows from the refreshed material.
    - `NewCommand` clears the details itself: after an unsaved new material nothing was selected, so the selection subscriptions don't fire.
    - Delete Price stays immediate and reloads only the price history, where selecting the refreshed material would drop unsaved edits.

- **After a command changes a row's server-computed fields (Phase 5: `DeletePriceCommand` changing `Ingredient.CurrentCost`/`CostPerGram`), refresh that one row rather than reloading the whole screen**: re-fetch it via the repository's `GetByIdAsync`, `_cache.AddOrUpdate(refreshed)` to update the grid, and reassign the `Selected*` property to the refreshed instance — `SfDataGrid` tracks selection by reference, so leaving `Selected*` pointing at the stale object silently desyncs the form/detail panel from what the grid now shows.
- **`UpdateAsync` must apply fields one by one onto a tracked, freshly-loaded entity — never `dbContext.Set<T>().Update(incoming)` on an object the caller built from scratch.** `Update()` marks *every* property Modified, so an `Ingredient`/`PackagingMaterial` built by a Save command's form fields (which never sets `CurrentCost`/`CostPerGram`, since those are server-owned) would silently overwrite them back to null/0 on every plain rename — a real bug found in Phase 6 while wiring `WeightLossPercent` through the same path, present in both `IngredientRepository` and `PackagingMaterialRepository` since Phase 4 and fixed in both at once. The fix is the same shape every time: load the tracked entity by id, copy across only the user-editable fields, leave every server-computed field untouched, then `SaveChangesAsync`. A related, easy-to-miss corollary: if a user-editable field feeds a server-computed one, the `UpdateAsync` that edits it must recompute that derived field too — it doesn't get another chance to until the next price entry. Originally `PurchaseUnitQty` feeding `CostPerGram`; since the multi-unit work it's an alternative unit's multiplier, which `RawMaterialUnitRepository.UpdateAsync` applies to the cost (and, for ingredients, to recipe-line grams).
- **`ExecuteDeleteAsync` doesn't wrap a failure in `DbUpdateException` the way `SaveChangesAsync` does** — it issues a raw `DELETE` outside the change tracker, so a foreign-key violation surfaces as the driver's own exception (`Microsoft.Data.SqlClient.SqlException` on SQL Server) instead. A test asserting `ThrowAsync<DbUpdateException>()` around an `ExecuteDeleteAsync` call needs `SqlException` instead (found in Phase 6, verifying `IngredientBomLine`'s Restrict-delete FK).
- **FluentValidation (Phase 13) is a thin, UI-facing pre-check layer added *alongside*, never in place of, the existing `ApplicationCore` Rules classes.** One `AbstractValidator<T>` per entity that actually has an editable Save form (`Ingredient`, `IngredientUnit`, `PackagingMaterial`, `PackagingMaterialUnit`, `SubAssemblyRole`, `SubAssembly`, `Product`, `CostingParameters`, `IngredientPriceHistory`, `PackagingPriceHistory` — ten total, the two unit validators added with the multi-unit work; read-only lookups like `IngredientCategory`/`PackagingCategory`/`UnitOfMeasure` deliberately got none, since there's no Save command to guard) mirrors the same rules the repository already enforces via `if/throw`. A Save/Add command runs the validator first and, on failure, sets `ErrorMessage` and returns *before* calling the repository — the repository's own checks are untouched and remain the authoritative last line of defense, so nothing about the already-tested defensive checks changes; FluentValidation only turns an invalid Save into an immediate, friendly on-screen message instead of a thrown exception the user never sees the text of. A "replace-all" set of lines or usages (the usages and packaging lines the Products Save sends, and the BOM lines the Raw Materials Save sends) gets no validator of its own — that cross-row validation already lives in the `ApplicationCore` Rules class the repository calls.
- **`ViewModelBase` (Phase 13)** — a shared `ReactiveObject` base class, introduced only once four CRUD ViewModels needed identical behavior (not before): `ErrorMessage`/`HasError` (an `ObservableAsPropertyHelper` derived from `ErrorMessage`, safe here specifically because `ErrorMessage` is itself a clean `RaiseAndSetIfChanged` property, not one driven by imperative collection mutations — see the OAPH lesson above), `IsBusy`, and a ReactiveUI `Interaction<string, bool> ConfirmDelete` the View fulfills with a real dialog. Two protected helpers wrap every command that touches the database: `RunSafelyAsync(Func<Task> action)` sets `IsBusy` for the call's duration and maps three exception types to a friendly `ErrorMessage` (`InvalidOperationException` → `ex.Message` verbatim, since every Rules class already writes a clear message; `DbUpdateException` → `"That name is already in use."`, the only scenario that type is ever thrown for anywhere in this app; `SqlException` → `"This item is currently in use elsewhere and can't be deleted."`, matching the `ExecuteDeleteAsync`-throws-`SqlException` behavior documented above) and lets any other exception type propagate uncaught, since that would be a real bug, not a user-facing condition to mask; `RunWithConfirmationAsync(message, action)` shows the confirmation dialog first and only calls `RunSafelyAsync` if the user agrees. Every command that calls a repository Delete method is wrapped in `RunWithConfirmationAsync`; every Add/Update-calling command is wrapped in `RunSafelyAsync` (with a validator pre-check, per the FluentValidation point above, when one exists for that entity); a Set-lines/Set-usages command is `RunSafelyAsync` only; a command that only mutates an in-memory edit list (`Add*Line`/`Remove*Line`/`Add*Usage`/`Remove*Usage`) or `NewCommand` is left unwrapped, since it's reversible pre-Save and carries no exception risk. `ProductsViewModel`'s tab-link commands (`LinkTabCommand`/`UnlinkTabCommand`) and `CloneCommand` are `RunSafelyAsync` only, not confirmation-gated — none of them destroy data (unlinking specifically *materializes* the tab's data rather than removing it, per the Phase 10 note above).
- **Serilog (Phase 13)** writes a daily rolling file to `logs/tinapayanrms-.log` under the app's base directory, 31-day retention, configured once via a static `Log.Logger` built in `App`'s static constructor (so even a licensing failure in that same constructor gets logged) and registered in DI as a `Serilog.ILogger` singleton. - **A "replace-all" editor's referenced-entity validation must run *before* `ExecuteDeleteAsync`, never only implicitly via a dictionary lookup or a database FK constraint afterward** — a real, latent bug found and fixed in Phase 14's coverage audit. `PackagingLineRepository.SetLinesAsync` and `ProductSubAssemblyUsageRepository.SetUsagesForRoleAsync` (both Phase 8) already got this right: they build a lookup of the referenced entities that actually exist and loop over the incoming rows checking each one, throwing a friendly `InvalidOperationException` immediately, all *before* the old rows are deleted. `SubAssemblyLineRepository.SetLinesAsync` (Phase 7) and `IngredientBomLineRepository.SetLinesAsync` (Phase 6) did not: both deleted the existing lines first and only discovered a bad reference afterward — the former via a plain dictionary indexer throwing a raw, unfriendly `KeyNotFoundException`; the latter via the database's own `Restrict` FK constraint throwing `DbUpdateException` at `SaveChangesAsync`. Neither path had a test covering "the new set references something that doesn't exist," which is exactly why it went unnoticed since Phase 6/7.   - **Retrofitting a status-bar row onto an existing `Grid` needs `Grid.Row` added to every pre-existing child, not just the new row itself.** WPF defaults an unset `Grid.Row` to `0`; inserting a new `RowDefinition="Auto"` above the existing content and giving only the *new* status-bar element `Grid.Row="0"` leaves every already-existing child (which never had an explicit `Grid.Row` before, back when there was only one row) silently defaulting to `Grid.Row="0"` too, overlapping the status bar. Caught and fixed in `IngredientsView.xaml` by re-reading the file after the first edit; applied correctly from the start in `PackagingMaterialsView.xaml` and `SubAssembliesView.xaml` afterward. `ProductsView.xaml` doesn't use a column-based `Grid` at all (its panels are a horizontally-scrolling `ScrollViewer` of `StackPanel`s, per the CRUD screen pattern note above) — for that shape, wrap the existing `ScrollViewer` in an outer two-row `Grid` (status bar in row 0, the untouched `ScrollViewer` in row 1) instead of touching every inner panel.
  - **Sending synthetic `WM_LBUTTONDOWN`/`WM_LBUTTONUP` directly to a window's `HWND` (via `SendMessage`/`PostMessage`, with screen-to-client-translated coordinates) doesn't reliably drive a Syncfusion `ButtonAdv`'s click, even though it targets the exact window and never touches the real screen cursor** (tried in Phase 13, verifying the new validation/confirmation wiring while the user had a game occupying the foreground — see the "can't win against a real foreground app" lesson above). Syncfusion's WPF controls also don't expose the standard UI Automation `InvokePattern` (`GetSupportedPatterns` on a `ButtonAdv` returns only `SynchronizedInputPattern`), so `AutomationElement`-based invocation doesn't work either. Both were dead ends for exercising a write-path command without either real OS focus or a real physical click — which matches, and reinforces, the existing Phase 5/7 guidance to rely on integration tests plus a line-by-line binding review for write paths when the app can't safely be given real focus.

## Reactive Costing Cascade

The core design problem is that a price change on any ingredient or packaging material must ripple up through everything that uses it, automatically. The cascade has two starting points, one per raw material type, and both end at the product:

```
Price entry added for an ingredient
  → purchased ingredient's CostPerBaseUnit (per gram) recomputed
    → every made ingredient that uses it recomputed, up every level of the BOM tree
      → every SubAssemblyLine using a changed ingredient recomputed
        → SubAssembly.TotalCost recomputed
          → every ProductSubAssemblyUsage of that sub-assembly recomputed ─┐
                                                                           ├→ Product total cost recomputed
Price entry added for a packaging material                                 │    → Product margin / selling price recomputed
  → packaging material's CostPerBaseUnit recomputed                        │
    → every PackagingLine using it recomputed ─────────────────────────────┘
```

The original idea was to model this with DynamicData `SourceCache<T>`s joined via `.Connect()`/`.InnerJoin()`/`.TransformMany()`, so derived observable collections update themselves. **That's not what got built.** Phase 6 established a different, simpler pattern first — a pure ordering function plus a stateful database orchestrator, described below — and it worked well enough that Phase 11 extended the *same* shape to the sub-assembly branch instead of introducing DynamicData joins partway through. EF Core stays the single source of truth throughout; nothing here lives only in an in-memory observable.

**Two costs go up the tree side by side** (since the buffered cost, 2026-09-14): the true `CostPerBaseUnit` and the `BufferedCostPerBaseUnit`. Every write that sets one sets the other: `RawMaterialRules.ApplyLatestPrice` for a purchased material, and `IngredientCostPropagator`, which runs `IngredientBomRules.CalculateCost` twice per made ingredient (true costs, then buffered costs plus its own buffer). Everything downstream reads the buffered one: `SubAssembly.TotalCost` (`SubAssemblyCostPropagator`, `SubAssemblyLineRepository`), sub-assembly line costs, and packaging line costs in Products and Reports. A buffer edit is one more way a cost changes: `RawMaterialRepository.UpdateAsync` reprices a purchased material's buffered cost itself and asks for the cascade for any ingredient whose buffer changed (packaging needs none, as below).

The one nesting exception is made ingredients: their BOMs nest to any depth, so that part of the cascade can't be a fixed one-hop join. An ingredient's cost can change from a new price entry, a BOM line edit, a `WeightLossPercent` edit, or a linked ingredient's link or share edit; when it does, the made ingredients that depend on it need recomputing in dependency order, components before the ingredients built from them. Sub-assemblies don't nest (a `SubAssemblyLine` only ever references an `Ingredient`, never another `SubAssembly` — Phase 7), so that branch needed no ordering logic at all, just "recompute every sub-assembly touched."

**Ingredient branch — implemented Phase 6** as `IngredientCostGraph.GetDependentsInOrder` (`ApplicationCore`, pure graph logic, no I/O — reverse-BFS from the changed ingredient to find every made ingredient that transitively depends on it, then a DFS-based topological sort restricted to that set) and `IngredientCostPropagator.RecomputeAndPropagateAsync` (`Infrastructure`, the orchestrator: loads every ingredient and every BOM line once, calls the graph function, walks the resulting order recomputing each ingredient's cost per gram (`CostPerBaseUnit`) from its own lines — reading each component's cost directly off the already-loaded, already-correct dictionary, never re-walking that component's own tree — then a single `SaveChangesAsync`). Every write path that can change an ingredient's cost calls it: `RawMaterialPriceHistoryRepository`'s add/update/delete (for an ingredient's price), `RawMaterialRepository.UpdateAsync` when `Source == Made` (a `WeightLossPercent` edit), `RawMaterialUnitRepository.UpdateAsync` when an ingredient unit's new multiplier reprices it (its latest price is in that unit), and `IngredientBomLineRepository.SetLinesAsync`. (Before the raw materials merge these were `IngredientPriceHistoryRepository` and `IngredientRepository`.) It loads ingredients only (`Type == Ingredient`), since packaging never takes part.

**Linked ingredients needed no new ordering** (2026-09-16). A linked ingredient's link is one more edge in the same graph: `IngredientCostPropagator` adds `linked → linked-to` beside every `made → component` before calling `IngredientCostGraph.GetDependentsInOrder`, which is unchanged, so egg white is recomputed after the egg and a made ingredient using egg white after egg white. In the walk, a linked ingredient is costed with `RawMaterialRules.LinkedCost` from its linked-to ingredient's already-fresh true cost, takes that ingredient's buffer percent, and its buffered cost is its cost with that percent on top, and a made one with the BOM rollup as before. A linked ingredient that's itself the changed one is recomputed first, as a made one is: `RawMaterialRepository` asks for the cascade when a linked ingredient is added or updated.

**Sub-assembly branch — implemented Phase 11** as `SubAssemblyCostPropagator.RecomputeAndPropagateAsync` (`Infrastructure`, taking the *set* of ingredient ids whose cost just changed — no per-ingredient ordering needed, since sub-assemblies don't nest: finds every `SubAssemblyLine` referencing any of them, groups by `SubAssemblyId`, and recomputes each affected sub-assembly's `TotalWeight`/`TotalCost` from *all* of its own lines' current ingredient costs — not just the changed line — in one loaded-once-saved-once pass). `IngredientCostPropagator` calls it at the end of its own run, passing `changedIngredientId` itself (whose own cost the caller already updated, for a Purchased ingredient) unioned with every made ingredient it just recomputed — so this one call, from the existing three ingredient-branch write paths, now reaches every sub-assembly transitively affected, at any BOM depth.

**Product and packaging branches needed no propagation code at all.** Neither `ProductSubAssemblyUsage`'s cost-per-piece, `PackagingLine`'s cost-per-piece, nor a product's total material cost is stored anywhere (Phase 8's "derived values are computed on read" decision) — they're plain `ProductRules` functions reading `SubAssembly.TotalCost` and the packaging material's `CostPerBaseUnit` fresh every time a screen asks. As long as those two columns are correct — which the ingredient and sub-assembly propagators now guarantee, and which the price history repository has guaranteed for packaging since Phase 5 (`RawMaterialPriceHistoryRepository` since the raw materials merge, which skips the ingredient cascade for a packaging price) — a product's displayed cost is automatically correct too, with nothing to propagate into. Verified end-to-end (`ReactiveCostCascadeTests.cs`): a price change several BOM levels deep reaches a sub-assembly's `TotalCost` with no direct edit to that sub-assembly, and a product's live-computed cost-per-piece reflects it immediately, with zero product-level or packaging-level code involved. Since 2026-09-14 a usage's weight per piece is itself computed on read (`ProductRules.ResolvePieceSize`, from the typed figure and the current `TotalWeight`), so a product that typed a yield sees its piece weight, and so its cost per piece, move when the owner changes the batch — with nothing to propagate either. Sub-assembly ownership didn't change the cascade at all: it still runs per sub-assembly, and a linked product reads the same row.

**Add-ins needed no propagation either, for the same reason** (2026-09-16). A `UsageAddInLine` stores only `UsageId`, `IngredientId` and `Grams`; its cost is `Grams × the ingredient's BufferedCostPerBaseUnit`, read fresh, and no derived total about it is stored anywhere. So the two propagators are untouched, and `SubAssemblyCostPropagator` deliberately still recomputes a sub-assembly from `SubAssemblyLines` alone — an add-in must never move the batch of a sub-assembly another product owns. `ReactiveCostCascadeTests` pins both halves: repricing an add-in's ingredient moves the linking usage's cost per piece, and leaves `SubAssembly.TotalCost` exactly where it was.

This does mean a product **already on screen** only reflects a price change made from a *different* screen once the user reselects it (or navigates back to it) — there's no cross-screen live push. That's the one piece of the original DynamicData-joins vision this phase deliberately didn't build; revisit only if that specific UX gap is ever reported as a real problem, not preemptively.

### Open items (for later phases)


- **Adopting a Syncfusion control the app doesn't use yet.** The theme package already styles every Syncfusion control, so a new control only needs its `PackageReference` in `TinapayanRMS.UI`, at the same version as the other Syncfusion packages. (Through Phase 15 this took a three-step procedure against the trimmed `TinapayanRMS.Theme` project — obsolete since the theme became a package.)
  - If the control is built around Syncfusion's newer "Sf*"/`Syncfusion.UI.Xaml.*` theming framework (as opposed to the older `Syncfusion.Windows.Tools.Controls`/`Syncfusion.Windows.Shared` control set), **check the locally installed Syncfusion Sample Browser source before assuming a property works the way its name suggests.** Essential Studio installs its full demo source to `C:\Users\Public\Documents\Syncfusion\WPF\<version>\SampleBrowser\` (grouped by area, e.g. `navigation\NavigationDrawer\Views\*.xaml`), and it is the authoritative answer to "which properties is this control actually meant to be set with, together" — a question neither the property list, the XML docs, nor the generated theme XAML answers. Demo filenames don't always contain the control's name (`DisplayMode.xaml`, `Hierarchical.xaml`), so grep contents rather than globbing filenames. These controls can have several control templates selected by a mode property, each honoring a genuinely different subset of properties, so the "does this control support X" question is really "does the template for the mode I'm in support X".
  - **`SfNavigationDrawer` is the worked example** (Phase 15, `MainWindow`'s navigation drawer): it has two control templates selected by `DisplayMode`. The `Compact`/`Expanded` template draws the drawer's **own built-in hamburger toggle** (a `ToggleButton` two-way bound to `IsOpen`, so no toggle button of your own is needed) and renders the `Items` collection through a `NavigationView`. The `Default` template has **neither** — no toggle at all, and it presents `DrawerContentView` instead, ignoring `Items` entirely. Setting `Items` under `DisplayMode="Default"` compiles fine and the drawer's own chrome still themes correctly, so it looks like a theming problem, but nothing from `Items` ever renders. `MainWindow` uses `DisplayMode="Compact"`: a `CompactModeWidth`-wide icon rail that expands to `DrawerWidth` over the content.
  - **A `NavigationItem`'s icon goes in `Icon` (a real element), not `IconTemplate`, and the element has to center itself** — `HorizontalAlignment="Center" VerticalAlignment="Center"`, as every icon in Syncfusion's own `DisplayMode.xaml` demo does. The item template drops the icon into a fixed-size `ContentPresenter` with a negative left margin, so an unaligned glyph renders visibly off-center. In compact mode the icon is the *only* thing visible for each destination, so every item needs one.
  - **`TabControlExt.CloseMode="Hide"` (Phase 16), not the default `Delete`, is what actually makes "close a tab, reopen it from the drawer" work.** The first implementation (Phase 15) left `CloseMode` at its default and had the drawer's click handler re-add the closed `TabItemExt` instance to `MainTabControl.Items` if it was missing (`if (!Items.Contains(tab)) Items.Add(tab);`). That compiled, selected the right content, and even looked right in a quick check — but a real close-then-reopen cycle (caught only once the user actually did it) showed the tab's *content* switching in correctly while its *header* never reappeared in the strip at all: `TabControlExt`'s header strip doesn't regenerate a header for a `TabItemExt` instance that has ever actually left `Items` under `Delete` mode, even when the exact same instance is re-added later. `CloseMode="Hide"` (`Syncfusion.Windows.Tools.Controls.CloseMode`, confirmed against `Syncfusion.Tools.WPF.xml`'s member docs) sidesteps the whole problem: a closed tab is only `Visibility.Collapsed`, never removed from `Items`, so `ShowTab` just needs `tab.Visibility = Visibility.Visible;` before selecting it — the instance was never invalid to begin with. This also fixed a smaller side effect of the `Delete`-mode workaround: a reopened tab used to land at the *end* of the tab strip (`Items.Add` appends) instead of back in its original position, since `Hide` mode never reorders `Items` at all. (Syncfusion also ships a fully built alternative for exactly this scenario — `TabListContextMenuOptions` including `ShowHiddenItems` on the tab-list dropdown menu, which lists and restores hidden tabs on its own — but the app keeps the `SfNavigationDrawer` as the single reopen affordance rather than offering two different ones for the same action.)

## Conventions

- The layered architecture is fixed: `Domain` has no external dependencies, business and costing rules live in `ApplicationCore`, and EF Core and other I/O stay in `Infrastructure`.
- The MVVM toolkit is **ReactiveUI**, not CommunityToolkit.Mvvm. Use `ReactiveObject`, `ReactiveCommand`, `WhenAnyValue`, etc.
- **Every file goes in the folder for its kind, and the folder is its namespace** (see Solution Structure). A new View goes in `Views/` with its ViewModel in `ViewModels/`, a new repository in `Repositories/` with its interface in `ApplicationCore/Interfaces/`, a new rule in `Rules/` with its test in `tests/…/Rules/`, and so on. Nothing goes at a project root except app-startup plumbing.
- **Prefer Syncfusion controls over native WPF controls whenever a Syncfusion equivalent is available** (e.g. `ButtonAdv` over `Button`, `TabControlExt` over `TabControl`, `ComboBoxAdv`/`SfDataGrid`/the `SfInput.WPF` edit controls over their native counterparts), so the whole UI picks up the Windows11Light theme consistently. Fall back to a native control only when no Syncfusion equivalent exists. Adopting a new Syncfusion control only needs its package added to `TinapayanRMS.UI` — the packaged theme already covers every control Theme Studio knows about.
- **Decimal precision**: keep `decimal` values at full precision through the whole cascade, and round only for display and for the final selling price. Rounding each per-piece cost before summing adds up to drift. Enforced once for every `decimal` column via `TinapayanRMSDbContext.ConfigureConventions` (`decimal(18,4)`, set in Phase 4 when the first `decimal` columns were added), rather than per-property — a future column can't silently fall back to SQL Server's `decimal(18,2)` default and truncate a fractional cost.
- **Use modern C# 14 / .NET 10 idioms** rather than older patterns still valid in the language: primary constructors, collection expressions (`[..]`), required members, file-scoped namespaces, pattern matching, and `record`/`record struct` for immutable data shapes, in line with what's already in the codebase (e.g. `CategoryPersistenceTests`'s primary constructor, `WellKnownUnitOfMeasureIds`'s collection expression). Don't reach for an older, more verbose equivalent just because it's more familiar.
- **Correctness and performance take priority over brevity or convenience.** Favor the approach that is provably correct and doesn't waste allocations, database round-trips, or UI-thread work, even if a shorter or simpler alternative exists — e.g. querying only the columns/rows actually needed rather than materializing more and filtering in memory, and avoiding unnecessary intermediate collections in hot paths like the reactive costing cascade.
- This document is a living plan. Update it as phases complete or decisions change, so it stays the single source of truth for the project.
