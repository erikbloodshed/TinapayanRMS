# TinapayanRMS — Project Guide & Build Plan

Product recipe management & costing app for Tinapayan Festival Bakeshoppe. Tracks ingredient expenses, recipe/product margins, and cascades ingredient and packaging price changes up through sub-assemblies and finished products automatically.

## Tech Stack

- **Language / Runtime**: C# 14, .NET 10 (`net10.0`; `net10.0-windows10.0.19041.0` for the UI and Tests projects — ReactiveUI.WPF requires at least that Windows SDK version, and the bare `net10.0-windows` moniker resolves to `windows7.0`, which is too low)
- **UI**: WPF, styled with **Syncfusion Essential Studio for WPF 34.2.2** and a custom Windows11Light theme authored in Syncfusion Theme Studio
- **MVVM**: ReactiveUI (24.x). This version requires explicit builder-pattern initialization before any `ReactiveObject` is touched — `RxAppBuilder.CreateReactiveUIBuilder().WithCoreServices().WithWpf().BuildApp()` — done once per process by `TinapayanRMS.UI/ReactiveUIBootstrapper.cs`. It also dropped `System.Reactive` as a dependency, so that package is referenced directly wherever Rx LINQ operators (`.Select`, `.Where`, …) are used on an `IObservable<T>`.
  - **`ReactiveCommand.Create`/`CreateFromTask`'s parameterless overloads return `ReactiveCommand<RxVoid, RxVoid>`** (`ReactiveUI.Primitives.RxVoid`), not `ReactiveCommand<Unit, Unit>` — this fork doesn't use `System.Reactive.Unit` for that. Import the type via a using-alias (`using RxVoid = ReactiveUI.Primitives.RxVoid;`), never `using ReactiveUI.Primitives;` wholesale — that namespace also carries its own C# 14 extension-member `Select`/`Where`/`Subscribe`, which collide (CS0121, ambiguous call) with `System.Reactive.Linq`'s the moment both are in scope over the same observable.
- **Reactive collections**: DynamicData
- **Persistence**: EF Core 10.0.12 → SQL Server (db name `TinapayanRMS`)
- **DI / Hosting**: `Microsoft.Extensions.Hosting` + `Microsoft.Extensions.DependencyInjection`, wired via `HostBuilder` in `TinapayanRMS.UI/CompositionRoot.cs`, called from `App.xaml.cs`
- **Validation**: FluentValidation
- **Logging**: Serilog (rolling file sink)
- **Charts**: Syncfusion SfChart (`Syncfusion.SfChart.WPF`) for margin/price-trend reporting — replaces the originally-planned LiveCharts2
- **Testing**: xUnit v3, AwesomeAssertions, NSubstitute, Respawn. Integration tests run against a locally installed SQL Server instance (such as LocalDB or SQL Server Express), and Respawn resets that database between tests. `AwesomeAssertions` replaces `FluentAssertions`: FluentAssertions 8+ requires a paid commercial license for use in a for-profit product, and AwesomeAssertions is a same-API, MIT-licensed fork of the last free FluentAssertions 7 release, created for exactly this situation.
- **Solution format**: `.slnx`
- **`dotnet test`**: the .NET 10 SDK dropped VSTest support for `dotnet test`; running under the new Microsoft.Testing.Platform mode needs a `test.runner` setting in `global.json` at the repo root (already added). Run tests with `dotnet test --solution TinapayanRMS.slnx`.
- **Syncfusion license key**: read from the `SYNCFUSION_LICENSE_KEY` Windows user environment variable and registered in `App`'s static constructor (`TinapayanRMS.UI/App.xaml.cs`), before anything else in the process touches a Syncfusion type. Running the app or its tests on another machine requires that variable to be set there too.

## Domain Model

- **UnitOfMeasure**: a flat lookup table with only `Id`, `Name` and `Abbreviation`. It has no base unit, conversion factor, or self-FK. It holds both standard units and purchase units: mass (Gram), count (Piece), length (Millimeter, Centimeter, Inch, Meter), and purchase units (Tin, Pack, Bag, Case, Box, Roll, etc.). Units are defined globally here, but each conversion ratio belongs to a specific material. A material's **standard unit** is the unit its quantities and costs are tracked in. For ingredients it is always the gram; each packaging material declares its own. The table can stay flat because each material has exactly one standard unit. The only conversion between two units in the table is between length units, and it uses fixed physical constants in code rather than table data.
  - **Length units** (Millimeter, Centimeter, Inch, Meter) are seeded rows with fixed Ids, and they can't be edited or deleted. A static `LengthConversion` helper in `ApplicationCore` maps those Ids to their factors (1 cm = 10 mm, 1 in = 25.4 mm, 1 m = 1000 mm); `UnitOfMeasureRules.IsProtected` in `ApplicationCore` is the guard every future edit/delete path must check.
  - **Gram and Piece are also seeded** (Ids 5 and 6), since they're the default standard units for ingredients and for boxes/wrappers respectively, but neither is protected — they can be renamed or removed like any other row. Purchase units (Tin, Pack, Bag, Case, Box, Roll, …) are **not** seeded; those are business-specific and left for the shop owner to add once a Units of Measure management screen exists.
- Materials are split into two separate tables, **Ingredient** and **PackagingMaterial**, each with its own category and price history tables. Nothing is shared between the two sides, so the schema itself stops a packaging material from being put in a recipe, or an ingredient on a packaging line. Packaging materials are always purchased. Ingredients can be purchased or made in-house.
- **IngredientCategory** (Flour, Dairy, …) / **Ingredient**:
  - **The standard unit for every ingredient is the gram.** All ingredient quantities are recorded in grams: sub-assembly lines, BOM lines, sub-assembly total weights, and weight-per-piece. Because of that, `Ingredient` has no standard-unit column.
  - **`Source`**: `Purchased` or `Made`. It is set when the ingredient is created and can't change afterwards, so an ingredient's cost always comes from exactly one place.
  - **`CostPerGram`** (derived): the value every sub-assembly line and BOM line uses, whichever the source.
  - **Purchased** ingredients:
    - `PurchaseUnitId` (FK to UnitOfMeasure) is the unit it's bought in.
    - `PurchaseUnitQty` is the number of grams in one purchase unit (a 25kg flour sack is `25000`). It is the only place an ingredient's purchase unit is converted to grams.
    - Priced through `IngredientPriceHistory`. `CostPerGram = CurrentCost / PurchaseUnitQty`.
  - **Made** ingredients are produced in-house from a bill of materials (BOM):
    - They have no purchase unit, purchase quantity, or price history.
    - **`WeightLossPercent`**: weight lost while making the ingredient (e.g. water boiled off syrup). At least 0 and less than 100, enforced by `IngredientRules.EnsureFieldsMatchSource`.
    - Output grams = `Σ BOM line grams × (1 − WeightLossPercent / 100)`.
    - `CostPerGram = Σ (BOM line grams × component CostPerGram) / output grams`. The formula itself is `IngredientBomRules.CalculateCost`; a component's `CostPerGram` used here is whatever's currently stored on it — see the propagation note below for why that's always safe to read directly rather than walking the tree every time.
    - Example: simple syrup made from 1000g sugar (₱0.09/g, so ₱90) and 500g water (₱0, i.e. never priced — see PLAN.md's PriceHistoryRules note: a literal ₱0 price entry is rejected, so "free" means unpriced, not a zero entry), with 20% weight loss, gives 1500 × 0.8 = 1200g. It costs ₱90 / 1200 = ₱0.075/g.
- **IngredientBomLine**: one component of a made ingredient. It has `IngredientId` (the made ingredient), `ComponentIngredientId` (FK to `Ingredient`, purchased or made), and `Grams`. `IngredientBomRules.EnsureValidLines` rejects an empty set, non-positive grams, or the same component twice (combine it into one line instead).
  - BOMs can nest to any depth: caramel can be made from syrup, and syrup from sugar. `IngredientBomRules.EnsureNoCycle` blocks an ingredient from appearing anywhere in its own BOM tree, checked at save time by walking the *other* made ingredients' current BOM graph.
  - `IngredientId`'s FK is Cascade (deleting the made ingredient takes its own BOM lines with it); `ComponentIngredientId`'s FK is Restrict (deleting an ingredient that's in use as a component is blocked — remove it from the BOM first). Both can't be Cascade: SQL Server rejects two cascade paths from the same table to the same parent table.
  - BOM lines use ingredients only, never packaging.
- **PackagingCategory** (Boxes, Wrappers, Ribbons, …) / **PackagingMaterial**:
  - `StandardUnitId` (FK to UnitOfMeasure) is its standard unit, set per material: Piece for boxes and wrappers, a length unit (mm, cm, inch or meter) for ribbon.
  - `PurchaseUnitId` (FK to UnitOfMeasure) is the unit it's bought in.
  - `PurchaseUnitQty` is the number of standard units in one purchase unit (a pack of 100 boxes is `100` pieces, a 1000cm ribbon roll is `1000` centimeters).
  - Packaging lines use the material's standard unit, with one exception: a material whose standard unit is a length unit can be entered in **any** length unit (see PackagingLine).
- **IngredientPriceHistory** / **PackagingPriceHistory**: a price timeline for each purchased material. Made ingredients have none. Prices are entered **per purchase unit** (the price of one sack or one pack), as they appear on the supplier's receipt. `CurrentCost` on the `Ingredient` or `PackagingMaterial` is recalculated from the latest entry and is also per purchase unit. Cost per standard unit is `CurrentCost / PurchaseUnitQty`.
- **SubAssemblyRole**: an editable lookup table (`Id`, `Name`, `SortOrder`), seeded with Dough, Filling, Topping, Inclusion and Finishing. More roles, such as Glaze, can be added later. `SortOrder` sets the order of a product's recipe tabs. A role can't be deleted while any sub-assembly uses it.
- **SubAssembly** + **SubAssemblyLine**: a sub-assembly is an in-house recipe that products use directly, such as a dough, a filling or a topping. Its lines are the ingredients that make it up.
  - `RoleId` (FK to `SubAssemblyRole`, required): each sub-assembly has exactly one role, so custard is always a Filling, and the Filling tab only offers filling sub-assemblies. To use the same recipe in another role, create a separate sub-assembly.
  - A sub-assembly's role can only be changed while no product uses it. Changing it would move the sub-assembly to a different tab in every product that uses it, and break that tab's links.
  - Each line has an FK to `Ingredient` (purchased or made) and a quantity in grams. Line cost = grams × the ingredient's `CostPerGram`.
  - A sub-assembly has a total weight in grams (the sum of its line grams) and a total ingredient cost.
- **Product** + **ProductSubAssemblyUsage**: a finished product is built from distinct sub-assemblies. It can use several sub-assemblies in the same role (e.g. an ube filling and a cheese filling), but each sub-assembly only once.
  - Each usage stores **`WeightPerPiece`** (grams). The UI accepts either weight-per-piece or yield (piece count) as input, but only `WeightPerPiece` is stored.
  - Yield is derived per usage: `Yield = SubAssembly.TotalWeight / WeightPerPiece`.
  - Usage cost per piece = `SubAssembly.TotalCost × WeightPerPiece / SubAssembly.TotalWeight`. For example, 100g/₱24 filling used at 10g/piece gives ₱2.40/piece, yield 10.
  - Rescaling a sub-assembly batch changes the yield, but the grams in each piece stay the same.
  - A product has **no yield of its own**. Each usage row has its own yield, and those will usually differ between a product's sub-assemblies. That's expected, not an error.
  - Product material cost per piece = the sum of all its usages' cost-per-piece, plus its packaging lines' cost-per-piece.
  - Sub-assembly and product weights are raw input weights, and baking/moisture loss is not modeled for them. Made ingredients are the only place weight loss is modeled (`WeightLossPercent`).
- **PackagingLine**: one packaging material used by a product.
  - FK to `PackagingMaterial`, so packaging price changes cascade like ingredient price changes.
  - **`EntryUnitId`**: the unit this line's quantities are entered in. It is the material's standard unit. The one exception is a material with a length standard unit, which can use any length unit (a ribbon with a cm standard unit can be entered in inch, cm or mm).
  - **`QtyPerPiece`**: amount of the packaging material used by one finished piece, in the entry unit (5 for 5 inches of ribbon, `0.1667` for a 6-piece box, 1 for a label).
  - **`PiecesPerPackagingUnit`**: finished pieces served by one entry unit of the packaging material (6 for that box).
  - **`AuthoredField`**: records which of the two the user typed. The other is recalculated as its reciprocal on every edit. Ribbon is naturally entered as `QtyPerPiece`, a box as `PiecesPerPackagingUnit`.
  - Quantities are stored exactly as entered, in the entry unit. Converting them to the standard unit when saving could lose precision, because cm-to-inch doesn't give a terminating decimal. Keeping the entered value means the user always sees back exactly what they typed.
  - Cost per piece = `PackagingMaterial.CurrentCost / PurchaseUnitQty × QtyPerPiece`, with `QtyPerPiece` first converted from the entry unit to the standard unit through `LengthConversion` (no conversion when the two units are the same).
  - Example: a ribbon costs ₱45.00 per roll. Its standard unit is cm and a roll holds 1000 cm, so it costs ₱0.045 per cm. One product uses 5 in per piece (12.7 cm → ₱0.5715). Another uses 80 mm per piece (8 cm → ₱0.36).
  - Storing both directions differs from `ProductSubAssemblyUsage` on purpose. People describe packaging quantities both ways, but they describe recipe weights only one way.
- **CostingParameters**: labor, overhead, margin %, VAT. **Always independent per product**, even for derived/linked products.

### Derived products

Some products derive from others (e.g. Special Ensaymada Small from Special Ensaymada Big, differing only in weight; or products sharing a dough sub-assembly but differing in toppings). Deriving supports:

- **Clone**: a one-time, fully independent copy.
- **Live Template**: linked sub-assemblies, kept in sync with the source product.
- A separate **"same sub-assembly, different weight"** state, in addition to fully independent. The two products share a `SubAssemblyId` and differ only in `WeightPerPiece`.
- A **tab** is one role on one product, identified by (`ProductId`, `SubAssemblyRoleId`). It holds all of that product's sub-assemblies in that role. Each product also has one **Packaging** tab for its packaging lines. Because a sub-assembly's role can't change while products use it, a tab's identity stays the same for the life of the product.
- Linking is chosen **per tab** when the product is derived, not all-or-nothing. Linking a tab links everything in it, so linking the Filling tab links both the ube and the cheese filling. Afterwards, any tab's link can be repointed to a different product or made fully independent at any time, separately for each tab.
- Live templating covers recipe tabs and packaging lines, but **never** CostingParameters (labor/overhead/margin/VAT), which always stay independent per product.
- Chains of derived products (a derived product used as the base for a further derived product) are allowed.

## Syncfusion UI Framework

The app is styled with **Syncfusion Essential Studio for WPF 34.2.2**, licensed via the `SYNCFUSION_LICENSE_KEY` environment variable, and a custom **Windows11Light** theme originally authored in Syncfusion Theme Studio.

- **`TinapayanRMS.Theme`** is that Theme Studio output, moved into the repo and converted from local-installer `<Reference HintPath>` entries to NuGet `PackageReference`s pinned to `34.2.2`, so the solution restores from nuget.org rather than depending on Essential Studio being installed on the build machine. **No project in the solution requires the Essential Studio installer anymore** — NuGet is the only source for every Syncfusion assembly.
- **Core control set**: the app adopts `SfDataGrid` (lists/grids), `Syncfusion.SfInput.WPF`'s edit controls (`ComboBoxAdv`, `AutoComplete`, `MaskedTextBox`, `DateTimeEdit`, `CurrencyTextBox`, and others), `ButtonAdv`, `TabControlExt`, `DockingManager`/`Ribbon` for the app shell, and `SfChart` for reporting. `TinapayanRMS.UI` takes its own `PackageReference`s (pinned to `34.2.2`) for exactly these.
  - **`DateTimeEdit`'s bindable date property is `DateTime`, not `Value`** (`Syncfusion.Windows.Shared.DateTimeEdit`, in `Syncfusion.Shared.WPF`) — it doesn't follow the `Value`-property convention `DoubleTextBox`/`IntegerTextBox` use. Confirmed by reflecting over the built assembly (`[System.AppDomain]::CurrentDomain.GetAssemblies() | Where Name -eq Syncfusion.Shared.WPF`, then `.GetType(...).GetProperties()`) rather than guessing again after the compiler rejected `Value`.
  - **`ButtonAdv` icons use `IconTemplate` (a `DataTemplate`), not `SmallIcon`/`LargeIcon`** — those two want an `ImageSource` (a bitmap/vector image file), not a font glyph. With no `IconTemplate` set, the Windows11Light theme falls back to a generic placeholder glyph on every button (reported as "always shows the letter A"). Icons are **Segoe Fluent Icons, falling back to Segoe MDL2 Assets** (`App.xaml`'s `IconFontFamily` resource) — Windows' own icon font, so no extra icon package, and it matches the theme natively. Four reusable `DataTemplate` resources in `App.xaml` (`AddIconTemplate` U+E710, `SaveIconTemplate` U+E74E, `DeleteIconTemplate` U+E74D, `RemoveIconTemplate` U+E738) cover every button so far — reuse them (`IconTemplate="{StaticResource AddIconTemplate}"`, etc.) on new screens' buttons rather than repeating the glyph markup, and add a new named template here if a future screen needs a verb these four don't cover.
- **`TinapayanRMS.Theme` is trimmed to that same core set**, not the ~50 assemblies Theme Studio generated by default (which covered every control, including PDF/DocIO/XlsIO/Gantt/Spreadsheet document engines and specialty visualization controls this app has no use for). Trimming turned up two real problems worth remembering:
  - Four packages (`Syncfusion.PivotAnalysis.WPF`, `Syncfusion.Pdf.Base`, `Syncfusion.DocIO.Base`, `Syncfusion.XlsIO.Base`) don't exist at `34.2.2` on nuget.org at all — Syncfusion renamed them (`Pdf.Wpf`, `DocIO.Wpf`, `XlsIO.Wpf`, and the Pivot WPF package under a name not yet tracked down). None of that chain is needed here, so they were dropped rather than chased.
  - The "SfTabControl" folder Theme Studio generated is **not** a general tab control — its XAML resolves `Syncfusion.Windows.Controls.SfTabControl` from `Syncfusion.SfChromelessWindow.WPF`, i.e. it's `SfChromelessWindow`'s own tab strip. The general-purpose tab control is `TabControlExt` (`Syncfusion.Tools.WPF`), which is what's actually kept.
  - The folders backing dropped controls were deleted from `TinapayanRMS.Theme`, not just excluded from compilation — see Open Items below before reaching for one of them again.
- **Applying the theme**: `App.xaml.cs`'s static constructor registers the license (`SyncfusionLicenseProvider.RegisterLicense`) before anything else touches a Syncfusion type; `OnStartup` then calls `SfSkinManager.SetTheme(mainWindow, new Theme("Windows11Light"))` before showing the window. Verified by actually launching the built app and screenshotting the themed `MainWindow` (custom title bar chrome, styled `ButtonAdv`) — not just a successful build.

## Application Architecture

- **Repository interfaces live in `ApplicationCore`, implementations in `Infrastructure`** (`IIngredientRepository`/`IngredientRepository`, and so on), consumed by UI ViewModels through DI. `ILookupRepository<T>` in `ApplicationCore`, with one generic `LookupRepository<T>` implementation in `Infrastructure`, covers every simple **read-only** lookup table (`UnitOfMeasure`, `IngredientCategory`, `PackagingCategory`) instead of writing a near-identical class per table. `SubAssemblyRole` turned out **not** to fit this: unlike those three, it's user-editable (Phase 7 gave it its own small embedded management panel), so it needed a dedicated `ISubAssemblyRoleRepository`/`SubAssemblyRoleRepository` with full CRUD instead. `ILookupRepository<T>` is for genuinely read-only lookups only — don't reach for it just because a table is small.
- **`TinapayanRMSDbContext` is registered with `AddDbContextFactory`, not `AddDbContext`.** ViewModels are DI singletons (`MainWindowViewModel`, `IngredientsViewModel`, …) so they outlive any single screen, and WPF has no ASP.NET-style per-request scope to hand a plain `AddDbContext`-registered instance to — resolving one into two singleton ViewModels at startup handed them the *same* `DbContext` instance, and two screens' tabs loading concurrently on app startup then threw `InvalidOperationException: A second operation was started on this context instance before a previous operation completed` the first time the app was actually run (not caught by the build or by any test — only by launching it). Every repository instead takes `IDbContextFactory<TinapayanRMSDbContext>` and creates-and-disposes a short-lived context per call (`await using var dbContext = await dbContextFactory.CreateDbContextAsync(cancellationToken);`), which is also naturally safe for concurrent calls from different screens. Follow this pattern for every future repository — never inject `TinapayanRMSDbContext` directly into a repository or ViewModel.
- **CRUD screen pattern** (established by `IngredientsView`/`IngredientsViewModel` and `PackagingMaterialsView`/`PackagingMaterialsViewModel`, Phase 4): a read-only `SfDataGrid` list on the left, bound to a `DynamicData SourceCache<T,int>` via `.Connect().SortAndBind(out collection, comparer).Subscribe()` (not the obsolete `.Sort().Bind()` pair); a master-detail edit form on the right built from Syncfusion input controls (`SfTextBoxExt`, `ComboBoxAdv`, `DoubleTextBox`, …), populated from the grid's `SelectedItem` via a `WhenAnyValue` subscription; `New`/`Save`/`Delete` as `ButtonAdv`s bound to `ReactiveCommand`s. Follow this pattern for future CRUD screens rather than in-grid cell editing, which needs SfDataGrid event wiring that's much harder to get right without a live designer. `ProductsView` (Phase 8/9) is the same shape stretched to four side-by-side panels (product form, usages, packaging lines, costing/summary) in a horizontally-scrolling `ScrollViewer` rather than fixed Grid columns, since the panel count varies more than earlier screens' fixed 2-3 columns — prefer a horizontal `ScrollViewer` of fixed-width `StackPanel`s over fighting Grid column-width arithmetic once a screen needs more than ~3 side-by-side panels.
- **Embedded management panel for an editable child lookup** (`SubAssembliesView`, Phase 7): `SubAssemblyRole` is editable but has no screen of its own — it gets a small self-contained grid + form + New/Save/Delete panel living directly inside `SubAssembliesView`, off to the side of the main sub-assembly list/form, with its own independent `SourceCache`, selection, and commands in `SubAssembliesViewModel` (not a separate tab, and not folded into the sub-assembly form itself). Use this shape for a future lookup that's editable but too small/tightly-coupled to its owning screen to deserve a top-level tab.
- **A "replace-all" child collection editor** (`SubAssemblyLineRepository.SetLinesAsync`, following `IngredientBomLineRepository.SetLinesAsync` from Phase 6, and now also `ProductSubAssemblyUsageRepository.SetUsagesAsync`/`PackagingLineRepository.SetLinesAsync` from Phase 8): the UI builds up an in-memory list of lines (here, `SubAssemblyLineEdit` — an ingredient plus a quantity, not yet saved) via Add/Remove commands, and a single Save command sends the *whole* list to the repository, which deletes the existing rows for that parent and inserts the new set, then (where relevant) recomputes and stores the roll-up totals, and saves once. Simpler and less error-prone than diffing an edited collection against the database, and matches how a recipe is actually edited by a person (the whole line list at once, not one row at a time). **Delete the old rows with `ExecuteDeleteAsync`, not `ToListAsync` + `RemoveRange`** — every row is being unconditionally discarded, never mutated first, so loading them into memory first (found during an EF Core query review across all four of these repositories) buys nothing but an extra round trip and change-tracking overhead. `ExecuteDeleteAsync` executes immediately against the database, so call it before the `AddRange`/`SaveChangesAsync` that follows, same ordering as the old load-and-remove version.
- **A repository that only ever needs the single "latest" row from a growing history table should query for just that row, not load the whole table** (`IngredientPriceHistoryRepository`/`PackagingPriceHistoryRepository`'s `AddAsync`/`UpdateAsync`/`DeleteAsync`, fixed during the same query review): `PriceHistoryRules.FindLatest` picks one row by `(Date desc, Id desc)`, but the original code loaded every price-history entry for the ingredient/material to run that pick in C# — a table that only grows over the life of the app, reloaded in full on every single price edit. Fixed by querying `OrderByDescending(Date).ThenByDescending(Id).FirstOrDefaultAsync()` for the current latest row (already well-served by the existing `HasIndex(IngredientId, Date)` composite index) and, where a new/updated in-memory candidate also needs to be weighed against it, running `FindLatest` over just that 1-2-item set — mathematically identical to running it over the full list, since the max of a set unioned with one more candidate equals the max of (the set's own max, that candidate).
- **Derived values are computed on read, never stored, until a phase actually needs to persist them** (Phase 8): `ProductSubAssemblyUsage` stores only `WeightPerPiece`; its `Yield` and cost-per-piece, and `PackagingLine`'s cost-per-piece, and `Product`'s total material cost, are all plain `ProductRules`/`CostingRules` functions called fresh every time a screen needs them (`ProductsViewModel.RecomputeSummary`), not columns kept in sync by a propagator. This is deliberately simpler than Phase 6/7's stored-and-propagated `CostPerGram`/`TotalCost`: nothing yet depends on *Product's* cost the way `SubAssembly` depends on `Ingredient.CostPerGram`, and wiring a real propagator here would be building Phase 11 early. Revisit when Phase 11 wires the full cascade — at that point a `RawMaterialPriceHistory` change needs to reach a product's displayed price without the user reopening the screen, which read-on-demand doesn't do on its own.
- **Cost-plus pricing, not gross-margin-on-price** (`CostingRules.CalculateSellingPrice`, Phase 9, an explicit user decision over the gross-margin alternative): `BaseCost = MaterialCost + Labor + Overhead`, `PreVatPrice = BaseCost × (1 + Margin%/100)`, `SellingPrice = PreVatPrice × (1 + VAT%/100)` — three separate multiplication steps, never folded into one formula, so a shop owner can audit each input by hand. If a future phase ever needs gross-margin pricing (margin as a % of the *final* price rather than a markup on cost), that's a different formula (`price = cost / (1 − margin%)`) and a different, explicitly-chosen mode — don't quietly swap the math in `CalculateSellingPrice`.
- **A full-precision in-memory reciprocal (e.g. `1m / 6m`) gets rounded to 4 places on its round trip through a `decimal(18,4)` column** (found by a failing Phase 8 test asserting the untruncated value): `PackagingLine.QtyPerPiece`/`PiecesPerPackagingUnit` are exact reciprocals in `ProductRules.ReconcileReciprocal`'s C# math, but SQL Server's `decimal(18,4)` (the app-wide convention from Phase 1) stores `0.1666666...` as `0.1667`. Expected and harmless for money-scale quantities, but any test asserting an exact reciprocal against data that's been through the database needs to assert the *rounded* value, not the raw division result.
- **A guarded field on an existing repository can be tightened once a later phase adds the FK that makes the guard meaningful, without that counting as "jumping ahead.**" `SubAssemblyRepository.UpdateAsync` left `RoleId` fully editable in Phase 7 because nothing referenced a sub-assembly yet; Phase 8 added `ProductSubAssemblyUsage` with a Restrict FK to `SubAssembly`, so `UpdateAsync` now blocks a role change (`InvalidOperationException`) whenever any `ProductSubAssemblyUsage` row references that sub-assembly, matching the Domain Model's "a sub-assembly's role can only be changed while no product uses it." Prefer this — tightening the one repository method whose precondition changed — over a broad revalidation pass across every earlier phase's code every time a new phase adds a relationship.
- **Every screen was verified by actually running the app**, not just building it or passing tests: launch `dotnet run --project TinapayanRMS.UI`, screenshot the running window, and where practical seed real rows via `sqlcmd` first so the screenshot proves the data-bound path (grid rows, selected-row-into-form binding, dropdown selection) and not just empty-state layout. Clean up any rows seeded this way afterward — the dev `TinapayanRMS` database should hold only what the user actually entered.
  - **Bringing the window to front needs `AttachThreadInput` around `SetForegroundWindow`, not just `SetWindowPos`-with-`HWND_TOPMOST`.** The plain topmost trick (recorded here through Phase 6) stopped reliably working in Phase 7: `SetWindowPos(hwnd, HWND_TOPMOST, ...)` would report success, but mouse clicks at the expected screen coordinates still landed on the foreground terminal window underneath, confirmed with `WindowFromPoint`. The fix that actually works: attach the calling thread's input queue to the current foreground window's thread (`AttachThreadInput(myThreadId, fgThreadId, true)`), then `ShowWindow`/`BringWindowToTop`/`SetForegroundWindow` on the target, all inside the *same* tool invocation as the click that follows (a separate tool call in between gives the terminal a chance to reclaim focus) — then detach. Verify with `WindowFromPoint` before clicking, not after. `PrintWindow` (not `CopyFromScreen`) remains the right way to capture the screenshot itself, since it captures a window's content directly regardless of what's on top of it on screen — it's specifically mouse input, not rendering, that needs true foreground focus.
  - **Even `AttachThreadInput` can't win against a real foreground app that keeps re-asserting focus** (seen in Phase 8: a game the user had open, not the terminal this time, stayed foreground through repeated retries, confirmed each time with `WindowFromPoint`). When that happens, stop retrying rather than keep fighting for focus — it means the user is actively doing something else on the machine. Fall back to whatever partial screenshot evidence was already captured (e.g. a new tab visible in the tab strip) plus the integration test suite and a manual line-by-line binding review (every `x:Path` in the view's XAML checked against the ViewModel's actual property names/types) as the verification of record for that screen.
  - **Synthetic click/type automation (`SetCursorPos` + `mouse_event` + `SendKeys`) against Syncfusion's custom input controls is unreliable** — coordinates that look right against a screenshot don't reliably focus/type into a `DoubleTextBox` (tried once, Phase 5, no app error, the value just never landed). Don't burn time chasing exact coordinates. The read/render/selection path (data flowing into the grid and the selected-row-into-form binding) is what screenshots verify well; for write paths (a button's command), rely on the repository/rules integration tests exercising the exact same call chain the command invokes, plus a code review of the binding — the same depth `New`/`Save`/`Delete` got in Phase 4.
  - **`SfDataGrid` sometimes renders only its first few columns when screenshotted via `PrintWindow` right after a tab switch or fresh data load** (seen in Phase 7's Sub-Assemblies grid, and on closer inspection, in the Phase 4 Ingredients grid too, so it predates Phase 7 and isn't a regression from it) — the grid's rendered width shrinks to fit only the columns it managed to realize rather than the full `*`-allocated Grid column width, with no visual trace (no header, no border) of the missing columns. This looks like a virtualization/layout-timing artifact of capturing a hardware-accelerated custom control via GDI shortly after it's populated, not a real data or binding problem — the same ViewModel data (e.g. a seeded sub-assembly's `Role`/`TotalWeight`/`TotalCost`) round-trips correctly through the integration tests. Don't chase this pixel-by-pixel; treat a screenshot showing at least the grid's leading column(s) with real seeded data, plus a passing integration-test suite covering every column's underlying property, as sufficient verification.
- **After a command changes a row's server-computed fields (Phase 5: `AddPriceCommand`/`DeletePriceCommand` changing `Ingredient.CurrentCost`/`CostPerGram`), refresh that one row rather than reloading the whole screen**: re-fetch it via the repository's `GetByIdAsync`, `_cache.AddOrUpdate(refreshed)` to update the grid, and reassign the `Selected*` property to the refreshed instance — `SfDataGrid` tracks selection by reference, so leaving `Selected*` pointing at the stale object silently desyncs the form/detail panel from what the grid now shows.
- **`UpdateAsync` must apply fields one by one onto a tracked, freshly-loaded entity — never `dbContext.Set<T>().Update(incoming)` on an object the caller built from scratch.** `Update()` marks *every* property Modified, so an `Ingredient`/`PackagingMaterial` built by a Save command's form fields (which never sets `CurrentCost`/`CostPerGram`, since those are server-owned) would silently overwrite them back to null/0 on every plain rename — a real bug found in Phase 6 while wiring `WeightLossPercent` through the same path, present in both `IngredientRepository` and `PackagingMaterialRepository` since Phase 4 and fixed in both at once. The fix is the same shape every time: load the tracked entity by id, copy across only the user-editable fields, leave every server-computed field untouched, then `SaveChangesAsync`. A related, easy-to-miss corollary: if a user-editable field feeds a server-computed one (`PurchaseUnitQty` feeds `CostPerGram` via `CurrentCost / PurchaseUnitQty`), `UpdateAsync` must recompute that derived field too (`IngredientRules.RecomputeCostPerGramFromCurrentCost`) — it doesn't get another chance to until the next price entry.
- **`ExecuteDeleteAsync` doesn't wrap a failure in `DbUpdateException` the way `SaveChangesAsync` does** — it issues a raw `DELETE` outside the change tracker, so a foreign-key violation surfaces as the driver's own exception (`Microsoft.Data.SqlClient.SqlException` on SQL Server) instead. A test asserting `ThrowAsync<DbUpdateException>()` around an `ExecuteDeleteAsync` call needs `SqlException` instead (found in Phase 6, verifying `IngredientBomLine`'s Restrict-delete FK).

## Reactive Costing Cascade

The core design problem is that a price change on any ingredient or packaging material must ripple up through everything that uses it, automatically. The cascade has two starting points, one per material table, and both end at the product:

```
IngredientPriceHistory entry added
  → purchased Ingredient.CostPerGram recomputed
    → every made Ingredient that uses it recomputed, up every level of the BOM tree
      → every SubAssemblyLine using a changed ingredient recomputed
        → SubAssembly.TotalCost recomputed
          → every ProductSubAssemblyUsage of that sub-assembly recomputed ─┐
                                                                           ├→ Product total cost recomputed
PackagingPriceHistory entry added                                          │    → Product margin / selling price recomputed
  → PackagingMaterial.CurrentCost recomputed                               │
    → every PackagingLine using it recomputed ─────────────────────────────┘
```

Model this with DynamicData `SourceCache<T>`s joined via `.Connect()` / `.InnerJoin()` / `.TransformMany()`, so the derived observable collections update themselves instead of the code walking the dependency graph by hand on every edit. EF Core remains the source of truth on disk: the caches load from it at startup, and writes go back through EF Core.

The one exception is made ingredients. Their BOMs nest to any depth, so that part of the cascade can't be a fixed chain of joins. An ingredient's cost can change from a new price entry, a BOM line edit, or a `WeightLossPercent` edit. When it does, recompute the made ingredients that depend on it in dependency order, components before the ingredients built from them. From the sub-assembly lines onward, the joins take over as normal.

**Implemented (Phase 6) as `IngredientCostGraph.GetDependentsInOrder`** (`ApplicationCore`, pure graph logic, no I/O — reverse-BFS from the changed ingredient to find every made ingredient that transitively depends on it, then a DFS-based topological sort restricted to that set) **and `IngredientCostPropagator.RecomputeAndPropagateAsync`** (`Infrastructure`, the orchestrator: loads every ingredient and every BOM line once, calls the graph function, walks the resulting order recomputing each ingredient's `CostPerGram` from its own lines — reading each component's `CostPerGram` directly off the already-loaded, already-correct dictionary, never re-walking that component's own tree — then a single `SaveChangesAsync`). Every write path that can change an ingredient's cost calls it: `IngredientPriceHistoryRepository`'s add/update/delete (a Purchased ingredient's price changed), `IngredientRepository.UpdateAsync` when `Source == Made` (a `WeightLossPercent` edit), and `IngredientBomLineRepository.SetLinesAsync` (the BOM itself changed — recomputes the edited ingredient first, since it's `Made`, then propagates to its dependents). This same shape — a pure ordering function plus a stateful orchestrator that loads once, recomputes in order, and saves once — is the template for wiring the sub-assembly and product branches in Phase 11, not a special case just for ingredients.

## Development Environment

- Development happens directly on a local Windows machine that has the .NET 10 SDK, SQL Server Express, and SQL Server LocalDB installed.
- Running the app (not just building it) requires the `SYNCFUSION_LICENSE_KEY` user environment variable to be set (see Syncfusion UI Framework below). The solution builds fine without it, but `App`'s static constructor throws on startup if it's missing.
- **Docker is not used anywhere in the project**: not for development, testing, or deployment.
- EF Core migrations are generated with `dotnet ef migrations add`, not written by hand, and applied to the local database with `dotnet ef database update`.
- **A phase is done** when the solution builds without errors, all tests pass, and any new migration applies cleanly to a local database. Mark it Done in the Build Plan table; there are no separate per-phase documents.
- **Integration test database**: tests never touch the developer's own `TinapayanRMS` database. `TinapayanRMS.Tests/Infrastructure/DatabaseFixture.cs` runs against a separate `TinapayanRMS_Test` database (same server, connection string's `Initial Catalog` overridden), migrated once per test run and reset with Respawn before every test via `[Collection(DatabaseCollection.Name)]` + `IAsyncLifetime`. Seed/reference data (currently just `UnitsOfMeasure`) is excluded from the Respawn reset, since it's owned by migrations, not by tests — add a table to `DatabaseFixture.TablesExcludedFromReset` whenever a future phase adds more seeded lookup data.
  - **Every Respawn-backed integration test class inherits `TinapayanRMS.Tests.Infrastructure.PersistenceTestBase(fixture)`** instead of retyping the `CreateDbContext`/`CreateDbContextFactory`/nested `TestDbContextFactory`/`IAsyncLifetime` plumbing per file (that scaffolding was identical across 8 test classes before being extracted). `[Collection(DatabaseCollection.Name)]` still has to be repeated on every concrete test class, though — it's deliberately **not** on the base, since xUnit's collection/fixture discovery isn't guaranteed to honor an attribute declared only on a base class, and getting that wrong would silently break the very Respawn-reset isolation this hierarchy exists to guarantee.

## Conventions

- The layered architecture is fixed: `Domain` has no external dependencies, business and costing rules live in `ApplicationCore`, and EF Core and other I/O stay in `Infrastructure`.
- The MVVM toolkit is **ReactiveUI**, not CommunityToolkit.Mvvm. Use `ReactiveObject`, `ReactiveCommand`, `WhenAnyValue`, etc.
- **Prefer Syncfusion controls over native WPF controls whenever a Syncfusion equivalent is available** (e.g. `ButtonAdv` over `Button`, `TabControlExt` over `TabControl`, `ComboBoxAdv`/`SfDataGrid`/the `SfInput.WPF` edit controls over their native counterparts), so the whole UI picks up the Windows11Light theme consistently. Fall back to a native control only when no Syncfusion equivalent exists, and add the corresponding package to `TinapayanRMS.UI` and (if needed) `TinapayanRMS.Theme` per the Syncfusion UI Framework section above.
- **Decimal precision**: keep `decimal` values at full precision through the whole cascade, and round only for display and for the final selling price. Rounding each per-piece cost before summing adds up to drift. Enforced once for every `decimal` column via `TinapayanRMSDbContext.ConfigureConventions` (`decimal(18,4)`, set in Phase 4 when the first `decimal` columns were added), rather than per-property — a future column can't silently fall back to SQL Server's `decimal(18,2)` default and truncate a fractional cost.
- **Use modern C# 14 / .NET 10 idioms** rather than older patterns still valid in the language: primary constructors, collection expressions (`[..]`), required members, file-scoped namespaces, pattern matching, and `record`/`record struct` for immutable data shapes, in line with what's already in the codebase (e.g. `CategoryPersistenceTests`'s primary constructor, `WellKnownUnitOfMeasureIds`'s collection expression). Don't reach for an older, more verbose equivalent just because it's more familiar.
- **Correctness and performance take priority over brevity or convenience.** Favor the approach that is provably correct and doesn't waste allocations, database round-trips, or UI-thread work, even if a shorter or simpler alternative exists — e.g. querying only the columns/rows actually needed rather than materializing more and filtering in memory, and avoiding unnecessary intermediate collections in hot paths like the reactive costing cascade.
- This document is a living plan. Update it as phases complete or decisions change, so it stays the single source of truth for the project.
